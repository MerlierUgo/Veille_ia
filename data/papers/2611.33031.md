Can a Frontier LLM Repair a Quantized Network
by Tool-Free Weight-Space Programming?
Steffen Urban
Independent Researcher
We give four large language models (LLMs) of the Claude family the complete weights of a 20k-parameter 
CIFAR-10 CNN as text and ask them to produce a 4-bit network without tools, data or the ability to run 
inference. Standard round-to-nearest (RTN) quantization to 4 bit lowers the test accuracy from 81.4% to 60.4%. 
We design four evaluation protocols that differ in the input and task description given to the LLMs and analyze 
their responses. In the first two protocols the LLMs are given the float and the 4-bit RTN network and are told 
that the accuracy has dropped significantly. In the last two they receive only the float network and the task to 
quantize it, which tests whether they apply an optimization on their own or fall back to plain RTN. Our analysis 
shows that a frontier LLM can recover most of the lost accuracy. Given one answer per layer, Opus 5.5 raises 
the accuracy of the 4-bit network to 77.95% by balancing the rounding errors within each 3×3 kernel, reasoning 
over the integer weights without tools. This is 3.5 pp below the float network and 2.8 pp below AdaRound, 
which learns the rounding from calibration data. Given only the float network, the LLMs name error-cancelling 
corrections but do not apply them and fall back to plain RTN, at most with mildly clipped scales, which still 
lifts Fable 5.2′s quantized network to 70.0%. We analyze in detail what the LLMs did and why it works. Code 
and prompts can be found at github.com/urbste/weight-space-programming-ptq.
1 Introduction
Post-training quantization (PTQ) converts a trained float 
network to low-bit integers without retraining [1], [2], [3]. 
Its simplest form, per-channel symmetric round-to-nearest 
(RTN), is close to lossless at 8 bit for most CNNs, while 
at 4 bit its accuracy loss varies widely between networks 
and can be large [2], [3]. Better PTQ methods fix this with 
calibration data and layer-wise reconstruction [4], [5], [6]. 
Data-free methods [7], [8], [9] work from the checkpoint 
alone, but they too are fixed numerical procedures.
We ask whether a large language model (LLM) can find 
and execute such a repair by reading the weights. The LLM 
gets the weights of a small CNN as text, either the float 
weights alone or together with the RTN integer weights, 
and writes integer weights and scales. It has no code 
interpreter, no calculator, no data and cannot evaluate the 
network. All arithmetic happens in its own reasoning. The 
setting is deliberately extreme. Of course, a short Python 
script quantizes better and faster. The question is what the 
LLM notices in the numbers, how accurately it executes 
what it decides, and what limits it.
To this end, we train a simple 20k-weight CNN on 
CIFAR-10 [10] that will fit into the context of current 
LLMs, which makes the question testable. We evaluate 
four protocols (Section 3.2) that differ in whether the 
LLM sees the RTN network and is told about the accuracy 
drop, whether it gets BatchNorm statistics, and whether 
it answers in one response or in one response per chunk.
We find that frontier LLMs without tools arrive at 
a published data-free PTQ correction by reading raw 
weights. Opus 5.5 and Sonnet 5.5 independently balance 
the per-kernel rounding error sums (kernel balancing, Sec-
tion 4.2.1), the kernel-wise step of SQuant [9]. With one 
answer per chunk, Opus 5.5 applies it to all 2,200 kernels 
by hand (96% of edits identical to exact kernel balancing) 
and reaches 77.95% (Section  4.2.2), so the one-answer 
result is limited by the amount of arithmetic per answer. A 
first-order error model shows that the per-kernel error sum 
sets the mean shift of each output, which explains why the 
rule works (Section 5.1). Given only the float weights, the 
LLMs write RTN, at most with clipped outlier rows, and 
none uses the BatchNorm statistics to cancel the mean 
shift (Section 4.2.3, Section 5.2).
2 Related work
Post-training quantization. Per-channel RTN with Batch-
Norm folding is the standard baseline [1], [2]. Clipping 
the range trades clipping error for resolution, analytically 
in ACIQ [11] and by MSE search in most toolchains [3]. 
Outlier channel splitting [12] avoids clipping by duplicat-
ing channels. Rounding to nearest is not optimal for the 
layer output. AdaRound [4] learns the rounding direction 
per weight from calibration data, BRECQ [5] reconstructs 
blocks, and GPTQ [6] uses second-order information to 
compensate errors column by column. Without data, DFQ 
[7] equalizes ranges across layers and corrects the bias 
shift caused by rounding, estimating input statistics from 
BatchNorm parameters. ZeroQ [8] synthesizes calibration 
data from BatchNorm statistics. SQuant [9] approximates 
the Hessian by element-, kernel- and channel-wise terms 
and flips rounding decisions until the absolute rounding-
error sum of every kernel is at most half a step, then does 
the same per output channel while allowing one step per 
kernel. Vendor toolchains for edge accelerators differ in 
scaling and clipping, so the same checkpoint can reach dif-
ferent accuracy on different backends [13]. The correction 
our LLMs find, constraining the sum of rounding errors 
per kernel, is the kernel step of SQuant. AdaRound learns 
rounding decisions of this kind from data.
LLMs over numbers and weights. LLMs can act as opti-
mizers that propose solutions from a history of scored 
attempts [14], or drive program search with an evaluator 
in the loop [15]. Both rely on feedback, which we remove. 
Weight-space learning trains networks that take other net-
works’ weights as input [16], [17]. We instead ask a general 
LLM to reason over weights in context. Bills et al. [18] 
use LLMs to explain individual neurons from activations, 
while here the LLM sees only parameters. Weight-space 
programming [19] lets LLM agents edit network weights 
with tools and evaluation. Our setting is its tool-free limit,

3 Method
3.1 Network, baseline and notation
SmallCNN has four conv(3×3)–BN–ReLU blocks with 8, 16, 
32 and 48 channels, 2×2 max-pooling after blocks 2 and 
3, global average pooling and a 48→10 linear layer (20,280 
weights). It is trained on CIFAR-10 for 500 epochs (SGD, 
Nesterov, one-cycle, weight decay 5 ⋅ 10−4, crop and flip) 
on a fixed 45k/5k train/val split and reaches 82.14% val 
and 81.42% test accuracy (Figure 1).
BatchNorm is folded into the convolutions. We call the 
weights that compute one output channel a row, which 
is one conv filter (𝐶in × 3 × 3 weights) or one row of the 
fc matrix (48 weights). Hence the network has 114 rows 
(8+16+32+48+10). The row is also the unit in which the 
LLMs read and write the network. The input lists each 
row with its scale and bias (Section A.1), edits address 
weights by layer and row, and in P3/P4 the LLM writes 
one line per row. Per-channel RTN gives each row 𝑟 with 
weights 𝑤𝑟𝑗 its own scale:
𝑠𝑟 = max 𝑗 |𝑤𝑟𝑗| /𝑞max, 𝑞𝑟𝑗 = round(𝑤𝑟𝑗/𝑠𝑟), (1)
where 𝑞𝑟𝑗 is the quantized integer weight for 𝑤𝑟𝑗, 𝑠𝑟 the 
per-row scale, and 𝑠𝑟𝑞𝑟𝑗 the dequantized weight used at 
inference. With 𝑏 bits, 𝑞max = 2𝑏−1 − 1 (𝑞 ∈ {−7,…,7} at 
int4). Biases and activations stay float (BN folding does 
not change per-channel RTN).
For a row with scale 𝑠 we write 𝑢 = 𝑤/𝑠 for a float weight 
in units of the quantization step, 𝑞 = round(𝑢) for its 
integer weight and 𝑒 = 𝑞 − 𝑢 ∈ [−1/2,1/2] for its rounding 
error. The kernel sum 𝐸 = ∑𝑘 𝑒𝑘 adds the rounding errors 
over the nine positions 𝑘 of one 3×3 kernel (for fc layers, 
over a whole row).
3.2 Protocols
In every experiment, a frontier LLM (Section  3.3 lists 
them) receives a task description and SmallCNN as text, 
and returns a quantized version of SmallCNN. Appendices 
A.4, A.5, A.6 and A.7 give the task descriptions of P1–P4. 
The four protocols differ in what the LLM sees and what 
it writes.
P1: whole network, one answer. The LLM sees the 
float weights in units of the step, 𝑢 = 𝑤/𝑠 (two decimals), 
and the RTN integer weights 𝑞 for every row, plus RTN 
scales and biases (format in Section A.1). It is told the 
architecture, input normalization, and that the float net-
work scores 82.14% on a held-out split while the quantized 
one scores 60.38% (int4). It answers with sparse edits that 
set one integer weight, replace a 3×3 kernel or an fc row, or 
set a scale or a bias. Unmentioned values keep their RTN 
value. Invalid lines are skipped, never repaired. Writing 𝑢 
instead of 𝑤 saves one division per weight and exposes the 
rounding residual 𝑢 − 𝑞 directly, which is a hint.
P2: layer by layer. Same input, but delivered in eleven 
chunks (conv1, conv2, conv3 in two, conv4 in six and fc, 
with at most 256 kernels each). The LLM answers each 
chunk in its own response, inside one conversation, so every 
chunk gets a fresh output budget while the context keeps 
everything so far.
P3: from float weights. The LLM gets only the float 
weights (three decimals), in 19 chunks of at most 1,152 
weights, and writes the 4-bit network itself as one line ROW 
<layer> <r> SCALE <s> Q <codes> per output row, with 
free scale and integer weights in [−7,7]. The prompt does 
not mention RTN or the accuracy gap. A missing row, a 
wrong number of integer weights or an out-of-range integer 
weight falls back to RTN for that row.
P4: from float weights with BN statistics. As P3, 
plus 𝛾, 𝛽, running mean and variance for every conv 
channel. Published data-free methods use these statistics 
in place of data. DFQ [7] estimates the input means from

3.3 LLMs and evaluation
LLMs and tool restriction. We use Claude Opus 5.5, 
Sonnet 5.5 and Haiku 5.5 in P1, P2 and P4, Opus 5.5 alone 
in P3, and Fable 5.2 only in P4 (API model IDs claude-
opus-5-5, claude-sonnet-5-5, claude-haiku-5-5, claude-
fable-5-2). P1–P3 ran as subagents that could call only 
the file-reading tool on their task files, which only delivers 
the input. We audited every transcript and found no 
other calls. P4 ran from the command line with all tools 
disabled (claude -p --tools ""), one chunk per message in 
one session, because API safeguards blocked the subagent 
route for Opus 5.5 and Sonnet 5.5.
Evaluation. We report test accuracy unless stated 
otherwise. For analysis only, we compute on 
the 5k validation images per-layer output SNR 
10log10(∑𝑦2 fp/∑(𝑦𝑞 − 𝑦fp) 2 ), isolated (float input to 
each layer) and accumulated (quantized network end to 
end), input means and patch covariances. The LLMs never 
see these.
Reference corrections. To judge the LLM edits, we also run 
two data-free corrections in Python. Kernel balancing re-
rounds integer weights, cheapest first, until every kernel 
sum satisfies |𝐸| ≤ 1/2. This is the rule Opus 5.5 and 
Sonnet 5.5 describe in P1 (Section 4.2.1). We call this im-
plementation, run on every kernel, exact kernel balancing. 
Bias correction [7] keeps the integer weights and cancels 
the mean output shift through the bias, using input means 
measured on validation images. In section Section 5.1.3 we 
provide more theoretical details about those two methods.
4 Results
4.1 What RTN does to the network
For our simple network, RTN is basically lossless at 8 
bit (81.45%, 98.6% agreement with float) and drops by 
21 percentage points (pp) to 60.39% at 4 bit (Table 1). 
Below 4 bit RTN gives 28.7% at 3 bit and chance at 2 
bit. Below 4 bit no data-free correction comes near float 
accuracy, hence in the remainder of the paper we study 
the 4-bit case, where corrections can recover most 
of the loss.

4.2 LLM results
Table 4 lists the int4 LLM results with the mechanism 
behind each result. We discuss them by protocol below.
4.2.1 P1: Editing the whole network
In P1 (Table 4), Opus 5.5 and Sonnet 5.5 arrive at the 
same idea. Both argue that natural images are smooth, so 
a 3×3 kernel responds mainly to the sum of its weights. 
They compare float and integer sums per conv1 kernel and 
re-round the weight closest to a boundary where they differ 
by more than about half a step. This is kernel balancing 
and we analyze it in Section  5.1. They change 11 and 
13 integer weights (0.05% of the weights, 8 in common) 
and gain 3.7–4.0 pp. Haiku 5.5 balances the fc row sums 
instead. None of the LLMs touches conv2–conv4. All state 
that the work does not fit into one answer and stop. The 
limit is the length of one answer, which must hold the 
reasoning and every edit. Their hand execution is accurate. 
Sonnet 5.5′s 13 edits match exact kernel balancing in 11 
positions, and the edited conv1 layers reach the same mean 
|𝐸| as exact kernel balancing (0.27 vs. 0.59 for RTN). 
Applied to all conv layers, the same rule gives 77.63% 
(Table  2). P2 lifts the output limit for the LLM itself 
(Section 4.2.2).
4.2.2 P2: One answer per layer
With one response per chunk, Opus 5.5 works through 
every kernel of every conv layer (13, 77, 300 and 974 edits) 
and reaches 77.95% test (78.62% val), which closes 17.6 of 
the 21 pp gap to float and matches exact kernel balancing 
within noise (Figure 4). Opus 5.5 did not edit fc, and exact 
kernel balancing on the conv layers alone gives 77.63%. 
The run was interrupted and its conv1 and conv2 edits 
were re-emitted after resumption (Section 6). 1,314 of its 
1,364 edits coincide with exact kernel balancing in position 
and value, no integer weight moves by more than one step, 
and 118 of 2,200 kernels keep |𝐸| > 1/2. Isolated SNRs 
match exact kernel balancing within 0.4 dB in every layer, 
and the accumulated SNR at the logits rises from 3.5 to 
12.8 dB. Ahead of exact kernel balancing by 2.3 pp after 
conv2 and a few tenths at the end, Opus 5.5′s curve mainly 
shows that the choice among nearly equivalent flips moves 
accuracy by about 1 pp.
Opus 5.5′s kernel sums have the same distribution as those 
of exact kernel balancing (Figure 3). Sonnet 5.5 reads all 
chunks and edits nothing, citing missing activation statis-
tics, although it found kernel balancing in P1. Haiku 5.5 
shrinks eleven scales by 0.9 and loses 0.5 pp.

4.2.3 P3/P4: Quantizing from float weights alone
Without the RTN result (P3), Opus 5.5 states the textbook 
recipe (𝑠 = max|𝑤|/7, “wastes none of the 15 levels”) and 
executes it accurately. In each layer, 98.1–100% of integer 
weights equal round(𝑤/𝑠) for its own scale, and 47 of the 
48 exceptions lie within 0.02 of a tie. Its one departure is a 
lower scale (median 0.96× RTN) for conv4 rows with one 
or two outliers. It scores 60.58%, +0.2 pp over RTN. The 
conv4 clipping is worth +1.5 pp, while three conv1 integer 
weights rounded the other way at exact ties cost 1.1 pp. 
Three rows have the wrong length (143, 290, 287 integer 
weights) and fall back to RTN. Without the RTN integer 
weights and without being told that RTN fails, the LLM 
does not look for a problem.
With BN statistics (P4), no LLM uses them (Table 4). 
Opus 5.5 and Fable 5.2 state that the statistics were only 
context. Sonnet 5.5 argues that they are already folded 
into the weights, which is true for the scales and misses 
that the running means describe activations. The statistics 
would have allowed one useful correction. They give the 
input means 𝜇𝑐 (Section 5.1.4), and with them each row 
can be rounded so that its mean shift in Equation  3 
cancels. None of the LLMs does this.
Opus (63.26%) repeats its P3 strategy with more clipping, 
with median scale ratios of 0.96 (conv4) and 0.97 (fc). Per-
layer swaps into RTN give +2.0 pp (conv4) and +1.5 pp 
(fc). Re-rounding the float weights exactly at its scales 
gives 63.07%, so the gain is in the scales. An MSE-optimal 
per-row scale search on conv4 and fc gives 64.39%, which 
Opus 5.5 approximates by eye.
Fable 5.2 (69.97%, all 114 rows valid) is the best LLM 
result without the RTN integer weights. Its summary 
describes “per-row round-to-nearest with a mildly clipped 
scale” and adds “when one weight was an isolated outlier, I 
picked a smaller scale and let that weight clip to ±7”. The 
data confirm this. In conv2, conv4 and fc the scale ratio 
correlates with the ratio of largest to second-largest weight 
at −0.87, −0.85 and −0.90, exact rounding at its scales 
gives 69.94%, and kernel sums are not reduced. Section 5.2 
analyzes this result.
Sonnet and Haiku choose a workable method and fail at 
execution. Both write plain max/7 RTN, but most rows 
have the wrong number of integer weights or are cut off 
(19–39 of 114 valid). Some valid Sonnet 5.5 rows contain 
shifted integer weights, and its valid conv4 rows have 
an RMS error of 1.7 steps against 0.29 for RTN. Haiku 
5.5 often does not return the correct number of integer 
weights, and otherwise more or less copies the input. Its 
valid rows equal RTN in 98–100% of the integer weights 
per layer.
4.3 Inference cost
For comparison, kernel balancing in Python runs in mil-
liseconds on a CPU, and AdaRound needs a few minutes 
on one GPU. Table 5 lists the approximate price of the 
LLM runs. We used a Claude Pro subscription, so those 
are estimates based on the number of tokens. All API calls 
of the experiments together produced 3.6M output tokens

5 What the LLMs did and why it works
The LLMs that gain over RTN use one of two mechanisms. 
In P1/P2 they keep the RTN scales and change the 
rounding of single weights (kernel balancing). In P3/P4 
they keep plain rounding and change the scales (outlier 
clipping). This section explains why each works and why 
the LLMs probably chose them.
5.1 Kernel balancing
Two observations call for an explanation. First, the per-
weight error of int4 RTN is small (about 13% relative 
RMS, Table  3), yet accuracy drops by 21 pp. Second, 
kernel balancing makes individual weights less accurate, 
so per-weight error cannot be what it optimizes. A first-
order model of the rounding error explains both and makes 
predictions that we test on validation data. A conv output

5.1.3 Two corrections
Bias correction [7] keeps the integer weights and changes 
the bias. It adds 𝛿𝑏𝑜 = −𝔼[Δ𝑦𝑜] from Equation 3, which 
removes the mean shift. It needs the input means 𝜇𝑐, from 
data or from the BN parameters, and leaves the fluctuating 
part of the error unchanged.
Kernel balancing (Figure 5(b)) keeps the bias and changes 
integer weights until every kernel has |𝐸| ≤ 1/2. Rounding 
a weight to its other neighboring integer changes its error, 
and therefore 𝐸, by exactly 1. A kernel with 𝐸 = +1.35, 
for example, reaches 𝐸 = +0.35 when one weight that 
was rounded up is rounded down instead. The weights to 
change are chosen by cost. Changing a weight with error 𝑒𝑘 
raises its squared error by 1 − 2|𝑒𝑘|. The cheapest weights 
are those with |𝑒𝑘| close to 1/2, whose float value lay 
almost halfway between two integers. Balancing therefore 
changes the weights whose error has the same sign as 𝐸 
and the largest magnitude. It needs no data and changes 
few integer weights. Because 𝐸 appears in both Equation 3 
and Equation 4, a smaller 𝐸 lowers the mean shift for any 
input means and lowers the correlated part of the error 
whenever 𝜌 > 0. For fc layers we apply the same rule to 
the sum over the whole row.
Kernel balancing is the kernel-wise step of SQuant [9], 
and our implementation produces the same integer weights 
(exact kernel balancing in the tables). SQuant motivates 
this step with a Hessian approximation that is constant 
within a kernel, which corresponds to 𝜌 > 0 in Equation 4. 
Equation 3 gives a second reason for it, because the same 
sum sets the mean shift.

5.2 Outlier clipping
Fable 5.2′s P4 result (Section 4.2.3) comes from the scales 
alone. Exact rounding at its scales gives 69.94%, and its 
kernel sums are not reduced. It clips less than MSE search 
(median ratios in conv2–fc 0.95–0.98 vs. 0.80–0.92, both 
about 0.99 in conv1), yet MSE search on all layers gives 
only 64.6%. A possible explanation, which we did not test, 
is that clipping one isolated outlier gives the bulk of a 
heavy-tailed row a finer grid at small cost, while clipping 
a group of large weights, which MSE does, puts the error 
on the weights that matter most.
The gain is uneven across layers, with +8.8 pp in conv2, 
+2.8 in conv4, +0.3 in fc, −2.7 in conv1 and −2.0 in 
conv3 (72.1% without its conv1 rows). Conv2 is unusually 
sensitive. Fable 5.2′s conv2 rows alone give 69.2%. Random 
per-row scale factors in [0.88,1] give 66.1% on average 
(61.4–69.0%, 12 draws), and Fable 5.2′s ratios shuffled 
across rows 64.3% (60.1–68.0%, 12 shuffles). Its assignment 
beats all 24 controls, but the best random draw comes 
within 0.3 pp, and with one run we cannot quantify how 
much luck it holds. Random factors already recover 5.7 
of the 8.8 pp, so most of the conv2 gain comes from re-
rounding at a slightly smaller scale, not from the choice 
of rows.

5.3 Why did the LLMs use these methods?
What the input allows. In P1/P2 the LLM may change 
integer weights, scales and biases, but it sees no data and 
no BN statistics. Bias correction needs the input means 
𝜇𝑐 of Equation 3, so it would require guessing them. Scale 
changes need an error criterion that the LLM would have 
to evaluate by hand for every candidate scale. The kernel 
sum is the one quantity that predicts the output error 
without knowing the inputs, under the single assumption 
that inputs are smooth, and the P1/P2 format shows every 
residual 𝑢 − 𝑞 next to its integer weight. Kernel balancing 
is therefore close to the cheapest correction that the input 
supports. Haiku 5.5 states the mean-shift argument of 
Equation 3 directly for the fc layer. Its inputs “are non-
negative after ReLU and global average pooling, so the 
sum of rounding errors in each row acts as a systematic 
shift on the logits”.
Recall or derivation. No LLM names SQuant, but Opus 
5.5 places its rule in the literature, writing “The idea 
follows the bias-correction and adaptive-rounding view of 
post-training quantization.” Our runs therefore cannot tell 
whether the rule is derived from the weights or recalled and 
then recognized as applicable. A prompt that describes the 
setting without any weights would separate the two.
Known and declined. In P3/P4 the LLMs list the correc-
tions and decline them. Opus 5.5 writes “Biases are fixed 
and there is no data, so I couldn’t do bias correction, 
activation-aware rounding, or cross-layer equalization.” 
Sonnet 5.5 writes “I didn’t use bias correction, cross-layer 
equalization, or any rounding that cancels error across 
a row.” Sonnet 5.5 thus names error-cancelling rounding 
in P4 and does not apply it. Both treat plain rounding 
as an adequate answer when nothing says that it fails. 
Section 7 discusses which differences between the prompts 
may cause this.
6 Limitations
Statistics. Every LLM number comes from one run of a 
particular LLM version. The binomial standard error is 
about 0.5 pp at 60%, and single flips in conv1 or conv2 
move accuracy by about 1 pp. Differences below about 
1 pp, such as the P3 result and the Haiku 5.5 results, 
are therefore within noise. We ran no paired test and no 
control with random near-tie flips for P1.
Scope. All four LLMs are Claude models. The network is 
small, and other architectures will have different rounding 
statistics. The input format of P1/P2 exposes the rounding 
residual, which hints at rounding-aware corrections. P4 
ran in a different harness, and we have no P3 runs for 
Sonnet 5.5, Haiku 5.5 and Fable 5.2, so the effect of the 
BN statistics on their behavior is not isolated.
Execution. The tool restriction in P1–P3 rests on instruc-
tions and audited transcripts, and hidden reasoning is not 
visible. Some runs were interrupted by usage limits and 
resumed, and in two runs the LLM’s first output was only 
in hidden reasoning and had to be re-emitted. The Opus 
5.5 P2 run stopped after chunk 10. Its conv1 and conv2 
edits had been written only in hidden reasoning and were 
re-emitted as text after resumption (without them it scores 
69.58%), and it did not redo the fc chunk.
Proprietary APIs. Midway through the experiments the 
API safety classifiers began to reject our runs. Requests of 
the same kind that had run before were stopped at the first 
message, for P4 with Opus 5.5 and Sonnet 5.5 as subagents 
and for a P3 rerun. We had to change the harness and try 
several prompt variants until the runs were accepted again, 
which is why P4 ran from the command line (Section 3.3). 
We do not know why the classifier fired. Such changes are 
invisible to the user, can stop an experiment at any point 
and make it hard to reproduce. This is a general problem 
of research run against proprietary APIs.
Next steps. Natural next steps are repeated runs with 
paired tests, a random-flip control for P1, a bias-correction 
reference from BN statistics alone, prompts that state the 
RTN gap in P3/P4, a P1 prompt with raw float weights, 
a prompt that describes the task without weights (to 
separate recall from derivation), a small evaluation budget, 
and a compressed delivery format.
7 Conclusion
Without tools, an LLM can repair part of a quan-
tized CNN by only reading its weights. At 4 bit two 
LLMs use kernel balancing (the kernel step of SQuant), 
a data-free rule that removes most of the mean shift our 
measurements show in every layer. Delivered one layer per 
answer, Opus 5.5 works through all 2,200 kernels by hand 
and reaches 77.95%, 3.5 pp below float. Tasked to output 
only a single answer the LLMs found the method but 
could apply it only to conv1, because the arithmetic for 
the other layers does not fit. When the LLM must quantize 
float weights itself, the gains come from row-wise outlier 
clipping, and Fable 5.2 scores above an MSE scale search 
(70.0% vs. 64.6%), partly by luck (Section 5.2). Rounding 
that cancels the mean shift, for which the BatchNorm sta-
tistics given in P4 suffice at least in conv2 and fc, appears 
in no run. Calibrated methods (AdaRound, GPTQ) reach 
80.7% on the same network, so the best LLM result is 2.8 
pp short of methods that use calibration data.
Why P3 and P4 did not perform rounding correction. 
Kernel balancing appears only when the LLM sees the 
RTN network and is told that it fails, and even then not 
in every run (Sonnet 5.5 and Haiku 5.5 in P2). In P3 and 
P4 every LLM writes plain rounding, at most with clipped 
scales.
• Stated defect. P1/P2 report that rounding lowers ac-
curacy on a held-out split from 82.1% to 60.4%, which 
turns the task into the search for a defect. P3/P4 re-
port only the float accuracy, and the LLMs treat plain 
rounding as the expected answer (Fable 5.2 writes “I 
expect it to behave like a reasonable 4-bit per-channel 
post-training quantization”).
• Visible residual. P1/P2 list every weight in units of the 
step, 𝑢 = 𝑤/𝑠, next to its integer 𝑞, so the rounding 
error 𝑢 − 𝑞 can be read off and summed per kernel. In 
P3/P4 each residual first requires a division by a scale 
that the LLM chooses itself.

• Output volume. P1/P2 accept sparse edits. P3/P4 
require all 20k integer weights, so most of the output 
goes into writing integers.
• Reference rounding. The RTN integers show what 
plain rounding produces and invite a comparison of 
integer and float sums, which is how Opus 5.5 and 
Sonnet 5.5 describe their P1 idea.
Fable 5.2 came close in P4, writing that it was “sometimes 
alternating direction within a row so the row sum would 
not drift one way”. A P3 prompt that states the RTN gap 
would test the first factor, and a P1 prompt with raw float 
weights the second.

A.2 Input variance and the two error terms
In Equation 4, 𝜎2 is the variance of a single input across 
patches, measured from the channel mean 𝜇𝑐, not the 
within-patch deviation 𝑑𝑘 of Equation  2. The two are 
linked by 𝜌. The patch mean has variance Var(𝑥̄) = 𝜎2(1 +
8𝜌)/9 and each deviation 𝔼[𝑑2 𝑘] = 𝜎2 ⋅ 8(1 − 𝜌)/9. Hence 𝜌 
sets how much of the input variation reaches the kernel-
sum term of Equation 2 and how much reaches the detail 
term.
