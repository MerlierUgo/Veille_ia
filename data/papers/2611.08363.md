## Résumé

Quantization reduces the memory and bandwidth demands of large language model (LLM) inference but can degrade accuracy; offloading higher-precision data can instead stall generation. We introduce StrataFlux, a framework that challenges this tradeoff by recovering accuracy lost to low-bit weight and key-value (KV) cache quantization while retaining quantization's memory and speed advantages. StrataFlux co-designs refinement representation, selection, and delivery to make host RAM and solid-state drives useful sources of additional precision. Its selective precision streaming reduces transfer volume, overlaps delivery with computation, and reuses fetched precision across decoding steps so generation need not wait for every transfer. We evaluate 2-4-bit weights and 2-3-bit KV-cache on dedicated GPUs and unified-memory platforms. ABSTRACT
Quantization reduces the memory and bandwidth demands of large language model (LLM) inference but can
degrade accuracy; offloading higher-precision data can instead stall generation. We introduce StrataFlux, a
framework that challenges this tradeoff by recovering accuracy lost to low-bit weight and key–value (KV) cache
quantization while retaining quantization’s memory and speed advantages. StrataFlux co-designs refinement
representation, selection, and delivery to make host RAM and solid-state drives useful sources of additional
precision. Itsselective precision streamingreduces transfer volume, overlaps delivery with computation, and
reuses fetched precision across decoding steps so generation need not wait for every transfer. We evaluate 2–4-bit
weights and 2–3-bit KV-cache on dedicated GPUs and unified-memory platforms. For 2-bit Llama-3.1-8B-Instruct
weights, StrataFlux reduces WikiText-2 perplexity from 9.46 to 8.40 while maintaining 95.4% of the quantized
base’s throughput on RTX 5090. With 2-bit weights and KV , StrataFlux raises Qwen3-8B’s AIME 2024/2025
accuracy from 11.0% to 47.1% at unchanged GPU memory use. At 128K context, Llama-3.1-8B-Instruct with
3-bit weights and 2-bit KV achieves comparable perplexity and speed to vLLM’s 4-bit AWQ weights and 8-bit
KV on RTX 5090, using approximately half the GPU memory. These results show that GPU-resident precision
need not set the accuracy ceiling, nor offloading-tier latency dictate decoding speed.
1 INTRODUCTION
LLM inference involves three coupled objectives: accuracy,
latency, and memory use. Model weights encode learned
parameters, while the key–value (KV) cache retains keys
and values from earlier tokens. Their representations deter-
mine both the precision available for computation and the
volume of data stored and moved during generation.
Quantization and offloading address limited fast-memory
capacity differently. Quantization reduces storage and traffic
with fewer bits; it can accelerate bandwidth-bound inference
but may degrade accuracy (Frantar et al., 2023; Liu et al.,
2024). Offloading preserves stored precision by placing data
in a larger, slower backing tier, but transfer latency can delay
generation (Na et al., 2025). These approaches suggest an
apparent choice between accuracy loss and transfer latency.
We argue that this is a false choice imposed by separating
representation from placement. Considered alone, quantiza-
tion discards precision that another tier could retain, while
offloading brings in that tier only after choosing the repre-
sentation. Can we use fewer bits in fast memory without
sacrificing accuracy or slowing inference?

2 BACKGROUND ANDMOTIVATION
2.1 Post-Training Quantization
Interactive on-device LLM inference repeatedly reads model
weights and the KV cache to generate new tokens. Their
size constrains which models and contexts fit in fast mem-
ory, while the traffic per token can make memory bandwidth
the bottleneck for generation speed (Pope et al., 2023; Liu
et al., 2024). Quantization reduces these demands by rep-
resenting values with low-bit codes, such as codebook in-
dices (Han et al., 2016) or scaled and offset integers (Jacob
et al., 2018). Post-training quantization (PTQ) compresses
weights without retraining the model (Frantar et al., 2023),
while KV-cache quantization compresses the keys and val-
ues generated during inference (Liu et al., 2024).
These savings introduce errors that affect accuracy differ-
ently across values. Large-magnitudeoutlierscan be diffi-
cult to represent alongside typical values (Dettmers et al.,
2022), whilesaliencydescribes how strongly representa-
tion errors affect computation or loss. PTQ methods ad-
dress these differences: SmoothQuant rescales activation
and weight channels (Xiao et al., 2023), and AWQ protects
salient weight channels through scaling (Lin et al., 2024).
SqueezeLLM instead combines sensitivity-weighted code-
books with higher-precision storage for selected sensitive
weights and outliers (Kim et al., 2024).

DecDEC (Park et al., 2025) finds that calibration-selected

3.2.2 KV Refinement
For KV refinement, we tailor nested reconstruction to the
resident cache format. Our main KV implementation,
StrataFlux-KV , adopts KVarN’s (Muller et al., 2026) quan-
tization format for its balance of accuracy and memory
footprint. We co-design its low-bit attention kernels and
selective refinement. For adaptations of StrataFlux to other
KV-cache formats, see Appendix E.
Nested encoding.As illustrated in Figure 2(a), we sub-
divide each KVarN code’s quantization interval into equal
sub-intervals and store their indices as refinement bits in the
backing tier. The resident code and fetched index identify a
finer reconstruction, independently for keys and values.

3.4 Reusing Precision Across Decoding Steps
For dedicated-GPU platforms, host RAM’s lower access
latency than SSD allows refinement bits to be fetched di-
rectly without an intermediate cache. For unified-memory
systems, however, SSD’s higher access latency motivates
caching fetched refinement bits in GPU-accessible RAM.
Caching fetched precision.Weight and KV selections
recur across consecutive decoding steps (Figure 5). To avoid
repeated SSD reads and their latency, we retain fetched
refinement bits in a configurably sized RAM cache that the
GPU reads directly (Figure 6).
Miss policy.Selections can still miss the cache. For weights
and KV , the current step can decide to skip missing refine-
ment and use the resident low-bit representation. A CPU
loader fetches the bits into the cache for future selections,
keeping the transfer useful without making the requesting
step wait. Alternatively, the runtime can wait and apply
refinement in the current step, trading speed for accuracy.
Cache organization.Weight and KV refinement have sep-
arate cache budgets. The weight cache stores refinement
bits for all four projection sets and uses least-recently-used
replacement. KV token groups share capacity across all KV
heads and Transformer blocks.
Populating the KV refinement cache.During prefill, we
write KV refinement bits to SSD and cache copies for the
most recently encoded token groups in RAM. During decod-
ing, newly produced refinement bits enter the cache directly,
serving subsequent selections without SSD readback.
3.5 Tuning Weight Refinement Within a Speed Budget
Search space.The weight tuner selects a configuration
subject to a user-specified slowdown limit relative to the
quantized base. It chooses channel budgets k, fetch lead/lag
distances s for each projection set, and whether the MLP
uses channel-wise refinement or neuron-wise refinement
with budget kn. Following DecDEC (Park et al., 2025),
it also tunes the number of GPU thread blocks (groups of
cooperating threads) executing refinement. More thread
blocks can accelerate refinement but also slow the concur-
rent quantized projections by competing for GPU resources.
Candidate selection.For each combination of shift dis-
tances and channel-wise or neuron-wise MLP refinement,
the tuner searches for the largest common channel budget
k that meets the slowdown limit in end-to-end decoding. It
selects the retained candidate with the lowest KL divergence
from the BF16 reference on held-out text, then increases
individual channel budgets or the neuron budget while the
measured slowdown remains within the limit. We tune each
model, weight quantizer, and platform separately. We then
fit refinements at the chosen selection budgets, as detailed
in Section 3.2.1.

5 RELATEDWORK
Heterogeneous-memory inference systems accommodate
weights and KV caches beyond GPU memory. Flex-
Gen (Sheng et al., 2023) schedules compressed tensors
across GPU, CPU, and disk; InfiniGen (Lee et al., 2024) and
FreeKV (Liu et al., 2026) prefetch selected KV entries from
host memory. Quest (Tang et al., 2024) and SparQ (Ribar
et al., 2024) reduce KV reads through query-dependent
selection. SpeCache (Jie et al., 2025) supplements a full
low-bit cache with prefetched 16-bit entries. StrataFlux in-
stead co-designs low-bit attention and selectively fetched
refinement bits, using caching and skipped misses to recover
accuracy without stalling decoding on backing-tier reads.
For weights, DecDEC (Park et al., 2025) selects refinement
channels from current activations and overlaps host-memory
fetching and refinement with the corresponding quantized
projection. Other inference systems overlap work across
Transformer blocks: Deja Vu (Liu et al., 2023) uses earlier
activations to predict which attention heads and MLP neu-
rons to compute, while KTransformers (Chen et al., 2025)
defers expert outputs to overlap CPU and GPU computa-
tion. StrataFlux extends weight-refinement overlap beyond
DecDEC’s projection window through early channel selec-
tion and deferred addition, and fits refinement values to
compensate for unselected channels.
6 CONCLUSION
StrataFlux recovers accuracy from low-bit weights and KV
caches while retaining quantization’s memory and speed
advantages. Its selective precision streaming makes host
RAM and SSD useful sources of additional precision by
coordinating what is fetched, when it arrives, and how it
refines computation. Across dedicated GPUs and unified-
memory platforms, StrataFlux demonstrates that precision
distributed across the memory hierarchy can improve accu-
racy without letting backing-tier transfers dictate decoding
speed.

A EVALUATIONSETUP AND
IMPLEMENTATIONDETAILS
Perplexity and KL.Weight evaluation uses 2K-token
WikiText-2 windows. For long-context evaluation, we sam-
ple 17 PG-19 test books with sufficient length and evaluate
16 windows of 128K tokens from each book. We prefill each
window except its final 256 tokens, then score those tokens
sequentially with teacher forcing. Context-length sweeps
shorten the windows to 8K–128K tokens while keeping
their endpoints and scored tokens fixed. KL uses the same
datasets, windows, and scored tokens as perplexity. We
approximate divergence from BF16 by keeping its 1,024
most probable vocabulary tokens separate and grouping all
remaining tokens into one category in both distributions.
Evaluation software.Weight evaluation uses the Language
Model Evaluation Harness (lm-eval) (Gao et al., 2023). We
evaluate LongBench (Bai et al., 2024) using the bench-
mark’s evaluation scripts.
Timing and memory.We implement StrataFlux in
llama.cpp, with CUDA 13.4.2 on NVIDIA GPUs and Metal
on the Mac. For fair comparisons, we port baselines with
author-provided kernels into the same framework. Systems
with their own runtimes, including KV offloading systems,
vLLM, and ExLlamaV3, are measured in their respective
implementations. KV and joint decode timing uses a PG-19
prompt, prefill to C−641 tokens for context length C, 512
untimed steps, and 128 timed steps. For weight-only com-
parisons on NVIDIA GPUs, we measure decode throughput
at empty context for WikiText-2 and at 128K context for PG-
19. Memory counts stored representations, metadata, and
RAM caches where used; captions specify whether weights,
KV , or both are counted. Memory values at 128K context
assume 131,072 tokens.
KV refinement settings.Main evaluations use resident
key/value bitwidths of 2/2, 3/2, and 3/3, with +4/+4 refine-
ment bits and a 1/128 token-group fetch fraction. Groups
contain two tokens on dedicated GPUs and four on unified-
memory platforms. Appendix C.6 varies resident and
fetched bitwidths, token-group size, and fetch fraction. The
first 128 tokens remain in FP16 unless ablated. A 128-token
buffer for the current token block also remains in FP16;
resident-memory totals include both allocations.
Baseline Kernels Integrated into llama.cpp
YAQA.We integrate QTIP’s released decompression and
matrix–vector kernels for Y AQA’s weight format.
SqLLM and LNQ+GQ.SqLLM uses Any-Precision
LLM’s quantizer and kernels; LNQ+GQ uses Guid-
edQuant’s weights with adapted Any-Precision kernels.
A WQ 4-bit.We integrate the authors’ released matrix–
vector and matrix–matrix kernels.
KVQuant.We add grouped-query attention support to
KVQuant’s released quantization and attention kernels.
KIVI.We retain KIVI’s released matrix–vector kernels and
supply packing and softmax integration in llama.cpp.
KVarN.KVarN baselines use the released Triton kernels.
DecDEC.We port DecDEC’s correction kernel into
llama.cpp and select its configurations with DecDEC’s tuner.
Our Baseline Implementations and Adaptations
A WQ 3-bit.The authors release a 4-bit matrix–vector kernel
but no 3-bit kernel, so we implement a group-size-128 3-bit
kernel in llama.cpp.
TurboQuant.With no author-released implementation
available at integration time, we adapt the community vLLM
backend (v0.30.0) to llama.cpp and match the paper’s quan-
tization settings.
AQUA-KV .The authors release PyTorch code without
CUDA kernels; we adapt it to CUDA, reconstructing cached
keys and values during decoding.
SpeCache.With no author-released code available, we
implement the paper’s low-bit KV cache and selective FP16
fetching in llama.cpp.
Systems Evaluated in Their Own Runtimes
We measure ShadowKV , FreeKV , ParisKV , TailorKV , and
KVSwap in their released runtimes. The vLLM, ExLla-
maV3, and QServe comparisons also use their respective
runtimes; we add Qwen3-8B support to QServe.
StrataFlux Implementation
Weights.We adapt DecDEC’s dynamic error-compensation
kernel, replacing bucket-based selection with exact radix-
sort selection and improving zero-copy request batching
at low GPU thread-block counts. We add fetch lead/lag
scheduling, RAM caches, and refinement delivery logic,
and develop an independent tuner inspired by DecDEC’s
search procedure.
KV .We adopt KVarN’s quantization algorithm and inde-
pendently develop CUDA and Metal attention kernels with
fused refinement operations.

B.7 Weight Refinement Tuner
The tuner searches separately for each model, weight quan-
tizer, and platform under a specified slowdown budget rel-
ative to the quantized base. It selects channel budgets k,
fetch lead/lag distances s, the MLP refinement scheme, and
GPU thread-block counts.
Resource allocation.We first profile base projections along-
side refinement while varying its thread-block count and
selection budget. The resulting timing table identifies launch
configurations that balance refinement speed against inter-
ference with the base projections.
Budget-constrained search.For each combination of shift
distances and channel-wise or neuron-wise MLP refinement,
the tuner searches for the largest common channel budget k
that satisfies the slowdown limit in end-to-end decoding. For
neuron-wise MLP refinement, it sets kn = round(3k/4):
each increment of kn fetches 4/3 as many bytes as each
increment of k for channel-wise gate/up and down refine-
ment. It also considers disabling refinement for projection
sets when needed to meet the budget. On DGX Spark, we
search skip-policy configurations only at s= 0: skipping
cache misses leaves no SSD wait for fetch lead/lag to hide.
Accuracy selection and budget allocation.The tuner com-
pares feasible candidates by KL divergence from BF16 on
held-out text. Starting from the lowest-KL candidate, it
increases individual selection budgets while remeasuring
end-to-end latency and retaining increases that satisfy the
slowdown limit. These final per-projection budgets need not
be equal.
Refinement fitting during search.Fitted refinement val-
ues depend on the selection budget (Section 3.2.1). We
approximate candidate KL during search using refinements
pre-fitted at a ladder of power-of-two selection budgets,
avoiding a separate fit for each candidate. Once the final
per-projection budgets are selected, we fit refinement values
at those exact budgets before quantizing them for inference.
Tuned configurations.Table A13 lists tuned configura-
tions across slowdown budgets and miss-policy sweeps.
Each row displays one configuration. The Weights column
gives the quantizer and bitwidth. Four-entry tuples give the
query/key/value, attention-output, gate/up, and down con-
figurations for channel-wise refinement. Three-entry tuples
give query/key/value, attention-output, and neuron bundles.
This order applies to selection counts (k, or kn for neuron
bundles) and shift distances s. ntb lists the GPU thread-
block count shared by channel-wise kernels, followed by
the count for the neuron-bundle kernel when used. Counts
k are per 1,024 input channels or neurons, and s is in Trans-
former blocks. SSD-backed configurations use a 128 MiB
cache; miss-policy sweeps identify skipping or waiting.

E APPLICABILITY TOOTHERKV BASES
The main KV implementation adopts KVarN’s quantization
format. Other bases require a refinement encoding and
decoder that combine their resident codes with separately
stored refinement bits. The selection of token groups and
the full-sequence attention update remain the same, but the
refinement levels must match the base’s quantization bins—
the value ranges mapped to each resident code—and its
coordinate transformations and metadata.
Nonuniform quantization bins.Our KVQuant-style adap-
tation starts from sensitivity-weighted nonuniform code-
books (Hooper et al., 2024) and fits finer levels within each
bin using sensitivity-weighted calibration samples. Our Tur-
boQuant adaptation uses its scalar quantizer optimized for
mean squared error in the rotated, normalized coordinate
system (Zandieh et al., 2026); each bin is refined using lev-
els derived from the base’s coordinate distribution restricted
to that bin. Both keep the resident code as the identifier of
the coarse bin and store the finer-level index separately.
