## Résumé

Memory is increasingly used in long-horizon agents, yet the net value of building memory over direct retrieval from raw history remains largely unclear. Through a large-scale evaluation across multiple benchmarks and model backbones, we find many dedicated memory systems underperform naive RAG in many cases, indicating a negative net value. Taking RAG as a reference, we dissect the net value of memory into the gains and losses over direct retrieval, termed memory benefit and memory tax. These gains and losses arise because memory process changes how the raw information is organized and accessed. We view such changes as the double-edged deviations from the raw history. They are originally designed and introduced to benefit the task, for example by reorganizing facts or distilling preferences, but some may also remove or obscure evidence, giving rise to memory tax. ## Memory Tax : Dissecting the Net Value of Agent Memory


### 1 Introduction

Memory has become an important component of long-horizon LLM agents, supporting recall across interaction histories and reuse of prior experience ( Wang et al., 2023 ; Xie et al., 2024 ; Gur et al., 2024 ; Hu et al., 2025a ) . Recent work has introduced increasingly diverse memory representations and management mechanisms ( Chhikara et al., 2025a ; Kang et al., 2025 ; Fang et al., 2026a ; Hu et al., 2026b ; Jiang et al., 2026a ) , aiming to make relevant information easier to preserve and utilize, but often incur additional computation over the original context. As memory systems grow more complex, it remains unclear how much these operations improve over a straightforward alternative, such as directly retrieve from the raw history.

Surveying prior works, it shows many memory designs primarily compare against other memories, while naive RAG is often overlooked, and when included, its setup is also not always fully specified (Appendix B.2 ). Without a retrieval baseline, the value of building memory remains entangled with the value of direct evidence retrieval, leaving its marginal or net value underexamined. So this suggests a gap between the growing complexity of memory design and our understanding of whether and where that complexity actually helps, motivating us to revisit a fundamental question:

To study this question, we start from a common setting, personal-agent conversational memory. We evaluate representative memory designs across several benchmarks and model backbones, using naive RAG as a reference to assess the net value of memory. The results show that naive RAG remains a strong baseline and many memory systems underperform it across diverse settings, indicating a negative net value in these cases. But a closer query-level comparison shows memory is not uniformly worse . It does solve some queries RAG misses, where organization or restructuring may help, while losing others that RAG already solves. We refer to the former as memory benefit and the latter as memory tax . When the tax outweighs the benefit, memory falls below RAG overall.

These gains and losses suggest a different view of memory. Memory goes far beyond a purely beneficial augmentation as often treated in prior works, and can be better understood as a double-edged process that changes how information from raw history is structured and accessed. We view such changes as inevitable deviations from the raw history. These deviations give memory its dual nature . They are originally designed and intended to better serve the task, e.g., by organizing scattered facts, distilling preferences, etc., yet some may also have unintended harmful effects due to particular design choices, such as losing or obscuring evidence. Memory benefit and tax thus capture the two sides, and their balance defines the net value of memory, reflected in the external performance.

Memory benefit reflects the intended gains of memory design, such as reorganization or abstraction, which is expected. So we focus more on how the memory tax emerges. We first examine faithfulness for how well the information survives memory process, and then accessibility for how easily the preserved information can be recalled or accessed. We further study robustness for reliability of memory across backbone changes. These dimensions characterize memory tax from system side, and its balance with memory benefit also highly depends on the task setting. Across more personal-agent memory benchmarks, we find naive RAG already achieves high absolute scores, suggesting a retrieval-friendly task setting with limited benchmark headroom for memory to deliver more benefit and thus making the tax more visible.

Moreover, the benefit-tax view is generalizable and not tied to particular memory forms, as nontrivial memory operations can introduce both beneficial and harmful deviations from the source. We further examine this in experiential memory and world-model memory . Finally, we derive some design implications from the perspective of memory deviations and benefit-tax trade-offs. We focus on simple changes that can be applied to existing memories without introducing new architectures.

We hope that the notion of memory tax can shift more attention from standalone memory performance to the net value of memory and its dissection into benefit and tax , thus informing more reliable memory design and evaluation. Our contributions are as follows:

Reassess the net value of long-term memory over direct retrieval holistically. 2 Dissect the net value into memory benefit and memory tax, and systematically analyze the source of memory tax. 3 Generalize the benefit-tax view to broader settings and derive general design implications.


### 2 Preliminary

Long-term memory for agents maintains information from past interactions and selectively exposes it to the model at query time. Let the interaction history be $\mathcal{H}=\{h_{1},\ldots,h_{T}\}$ , where each $h_{t}$ may contain user/agent messages, observations, or other types of content. A memory system processes this history into a persistent memory $\mathcal{M}=I(\mathcal{H})$ , where $I$ denotes the memory ingestion process. Given a task query $q$ , it retrieves relevant memory units $\mathcal{C}=R(q,\mathcal{M})$ and generates an answer $\hat{y}=G(q,\mathcal{C})$ . Different systems instantiate $\mathcal{M}$ as summaries, extracted facts, structured records, episodic entries, or other representations.

Naive chunk-based RAG provides a natural reference under this formulation. It keeps raw history with minimal processing and retrieves relevant chunks directly. We use it throughout this work as the comparison reference for assessing the net value of memory, and measured memory benefit and memory tax are thus relative to this reference.

Benchmarks. We evaluate on LongMemEval-s ( Wu et al., 2025 ) , PersonaMem-v2 ( Jiang et al., 2025b ) , and MINT-Eval ( Lee et al., 2026 ) . Baselines. We group the memory systems by how they organize what they store, and take open-source representatives of each group. Flat store : A-Mem ( Xu et al., 2026a ) , SimpleMem ( Liu et al., 2026b ) , MemOS ( Li et al., 2025b ) . We use RAG over the raw corpus as the main memory-free baseline, with both single-round (1rd) and two-round (2rd) variants. We also include several vanilla references, including No Context, Gold Context, etc. Appendix A.2 shows the full details.

Implementation details. We run every system on three backbones, Qwen3.5-4B , Qwen3.6-27B and GPT-5.6-luna(low) , sharing the same embedding model, Qwen3-Embedding-0.6B . Answers are scored by an LLM-as-Judge backed by Qwen3.6-27B , with judge prompts in Appendix F.2 . Alongside accuracy we report several cost metrics including token cost, end-to-end wall-clock time, number of LLM calls, and memory storage size.

Since memory granularity and storage capacity vary substantially across systems, a fixed top- $k$ can correspond to very different amounts of retrieved information. For a fair comparison, we align retrieval budgets using Retrieval Scope (RS), defined as the tokens in the memory units exposed to the LLM from retrieval through answering, normalized by the total tokens within the system’s retrievable store. We tune top- $k$ for each system (increasing it from the default in most cases) so its Retrieval Scope is roughly no lower than that of RAG (1-round), while roughly comparable across systems. The exception includes systems that contain only a few memory units, which retains a fixed top- $k$ . See full details in Appendix A.3 and A.4 .

### 4 Memory Tax


#### 4.1 Overview

§ 3.2 shows many memory systems underperform the naive RAG despite substantially higher costs. Since RAG accesses the same raw history with minimal processing, it provides a reference for assessing the net value of building memory .

We dissect this net value through a per-query comparison with RAG (1rd) (Figure 3 ). Memory does solve some queries RAG misses, benefiting from additional organization or processing, while losing others that RAG already solves, where evidence may become lost, obscured, or harder to access after memory processing. These two outcomes can be understood through the inevitable deviations introduced by memory from the raw history, as any nontrivial memory process can change how information is structured, preserved, or accessed. These deviations give memory its dual nature . They are originally intended to better serve the tasks, yet may also have unintended harmful effects due to particular design choices, giving rise to Memory Benefit and Memory Tax . Their balance determines the net value of memory, and for the above cases, the tax outweighs the benefit. These quantities are reference-dependent, and throughout this work are defined relative to the naive RAG.

#### 4.2 Memory Tax - Faithfulness: How Well Is the Information Preserved?

To trace where memory tax comes from, the first place to look is how well the memory system preserves past information. Memory operations like restructuring and compression may discard or distort evidence before retrieval begins, and such loss can not be recovered later, so we first investigate the faithfulness for a memory system, at both the macro level and micro level.

At the macro level, we replay QA with only the gold raw turns and, separately, only the gold memory units. Gold memory units remove retrieval failures, so the remaining memory tax reflects the losses introduced in memory construction, as shown by the red boxes in Figure 3 . However, the reduced tax after having oracle memory also indicates degradation arises beyond construction. The performance shows a similar signal. Some systems ( MAGMA , LightMem ) achieve gold-mem scores close to gold-raw-turn scores, yet far above their original, suggesting the preserved evidence may become harder to access.


#### 4.3 Memory Tax - Accessibility: How Easily Can Stored Information Be Accessed?

§ 4.2 examines how much information survives memory construction. However, preserved information is useful only if it remains accessible at query time. So next we measure the accessibility of memory from both macro and micro levels.

At the macro level, we replay retrieval iteratively for multiple rounds over the constructed memory and record how many rounds are needed to recover all gold memory units for a given query. Evidence lost in construction is marked as not retrievable. As shown in Figure 5 , Memory systems recover fewer queries than RAG in the first round, suggesting that some relevant evidence is buried deeper after memory construction.

To understand why preserved evidence becomes harder to access, we further inspect some cases as the micro level analysis (Appendix D.3 ). We observe several recurring patterns where evidence is fragmented across multiple memory units, diluted with unrelated information, or rephrased , weakening its accessibility compared with raw history. To visualize this effect more broadly, we compare the (query, gold raw turn) similarity with the (query, gold memory unit) similarity, reporting the point-wise changes and overall drift in Figure 5 . Since each system retrieves within its own memory store, absolute similarity values across systems are only indicative, the main signal is how memory construction shifts the query alignment of the same evidence. Appendix C.3 provides more results.


#### 4.4 Memory Tax - Robustness: How Robust Is the Memory Across Backbones?

The above analyses examine memory under a fixed backbone setting. However, long-lived agents may construct memory with one model and later consume it with another, making backbone robustness another important property. We construct memory independently with three backbones and evaluate each memory with different QA backbones.

Two patterns emerge. 1 First, with the QA backbone fixed, changing the construction model leads to noticeable score variation. This is expected since many intermediate operations rely heavily on the backbones and can produce different memory items from the same raw history. 2 More interestingly, with the construction fixed, changing the QA backbone causes larger performance variation than naive RAG for many systems, as shown in Figure 7 . This suggests many memory mechanisms can introduce additional fragility beyond the raw-history retrieval. In this sense, memory tax is reflected not only in point-wise performance loss, but also in the reduced robustness to backbone changes. See Appendix C.4 for more details.

#### 4.5 Benchmark Headroom Further Exposes the Memory Tax

The analysis so far focuses on how memory tax arises within a memory system. Yet the balance between memory benefit and tax also depends on the task settings. Some tasks naturally favor direct recall from raw history, while others may benefit more from abstraction or distillation. To examine this evaluation-side effect, we run several naive baselines across a broader set of long-term memory benchmarks, including 1 No Memory, 2 IDF-keyword, a lexical matching baseline based on the keyword rarity, 3 RAG-Emb, and 4 RAG-Hybrid. Details are in Appendix C.5 .

Figure 7 shows that simple retrieval baselines already performs quite well on some of the benchmarks, including some widely-used ones. For example, the extremely simplified IDF-keyword based method can even achieve more than 50% in absolute score on some of them, while RAG-Hybrid reaches about 70%. Such results suggest some current evaluation settings are relatively retrieval-friendly, leaving quite limited headroom for heavy memory to improve over naive retrieval.

This also helps explain why some systems with lightweight or even no explicit memory construction can achieve strong performance and efficiency ( Yan et al., 2025b ; Yu et al., 2026b ; Xiao et al., 2026 ; Xu et al., 2026b ; Zhang et al., 2026b ; Wu et al., 2026b ) . When naive retrieval already provides a strong baseline, they “inherit” much of that performance while introducing little memory tax , so lightweight design can be particularly competitive under limited benchmark headroom.

On the other hand, many real-world queries are also naturally retrieval-friendly, making such accurate recall tasks essential and meaningful in its own right. Current benchmarks contain a large share of such queries, and future evaluations could complement them with harder settings. Moreover, reporting memory systems alongside naive RAG can make remaining improvement room more explicit , which also helps clarify the contribution of built memory. RAG scores can also serve as a reference for calibrating difficulty and leaving meaningful room for more reliable evaluations.


### 5 Generalizing Memory Tax

Memory serves a wide range of application scenarios beyond personal-agent memory. We next examine whether the same benefit-tax view extends to two substantially different settings.


#### 5.1 Experiential Memory

In this setting, agents accumulate experience from past task traces to guide future ones. We evaluate on several agentic scenarios covering embodied tasks ( ALFWorld ), web ( WebShop, Mind2Web ), coding ( BigCodeBench ) and tool use ( AppWorld, $\tau^{2}$ -Bench ), with Qwen3.5-4B as backbone. Experience is accumulated on the training split and evaluated on the test split with memory frozen. We compare Mem p ( Fang et al., 2026b ) , ReasoningBank ( Ouyang et al., 2026 ) , G-Memory ( Zhang et al., 2025a ) and SkillPro ( Mi et al., 2026 ) against a ReAct agent without memory and a naive RAG baseline, which retrieves the most similar past tasks by their descriptions and places the trajectories into the context, details are in Appendix C.6.1 .

Figure 8 shows the effect of memory varies across task domains. In web-based tasks, distilling long traces into workflows or strategies can outperform naive RAG, while for tool-use, several memory methods fall behind it, suggesting memory tax also emerges in experiential memory , but its magnitude depends strongly on the task settings.


#### 5.2 World-Model Memory

Long-horizon world models need to retain information about past environment states to maintain temporal and scene consistency ( Zhang et al., 2026e ; Li et al., 2026 ; He et al., 2026 ; Chen et al., 2026f ; Chen et al., 2026d ; Chen et al., 2026c ) . Existing approaches have explored diverse memory representations and mechanisms, including raw frames, visual latents, and KV caches. We evaluate representative methods on two settings for long-horizon consistency: Context-as-Memory ( Yu et al., 2025 ; King et al., 2026 ) and MemoBench ( Chen et al., 2026b ) . Full details are in Appendix C.6.2 .

A similar pattern appears in these settings (Table 3 ). Directly retrieving and reinjecting past observations achieves strong consistency, while latent- or cache-based memories do not consistently outperform this simpler alternative. This suggests that memory tax can also arise in world-model memory , where additional memory operations may introduce losses that offset their intended benefits. It also motivates exploration of more unified memory carriers in video world models.

### 6 Design Implications

In this section, we derive some simple yet effective design implications for reducing or compensating for the memory tax. We focus on improvements that can be used on existing memory systems without introducing another new architecture, and deliberately exclude common test-time scaling techniques like retrieval depth / width expansion, query refinement, using stronger backbones, etc.

As we discussed above, building memory can introduce changes and deviations from the raw history about how information is preserved and accessed through diverse memory operations. While no single design can predict and fit all tasks needs, and the harmful deviations are difficult to eliminate entirely, a more promising way to reduce memory tax is to make such deviations recoverable , preserving a lightweight path back to the source history when memory becomes insufficient. As a simple proof of concept, we retrieve from source history alongside normal memory retrieval and jointly rerank them before QA. This lightweight recovery path can restore evidence lost during construction or missed in access. Results in Table show consistent improvements and reduction of memory tax across several memory systems.

Memory tax can only be visible in actual use, when relevant evidences become harder to access and are recovered only after deep search. Such retrieval experience directly reflects the harmful deviations memory introduced, and can in turn provide feedback to improve future memory access, creating a recursive loop between memory access and construction. Inspired by progress on recursive self-improvement (RSI) ( Zhang et al., 2026c ; Karten et al., 2026 ; Zhang et al., 2026d ) , where a system is expected to “improve how it improves” , memory can similarly “remember how it remembers” . Past queries, evidences, and retrieval paths can themselves be source materials for memory, and this is particularly useful for multi-round retrieval, since evidence found in deeper rounds can then be accessed directly by similar information needs. It also offers a new dimension of test-time scaling at query-side, allowing inter-query scaling beyond a single query. As a simple proof of concept, we treat past queries and retrieved evidence as additional inputs into memory store, making them available for future retrieval. Results in Table also validate its effectiveness.

Many methods build memory ahead of time (AoT) before future queries come. As we discussed before, memory makes deviations on the raw history, with the intention of better serving task queries, but may also add implicitly harmful effects. Without knowing future demand accurately, it is unclear what kind of deviations will be beneficial. To cover a broader range of possible queries, AoT systems may need to process more information in more elaborate ways, making it increasingly expensive. The opposite is just-in-time (JiT) memory ( Yan et al., 2025a ; Zhou et al., 2026b ; Yan et al., 2026a ) , which delays memory operations until queries arrive. With query already known, JiT can choose more targeted forms and directions of deviation to maximize the memory benefit and minimize the memory tax, but moves computation to the online part and increases user-facing latency, to which the users are highly sensitive.

A middle ground is to model the future demand . In personal agent settings, task queries are not purely random. Past interests, habits, and access patterns provide a prior over what information is likely to matter, and hence what kinds of deviations that memory introduces are likely useful. Such signals may help construction allocate effort more selectively, and reduces harmful deviations, without paying the full online cost of JiT. From this view, memory can partly be seen as an implicit recommendation system that estimates future relevance of past information. Exploring this perspective in real-world personal-agent settings may be a promising direction for future exploration.


### 7 Related Works

Long-term memory has become an important component for long-horizon agents, supporting the retention of specific information, past interactions, and task experience. Existing systems explore a variety of memory representations, including relatively flat stores ( Liu et al., 2026b ; Yang et al., 2026b ; Meng et al., 2026 ) , hierarchical organizations, from short-/long-term memory layers ( Kang et al., 2025 ; Fang et al., 2026a ) to filesystem-tree designs in recent industrial systems ( Volcengine, 2026 ; Tencent-Cloud, 2026 ) , and graph-based representations ( Jiang et al., 2026a ; Yang et al., 2026a ) . Another line of variation lies in how memory operations are governed. Some systems rely on predefined harness for writing, updating, and using memories, while others allow an LLM agent to decide these operations dynamically ( Wang and Chen, 2025 ; Xu et al., 2026a ; EverMind-AI, 2026 ) or explore learned memory policies ( Yan et al., 2026c ; Yu et al., 2026a ; Yan et al., 2026b ) . In this work, we study these memory systems through the lens of their net value , examining the gains and the losses introduced by memory operations.

Recent empirical studies examine agent memory from different perspectives, including how memory systems are designed and deployed, their performance-cost trade-offs, and where computation and time are spent ( Jiang et al., 2026b ; Omri et al., 2026 ; Zhou et al., 2026a ; Huang et al., 2026 ; Wolff and Bennati, 2026 ) . These works mainly characterize existing memory designs and their empirical behavior, but our work focuses on the net value introduced by memory processing itself. We introduce memory tax to characterize its losses relative to direct retrieval, analyze how such losses arise from both system and evaluation sides, and derive system-agnostic design implications.


### 8 Conclusion

We revisit the agent memory by studying its net value over direct retrieval from raw history. Across the evaluation on three benchmarks with many retrieval-friendly queries alongside some complex ones, many memory methods underperform naive RAG, indicating a negative net value in these settings. We dissect this net value into memory benefit and tax, showing memory can improve how past information is organized and used, but may also have harmful effects. We analyze memory tax from both system sides and evaluation settings, and generalize it to broader scenarios like experiential memory and world-model memory. We hope memory tax can shift more attention from standalone performance to the net value of memory, and encourages more reliable memory design and evaluation.


### Limitations

Given the rapid development of this field, our baseline selection is representative rather than exhaustive. We also follow official configurations wherever possible, though further system-specific tuning may yield better performance. Our benchmarks are primarily static, offline, and English-language, leaving long-lived deployments with interleaved queries and multilingual interactions underexplored. Extending the analysis to other forms of memory, such as omnimodal, latent, and parametric memory, is also left for future work. Our evaluation is limited by computational and API-calling cost. We do not include stronger frontier models beyond GPT-5.6 Luna (low) , and use stratified subsets for some benchmarks (20% of PersonaMem-v2, 10% of MINT-Eval, and 20% LongMemEval-s questions for GPT-5.6 Luna).

### Appendix A Experiment Details


#### A.1 Benchmark Details

Table 4 summarizes the evaluation data.

Each question has its own chat history of about 50 sessions, with a few evidence sessions hidden among distractors. We use the full set, except a 100-corpus subset stratified by question type for GPT-5.6 Luna .

Each corpus is one simulated user’s chat history (128k-token variant), with four-way MCQs on the user’s implicit persona and preferences. We evaluate a 20% subset (40 of 200 corpora).

Each corpus is an ordered stream of steps from one of four sub-domains, testing memory under multi-target interference. We draw a 10% stratified sample (60 of 595 corpora).


#### A.2 Baseline Details

These references use no retrieval or memory building. No Context answers from the question alone. Full Context provides the entire raw corpus in chronological order, truncating the earliest units if it exceeds the model’s context window. Gold Context provides only the gold evidence (raw turns supporting the answer) for each question, serving as an oracle reference. We omit this baseline on MINT-Eval, where author-annotated and verified gold evidence is available for only about half of the questions (Appendix C.2 ).

The raw corpus is first chunked and indexed. Chunking follows conversation turns (or observation steps) and never crosses session boundaries. Short turns are greedily merged into chunks of about 1024 characters, with the last turn carried over as overlap. Longer turns remain separate, while turns exceeding 8192 characters are split into 8192-character windows with 1024-character overlap. Each chunk is prefixed with a session date-time header. At question time, BM25 and dense retrieval ( Qwen3-Embedding-0.6B ) independently return their top- $k$ chunks. Their deduplicated union is reranked by Qwen3-Reranker-0.6B , and the top $k$ chunks, roughly half of the candidate pool, are passed to the backbone with the shared QA prompt.

For RAG (2-round) , we add a second retrieval round. The backbone checks whether the first-round chunks suffice and, if not, issues a follow-up query against the remaining pool. Chunks from both rounds are used for answering.

We group the memory systems as follows:

Flat store keeps memory as a flat collection (extracted facts, notes, etc.), indexed for similarity search: A-Mem ( Xu et al., 2026a ) , SimpleMem ( Liu et al., 2026b ) , MemOS ( Li et al., 2025b ) .

Hier/Lifecycle manages memory across tiers that differ in lifetime or abstraction, and moves, consolidates or updates units between them over time: MemoryOS ( Kang et al., 2025 ) , LightMem ( Fang et al., 2026a ) , and OpenViking ( Volcengine, 2026 ) .

Graph-based links memory units through explicit relations (e.g., entities, events or causal edges), and retrieval can expand along them: HippoRAG2 ( Gutiérrez et al., 2025 ) , PlugMem ( Yang et al., 2026a ) , MAGMA ( Jiang et al., 2026a ) .

Trained Policy learns how memory is written, updated and used through reinforcement learning rather than a hand-designed pipeline, whatever the store layout (hierarchical for Mem-T , flat for Memory-R2 ): Mem-T ( Yue et al., 2026 ) , Memory-R2 ( Yan et al., 2026b ) . For these two systems, memory construction, update and retrieval are carried out by their own policy models ( Qwen3-4B for Mem-T , Qwen2.5-7B-Instruct for Memory-R2 ), which we keep as released, replacing only the QA model with our backbones.

#### A.4 Implementation

In existing comparisons of memory systems, the retrieval top- $k$ used at QA time is usually inherited from each repository’s default configuration or aligned with that of the proposed system. Since memory units vary widely across systems, from a single turn to a merged chunk or session summary, the same top- $k$ can span from a few hundred to tens of thousands of tokens. So we measure Retrieval Scope (RS), defined as the fraction of tokens in memory units seen by the LLM from retrieval through QA over the total tokens in all memory units within the system’s retrieval range. We average this ratio over questions and report it as a percentage. Tokens are counted with the Qwen3.6-27B tokenizer. We adjust each system’s top- $k$ so that its RS is no lower than that of “RAG (1-round)”, while keeping RS reasonably comparable across systems.

We further clarify what counts as “the docs LLM sees” in RS. This depends on the LLM’s involvement in retrieval, which falls into three levels: 1 no involvement, where retrieval relies entirely on embeddings, indices, or other non-LLM components. 2 pre-retrieval involvement, where LLM rewrites query or extracts keywords but reads no retrieved units. 3 retrieval-time involvement, where the LLM reads retrieved units, e.g., to decide whether further retrieval is needed, reformulate the query, or assess whether a unit is useful.

Only level 3 exposes the LLM to memory units beyond the final answer prompt. RS counts all such exposure, including every unit read from retrieval through QA regardless of whether it appears in the final answer context. Both the numerator and denominator count only content that participates in retrieval. Metadata attached to memory units, such as topic, involved people, or date, is excluded when it is not searched over.

The RS requirement has some exceptions. Some memory systems produce only a few memory units, each covering a large part of the corpus. Forcing their RS to match would leave a very small top- $k$ , as for OpenViking, so we fix a top- $k$ for them.

We use NVIDIA H20 GPUs to locally served Qwen3.6-27B and Qwen3.5-4B , and they are decoded with temperature $0.0$ and top- $p$ $1.0$ for every ingestion and QA call, with reasoning disabled. GPT-5.6 Luna (low) is accessed through the OpenAI API with the default sampling config and reasoning effort set to low .

For a fair comparison, we unify the embedding model and, where a system uses one, the reranker model across all baselines. Unless otherwise stated, all baselines use Qwen3-Embedding-0.6B ( Zhang et al., 2025b ) as the embedding model and Qwen3-Reranker-0.6B ( Zhang et al., 2025b ) as the reranker if used in certain memory system.

#### B.2 RAG Implementation in Prior Works

All above results also raise a natural question: given its strong performance and simplicity, has the naive RAG been largely overlooked in prior memory methods and studies?

Revisiting the papers from all of our evaluated baselines along with several other influential memory papers ( Chhikara et al. (2025b) , Rasmussen et al. (2025) , Packer et al. (2024) , Ma et al. (2026) , Zhang et al. (2026a) ), we find that only three of them (excluding originally RAG system like HippoRAG2) report RAG results ( LightMem , PlugMem , and Mem-T ), while the others primarily compare against other existing memory systems. Specifically, LightMem segments corpus by turn and retrieves using all-MiniLM-L6-v2 embedding without specifying retrieval budget and other settings . PlugMem also uses turn-level chunks and retrieves using NV-Embed-v2 embedding (top-10). Mem-T adopts BGE-M3 with a top-5 retrieval, without specifying its chunking strategy .

These observations suggest that the potential of naive RAG may have been underestimated and not fully realized in prior memory studies. With a widely-used standard hybrid retrieval and reranking pipeline, RAG becomes a strong baseline, highlighting the importance of adequately evaluating retrieval controls when assessing the added value of constructed memory.

#### C.5 Benchmark Headroom Further Exposes the Memory Tax

We probe the benchmark headroom with the retrieval-only controls on a broader set of long-term memory benchmarks, listed here in order of release date (including the three benchmarks used in our main experiments): LoCoMo ( Maharana et al., 2024 ) , LongMemEval-s and LongMemEval-m ( Wu et al., 2025 ) , PersonaMem-v1 ( Jiang et al., 2025a ) , MemoryAgentBench ( Hu et al., 2025b ) , HaluMem-Medium ( Chen et al., 2026a ) , PersonaMem-v2 ( Jiang et al., 2025b ) , MINT-Eval ( Lee et al., 2026 ) , KnowMe-Bench ( Wu et al., 2026a ) , RealMem ( Bian et al., 2026 ) , EverMemBench-MCQ ( Hu et al., 2026a ) , AMA-Bench ( Zhao et al., 2026 ) , ES-MemEval ( Chen et al., 2026e ) , and the multimodal benchmarks Mem-Gallery ( Bei et al., 2026 ) and WorldMemArena ( Liu et al., 2026a ) .

We run the four naive baselines of Section 4.5 . #### C.6 Generalizing Memory Tax


##### C.6.1 Experiential Memory

Experience is accumulated on the training (or dev) split and evaluated on test split, with task counts provided (experience / test).

ALFWorld ( Shridhar et al., 2021 ) : text-based household tasks (300 / 134).

WebShop ( Yao et al., 2023a ) : searching for and buying a product on a simulated e-commerce website (1,000 / 500).

Mind2Web ( Deng et al., 2023 ) : navigation on real-world websites, tested on the cross-task, cross-website and cross-domain splits (1,009 / 1,341).

BigCodeBench ( Zhuo et al., 2025 ) : Python programming with calls to diverse libraries, tested on the Hard subset (992 / 148).

AppWorld ( Trivedi et al., 2024 ) : everyday tasks solved by writing code that calls app APIs, tested on test-normal and test-challenge (147 / 585).

$\tau^{2}$ -Bench ( Barres et al., 2025 ) : customer service with domain policies, tools and a simulated user in the airline, retail and telecom domains (178 / 100).

No Memory : the agent interacts with the environment purely in the ReAct ( Yao et al., 2023b ) , with no memory across tasks.

Naive RAG : At the start of each task, we retrieve the top-2 previously accumulated tasks based on their description similarity to the current task and include their raw trajectories in the prompt. We use the same embedding model as in Section 3.1 , Qwen3-Embedding-0.6B .

Mem p ( Fang et al., 2026b ) : distills past trajectories into procedural memory, i.e., step-by-step workflows, and retrieves those of similar tasks as guidelines.

ReasoningBank ( Ouyang et al., 2026 ) : induces generalizable reasoning strategies from both successful and failed trajectories as structured memory items, retrieved by task similarity.

G-Memory ( Zhang et al., 2025a ) : organizes experience in a three-tier graph hierarchy of insights, queries and interaction trajectories, and retrieves both high-level insights and condensed past trajectories from it.

SkillPro ( Mi et al., 2026 ) : maintains an evolving pool of skills, from which the agent selects one to follow at each step, and the skills are refined from the feedback of the tasks.

We follow the default task protocols of each benchmark consistent with prior work, including a step limit of 50 for ALFWorld, 15 for Webshop, 50 for AppWorld and 50 for $\tau^{2}$ -Bench, while Mind2Web imposes no explicit step limit. We follow each benchmark’s official metric: success rate for ALFWorld, task score for WebShop, step success rate for Mind2Web, pass@1 for BigCodeBench, passˆ1 for $\tau^{2}$ -Bench, and Task Goal Completion (TGC) for AppWorld, where a task succeeds only if all associated unit tests pass. Although pass@ $k$ and passˆk differ in definition, they are equivalent when $k=1$ .


##### C.6.2 World-Model Memory

2 benchmarks adopted:

Context-as-Memory Test set ( Yu et al., 2025 ) . We use 60 samples from it. Starting from the first-frame input image, each sample generates four video segments in sequence that complete a revisit, e.g., with instruction of turning right by 45 ∘ , right by 45 ∘ , left by 45 ∘ and left by 45 ∘ , which return the camera to its original position. We then compare the final frame with the original view and report PSNR, SSIM and 1 $-$ LPIPS, all higher is better.

MemoBench ( Chen et al., 2026b ) . A target object undergoes a physical process (e.g., dissolution), leaves the view through camera motion, and must reappear in its updated state. We test 25% of it, i.e., 90 samples.

6 baselines adopted:

WorldKV ( Yi et al., 2026 ) keeps the key-value cache of past frames as world memory, and retrieves and compresses the cached entries for the current generation step. ReWorld ( Chen et al., 2026f ) an interactive world model that carries long-horizon memory in a learned, bounded key-value memory updated as the video is generated. MagicWorld ( Li et al., 2025a ) stores the visual latents of past frames and reuses them as context to keep long-horizon exploration stable. FramePack ( Zhang et al., 2026e ) packs the history into a fixed-length context of visual latents, compressing older frames more aggressively, with sampling that prevents drift. HyDRA ( Chen et al., 2026d ) summarizes the history into a small set of memory tokens that the generator attends to.

### Appendix D Case Studies

In this section, we show some representative case studies for both Memory Benefit ( D.1 ) and Memory Tax ( D.2 , D.3 ), and also some comparison examples of benefit and tax within the same memory mechanism to directly show the dual nature of memory ( D.4 ).


#### D.1 Memory Benefit

Even the main results show memory underperform RAG in the overall performance in many cases, memory systems can still answer some questions correctly where naive RAG fails and we still need them in such scenarios. We inspect a sample of such questions and group the wins of memory into several representative types (Figures 18 and 19 ):

Focused atomic extraction : each fact becomes a short unit, so the gold facts fit into the retrieved context, while RAG’s top- $k$ is filled by long chunks that other irrelevant information, making the evidence hard to recover.

Multi-hop linking : facts from different sessions are retrieved together and combined, while for naive RAG the evidences are scattered.

Implicit preference exposure : a trait mentioned only in passing becomes an explicit unit in the memory.

Temporal anchoring : relative time expressions are anchored to absolute dates during construction.

Explicit forgetting : a forget request updates the stored state by removing or deactivating the targeted content.

Processing for heterogeneous inputs : non-dialogue inputs such as code diffs are described in natural language, making it easier to be recalled with semantic retrieval.

#### D.3 Memory Tax - Accessibility

Figure 24 shows examples from the round replay in Section 4.3 . In each case the evidence is still preserved in memory, but it is returned in a later round than the raw turns. The badges give the round in which a unit is first retrieved and the maximum number of rounds for that store. We observe three recurring patterns:

Fragmenting : one raw turn is split into several units, and a unit carrying a necessary part of the evidence ranks far behind the others.

Diluting : the evidence is wrapped in unrelated or additional content, such as a long profile or an elaborated note, which weakens its match with the query.

Rephrasing : the evidence is rewritten, sometimes with a slight shift in meaning, and no longer matches the query as well as the raw wording.
