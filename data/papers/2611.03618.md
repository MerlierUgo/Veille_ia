### Section 1 Introduction

> Figure 2 : Strategy design is per task; Strategist makes it cumulative. By hand and in prior automated search, nothing carries between tasks. Strategist keeps every strategy in a library that the next task starts from.

A model is only half of an AI system. The other half is how that model is put to work, and it matters just as much. Everything from the prompt to the reasoning procedure decides how it behaves. Today that second half is designed by people, fixed, one system at a time. Someone writes the prompt, tries it, adjusts it, and once the system works, the design is left as it is. It is the part of the system that never improves on its own.

There is no reason it has to stay that way. The prompts and reasoning procedures that put a model to work are text and code, and agents themselves have become good at writing both. What humans do to design (write, try, adjust) such inference strategies is the natural agentic loop. Such loops have already been shown to evolve programs far beyond their starting point ( Novikov et al., 2025 ) , and AI scientists now run the same loop end to end ( Lu et al., 2024 ; Gottweis et al., 2025 ; Yamada et al., 2025 ) . Designing an inference strategy is the same work with a different object. So why not evolve agentic reasoning itself the same way? Run on far more cases than a person could try, the loop could outdo what people build by hand.

Recent work has begun to automate this loop: searching over strategy designs, as raw code or as assemblies of fixed components ( Hu et al., 2025 ; Zhang et al., 2025c ; Shang et al., 2025 ; Zhang et al., 2025a ) ; training controllers that route each input to an existing strategy ( Taparia et al., 2026 ; Yue et al., 2025 ; Zhang et al., 2025b ; Su et al., 2025 ) ; or optimizing one strategy per task by training, evolution, or iterative refinement ( Gao et al., 2024 ; Li et al., 2024 ; Zhang et al., 2026 ; Gao et al., 2025 ; Liu et al., 2025a ) . All of them beat hand-designed strategies on individual benchmarks, and all of them stop there. Searching or routing over a fixed set of strategies can never discover a new one. Trained optimizers need to start over for every task. These methods make the design automatic. We want to make it cumulative (Figure 2 ).

We start from the representation. Evolving strategies needs a form open enough to express any reasoning procedure and structured enough for later searches to reuse and combine. We introduce the Strategy Blueprint : an executable program with one shared code interface, so any blueprint can serve as a component inside another. New designs are built from old ones, and the library grows as it is used.

On this representation we build Strategist , a meta-agent that does not answer questions but designs the strategies that do. It runs the write, try, adjust loop at scale, with frozen models and no training. Given a task and a small development set, it writes candidate strategies as blueprints, runs them on real samples, reads the traces, and revises them against measured accuracy and cost. Before each round it queries a shared library for relevant blueprints and for diverse ones as inspiration. After each round every candidate goes back into the library with its measurements and experience notes.

On 30 benchmarks spanning math, code, commonsense, multi-hop QA, knowledge, logic, and recommendation, we compare Strategist against 18 baselines. Strategist wins on 24 of 30, matching the strongest baseline’s average accuracy ( $74.0\%\!\to\!74.7\%$ ) at 39% lower cost. The library pays off on its own: on 10 held-out benchmarks, retrieval with no search stays within 2 points of the strongest baseline on all 10 and beats it on 8 ( $77.8\%\to 81.4\%$ ). The same strategies, moved to GPT-5 and Gemini-2.5 without changing a line, still beat the baselines there. Each task solved leaves the next one a better place to start. Until now, only the model in an AI system could learn. Now the rest of it can too.

### Section 2 The Strategy Blueprint

Every inference strategy, ultimately, is a program. How it is represented determines what an automated designer can build, test, and reuse. Existing work represents strategies as computation graphs ( Wu et al., 2024 ; Zhuge et al., 2024 ) and declarative pipelines ( Khattab et al., 2024 ; Yue et al., 2026 ) , which are composable but can only express pre-defined patterns, or as monolithic code ( Hu et al., 2025 ) , which can express anything but produces isolated strategies. We introduce the Strategy Blueprint : a reasoning flow that specifies how to solve a task (which models to call, in what order, at which tier, and how) using the open interface of code. Every blueprint exposes the same interface, so any can call any other, and a library can grow by composition.

> Figure 4 : Strategy blueprint captures reasoning structure. This simplified blueprint example defines the steps, control flow, and the model tier for each step. Prompts are not specified; filling in produces a runnable strategy.


##### Foundations.

A blueprint is a Python program that captures the structure of a reasoning strategy without the task-specific prompts. For example, one blueprint defines a loop: generate three candidate answers, review each, then majority-vote. Filling in prompts produces a runnable strategy . It has one interface, execute(llm, task) -> str , and is built from two foundations: chat (single- or multi-turn conversation) and agent (with scaffold and tools). See Figure 4 for an example.


##### Multi-tier model routing.

We allow strategies to route across three model tiers ( fast , balanced , complex ), each in two modes ( nothink and thinking ), mirroring the tiered pricing and effort levels of common model providers. Not every reasoning step needs the same intelligence, so each step can target a different tier. This internal routing is what allows a single strategy to be accurate and cost-efficient at the same time.


##### The Blueprint Library.

Blueprints live in a shared library that grows over time. They are added along with their measured performance and experience notes on when it works and when it does not. Because every blueprint exposes the same interface, a new blueprint can use any existing one as a component, so the library compounds: early blueprints build on the two foundations, later ones compose from those, and depth grows naturally (Figure 3 a ). Four protocols govern the library (Figure 3 b ): a shared interface, no forward calls, no cycles, and no duplicates.

> Figure 5 : The Strategist four-stage iterative pipeline. Each iteration: (1) Retrieve relevant blueprints and diverse inspiration from the Library; (2) Propose $K$ candidates as a mix of new , composed , and reuse blueprints paired with task-specific prompts; (3) Evaluate each candidate, seeing full traces on the training set and aggregated scores on validation; (4) Accumulate the underlying blueprints into the library with measurement cards and experience notes.


### Section 3 Strategist

Given a task and a small development set, Strategist iteratively retrieves relevant blueprints, proposes $K{=}5$ candidates, evaluates them on real samples, and accumulates the results back into the library (Figure 5 ). After $N$ iterations, the candidate that beats BL on both the validation and hidden splits by the largest hidden-set margin is returned, or BL itself if none does (Algorithm 1 ).


##### Step 1: Retrieve.

The strategist queries the Blueprint Library with a short text prompt. The search is hybrid (TF–IDF plus embedding similarity). Each blueprint carries traits, a measurement card, and experience notes written by previous strategists; the search indexes over all of these, so the strategist finds blueprints by measured behavior and prior analyses, not just structural similarity. Beyond relevant results, the library returns adjacent inspiration (blueprints from other domains or reasoning patterns) to inspire new designs.


##### Step 2: Propose.

Using the retrieved blueprints and inspiration, the strategist designs new blueprints or composes from existing ones, each paired with task-specific prompts to form candidate strategies. Each blueprint must be one of three kinds: new (a blueprint with no library backbone), composed (a blueprint that wraps or extends an existing one), or reuse (directly applies an existing library blueprint with new prompts). Every iteration includes at least one candidate of each kind, balancing exploration and exploitation.


##### Step 3: Evaluate.

The system operates at two levels. At the agent level (inner loop), each candidate strategy processes inputs directly, and the strategist observes the full reasoning trace, execution status, and scores. At the meta level (outer loop), the strategist uses these observations to improve its proposals. The data is split into four parts. The training set : strategies run on these samples and the strategist sees both the scores and the full agent traces. The validation set : strategies also run on these samples, but the strategist sees only the aggregated scores; this mirrors standard train/validation practice and prevents overfitting to the training signal. The hidden set : used to select the winning strategy across all iterations, preventing overfitting to any single iteration. The test set : held out entirely from the search loop and used only for final confirmation.


##### Step 4: Accumulate.

The library stores blueprints, not strategies: it retains the reusable structure while discarding task-specific prompts. This is what enables cross-task transfer. After each iteration, the strategist writes an analysis of each candidate’s structural properties and adds the underlying blueprints to the library with their measurement cards and experience notes, with deduplication.

##### Models.

The task models consist of three tiers: Qwen3-0.6B (fast), Qwen3-1.7B (balanced), and Qwen3-4B (complex), each run with thinking off (nothink) or on (thinking), giving six model configs. The strategist is GPT-6, a separate frozen LLM accessed through the Codex CLI; it writes strategies but never answers questions.


##### Baselines.

We compare against 18 baselines (Table 2 ), all using the same task models without internet access. They span from direct prompting to multi-agent workflows, and each runs at all six model configurations, giving $18\times 6=108$ cells per benchmark. Our baseline (BL) is the cell most accurate on a benchmark’s training split, scored on the test set. This mirrors deployment: a method is chosen on the small sample at hand, then applied to a larger unseen sample from the same distribution. Our strategy is likewise chosen without seeing the test set.


##### Metrics.

We report accuracy and weighted cost. Cost is token usage (input and output) weighted by tier (fast $=1\times$ , balanced $=2.83\times$ , complex $=6.67\times$ , matching the 0.6B/1.7B/4B parameter ratio), since per-token floating-point operations (FLOPs) scale linearly with the parameter count ( Kaplan et al., 2020 ) .

### Section 5 Results

We run the full Strategist loop on each of the 30 main benchmarks. BL is the cell of the $18\times 6$ baseline matrix that is most accurate on the benchmark’s training split; all methods share the same executors, extractor, and 200-sample test split. A strategy wins if it is better than BL on accuracy (by more than 2 points) or on cost (by more than 2%) and worse on neither. Strategist wins on 24 of 30 benchmarks, ties on 2 (MBPP+, MinervaM), trades accuracy for cost on 2 (MedQA, AIME) and loses on 2 (HotpotQA and COPA, at equal accuracy but 9% and 6% higher cost); it cuts weighted cost by more than 2% on 26 of 30 (Figure 7 ; Figure 6 places Ours among all 108 baseline cells; per-benchmark numbers in Appendix C.1 ). On average, Strategist matches BL’s accuracy ( $74.0\%\to 74.7\%$ ) while reducing weighted cost by $39\%$ (a mean per-benchmark cost ratio of $0.61\times$ relative to BL).

##### One-shot library retrieval.

The 30-benchmark main run grew the library to $1{,}865$ blueprints. We test if a future task can skip the full search: on 10 held-out benchmarks, the strategist queries the final strategies of the main searches (not the full library) once, instantiates the top-5 retrieved blueprints for the task, measures each on up to 300 development questions, and runs the chosen one (the most accurate candidate cheaper than BL if within 2 points of the best, otherwise the best) on the test set, with no search. It stays within 2 points of BL’s accuracy on all 10 and above it on 8 ( $77.8\%\to 81.4\%$ on average) and wins on 6 (Table 4 ); on BoolQ, SIQA, and DROP it is more accurate but costlier than their very cheap BL ( $1.0$ – $4.9$ k per sample), and on QUALITY it costs $7\%$ more at equal accuracy. Its per-benchmark average cost (as in Figure 7 ) is $0.77\times$ BL’s without BoolQ and SIQA, whose single-call BL puts their ratios at $32\times$ and $4.5\times$ .


##### Cross-model transfer.

A strategy is most useful if it captures structure of the task rather than idiosyncrasies of the executor it was searched on. We re-run Strategist -discovered strategies, without any modification to the blueprint code or its prompts, on two model families the strategist never saw during search: OpenAI GPT-5 (nano, mini, full) and Google Gemini-2.5 (flash-lite, flash). On GPT-5 the strategies win on 7 of 10 benchmarks and lose on 3 (ASDiv, HellaSwag, MinervaM: within 2 points of the baseline but costlier); on Gemini they win on 8 of 10, with SQuAD2 and MinervaM mixed (cheaper but less accurate). Aggregate cost in USD drops by $35\%$ and $40\%$ . Part of the GPT-5 margin comes from baseline workflows that break on the new backend ( self_refine and multi_agent_debate return malformed answers there) while the discovered strategies run unchanged. That a Qwen3-discovered blueprint carries over at all shows that Strategist captures the structure of the task, not executor-specific tricks.

### Section 6 Analysis


##### Anatomy of a discovered reasoning strategy.

Figure 8 shows one strategy (accuracy driven) designed for the Amazon-Rec task: it builds a user profile with cheap calls, extracts brand and category signals, and conditionally routes to a multi-agent debate only for users with shifting preferences, before merging and auditing the top picks. The branching is cheap deterministic logic that decides which inputs deserve the expensive call, so the strategy spends its capacity where it actually changes the answer rather than uniformly across all inputs. The conditional routing, the merge weighting, and the audit step all emerged from iterative proposals against measured accuracy. Because the result is plain Python, a user can read and edit it directly, and the call is structural, which is hard to do with prompt-bag methods or training-based alternatives.


##### Overfitting across data splits.

The strategist sees training traces and validation scores at every iteration and could fit noise in them; if it did, the training curve would pull away from the hidden curve. Figure 9 plots, per iteration, the mean accuracy of that iteration’s five candidates on each split, averaged over the 30 main benchmarks. The curves move together and the training–hidden gap stays between $1.2$ and $2.5$ points, so the proposals do not drift away from data the strategist never sees. Selection is a different matter: the final strategy is chosen for being best on the hidden split, and part of that is luck. Across the 30 benchmarks the pick is $4.3$ points above BL on hidden but $0.7$ on test (BL itself moves by $0.5$ ). The test split, on which nothing is chosen, is the only unbiased estimate, and it is what every table reports.

### Section 8 Related Work


##### LLM agents.

LLM agents span chain-of-thought (CoT) and self-consistency reasoning ( Wei et al., 2022 ; Wang et al., 2023 ) , deliberate search ( Yao et al., 2023a ) , tool-use loops ( Yao et al., 2023b ; Schick et al., 2023 ) , verbal self-reflection ( Shinn et al., 2023 ) , multi-agent conversation ( Wu et al., 2023 ) , and formal representations from state machines to declarative compilation to optimizable graphs ( Wu et al., 2024 ; Khattab et al., 2024 ; Zhuge et al., 2024 ; Yue et al., 2026 ) . The strategy layer (how models are called, in what order, and with what verification) has become the central design bottleneck; Strategist automates its design. (An extended discussion of related work is in Appendix D .)


##### Automated design of agentic systems.

Structure-search methods write strategies as raw code ( Hu et al., 2025 ) or compose them from fixed components or predefined modules ( Zhang et al., 2025c ; Shang et al., 2025 ; Zhang et al., 2025a ) ; the first yields isolated programs, the second bounds what can be discovered. Optimization methods refine one strategy per task, by reinforcement learning ( Li et al., 2024 ; Zhang et al., 2026 ; Gao et al., 2025 ) or by LLM-driven evolution and refinement ( Gao et al., 2024 ; Liu et al., 2025a ) , and start over on the next task. Routing methods select among existing strategies without building them ( Taparia et al., 2026 ; Yue et al., 2025 ; Zhang et al., 2025b ) . Strategist instead allows freeform creation via the Strategy Blueprint, needs no training, builds strategies itself, and routes across model tiers in each strategy.


##### Cross-task transfer and experience accumulation.

Cross-task transfer has been studied through meta-learning ( Finn et al., 2017 ; Hospedales et al., 2022 ) , neural architecture search ( Elsken et al., 2019 ) , and prompt optimization ( Yang et al., 2024 ) ; in the LLM-agent setting, ExpeL ( Zhao et al., 2024 ) and Voyager ( Wang et al., 2024 ) accumulate experience or skills, and lifelong-agent learning has been formalized as a direction ( Zheng et al., 2025 ) . Existing automated design methods ( Hu et al., 2025 ; Zhang et al., 2025c ) still largely optimize per task. Strategist maintains a shared blueprint library that grows with every task, providing both exploitation (relevant components) and exploration (diverse inspiration); to our knowledge, the first automated strategy-design system that accumulates knowledge from one task to the next.


### Section 9 Conclusion

We presented Strategist , a meta-agent that designs inference strategies as freeform executable programs on a layered framework, the Strategy Blueprint, and grows a shared Blueprint Library across tasks. On 30 benchmarks, Strategist -designed strategies match or beat most strongest baselines on accuracy while running at substantially lower cost, and the discovered strategies transfer to backends the strategist never searched on. We view freeform strategy design over an accumulating library as a step toward inference systems that get better the more they are used.

### Appendix A Method and Implementation Details


#### A.1 Pseudocode for the Strategist Design Loop

Algorithm 1 formalizes the four-stage iterative pipeline described in Section 3 . Inputs are a task description $\mathcal{T}$ , a development set $D$ split into feedback/validation/hidden subsets, the current shared blueprint library $\mathcal{L}$ , and the number of iterations $N$ . Each iteration runs four steps: (i) the strategist queries $\mathcal{L}$ for the most relevant blueprints and a set of adjacent-domain inspirations; (ii) the strategist proposes $K$ candidate strategies, balanced across the kinds new / composed / reuse and the targets accuracy / efficiency / balanced ; (iii) each candidate is executed on $D$ and scored on accuracy and cost; (iv) the strategist writes experience notes summarizing what worked and what failed, and the candidates plus their measurement cards are written back to $\mathcal{L}$ with structural deduplication. The reference baseline $b$ (the baseline cell most accurate on the training split, run with its exact code) is evaluated alongside the candidates in the first iteration. After $N$ iterations, every candidate is compared with $b$ question by question on the validation and hidden splits; among the candidates that beat $b$ under the 2% rule on both (better by more than 2 points in accuracy or 2% in cost, worse on neither), the one with the largest hidden-set accuracy gain is returned as $s^{*}$ , and $b$ itself if none qualifies. The updated library $\mathcal{L}^{\prime}$ is carried forward for future tasks.

#### A.2 Benchmark and Baseline Settings


##### Scoring mechanism.

All strategies and baselines run as 0-shot generation: the executor LLM produces a free-form response and an answer extractor parses the final answer from the trace. The extractor is benchmark-aware (multiple-choice letter, integer, LaTeX numeric, span, or yes/no) and is the same across Strategist , all baselines, and all five comparison frameworks, so reported accuracy differences reflect strategy choices rather than scoring asymmetries.


##### Benchmarks.

We evaluate on 40 publicly released benchmarks. From these, $30$ are randomly selected as the main benchmark set used for the iterative search and the remaining $10$ are held out exclusively for the one-shot retrieval experiment.

- • Mathematical reasoning: GSM8K ( Cobbe et al., 2021 ) (grade-school word problems, numeric), MATH500 ( Hendrycks et al., 2021b ) (competition math, LaTeX/numeric), AQuA-RAT ( Ling et al., 2017 ) (algebra, 5 choices), AIME 2024 ( Mathematical Association of America, 2024 ) (American Invitational Math, 30 problems, integer 0–999), ASDiv ( Miao et al., 2020 ) (diverse word problems, numeric), SVAMP ( Patel et al., 2021 ) (perturbed word problems, numeric), MinervaMath ( Lewkowycz et al., 2022 ) (graduate-level quantitative, LaTeX/numeric), Gaokao-Math-QA ( Zhong et al., 2024 ) (Chinese college-entrance MCQ, 4 choices).

- • Code generation: MBPP+ ( Liu et al., 2023 ) (Python function synthesis, pass@1 on extra-test variant of MBPP).

- • Commonsense reasoning: HellaSwag ( Zellers et al., 2019 ) (sentence completion, 4 choices), PIQA ( Bisk et al., 2020 ) (physical commonsense, 2 choices), Social IQa ( Sap et al., 2019 ) (social commonsense, 3 choices), WinoGrande ( Sakaguchi et al., 2020 ) (coreference, 2 choices), CommonsenseQA ( Talmor et al., 2019 ) (general commonsense, 5 choices), COPA ( Roemmele et al., 2011 ) (causal alternatives, 2 choices), OpenBookQA ( Mihaylov et al., 2018 ) (elementary science, 4 choices), SciQ ( Welbl et al., 2017 ) (crowdsourced science, 4 choices), StrategyQA ( Geva et al., 2021 ) (implicit-reasoning yes/no), BoolQ ( Clark et al., 2019 ) (passage-grounded yes/no).

- • Knowledge and QA: MMLU ( Hendrycks et al., 2021a ) (57 subjects, 4 choices), MMLU-STEM-Hard (filtered hard STEM subset, 4 choices), TriviaQA ( Joshi et al., 2017 ) (closed-book trivia, EM), NQ-Open ( Kwiatkowski et al., 2019 ) (closed-book Wikipedia QA, EM), TruthfulQA ( Lin et al., 2022 ) (misconception-resistant MC1), SQuAD v2 ( Rajpurkar et al., 2018 ) (extractive with unanswerables, F1).

- • Multi-hop QA: HotpotQA ( Yang et al., 2018 ) (2-hop with passages, EM), 2WikiMultihopQA ( Ho et al., 2020 ) (Wikipedia multi-hop, EM), MuSiQue ( Trivedi et al., 2022 ) (2–4-hop composition, EM), DROP ( Dua et al., 2019 ) (discrete reasoning over paragraphs, EM), QuALITY ( Pang et al., 2022 ) (long-passage MCQ on 5 k-token articles, 4 choices).

- • Logical and analytical reasoning: BBH ( Suzgun et al., 2023 ) (23 BIG-Bench Hard tasks, mixed format), ANLI-R3 ( Nie et al., 2020 ) (round-3 adversarial NLI, 3 choices), ReClor ( Yu et al., 2020 ) (logical reading comprehension, 4 choices), AGIEval English MCQ ( Zhong et al., 2024 ) : SAT-Math, SAT-EN, LSAT-AR, LSAT-LR, LSAT-RC (4–5 choices each), MedQA ( Jin et al., 2021 ) (USMLE-style, 4 choices).

- • Recommendation: Amazon-Rec ( Liu et al., 2025b ) (rank top item from a candidate pool, hit-rate).


##### Baselines.

We compare against $18$ standard baselines covering both single-call prompting and full agentic systems. Each baseline is evaluated on every one of the six tier/mode configurations, giving an $18\times 6=108$ -cell baseline matrix per benchmark. The matrix is measured on both the training split and the test set; the cell most accurate on the training split is BL, and its test result is reported.

- • direct: a single LLM call that returns the answer with no intermediate reasoning. The minimum-cost baseline; serves as the floor for comparisons on easy benchmarks.

- • chain-of-thought (CoT) ( Wei et al., 2022 ) : a single call prompted with “Let’s think step by step”, encouraging the model to emit intermediate reasoning before the final answer.

- • self-consistency ( Wang et al., 2023 ) : sample $3$ CoT trajectories at temperature $0.7$ and return the majority-voted final answer; trades cost for variance reduction.

- • direct-thinking: a single call in thinking mode with no extra prompting, isolating the contribution of the model’s hidden reasoning trace from any prompting trick.

- • tree-of-thoughts (ToT) ( Yao et al., 2023a ) : maintain a tree of partial reasoning states, expand each by sampling a few continuations, score with the model itself, and search BFS-style for a high-scoring leaf.

- • least-to-most ( Zhou et al., 2023 ) : a first call decomposes the question into sub-problems; subsequent calls solve them in order, each conditioned on prior answers.

- • chain-of-verification (CoVe) ( Dhuliawala et al., 2024 ) : produce a draft answer, generate verification questions about it, answer those independently, and revise if any verification disagrees.

- • self-discover ( Zhou et al., 2024 ) : the model first selects and composes a custom reasoning structure (decomposition, verification, etc.) from a fixed pool, then applies that structure to the input.

- • self-refine ( Madaan et al., 2023 ) : a feedback-and-revise loop in which the model critiques its own draft and rewrites it; we cap the loop at three rounds.

- • vanilla-agent: an OpenHands ReAct loop with the TerminalTool and FileEditorTool only, no extra prompt scaffolding.

- • agent-code: the same agent but the prompt instructs the model to write and execute Python via the terminal tool, so numeric/code-heavy steps are grounded in actual computation.

- • multi-agent-debate ( Du et al., 2024 ) : $3$ agents propose answers, then in $2$ subsequent rounds each agent sees the others’ answers and revises; the final majority vote is returned.

- • MetaGPT ( Hong et al., 2024 ) : a role-based pipeline (planner, executor, reviewer) that hands a structured artifact between roles; we use the open-source role prompts unchanged.

- • AutoGen ( Wu et al., 2023 ) : a two-agent conversable setup (assistant + user-proxy with tool-use) that converses until the assistant emits a termination signal.

- • chain-of-agents (CoA) ( Zhang et al., 2024 ) : a chain of worker agents each summarises a slice of the input and passes a hand-off message to the next; a final manager agent answers from the chain.

- • reflexion ( Shinn et al., 2023 ) : an outer loop that, on failure, asks the model to write a verbal self-reflection and retries with the reflection appended to the next prompt.

- • monte-carlo-vote / shortlist-vote: two self-consistency variants—the first samples $5$ traces and returns the strict majority (resampling on a tie), the second pre-filters to a top- $10$ shortlist before a $3$ -way vote—used to test whether voting beyond the standard $3$ samples helps.

All baselines run on the same Qwen3 executors and the same OpenHands tool sandbox ( TerminalTool + FileEditorTool only) with no internet access, identical to Strategist strategies. Each baseline is evaluated independently at every one of the six tier/mode configurations, but baselines do not internally route across tiers within a single run; the ability to mix tiers within one strategy is part of the design space Strategist searches over, and BL is the single-config cell most accurate on the training split.


#### A.3 Data Split and Scaling

Every benchmark is partitioned into four disjoint subsets: training , validation , hidden , and test . The training set is what the strategist sees in full, including per-sample reasoning traces, when proposing the next iteration’s slate. The validation set is also evaluated each iteration but only aggregate scores are visible, mirroring standard train/val practice. The validation and hidden sets are used to pick the final strategy across all $N$ iterations (Algorithm 1 ); the hidden set is never shown to the strategist; in particular, experience notes written back to the library are derived from training-set traces only, so hidden-set signal cannot leak across iterations or to future tasks. The test set is held out from the search loop entirely and is used only for the final number reported in the main text.


##### Sizes and caps.

The development rows of each benchmark come from a separate development pool (300 rows where available), drawn deterministically with a fixed seed and split into training, validation, and hidden sets of $100$ rows each; benchmarks with smaller pools scale all three down proportionally, and AIME 2024 and Amazon-Rec, whose questions are about $10\times$ longer to solve, use $50$ rows per split. Where a benchmark’s own pool was too small, it was extended: COPA and SVAMP with rows from their official training data, and AIME with the 299 problems of AIME 2014–2023. The test set is around the first $200$ rows of each benchmark’s test file, disjoint from all development rows and never seen during search. Six benchmarks have fewer questions due to limit data. Splits are deterministic, so reruns and ablations operate identically.


#### A.4 Search, Library, and Models


##### Search loop.

Each iteration proposes $K=5$ candidate strategies; the search runs for $N=10$ iterations per benchmark. Every iteration must include at least one candidate of each kind ( new , composed , reuse ) and of each target ( accuracy : beat BL’s accuracy within its cost; efficiency : hold its accuracy at lower cost; balanced ); slates that violate this rule, deduplicate a recent candidate, or omit required JSON fields are rejected and the strategist is re-prompted. The strategist is shown the baseline matrix measured on the training split (every baseline at all six configurations, with BL highlighted) and the 2% rule by which candidates are judged; it keeps one session across iterations, so later iterations send only the new results. Each LLM call from a strategy uses max_tokens=16384 . A full search evaluates about 60 candidates per benchmark ( $K{=}5$ per iteration plus the reference and repairs), each on all three development splits, roughly $20{,}000$ candidate-sample executions for a benchmark with $100$ rows per split, plus about $135$ k prompt tokens and $45$ k response tokens for the strategist (about $10$ k prompt tokens per iteration), so the search dominates the per-task cost and amortises across future tasks via library reuse (Section 5 ).


##### Deduplication.

Two blueprints are considered duplicates if their execute function bodies hash to the same value after task-specific string literals (prompts, format instructions) are elided; this is computed over the Python AST so that whitespace and comment changes do not produce spurious distinctions. Duplicate proposals are rejected at submission time and not added to the library.


##### Strategist proposal format.

Each iteration the strategist returns Python code (the candidate strategies) followed by a JSON block describing the slate. The JSON has six required fields per candidate ( name , kind , target , tier_mode_anchors , why , builds_on ) and an optional prompts field that replaces a blueprint’s prompt texts for this task, plus three search-side fields ( search_queries , read_cards , experience ). A non-fatal AST audit checks that builds_on matches the imports in the code block; warnings are fed into the next iteration’s prompt rather than killing the run.


##### Library retrieval.

At each iteration the strategist issues two textual queries against the library: a relevance query summarising what the current task is asking for, and an inspiration query phrased to deliberately drift from the task description (e.g., asking for “multi-path verification on long-context QA” when the task itself is short-form math). Each query is scored by a hybrid function $s=\alpha\,s_{\text{tfidf}}+(1-\alpha)\,s_{\text{emb}}$ over every blueprint’s index entry, where $s_{\text{tfidf}}$ is computed over the blueprint name, one-line description, when-to-use field, and trait tags, and $s_{\text{emb}}$ is the cosine similarity between the query and a sentence-transformer ( all-MiniLM-L6-v2 ) embedding of the blueprint’s measurement card and experience notes; we use $\alpha=0.4$ throughout. Each query returns its top- $5$ blueprints, deduplicated against blueprints already returned by the relevance query so the inspiration slate cannot overlap. The strategist sees a total of $10$ blueprints per iteration (5 relevance hits with their measurement cards rendered in full, 5 adjacent inspirations with only the one-line description shown) and is asked, in the prompt, to use the relevance hits as composition or reuse candidates and the inspiration hits as material for new blueprints.


##### Library size.

After the 30 main searches, the library contained $1{,}865$ blueprints (deduplicated by structural hash) with measurement cards (cards are written only after a blueprint has been evaluated at least once). Of these, the strategist chose only those with relevance scores above a fixed threshold during retrieval; on average, $5$ relevance hits and $5$ adjacent inspirations were returned per query.


##### Models.

The executor LLMs are Qwen3-0.6B ( fast tier), Qwen3-1.7B ( balanced ), and Qwen3-4B ( complex ), each available in nothink and thinking modes for a total of six configurations; cross-model transfer (Section 5 , Appendix A.7 ) maps each tier to GPT-5 (nano, mini, full) or Gemini-2.5 (flash-lite, flash). The strategist agent is GPT-6 ( gpt-6-sol ), accessed through the Codex CLI. All five comparison frameworks in the cross-framework table use the same strategist and executor as Strategist for fairness.


##### Infrastructure.

The Qwen3 executors are served via vLLM on a local cluster of $8\times$ NVIDIA H200 GPUs (144 GB each). Agent-tier strategies execute through OpenHands with TerminalTool and FileEditorTool only; we cap subprocess concurrency at 48 to avoid timeouts. All hyperparameters above are fixed across the 30 main benchmarks, the 10 one-shot held-out benchmarks, and the cross-model transfer experiments.

### Appendix D Extended Related Work

This appendix expands the three Related Work paragraphs in the main text. Citations are identical; only the discussion is longer.


##### LLM agents.

Large language models have rapidly evolved from single-call question answerers into multi-step agent systems. Chain-of-thought prompting ( Wei et al., 2022 ) and self-consistency decoding ( Wang et al., 2023 ) showed that intermediate reasoning steps improve accuracy on complex tasks. Tree of Thoughts ( Yao et al., 2023a ) extended this to deliberate search over reasoning paths. ReAct ( Yao et al., 2023b ) interleaved reasoning with tool use, and Toolformer ( Schick et al., 2023 ) taught models to call external APIs autonomously. Reflexion ( Shinn et al., 2023 ) introduced verbal self-reflection as a feedback mechanism. Multi-agent frameworks such as AutoGen ( Wu et al., 2023 ) enabled conversational collaboration among multiple LLM agents. Formal representations for these systems range from state machines ( Wu et al., 2024 ) to declarative compilation ( Khattab et al., 2024 ) to optimizable computational graphs ( Zhuge et al., 2024 ) . A recent survey ( Yue et al., 2026 ) organizes this landscape as agentic computation graphs, distinguishing static, pre-execution, and in-execution optimization. As these systems grow more complex, the strategy layer that determines how models are called, in what order, and with what verification has become the central design bottleneck. Strategist addresses this bottleneck by automating the design of the strategy layer itself.


##### Automated design of agentic systems.

Structure search methods write strategies as raw code ( Hu et al., 2025 ) or compose them from fixed components ( Zhang et al., 2025c ) or predefined modules ( Shang et al., 2025 ; Zhang et al., 2025a ) ; the first yields isolated programs, the second bounds what strategies can be discovered. Optimization methods refine one strategy per task, by reinforcement learning ( Li et al., 2024 ; Zhang et al., 2026 ; Gao et al., 2025 ) or by LLM-driven evolution and refinement ( Gao et al., 2024 ; Liu et al., 2025a ) , and start over on the next task. Routing methods train controllers to select among existing strategies ( Taparia et al., 2026 ; Yue et al., 2025 ) without constructing them ( Zhang et al., 2025b ) . Strategist differs by allowing freeform creation through the Strategy Blueprint, requiring no training, constructing strategies itself, and routing across model tiers within each strategy.


##### Cross-task transfer and experience accumulation.

Transferring knowledge across tasks has been studied through meta-learning ( Finn et al., 2017 ; Hospedales et al., 2022 ) , neural architecture search ( Elsken et al., 2019 ) , and prompt optimization ( Yang et al., 2024 ) . In the LLM agent setting, ExpeL ( Zhao et al., 2024 ) extracts reusable insights from agent experiences, Voyager ( Wang et al., 2024 ) grows a skill library as it explores new environments, and recent work has formalized this direction as lifelong learning for LLM agents ( Zheng et al., 2025 ) . Despite this, automated system design methods ( Hu et al., 2025 ; Zhang et al., 2025c ) still optimize per task independently. Strategist maintains a shared library of blueprints and their measured properties that grows with every task, providing both relevant components (exploitation) and diverse inspiration from other tasks (exploration). To our knowledge, it is the first system for automated strategy design that accumulates knowledge across tasks.
