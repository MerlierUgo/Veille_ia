## How Much Can Tool Calls Reveal About You? Privacy Leakage from Tool-Call Traces

Large language model (LLM)-based agents interact with external tools through protocols such as the Model Context Protocol (MCP), producing tool-call traces that may expose behavioral signals about users. In this work, we systematically study the risk of user-profile inference from MCP tool-call traces, where observers infer user attributes from protocol-valid tool interactions without access to user conversations. We introduce PrivacyTrace, a benchmark containing 1,000 synthetic user profiles and 4,000 agent trajectories across four domains, generated with real MCP tools from 25 servers. Experiments with four mainstream LLM attackers show that tool-call traces enable a 26.25% attack success rate for profile inference, compared with 17.97% from prior-based guessing. Further analysis reveals that tool arguments and returned results provide the main trace-grounded evidence, while linking traces across sessions further amplifies profiling risk. These findings demonstrate that MCP tool-call traces can act as effective behavioral side channels for user profiling, motivating the development of privacy-aware mechanisms for agent-tool interactions. Code and data are available at https://github.com/AI45Lab/PrivacyTrace .


### 1 Introduction

Large language model (LLM)-based agents increasingly serve as intermediaries between users and external services. To fulfill a request, an agent converts user instructions into tool selections, tool arguments, and sequences of tool invocations ( Yao et al., 2022 ; Schick et al., 2023 ; Qin et al., 2024 ) . The Model Context Protocol (MCP) standardizes interactions between agents and remote tool servers ( Anthropic, 2024 ) . These interactions generate tool-call traces containing tool names, arguments, returned results, and call sequences. Remote servers can observe the calls they serve, even without access to user conversations or agent reasoning. This raises a privacy question: what user information can an observer infer from an agent’s tool-call traces?

> Figure 1 : Tool-call traces as a privacy side channel. In this example, geocoding results and patterns in requested travel times and transport modes may support inferences about the user’s location, health condition, and religious affiliation.

We observe that tool-call traces generated by MCP-based agents can reveal user attributes beyond explicit disclosures . The example in Figure 1 illustrates how legitimate tool-call traces can reveal behavioral signals that may support inference of sensitive user attributes, such as religious beliefs and health conditions. Such inference represents a fundamental privacy risk, as it allows observers to uncover user attributes that are neither directly disclosed nor necessary for completing the intended task. Existing studies on agent privacy have mainly examined task-level risks, including unnecessary acquisition of sensitive data ( Zhang et al., 2026 ) , inappropriate disclosure ( Shao et al., 2024 ; Wang et al., 2025 ; Hu et al., 2026 ) , and inference of immediate user intent from tool interactions ( Yao et al., 2025 ) . However, whether MCP tool-call traces can serve as behavioral footprints that reveal persistent user attributes and enable profile inference remains unexplored.

In this paper, we propose PrivacyTrace , a benchmark for systematically evaluating profile inference from MCP-based agent tool-call traces. PrivacyTrace models this problem as an observer attempting to recover a user’s latent profile from protocol-valid agent interactions. The benchmark contains 1,000 population-informed synthetic user profiles and 4,000 agent trajectories across four domains: travel, health, shopping, and career learning. Each profile includes 17 ground-truth attributes and is generated through controlled sampling and consistency validation, enabling evaluation without collecting sensitive real-user traces. For each profile and domain, we construct profile-conditioned tasks and execute them using real MCP tools from 25 servers, producing 67,950 tool-call records.

We implement the MCP agent using Pydantic AI ( Maan et al., 2025 ) and evaluate PrivacyTrace with four mainstream LLMs, including MiniMax-M3, DeepSeek-V4-Flash, GPT-5.5, and Gemini-3-Flash ( MiniMaxAI, 2026 ; DeepSeek-AI, 2026 ; OpenAI, 2026 ; Google DeepMind, 2025 ) . Our experiments show that MCP tool-call traces can enable profile inference beyond prior-based guessing: the average attack success rate (ASR) increases from 17.97% to 26.25% when trace evidence is available. We further analyze this phenomenon from four perspectives. Trace channels: tool arguments and returned results provide the most informative signals, improving ASR by 13.18 and 10.01 percentage points, respectively, over metadata and call sequences alone. Trace visibility: linking more user activities leads to stronger inference, with cross-domain traces achieving 32.77% ASR compared with limited observations from individual servers. Attribute recovery: traces reveal diverse user attributes, although highly specific identifiers remain difficult to infer, with only 35 correct predictions among 16,000 identifier slots. Inference protocol: attributes inferred from traces can further improve recovery of remaining profile information, increasing unresolved-attribute accuracy by 3.30 percentage points over prior-based guessing, while a two-stage inference strategy achieves comparable performance to one-shot inference.


##### Contributions.

- • We identify and formalize profile inference from agent tool-call traces as a privacy risk in MCP-based agents, showing that protocol-valid interactions can reveal user attributes beyond explicit task information.

- • We introduce PrivacyTrace , a benchmark with population-calibrated synthetic users and realistic MCP-based agent trajectories.

- • We systematically investigate the prevalence of profile inference risks across diverse observer scopes, trace channels, application domains, user attributes, and attacker settings.


### 2 Related Work


#### 2.1 Agent Security & Privacy

Tool use expands agent security beyond harmful model outputs to actions over external systems and data from untrusted sources. ToolEmu probes risky tool use, AgentDojo evaluates indirect prompt injection, and ASB benchmarks attacks and defenses across prompts, tools, and memory ( Ruan et al., 2024 ; Debenedetti et al., 2024b ; Zhang et al., 2025a ) . ATBench and AgentDoG extend this line to long-horizon trajectories and trajectory-level guardrails ( Li et al., 2026 ; Liu et al., 2026 ) . Agent privacy work focuses on whether sensitive data is acquired, used, or transmitted according to context, purpose, and necessity. ConfAIde, PrivacyLens, and Privacy in Action evaluate contextual judgments and agent actions; AirGapAgent and AgentDAM study data minimization ( Mireshghallah et al., 2024 ; Shao et al., 2024 ; Wang et al., 2025 ; Bagdasarian et al., 2024 ; Zharmagambetov et al., 2025 ) . PrivacyPeek and ToolPrivacyBench audit acquisition and purpose-bound transmission, while tool-schema and web-agent studies expose oversharing ( Zhang et al., 2026 ; Hu et al., 2026 ; Shayesteh & Wilson, 2026 ; Roh et al., 2026 ) . These works examine whether agents acquire or transmit sensitive data; we study how legitimate tool traces become evidence for hidden attributes without malicious tools or access to the underlying conversation.


#### 2.2 Privacy Inference Attacks

Privacy inference attacks recover private traits from indirect evidence rather than explicit disclosure ( Li et al., 2024 ) . Classical attacks exploit search logs, sparse ratings, and social-media reactions ( Adar, 2007 ; Narayanan & Shmatikov, 2008 ; Kosinski et al., 2013 ) ; LLMs extend inference to unstructured posts, discussions, and public activity ( Staab et al., 2024 ; Yukhymenko et al., 2024 ; Du et al., 2026 ) . Private cues can survive entity removal, motivating attacker-guided anonymization methods including RUPTA, SEAL, and RLAA ( Staab et al., 2025 ; Yang et al., 2025 ; Kim et al., 2025 ; Duan et al., 2026 ; Li et al., 2023 ) .

This literature primarily studies user-authored content, while agent traces provide a different evidence source. IntentMiner reconstructs current requests from semantic MCP tool calls ( Yao et al., 2025 ) . At the network layer, Jeong et al. infer prompts and persistent user traits from domain-access and timing metadata of web and research agents, while AgentPrint profiles agent activities and user attributes from encrypted traffic fingerprints ( Jeong et al., 2025 ; Zhang et al., 2025b ) . Neither line studies profile inference from the semantic tool-call records exposed to MCP servers. TOP-R instead studies conclusions composed from tool results and disclosed in agent responses ( Qiao et al., 2025 ) . These attacks instantiate privacy side channels beyond direct model outputs ( Debenedetti et al., 2024a ) . In PrivacyTrace, we evaluate persistent, multi-attribute profile inference from MCP tool-call traces.


#### 2.3 Synthetic Privacy Datasets

Evaluating privacy inference requires private labels paired with observable behavior, but privacy regulations, consent requirements, and data-governance constraints make such real-user datasets difficult to collect, share, and reuse ( European Union, 2016 ; State of California, 2018 ; U.S. Department of Health and Human Services, 2018 ) . Synthetic data therefore provide a practical alternative. SynthPAI simulates users and their discussions, while demographic prompting and persona backstories offer broader ways to generate synthetic human samples ( Yukhymenko et al., 2024 ; Argyle et al., 2023 ; Moon et al., 2024 ) . Purely LLM-generated populations can underrepresent groups, reproduce stereotypes, distort demographic distributions, and suppress population-level variation ( Santurkar et al., 2023 ; Cheng et al., 2023 ; Moon et al., 2024 ; Bisbee et al., 2024 ) . Population synthesis offers another approach by constructing micro-level records from aggregate statistical constraints ( Beckman et al., 1996 ) . PrivacyTrace combines population statistics and LLM-based consistency checking with real MCP executions to construct observable trajectories without collecting sensitive real-user data.


### 3 Problem Formulation


#### 3.1 System Architecture

We consider a user interacting with a tool-augmented agent who has a latent profile $P=(p_{1},\ldots,p_{d})$ of $d$ attributes that may shape their preferences, needs, and constraints. The agent receives dialogue and runtime context, invokes tools from a predefined catalog, routes requests to external servers, and uses their outputs in subsequent reasoning.

Each task execution produces an agent trajectory, from which we extract an ordered tool-call trace:

[Tableau] $$T=(c_{1},\ldots,c_{n}),\qquad c_{i}=(e_{i},t_{i},a_{i},r_{i}),$$ (1)

where $n$ denotes the number of tool calls. For each call $c_{i}$ , $e_{i}$ denotes the server endpoint, $t_{i}$ the tool name and visible documentation, including its schema, $a_{i}$ the invocation arguments, and $r_{i}$ the tool response, which contains either a returned result or an error. The trace preserves server provenance but excludes user–agent dialogue and internal reasoning that are not exposed through tool calls. The architecture in Figure 2 summarizes this threat model.


#### 3.2 Threat Models

We consider semi-honest observers that faithfully execute their assigned functions while retaining legitimately accessible tool-call traces for passive profile inference. An observer may deploy an inference model to analyze retained traces and infer the latent profile $P$ , and the amount of information available to an observer depends on its position in the tool-use infrastructure. Therefore, we distinguish two observer scopes:

- 1. Local Observer: A service provider, such as an MCP server, observes only calls routed to its own endpoint.

- 2. Global Observer: A centralized gateway or platform observes the full task trace $T$ . With sessions linked by a persistent user identity, it can aggregate $D$ task traces:

> Figure 2 : System architecture.

[Tableau] $$\mathcal{T}^{(1:D)}=T^{(1)}\oplus\cdots\oplus T^{(D)},$$ (2)

where $T^{(j)}$ is task $j$ ’s trace for the same user and $\oplus$ concatenates linked sessions.

In the experiments, we refer to these inputs as local-server views , single-domain views , and linked four-domain views , corresponding respectively to one server’s visible calls, one complete task trace, and four linked domain traces.


#### 3.3 Profile Inference Model

We formulate profile inference as forced prediction over an attribute schema $\mathcal{S}=\{(k,\mathcal{V}_{k})\}_{k=1}^{d}$ , where $\mathcal{V}_{k}$ is the admissible value space of attribute $k$ and $p_{k}\in\mathcal{V}_{k}$ is its ground-truth value. The schema specifies attribute meanings and output granularity; it does not expose the user’s values.

An observation configuration $\omega$ specifies the observer scope and retained trace channels. The observation operator $O_{\omega}$ maps the available trace records to the attacker-visible input:

[Tableau] $$X_{\omega}=O_{\omega}(T)\quad\text{or}\quad X_{\omega}=O_{\omega}(\mathcal{T}^{(1:D)}).$$ (3)

Let $f_{\theta}$ denote the one-shot (OS) profile inference attacker with model parameters $\theta$ . It predicts every attribute in a single pass:

[Tableau] $$\widehat{P}^{\mathrm{OS}}_{\omega}=f_{\theta}(X_{\omega},\mathcal{S}).$$ (4)

The prior-based baseline $b_{\theta}$ receives only the attribute schema $\mathcal{S}$ and no user-specific observations, producing $\widehat{P}^{0}=b_{\theta}(\mathcal{S})$ . This baseline measures prior-based guessing under the same evaluation protocol. All inference functions share the LLM parameters $\theta$ and use fixed, stage-specific prompting and decoding protocols.


##### Trace-supported attribute selection.

In the first step, the attacker $h_{\theta}$ selects attributes supported by the observed trace and proposes values for them, leaving the remaining attributes unresolved:

[Tableau] $$(M_{\omega},\widetilde{P}_{\omega})=h_{\theta}(X_{\omega},\mathcal{S}),$$ (5)

where $M_{\omega}\in\{0,1\}^{d}$ is a selection mask and $M_{\omega,k}=1$ indicates that attribute $k$ is selected as trace-supported. The selected attribute–value pairs form the partial profile $\widetilde{P}_{\omega}=\{(k,\widetilde{p}_{\omega,k}):M_{\omega,k}=1\}$ , where $\widetilde{p}_{\omega,k}$ is the value proposed by the first-stage attacker for attribute $k$ . Selection coverage is the proportion of selected attributes, and selection precision is their prediction accuracy against the ground truth.


##### Partial-profile completion.

The second-stage attacker $g_{\theta}$ receives only $\widetilde{P}_{\omega}$ and the schema, without the original trace. We implement this two-step inference model as a two-stage (TS) attack, which predicts unresolved attributes while retaining the selected values:

[Tableau] $$\widehat{p}^{\mathrm{TS}}_{\omega,k}=\begin{cases}\widetilde{p}_{\omega,k},&M_{\omega,k}=1,\\ [g_{\theta}(\widetilde{P}_{\omega},\mathcal{S})]_{k},&M_{\omega,k}=0,\end{cases}$$ (6)

where $[\cdot]_{k}$ denotes the generated value of attribute $k$ . The complete prediction is $\widehat{P}^{\mathrm{TS}}_{\omega}=(\widehat{p}^{\mathrm{TS}}_{\omega,k})_{k=1}^{d}$ .

We evaluate whether trace-grounded selection concentrates correct predictions and whether conditioning on selected values improves completion over prior-based guessing on the same unresolved targets. Comparing $\widehat{P}^{\mathrm{TS}}_{\omega}$ with $\widehat{P}^{\mathrm{OS}}_{\omega}$ assesses how closely the two-stage attack matches one-shot inference in overall accuracy and overlap in correctly inferred attributes.

### 4 Methodology

The pipeline in Figure 3 first constructs population-calibrated synthetic profiles and profile-conditioned scenarios, then executes agent tasks through real MCP tools to generate interactive trajectories. We extract observer-visible tool-call traces from these trajectories and compare prior-based guessing with one-shot and two-stage profile inference.


#### 4.1 Synthetic Dataset Construction

Profile synthesis. To retain realistic aggregate structure and exact attribute labels, we sample profile candidates from a mixture of target-informed and uniform proposals:

[Tableau] $$Z_{i}\sim\lambda\pi_{\mathrm{target}}+(1-\lambda)\pi_{\mathrm{unif}},$$ (7)

where $\pi_{\mathrm{target}}$ is the target-informed proposal, $\pi_{\mathrm{unif}}$ is the uniform proposal over the candidate support, and $\lambda\in[0,1]$ controls their mixture. An LLM consistency reviewer filters inconsistent candidates. We then generate synthetic identifiers without changing the structured attributes and use targeted generation to fill unsupported positive-mass cells. After schema, identifier, uniqueness, and support checks, the valid candidate pool is $\mathcal{C}=\{P_{i}\}_{i=1}^{K}$ .

Statistical calibration. Candidate coverage alone does not recover population composition, so we fit $\mathcal{C}$ to 25 low-dimensional margins using iterative proportional fitting (IPF) ( Deming & Stephan, 1940 ; Ireland & Kullback, 1968 ; Fienberg, 1970 ; Beckman et al., 1996 ) . Margins are derived primarily from official aggregates released by UN DESA, the World Bank, UNESCO, and ILOSTAT. Appendix B.2 documents every target family and source.

Let $\mu$ index the fitted margins, $b_{\mu}(P_{i})$ be the cell occupied by candidate $P_{i}$ , and $q_{\mu}(b)$ its target mass. Starting from $w_{i}^{(0)}=1$ , IPF updates each candidate weight as

[Tableau] $$\widehat{q}_{\mu}^{(t)}(b)=\frac{\sum_{i:b_{\mu}(P_{i})=b}w_{i}^{(t)}}{\sum_{i=1}^{K}w_{i}^{(t)}},\qquad w_{i}^{(t+1)}=w_{i}^{(t)}\frac{q_{\mu}(b_{\mu}(P_{i}))}{\widehat{q}_{\mu}^{(t)}(b_{\mu}(P_{i}))}.$$ (8)

Here, $t$ indexes updates and $\widehat{q}_{\mu}^{(t)}$ is the induced mass for margin $\mu$ under the current weights. We sample $N$ unique profiles $\mathcal{P}_{N}=\{P_{j}\}_{j=1}^{N}$ using the final weights. Appendix B.1 reports generation, sampling, and IPF diagnostics.

Scenario construction. For each profile–domain pair $(P_{j},\delta)$ , we construct a profile-conditioned scenario before agent execution, where $\delta\in\Omega$ and $\Omega=\{\text{travel},\text{health},\text{shopping},\text{career learning}\}$ . Let $\mathcal{L}_{\delta}$ denote the full tool catalog for domain $\delta$ . At planner attempt $a$ , a candidate subset $\widetilde{\mathcal{L}}_{j,\delta}^{(a)}\subseteq\mathcal{L}_{\delta}$ is formed by independently including each tool with a fixed probability.

The scenario planner receives the complete profile $P_{j}$ , the domain specification, and the schemas of $\widetilde{\mathcal{L}}_{j,\delta}^{(a)}$ . It either rejects the draw or returns a structured user task $Q_{j}^{\delta}=\bigl(g_{j}^{\delta},\kappa_{j}^{\delta},\mathcal{R}_{j}^{\delta},y_{j}^{\delta}\bigr)$ , where $g_{j}^{\delta}$ is the task goal, $\kappa_{j}^{\delta}$ the user-facing context, $\mathcal{R}_{j}^{\delta}$ the constraints, and $y_{j}^{\delta}$ the expected result. The planner excludes personal identifiers, unrelated sensitive information, and tool-execution instructions from the user task. It also produces a hidden tool plan specifying the selected tools, their intended order, and required input bindings. The validator checks that selected tools form a nonempty subset of the candidate draw and that all required bindings are present; rejected or invalid draws are resampled within a fixed attempt budget. Appendix B.1 provides the scenario-generation settings. Each accepted draw yields $S_{j}^{\delta}=\bigl(\delta,Q_{j}^{\delta}\bigr)$ . The hidden plan is retained for generation-time auditing; the user simulator and evaluated agent do not see it, and it does not constrain the agent’s runtime tools.

Interactive trajectory generation. The user simulator $U$ is privately conditioned on $(P_{j},Q_{j}^{\delta})$ and generates task-consistent messages. The evaluated agent $\mathcal{A}$ observes only the exchanged conversation and can use the full domain catalog $\mathcal{L}_{\delta}$ , including tools outside the planner’s candidate subset. The resulting trajectory and its extracted tool-call trace are

[Tableau] $\displaystyle\tau_{j}^{\delta}=\operatorname{Rollout}\bigl(U(P_{j},Q_{j}^{\delta}),\mathcal{A},\mathcal{L}_{\delta}\bigr),\quad T_{j}^{\delta}=\operatorname{Extract}(\tau_{j}^{\delta}).$ (9)

Each trajectory contains user–agent interactions and tool executions. The extracted trace retains server and tool metadata, invocation arguments, returned results, errors, and call order. This yields four scenario–trace pairs per profile:

[Tableau] $$\mathcal{D}_{\mathrm{PT}}=\left\{\left(P_{j},\left\{(S_{j}^{\delta},T_{j}^{\delta})\right\}_{\delta\in\Omega}\right)\right\}_{j=1}^{N}.$$ (10)


#### 4.2 Inference Attack Design

Trace preparation. From each rollout, we retain the ordered tool-call trace rather than the user–agent dialogue. For an observation configuration $\omega$ , $O_{\omega}$ selects the calls and channels available in a local-server, single-domain, or linked four-domain view. We serialize the resulting $X_{\omega}$ using a lossless catalog representation: visible tool definitions appear once, followed by ordered call events that reference them. This preserves server provenance, arguments, returned results, errors, and call order without repeating tool documentation. Appendix A.2 provides serialization details.

Inference protocols. The right panel of Figure 3 shows three prediction paths over the same attribute schema $\mathcal{S}$ . Prior-based guessing receives only $\mathcal{S}$ and provides a no-trace reference, while one-shot inference predicts every attribute directly from $(X_{\omega},\mathcal{S})$ . In the two-stage attack, Stage 1 selects trace-supported attributes, proposes their values, and records evidence, forming the partial profile $\widetilde{P}_{\omega}$ . Stage 2 receives only $\widetilde{P}_{\omega}$ and $\mathcal{S}$ , predicts the unresolved attributes, and merges these completions with the retained Stage-1 values. All three paths output a complete profile, allowing them to be evaluated with the same attribute-level scoring rules. Appendix D.3 provides the prompt skeletons.


### 5 Experiments

Our experiments answer three research questions:

RQ1: How Much Profile Information Do Tool-Call Traces Reveal?

RQ2: Which Trace Channels Drive Profile Inference?

RQ3: How Well Does the Two-Step Model Account for One-Shot Inference?


#### 5.1 Experimental Setup

Each of the 1,000 profiles contributes one trajectory in each of four domains, yielding 4,000 trajectories and 67,950 tool calls. With 17 target attributes per profile, the default single-domain evaluation has 68,000 view–attribute slots; each trajectory contributes equally regardless of its call count. Let $\mathcal{E}$ be the evaluated set of view–attribute pairs $(u,k)$ , where $u$ indexes an observer-visible input, $p_{u,k}$ is its user’s true value, and $\widehat{p}_{u,k}$ is the prediction. We define the average attack success rate (ASR) over this set as

[Tableau] $$\operatorname{ASR}(\mathcal{E})=\frac{1}{|\mathcal{E}|}\sum_{(u,k)\in\mathcal{E}}C_{k}(\widehat{p}_{u,k},p_{u,k}),$$ (11)

where $C_{k}$ is one when the prediction satisfies the attribute-specific scoring rule and zero otherwise. A hybrid scorer applies deterministic attribute-specific rules, then uses GLM-5.2 for unresolved semantic cases, without trace access. Uncertain or exhausted judge outcomes count as incorrect. Appendix A.3 gives all 17 attributes and scoring rules. Failed or unparseable generations remain in the denominator and are scored as incorrect. DeepSeek-V4-Flash is the default attacker model; generation and judging models are listed in Appendix A.1 .

For local-server evaluation, we retain 10,645 nonempty server views; Appendix C.3 gives the view construction and paired comparison details. The main comparisons test trace access and observer scope (RQ1), visible trace channels (RQ2), and inference protocol (RQ3), using the same target attributes and scoring rules. Our reference condition is prior-based guessing: the attacker only receives the attribute definitions. Each trace condition exposes only records available to the stated observer. By default, we use the lossless catalog serialization described in Section 4.2 . Appendix C.1 compares this representation with raw trace serialization.


#### 5.2 RQ1: How Much Profile Information Do Tool-Call Traces Reveal?

Tool-call traces reveal user-specific profile information beyond prior-based guessing. The trace-access comparison in Figure 4(a) shows that single-domain access raises ASR from 17.97% to 26.25% under the same forced-prediction protocol, an 8.28-point gain. The remaining panels of Figure 4 place this gain alongside observer scope and visible-call volume.

Broader observer access is associated with higher ASR. Across the observer scopes in Figure 4(b) , pooled ASR is 24.24% for local-server views, 26.25% for single-domain views, and 32.77% for linked four-domain views. Because these pooled summaries use different view populations, we separately perform a paired comparison, which shows a 3.09-point gain from local-server to single-domain visibility (Appendix C.3 ). This within-task gain suggests that profile clues are spread across calls to different servers, allowing a domain-wide observer to combine evidence that individual servers see only in part.

The visible-call analysis in Figure 4(c) shows an association between call count and inference success. ASR rises from 20.87% for views with 1–5 calls to 29.26% for those with 21–40 calls. The 41+ bin deviates from this trend, reaching 27.43%, but contains only 101 views and a different mixture of tasks and servers. Because these bins arise from naturally occurring trajectories rather than controlled trace prefixes, we interpret the result as an association rather than a causal effect of trace length. Appendix C.2 reports the complete bin counts and failure accounting.

The comparison in Table 1 evaluates four LLM attackers on the same 4,000 single-domain views. ASR remains within 25.29–28.32%, indicating that the observed profile leakage is not specific to the default attacker. DeepSeek-V4-Flash is considered as the default attacker because it achieves comparable ASR at substantially lower estimated cost. Appendix C.4 reports token usage, rates, and failures.

#### 5.3 RQ2: Which Trace Channels Drive Profile Inference?

> Figure 6 : ASR by channel.

The channel ablation in Figure 6 shows that argument and result content carry more profile information than metadata and call order alone. The shared metadata-and-sequence baseline reaches 14.53% ASR. Adding arguments raises ASR to 27.71%, a 13.18-point gain over the baseline, while adding returned results reaches 24.54%, a 10.01-point gain. The argument-added condition exceeds the result-added condition by 3.17 points. Arguments record the entities, constraints, locations, and queries the agent chooses to send; returned results can confirm these signals but may also contain alternatives that do not describe the user.

Metadata and call order alone score below schema-only prior-based guessing (14.53% versus 17.97%), so the measured gain in this setting comes from semantic content rather than call structure. The argument-added condition omits returned results yet reaches 27.71% ASR: requests sent to tools already expose substantial profile information without access to returned result bodies.

These channel gains are not simply additive. The complete trace reaches 26.25% ASR, 1.46 points below the argument-added condition and 1.71 points above the result-added condition. Thus, exposing returned results alongside arguments does not improve aggregate ASR in this comparison. The channel ablations measure the net value of each input condition; aggregate ASR alone cannot distinguish overlapping evidence from result content that complicates the attacker’s predictions.

On the 56,179 unresolved slots from non-failed two-stage views, Figure 7(a) shows that conditioning on $\widetilde{P}_{\omega}$ raises completion ASR from 18.48% under prior-based guessing on the identical subset to 21.78%, a 3.30-point gain; Appendix C.6 details the slot accounting. The correctness overlap in Figure 7(c) shows that 74.96% of correct two-stage predictions are shared with one-shot inference; together with near-matched ASR (25.83% vs. 26.25%), this supports the proposed behavioral account.


### 6 Limitations

Synthetic User Behavior: PrivacyTrace uses synthetic profiles and tasks to obtain labels without collecting private user records. Population calibration matches demographic margins to statistics but does not guarantee behavioral realism, motivating evaluation on consented user interactions.

Behavioral Interpretation: Our two-step formulation makes partial-profile selection and completion explicit and testable. Completion gains and shared correct predictions support this behavioral account, but do not show that one-shot attackers internally follow the same reasoning process.

Mitigation Effectiveness: Potential defenses include query obfuscation, reducing exposed tool-call content, and isolating sessions across services, but their effectiveness remains untested.


### 7 Conclusion

This paper introduces PrivacyTrace to systematically measure profile inference from MCP tool-call traces. Across 4,000 trajectories, single-domain trace access raises ASR from 17.97% under prior-based guessing to 26.25%, with arguments and returned results contributing the largest gains. Profile inference strengthens with broader observer access and cross-session linkage, while exact identifiers remain difficult to recover. A two-stage attack nearly matches one-shot accuracy, and conditioning on a trace-supported partial profile improves completion by 3.30 points over matched prior-based guessing, although Stage 2 also benefits from model priors. By separating trace channels from observer scope, PrivacyTrace reveals where profiling evidence accumulates and shows that routinely exposed tool-call traces can form a meaningful privacy side channel. These findings highlight trace content, retention, and linkage as concrete privacy concerns, motivating defenses such as obfuscating queries, minimizing exposed trace information, and limiting unnecessary cross-session linkage.

### Ethics statement

This work evaluates privacy inference using synthetic profiles, synthetic user tasks, and recorded executions against MCP tools; no real-user conversations or personal traces are collected. The inference pipeline could also be applied to retained operational logs. The retained research artifacts contain generation and evaluation code, aggregate results, and plotting scripts, but no real-user traces. The findings motivate limiting evidence-rich arguments and returned results, shortening trace retention, and restricting linkage across servers and domains.

### Appendix B Dataset Construction and Statistics


#### B.1 Generation and Sampling

We set $\lambda=0.9$ , generate 100,000 base candidates, and retain 96,538 candidates after validation. IPF runs for 500 iterations and yields a final maximum marginal $L_{1}$ discrepancy of 0.015620; the released benchmark contains $N=1000$ profiles.

Capacity checks require at least $\lceil Nq_{\mu}(b)\rceil$ candidates for each target cell $b$ , with backfill or failure otherwise. Sampling without replacement assigns candidate $i$ the key $\log(\xi_{i})/w_{i}$ , where $\xi_{i}\overset{\mathrm{iid}}{\sim}\mathrm{Uniform}(0,1)$ , and retains candidates with the largest keys.

For each profile–domain pair, each tool in the domain catalog is independently included in the candidate subset with probability $0.25$ . Rejected or invalid draws are resampled, with at most eight planner attempts per pair. Planner models and decoding settings are listed in Appendix A.1 , and the planner prompt is reproduced in Appendix D.2 .

#### C.6 Two-stage Implementation Details

The 68,000 attribute slots comprise 11,600 Stage-1 selections, 56,179 unresolved slots from non-failed two-stage views, and 221 slots from 13 failed views. On the same 56,179 unresolved slots, Stage 2 recovers 12,237 attributes (21.78% ASR), compared with 10,384 (18.48%) for prior-based guessing. Stage 1 contributes 5,324 correct predictions, so the final ASR is 25.83%; the two stages contribute 7.83 and 18.00 percentage points, respectively. All 221 failed slots are counted as incorrect in this fixed denominator; 11 of the 13 failures result from exceeding the input context limit.
