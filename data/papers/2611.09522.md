## Atik: A Shared-Mesh Transformer Accelerator for RISC-V

Transformer inference repeatedly invokes dense matrix multiplication and attention, including its data-dependent softmax normalization. We present Atik, an open-source RoCC accelerator for RocketChip that executes matrix multiplication and dense attention through one shared fixed-point MAC mesh. Atik accepts and returns BF16 tensors, uses a streaming online-softmax schedule that never materializes the full score matrix, and is invoked through a small descriptor-based ABI. We evaluate three meshes cycle-by-cycle on FireSim and report standalone Sky130 physical-design area. Across 137 logged FireSim test records, all tests pass their benchmark tolerance with zero reported output mismatches. Relative to the same scalar Rocket BF16 reference, the 8 $\times$ 8 configuration reaches 31.5 $\times$ peak matmul speedup and 225.8 $\times$ peak attention speedup. Hybrid projections for the single-layer workload-derived C models, using directly measured accelerator-kernel cycles, give aggregate speedups of 44.2 $\times$ , 77.1 $\times$ , and 32.3 $\times$ for ViT, TinyBERT, and GPT-2 prefill, respectively; these are not full-model hardware replays.


### 1. Introduction

The rapid, cross-domain adoption of transformer models has made a small number of compute kernels disproportionately important. Nearly every modern language and vision model is built on the same backbone, so the same operations dominate inference cost across otherwise unrelated workloads. Two kernels stand out: dense matrix multiplication, which drives the linear projections and feed-forward layers, and the attention mechanism, whose softmax normalization introduces data-dependent, non-linear work that general-purpose datapaths handle poorly. Where the bottleneck lies is not fixed. On a general-purpose core without specialized vector or matrix units, both dense matrix operations and software softmax can be costly. Dedicated matrix hardware can reduce the relative cost of matrix multiplication, exposing normalization and attention data movement as additional bottlenecks ( Milakov and Gimelshein, 2018 ; Stevens et al., 2021 ; Wang et al., 2025 ; Islamoglu et al., 2023 ) . Their relative costs depend on the platform, model, and sequence length. An accelerator that addresses only one of the two kernels leaves a substantial fraction of the workload on the slow path. The architecture community has responded with a large body of specialized hardware, but the resulting designs tend to cluster into a few shapes, each with a practical limitation. Many are standalone ASICs that accelerate attention or softmax as standalone blocks, rather than demonstrating the RoCC integration and shared memory-system interface targeted here ( Ham et al., 2020 ; Ham et al., 2021 ; Lu et al., 2021 ; Zhou et al., 2023 ) . Other work uses architectural full-system simulation rather than an FPGA execution of the integrated RTL ( Amirshahi et al., 2023 ) . A third group targets a single narrow operation, such as adding an exponential unit to a floating-point pipeline ( Wang et al., 2025 ) . Finally, most of these designs commit to quantized or integer datatypes such as INT8 ( Islamoglu et al., 2023 ; Marchisio et al., 2023 ) , or approximate softmax with lookup tables or powers of two, introducing numerical trade-offs that must be evaluated at the workload level ( Stevens et al., 2021 ; Wang et al., 2023 ) . The mature open-source DNN accelerators that predate the transformer era, such as Gemmini ( Genc et al., 2021 ) , were optimized for convolutional and matrix workloads rather than a dedicated streaming attention pipeline. Atik instead exposes a BF16 tensor interface around a fixed-point datapath for both matrix multiplication and attention.

The RISC-V ecosystem offers an underused integration point for exactly this kind of accelerator. RocketChip ( Asanović et al., 2016 ) exposes the Rocket Custom Coprocessor (RoCC) interface, through which a tightly-coupled accelerator can be attached alongside the main core and access the system memory hierarchy. Because RocketChip is generated with Chisel ( Bachrach et al., 2012 ) inside the Chipyard framework ( Amid et al., 2020 ) , the same design can be simulated at RTL, run cycle-accurately on an FPGA through FireSim ( Karandikar et al., 2018 ) , and pushed through a physical-design flow ( Liew et al., 2022 ) . This makes RoCC an attractive middle ground: an accelerator that is neither as heavyweight and isolated as a from-scratch ASIC, nor as limited as a pure instruction-set extension, and that can be exercised by real software running on a real core.

We present Atik , an open-source transformer accelerator that occupies exactly this middle ground. Atik attaches to RocketChip over RoCC and accelerates both matrix multiplication and attention with BF16 input/output. Its central design decision is a shared fixed-point MAC mesh that serves all three heavy operations—matmul ( $C\mathrel{+}=A\,B$ ), attention scoring ( $\mathrm{score}\mathrel{+}=Q\,K^{\top}$ ), and probability-value accumulation ( $O\mathrel{+}=P\,V$ )—rather than provisioning separate datapaths. Around this mesh, attention is executed with a streaming online-softmax schedule that never materializes the full score matrix, keeping only per-row running maxima and denominators as live state. Software drives the accelerator through a deliberately small descriptor-based ABI: it fills a descriptor with tensor pointers and shapes, issues a set-descriptor and a run command, and polls for completion, while the hardware owns all tiling, DMA, packing, conversion, softmax bookkeeping, and writeback. Atik is validated on two fronts that most prior work treats separately: it runs cycle-accurately on an AWS F2 FPGA through FireSim, and it has a preliminary standalone Sky130 area study.

This paper makes the following contributions:

- • A tightly-coupled, software-callable accelerator on a real core. Atik integrates directly into RocketChip over RoCC, is invoked from ordinary C software, and shares the core’s memory hierarchy, rather than existing as an isolated ASIC or a non-cycle-accurate simulation model.

- • A unified design for both transformer bottlenecks. A single shared fixed-point MAC mesh accelerates dense matmul, QK scoring, and the accumulation of probabilities against values, while a streaming softmax schedule handles the nonlinear normalization without ever storing the full score matrix. Atik therefore targets matrix multiplication and attention together, rather than either one in isolation.

- • BF16-compatible interface with measured numerical checks. Atik consumes and produces row-major BF16 tensors, while its mesh and softmax datapath use fixed point and lookup tables. We report benchmark tolerance checks rather than claiming bit-exact BF16 arithmetic.

- • System-level evaluation and preliminary area evidence. We evaluate Atik cycle-by-cycle on AWS F2 through FireSim and report a standalone Sky130 area estimate across 2 $\times$ 2, 4 $\times$ 4, and 8 $\times$ 8 mesh configurations.

- • An open-source artifact. The complete design, software, and hardware/VLSI flow are released to the community.


### 2. Background and Related Work

Systolic arrays are a standard approach to dense matrix multiplication ( Kung, 1982 ; Jouppi et al., 2017 ; Genc et al., 2021 ) , while online softmax avoids materializing full score rows ( Milakov and Gimelshein, 2018 ; Stevens et al., 2021 ) . Transformer accelerators span tightly-coupled systems such as TiC-SAT ( Amirshahi et al., 2023 ) , narrow exponential units such as VEXP ( Wang et al., 2025 ) , and standalone attention ASICs ( Islamoglu et al., 2023 ; Ham et al., 2020 ; Ham et al., 2021 ; Lu et al., 2021 ; Zhou et al., 2023 ) . Table summarizes the dimensions relevant here. Atik’s narrow contribution is not a claim of bit-exact floating-point execution or superiority to these systems; it is the combination of a RoCC-attached interface, a shared mesh for matmul and both attention products, and cycle-level evaluation of the integrated design.


### 3. Atik Architecture

Atik is a RoCC-attached accelerator for two operations: dense matrix multiplication and attention. Its guiding principle is reuse: rather than provisioning a separate datapath per operation, the design routes matmul, the QK score computation, and the probability–value accumulation through a single shared fixed-point MAC mesh, and moves all data with one shared tile-DMA engine and one set of SRAM tile buffers. Figure 2 shows the resulting core. Software interacts with Atik only through a small descriptor and a handful of RoCC commands; the hardware owns tiling, data packing, DMA scheduling, numeric conversion, softmax bookkeeping, and writeback.


#### 3.1. RoCC Integration and Control Flow

Atik is instantiated as a Rocket Custom Coprocessor on the custom0 opcode and exposes a TileLink client port, through which it issues Get and Put transactions to the RocketChip memory system. Software drives the accelerator with a minimal command set: it fills an 80-byte descriptor in memory, passes the descriptor address with set_desc , and starts execution with run ; additional commands read the status word and the performance counters. The descriptor carries the operation code (matmul, attention, or causal attention), the tensor base addresses and leading dimensions, the problem dimensions, and, for attention, the BF16 scale factor. On run , a descriptor reader fetches the descriptor over the shared read port, the top-level controller decodes the operation, and it hands off to either the matmul or the attention controller. Software then polls the status word until the busy bit clears. Crucially, the software-visible interface never exposes tiling, packing, or internal addresses: the same descriptor describes an arbitrarily large problem, and the hardware streams it in tiles.


#### 3.2. Shared MAC Mesh

The compute core is an $R\times C$ mesh of fixed-point multiply–accumulate cells (Fig. 2 ), configurable as $2\times 2$ , $4\times 4$ , or $8\times 8$ . Each cycle the mesh is driven by a row vector of $R$ operands and a column vector of $C$ operands, and every cell $(r,c)$ computes the outer-product update $\mathit{acc}_{r,c}\mathrel{+}=a_{r}\cdot b_{c}$ against a live accumulator tile held in registers. The accumulator remains resident across the entire reduction dimension of a tile, so a large $K$ (or key/value length) is consumed as a sequence of depth- $K_{T}$ chunks without ever spilling partial sums to memory.

The same mesh serves all three heavy computations. For matmul it evaluates $C\mathrel{+}=A\,B$ ; for attention it first evaluates the score tile $\mathrm{score}\mathrel{+}=Q\,K^{\top}$ , and later folds the normalized probabilities into the output as $O\mathrel{+}=P\,V$ . A single multiplexer at the mesh inputs selects whether the operands come from the matmul or the attention controller, so the largest arithmetic structure in the design is paid for once and amortized across every operation. This is the central difference from designs that instantiate independent matmul and attention engines. The preliminary area study in Section 7 measures this amortization as the mesh grows.


#### 3.3. Numeric Datapath

External tensors are row-major BF16. Internally, Atik computes in fixed point: on the way into the mesh, a BF16toFixed unit converts each element to a 24-bit signed fixed-point value, products accumulate in a 64-bit signed accumulator, and a FixedToBF16 unit converts results back to BF16 for writeback. The attention softmax path uses a wider 32-bit unsigned fixed-point format for exponentials and running sums. Exponentiation and reciprocal are implemented as small lookup tables—a 256-entry table evaluating $e^{-x}$ over $[0,16]$ and a 256-entry reciprocal table for final normalization—so the design avoids iterative dividers. These conversions and lookup tables are approximations; Section 5 reports the implemented tolerance-based checks.


#### 3.4. Tile DMA and Local Buffering

A single small tile-DMA engine decouples memory movement from compute. It is parameterized only by a base address, row and column counts, a stride, and a direction, which is sufficient to gather a row-major BF16 tile from memory or scatter one back. The matmul and attention controllers arbitrate for the shared reader and writer, and the descriptor reader shares the same read port, so the entire core presents just one read and one write stream to the memory system. Loaded tiles land in SRAM-backed buffers—per-row banks for the $A$ / $Q$ operand and per-column banks for the $B$ / $K$ operand—from which the controllers read back $K_{T}$ -deep chunks, convert them to fixed point, and drive the mesh. Only the small live state (the accumulator tile and, for attention, the per-row maximum and denominator) is kept in registers. This explicit, tile-granular data movement keeps the memory interface simple and makes the accelerator’s traffic predictable, which the on-chip performance counters expose directly for analysis.


### 4. Attention Dataflow

Attention computes $O=\mathrm{softmax}\!\left(QK^{\top}\!/\sqrt{d_{k}}\right)V$ . The naive formulation materializes the full $q_{\text{rows}}\times kv_{\text{rows}}$ score matrix, which is both memory-hungry and a poor match for a small tightly-coupled accelerator. Atik instead follows the streaming online-softmax formulation ( Milakov and Gimelshein, 2018 ) : it walks the key/value axis in chunks, and for each chunk it computes a score tile, updates a running per-row maximum and denominator, and immediately folds the result into a resident output accumulator. The full score matrix is never stored—only one $\mathit{MR}\times\mathit{KC}$ score tile and its exponentiated copy exist at any time. Algorithm 1 gives the resulting schedule.

The two matrix products in attention, $QK^{\top}$ and the probability–value product, run on the shared MAC mesh, while softmax bookkeeping runs on one scalar lane with exponential and reciprocal lookup tables.

> Algorithm 1 Atik tiled online-softmax attention. $MR$ / $NC$ are the mesh row/column tile sizes, $KC$ the key/value chunk, and $KT$ the internal reduction depth. The score matrix is never fully materialized; $QK^{\top}$ and the probability–value product run on the shared mesh, and the softmax update runs on the scalar lane.

For each key/value chunk, the mesh computes $QK^{\top}$ over depth- $K_{T}$ slices. The scalar lane applies scaling and the causal mask, updates the running maximum and denominator, and rescales the live output. The resulting probability tile is then multiplied by $V$ on the same mesh. After the final chunk, reciprocal-based normalization and BF16 conversion precede writeback. The implementation uses one scalar lane, an explicit area-first choice that serializes this non-linear phase.

The value-column loop encloses the key/value loop in Algorithm 1 . Consequently, the score and softmax computations are repeated for each output-column tile when $\mathit{val\_cols}>NC$ . This schedule bounds the resident output state at the cost of recomputation and additional input traffic.


### 5. Experimental Setup


#### 5.1. Configurations and Platform

We evaluate three Atik instances that differ only in mesh size: $2\times 2$ , $4\times 4$ , and $8\times 8$ , corresponding to 4, 16, and 64 MAC lanes. All three expose the identical descriptor ABI and run the same unmodified benchmark binaries; only the generated hardware changes. Each instance is attached over RoCC to one Rocket core in a Chipyard-generated SoC with a 128-bit system bus. Functional bring-up and debugging use a Verilator RTL simulator, while all reported performance numbers come from cycle-accurate FPGA emulation with FireSim on AWS F2. The logged runs use an effective target frequency of approximately 10 MHz. Because FireSim is cycle-accurate, every measurement is expressed in target clock cycles , read from the RISC-V cycle CSR and from Atik’s on-chip performance counters; these cycle counts are independent of the host FPGA clock, so speedups are reported as cycle ratios rather than wall-clock times.


#### 5.2. Baseline

The baseline is the same Rocket core running a BF16 software reference implementation of each kernel, on the same SoC and memory system. This isolates the effect of the accelerator: the comparison is Rocket-with-Atik against Rocket alone, not against a different platform. For every accelerated kernel, the hardware output is compared with the software reference using a workload-specific absolute-error tolerance. The archived FireSim logs contain 137 passing result records with zero reported mismatches; the largest logged absolute difference is 0.0625. These checks establish benchmark-level numerical agreement, not task accuracy or bit-exact equivalence.


#### 5.3. Workloads

The benchmark suite spans two standalone kernels and three workload-derived C transformer models, chosen to exercise both overhead-dominated and compute-dominated regimes.

Standalone kernels. The matmul benchmark multiplies an $M\times K$ matrix by a $K\times N$ matrix over a range of $M$ , $N$ , and $K$ , and the attention benchmark computes both non-causal and causal attention over query count $Q$ , key/value count $KV$ , key/query dimension $D$ , and value dimension $V$ . These isolate the accelerator’s behavior without surrounding model bookkeeping.

Workload-derived C models. TinyBERT, a Vision Transformer (ViT), and the GPT-2 prefill stage are represented by small C reference models that preserve the relevant layer structure while varying sequence length, model width, head count, and final projection size. Multi-head attention is decomposed into per-head $QK$ , softmax, and $PV$ operations; Atik accelerates these repeated attention and projection kernels while the software harness keeps the tensor layout and model-level accounting consistent. Numerical fidelity is tracked by comparing three outputs—the original ground-truth result, the C reference, and the Atik result—so that the C port is validated against the model before the accelerator is judged against the C port.


#### 5.4. Measurement Methodology

For the standalone kernels, the software reference is timed with the RISC-V cycle counter. Atik is measured two ways: the same counter surrounds the RoCC call for end-to-end cycles, while TOTAL_CYCLES records internal accelerator cycles. We report algorithmic FLOP/cycle from both denominators; these counts describe the equivalent matrix work, although Atik executes fixed-point arithmetic internally. Matmul work is $2MNK$ FLOPs. For attention we report attention-matmul FLOPs , $2QKV(D+V)$ , for $QK^{\top}$ and $PV$ ; softmax remains in the cycle denominator but has no arbitrary FLOP-equivalent count. Replaying the full workload-derived C models on both paths would be expensive in FPGA simulation, so for those workloads we profile the full CPU execution, separately profile the stages that Atik replaces, and form a hybrid projected cost as

[Tableau] (1) $$c_{\text{acc}}=c_{\text{cpu,total}}-c_{\text{cpu,replaced}}+c_{\text{hw,replacement}},$$

where $c_{\text{cpu,replaced}}$ is the measured CPU cost of exactly the kernels Atik takes over and $c_{\text{hw,replacement}}$ is their measured cost on Atik. This is a hybrid projection rather than a full-model hardware replay: it uses directly measured hardware-kernel cycles while assuming the unaccelerated remainder is unchanged. We report two summaries per workload and configuration. The aggregate speedup sums all baseline cycles and all accelerated cycles over the matching problem sizes and takes their ratio, $\sum c_{\text{cpu}}/\sum c_{\text{hw}}$ , which weights cases by their cycle costs; the peak speedup reports the single best observed case, which reflects how well the design amortizes control, DMA, and setup overhead once the problem is large enough to keep the mesh busy.

#### 6.2. Scaling Behavior

The representative cases make two trends visible across the suite. First, wider meshes help more on larger problems: moving from $2\times 2$ to $8\times 8$ multiplies the available MAC lanes by $16\times$ , but that capacity only translates into speedup when a tile is large enough to keep the mesh busy, so the largest gains appear on the biggest matmul, attention, and prefill cases, where the $8\times 8$ curve pulls furthest ahead. Second, small problems are overhead-dominated: fixed descriptor handling, DMA setup, and controller scheduling are amortized poorly when there is little compute per launch, which is why the smaller configurations improve over Rocket but saturate earlier and why aggregate speedups (which include every small case) sit below the peaks. Causal attention is slower than its non-causal counterpart: masking removes useful work from part of the score matrix while the control flow must still preserve the causal dependency structure. Overall, the results confirm that a single shared-mesh design scales smoothly across an order of magnitude of lane count while covering both matrix multiplication and full attention.

### 8. Discussion and Limitations


##### Baseline.

The reported speedups are measured against the same in-order Rocket core running BF16 software kernels. This deliberately isolates the effect of the accelerator on a fixed RISC-V system, but Rocket is a scalar core without a SIMD or vector unit, so part of the large absolute speedup reflects how poorly a scalar pipeline handles dense BF16 matrix work and data-dependent softmax. The comparison answers “what does attaching Atik buy this core,” not “how does Atik compare to a GPU or a vector machine”; those cross-platform comparisons are future work.


##### Scalar-scheduled softmax.

Atik keeps $QK^{\top}$ and $PV$ on the shared mesh but runs the online-softmax bookkeeping and final normalization on a single scalar lane (Section 4 ). This is an area-first choice, but it also serializes the non-linear part of attention. On very large score tiles this scalar region becomes the dominant sequential cost. The number of scalar lanes and LUT instances is a hardware parameter, not an ABI feature, so a throughput-oriented instance can widen it without changing accelerator software; quantifying that trade-off is left to future work.


##### Dense, non-sparse attention.

Atik accelerates dense attention and does not exploit sparsity. Sparse-attention accelerators skip low-contribution key/value rows and can achieve higher effective throughput on workloads with exploitable sparsity, at the cost of approximation and, often, retraining. Atik trades that opportunity for generality and a BF16-compatible interface with measured benchmark error; adding an optional sparsity path is complementary rather than contradictory.


##### Implementation scope.

The preliminary area study targets standalone AtikCore on Sky130; it does not include RocketTile, ChipTop, routing closure, or tapeout. Its area estimate is not a silicon or PPA result. Extending the flow to a complete tile and reporting timing and power are natural next steps. Finally, the workload study covers matmul, attention, and single-layer ViT, TinyBERT, and GPT-2 prefill; the autoregressive decode stage with a KV cache is not yet accelerated and is an important target for future work.


### 9. Conclusion

We presented Atik, an open-source, tightly-coupled transformer accelerator for the RISC-V RocketChip. Atik attaches over RoCC, is driven by a minimal descriptor-based software interface, and accelerates both of the recurring transformer bottlenecks—dense matrix multiplication and attention—with BF16 input/output. Its central idea is a single shared fixed-point MAC mesh that serves matmul, $QK^{\top}$ scoring, and probability–value accumulation, wrapped in a streaming online-softmax schedule that never materializes the full score matrix. Evaluated cycle-accurately on an AWS F2 FPGA through FireSim, Atik reaches up to $225.8\times$ speedup on attention and $31.5\times$ on matmul over the Rocket baseline, with hybrid projected model speedups of $44\times$ on ViT and $32\times$ on GPT-2 prefill. The preliminary area estimate shows the expected amortization of shared control as the mesh grows, but it is not a PPA result. Together these results show how a shared-mesh, BF16-interface, tightly-coupled accelerator can reduce transformer-kernel cycles in the open RISC-V ecosystem.
