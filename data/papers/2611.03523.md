## DistDebug-Bench : Can LLM Agents Diagnose Bugs in Distributed Systems?

LLM agents show strong potential in software engineering tasks such as competitive programming and code synthesis. Existing benchmarks, however, largely focus on small-scale settings such as self-contained Python modules, leaving distributed systems, an essential class of production software, under-examined. We introduce DistDebug-Bench , a benchmark for evaluating agents’ ability to diagnose complex-system failures at the code level. It curates 120 high-quality real-world bugs from 11 widely used distributed systems, spanning 5 programming languages and 10 failure patterns. Through an extensive evaluation of state-of-the-art LLMs and agents, we identify substantial gaps between current agents and real-world debugging tasks. A recurring gap is tunnel vision due to a lack of explicit reasoning structure and nondeterminism from inconsistent tool-use scope. The benchmark and evaluator are available at https://github.com/OrderLab/distdebug-bench , with agent traces and a leaderboard at https://distdebug.com .


### 1 Introduction

Large language models (LLMs) and agents have made rapid progress on software engineering tasks, including code synthesis, repository navigation, and issue resolution. Early code benchmarks measure LLM capabilities on short-program synthesis [ 4 , 3 ] ; programming-contest benchmarks evaluate more challenging algorithmic problem solving [ 12 , 36 ] ; RepoBench measures cross-file repository-context use [ 17 ] ; later benchmarks such as SWE-bench and SWE-bench Verified evaluate whether an agent can resolve GitHub issues by producing a patch that passes a test suite [ 14 , 6 ] . These benchmarks help shape the designs of both models and agent harnesses.

However, much existing benchmarking focuses on small-scale or locally scoped settings, such as standalone functions, self-contained modules, and library-style repositories. These settings are useful, but leave a critical real-world target under-examined: debugging large-scale, production systems . Existing evaluations also often emphasize patch generation, which can conflate diagnosis with repair synthesis. A patch may suppress a symptom without addressing the root cause; even when the final fix changes only a few lines, finding that cause may require understanding a much larger causal chain. In many production workflows, engineers must therefore diagnose a failure before writing a proper fix. This debugging workflow is crucial yet not directly measured by existing benchmarks.

Distributed systems debugging is a particularly important and challenging setting in this gap. Production distributed systems, including distributed storage, coordination, and stream processing, underpin modern computing services. Their failures are costly and hard to debug for several reasons. First, these systems span millions of lines of code across many subsystems and layered abstractions, creating a large search space in which the true root cause occupies only a tiny subset. Second, failures involve interactions across modules, network calls, and service tiers. An observed symptom often exposes only downstream effects while the originating fault is far away. Third, the available evidence is noisy and incomplete: issue reports, logs, stack traces, and artifacts provide only partial observations . Large-scale distributed systems also experience gray failures with ambiguous symptoms [ 11 , 18 ] . Debugging therefore requires reasoning from high-level symptoms to low-level code under weak evidence. Developers need to generate and test competing hypotheses, reconcile evidence with code context, trace causal relationships across modules and historical design decisions, and revise assumptions as new evidence appears. Distributed-system debugging thus stresses capabilities central to LLM and agent design: long-context retrieval , large-repository navigation , multi-hop causal reasoning , decision-making under noisy and incomplete evidence , and belief revision .

To address this gap, we introduce DistDebug-Bench , a benchmark for evaluating LLM agents on code-level diagnosis of real-world distributed-system failures . In each benchmark instance, the agent is given an incident report, accompanying evidence ( e.g. , stack trace), and the pre-fix repository snapshot, and must identify one or more source-code blocks that best explain the observed failure. Outputs are judged against human-annotated labels that capture the root-cause regions. The benchmark contains 120 curated incidents from 11 distributed systems and 5 languages, with 218 gold root-cause blocks. It captures the properties that make distributed-system debugging difficult: 45% require multiple blocks to express the root cause, 23% span multiple files, 69% of reports do not mention the gold method, and 63% contain no usable internal stack trace. The benchmark repository is available at https://github.com/OrderLab/distdebug-bench , with project documentation and updates at https://distdebug.com .

We evaluate state-of-the-art LLMs and agents on the benchmark. The results reveal a substantial gap between broad repository navigation and precise diagnosis. The strongest configuration achieves high file-level coverage but much lower block-level coverage and precision. Agents often find a relevant component but fail to pinpoint the causal source lines. Performance degrades most for opaque reports and cross-component bugs. Through trace inspection, we find a recurring failure mode: agents commit early to a plausible local explanation and rarely recover when the initial search scope misses the causal region. We call this behavior tunnel vision and analyze how it arises from evidence structure and tool-call trajectories. Non-determinism further compounds the problem: even a leading solution produces flaky diagnoses on 17% of incidents, rising to 26% on no-stack opaque reports.

Our contributions are:

- • A benchmark task for distributed-system diagnosis in which agents localize the pre-fix code blocks that best explain an observed failure.

- • A curated dataset of real-world failures in widely used distributed systems, with a label design process focused on reproducibility and non-trivial causal structure.

- • An empirical evaluation of current LLM agents and harnesses showing gaps in precise causal localization, especially for weak-evidence and cross-component failures.

- • A failure-mode analysis identifying key obstacles for reliable debugging.


### 2 Related Work

Code-generation and repository-context benchmarks. Early code benchmarks such as HumanEval and MBPP evaluate functional correctness for short programming tasks [ 4 , 3 ] . LiveCodeBench and LiveCodeBench Pro extend this line with newer competitive-programming tasks and broader code-execution signals [ 12 , 36 ] . Repository-context benchmarks such as RepoBench move beyond single-file synthesis by testing retrieval and completion across files [ 17 ] . These benchmarks measure code synthesis abilities but not failure diagnosis.

Bug, repair, and debugging datasets. Long-running software-engineering datasets such as Defects4J, ManyBugs, Bugs.jar, Bears, BugSwarm, and BugsInPy provide reproducible real bugs and failing and passing versions for testing, fault localization, and automated program repair [ 15 , 16 , 26 , 19 , 30 , 31 ] . More recent LLM debugging benchmarks such as DebugBench directly test whether models can repair or reason about injected buggy snippets [ 29 ] . In these datasets, the primary oracle is typically a test suite, a fixed version, or a snippet-level repair target; diagnosis is not directly evaluated. DistDebug-Bench explicitly measures root-cause localization. Agents must identify the precise causal block(s). It targets large-scale distributed systems. Its bugs are drawn from challenging, real-world failures. Its diagnosis tasks model the multi-source, noisy evidence of a real incident.

Issue-resolution agent benchmarks. SWE-bench changed the evaluation target from standalone synthesis to real GitHub issue resolution, and follow-on suites add human verification, visual software domains, live task collection, multilingual ecosystems, broader repository languages, and long-horizon enterprise-style tasks [ 14 , 6 , 33 , 35 , 34 , 25 , 9 ] . SWE-Gym further targets training environments and verifiers for software-engineering agents [ 23 ] . DistDebug-Bench shares the basic format (repository-level context and natural-language issue reports) but differs along several axes: (1) they score patches, while DistDebug-Bench scores root-cause localization directly; (2) SWE-bench-style instances are dominated by single-process projects with short causal chains; (3) they require a test suite for evaluation, a constraint that biases curation toward bugs whose fixes are exercised by existing tests. For many distributed systems failures, a regression test rarely exists at the time of diagnosis.

Operational benchmarks. Recent benchmarks evaluate LLM agents on IT automation and fault localization. AIOpsLab evaluates AIOps agents in microservices with fault injection, workload generation, and telemetry export [ 5 ] . ITBench evaluates AI agents across IT automation tasks [ 13 ] . SREGym evaluates SRE agents in a controlled platform [ 7 ] . Benchmarks such as OpenRCA [ 32 ] , RCAEval [ 24 ] , and PetShop [ 10 ] evaluate LLMs on fault localization: identifying the faulty services, machines, or resources from telemetry, metrics, traces, and injected performance anomalies. These benchmarks are valuable for AIOps [ 8 ] workflows. They typically operate over telemetry data and focus on coarse-grained localization. DistDebug-Bench addresses a complementary problem: precise source-level debugging . In incident response, engineers still need to perform the last-mile reasoning that connects symptoms to the root cause block(s) in code, which is often the most time-consuming step. DistDebug-Bench evaluates LLMs’ abilities in this task. It preserves repository-level, source-code grounding while capturing the weak evidence, interactions, and ambiguity characteristic of distributed-system debugging.


### 3 Benchmark

> Figure 1 : DistDebug-Bench task flow.

DistDebug-Bench is a benchmark for code-level diagnosis of real-world distributed-system failures. DistDebug-Bench evaluates coding agents in the real-world systems maintenance workflow where developers have to start with a high-level symptom, explore possible root causes by forming and testing multiple causal hypotheses from partial evidence, and identify where in the code the root cause is encoded before any fix is applied. Each benchmark instance asks the agent to identify, from an incident report, a realistic evidence bundle, and the pre-fix snapshot, the code block or set of blocks that best explains the observed failure.


#### 3.1 Task Workflow

Figure 1 shows the task flow. The agent-facing input consists of an incident report, issue-side artifacts such as logs or stack traces, the pre-fix repository snapshot, and a structured output schema. The fixing change and human root-cause labels are held out for annotation and scoring. The agent must return one or more repository-local source blocks that encode the pre-fix failure mechanism. The evaluator validates the structured output, canonicalizes symbols, and scores whether the predicted blocks capture the minimal causal region(s) that explain the incident.

The benchmark release contains 120 incidents from 11 production-scale distributed systems across 5 languages. Each incident is selected to be diagnosable from issue-side context, stripped of answer-leaking discussion, and labeled with precise pre-fix root-cause blocks. Because DistDebug-Bench is built from public historical bugs, we also include leakage controls in the task workflow. The prepared workspaces anonymize directory names and remove commits after the task snapshot. The leakage guard in Figure 1 scans visible reasoning and tool inputs/outputs for the original issue identifiers withheld from the agent. Flagged attempts are discarded and rerun; Section A.6 describes the guard and follow-up audit process. For GPT-5.4, flagged attempts fell from 102/360 to 4/360 after future-commit removal. In closed-book probes on 66 reports without exact gold file/function names, revealing the issue ID gives no advantage: function coverage is 17.3% with the ID and 21.4% without it, versus 45.5% with repository access. Repository access substantially improves localization in these probes, although pretraining exposure cannot be ruled out ( Section G.2 ).


#### 3.2 Bug Selection

DistDebug-Bench is constructed from issue reports and fixing changes drawn from large-scale, production distributed systems. We select candidate bugs using three principles: the issue should describe a representative production failure, the available evidence should support diagnosis without revealing the answer, and the fixing change should support precise root-cause labeling.

Real production failures. We prioritize high-impact, user-facing bugs on stable releases. Eligible issues must be closed, have an associated fix, and describe a concrete failure rather than a feature request or internal cleanup.

Realistic and diagnosable evidence. We prefer reports that expose the kinds of signals engineers actually use in practice: stack traces, logs, reproduction steps, cross-linked prior issues, or explicit symptom descriptions. We also check that the issue is diagnosable from issue-side context alone. Later issue-thread comments that reveal the root cause or patch strategy are removed or ignored, since those no longer reflect realistic diagnosis.

Labelable root-cause fixes. We retain bugs whose fixes are local enough to support precise root-cause labeling. Large refactorings, test-only changes, and patches dominated by unrelated cleanup are excluded because they make the minimal causal span ambiguous. As a practical filter, we also exclude fixes with more than 100 changed source lines unless the causal span remains clearly separable from auxiliary edits.


#### 3.3 Root-Cause Labeling

For each accepted issue, annotators derive the minimal pre-patch root-cause span from the fixing change and its surrounding context. Each label marks a buggy code block with a file path, function or method symbol, and a start/end line range in the pre-fix snapshot. Section A.1 shows the concrete label format.

In practice, annotators inspect the issue report, the fixing patch, and the affected code, and then mark only the code that embodied the bug before the fix. We exclude tests, helper refactors, defensive hardening, and incidental cleanup unless these are necessary parts of the minimal causal explanation, because such edits do not directly encode the original failure mechanism. Each issue is independently annotated by three annotators and then reconciled into a final gold label set; Section A.5 reports inter-annotator agreement.

In addition to root-cause labels, we record characterization metadata for each bug. These fields include textual code anchors, crash-to-fix distance, issue-side signals, and coarse root-cause type. They are not scoring targets or agent-facing hints, but they provide the foundation for the fine-grained breakdowns in Section 4 .

Scaling collection. The released DistDebug-Bench labels are fully human-curated and human-reconciled; LLM outputs are not used in the gold annotation workflow. Because human review remains the main bottleneck for scaling, we also developed an LLM-assisted label extraction pipeline for future exploration. Appendix B describes it and reports a small-subset comparison between this pipeline, a non-LLM extraction pipeline, and the final human labels.


#### 3.4 Benchmark Characteristics

> Figure 2 : DistDebug-Bench workload characterization.

Figure 2 summarizes the workload beyond headline dataset size. The characterization highlights three properties that make diagnosis difficult and later enable fine-grained evaluation breakdowns: the issue-side evidence is heterogeneous, the symptom is often far from the causal code, and many gold labels require non-local or multi-block explanations.

Issue-side evidence and anchors. DistDebug-Bench reports contain heterogeneous evidence rather than a uniform problem statement. Code identifiers appear in 96 / 120 reports, but direct debugging signals are much less common: 37 include prior analysis, 28 include stack traces, 20 include logs, and only 7 include attached artifacts. Even when a report contains concrete code names, it rarely names the final fix location: in 83 / 120 reports (69.2%), the exact gold method does not appear in the title or description.

Crash-to-fix distance. Stack traces are also an incomplete localization signal. In 75 / 120 incidents, the report does not contain a usable project-internal stack trace. Among the remaining incidents with an observable crash site, only 12 are co-located with the fix, while 27 require crossing component boundaries from the crash site to the gold block and 6 are adjacent within nearby package structure.

Ground-truth structure. The labels also show that diagnosis is not simply a single-location search problem. DistDebug-Bench contains 218 gold buggy blocks, and 45.0% of incidents require more than one block to express the root cause. Nearly a quarter span multiple files. At the same time, the median block is only five lines, so a useful agent must both follow non-local causal chains and report precise source spans. Appendix A gives the full artifact layout, raw instance examples, label schema, and classification rules used for the benchmark characterization. For a concrete illustration of how issue evidence can point to a plausible symptom-side investigation space while the actual root cause lies elsewhere, Section A.2 walks through ZooKeeper-2845.


### 4 Evaluation

We evaluate whether current software-engineering agents can identify source-level root causes for DistDebug-Bench incidents, and where their diagnosis quality breaks down. The central result is that contemporary agents often reach relevant code, but their diagnosis process breaks down when weak incident evidence requires sustained navigation and hypothesis revision.


#### 4.1 Evaluation Setup

We run DistDebug-Bench along two axes: (1) the model axis and (2) the harness axis. We first conduct a thirteen-configuration sweep on Mini-SWE-Agent, including GPT-6 Astra, Claude Opus 5.5, GPT-5.5, GPT-5.4, GPT-5.3-Codex, GPT-5.2-Codex, Hunyuan3, o4-mini, DeepSeek V4 Flash, Kimi K2.6, Gemini 3.5 Flash, MiMo v2.5, and MiMo v2.5 Pro. We then run GPT-5.2-Codex and o4-mini on Codex CLI v0.128.0 and OpenCode v1.4.6 to provide harness comparison points. Mini-SWE-Agent is the common minimal harness used by existing coding benchmarks [ 28 , 27 ] ; Codex CLI is OpenAI’s terminal coding agent [ 20 ] ; and OpenCode is a highly starred open-source terminal coding agent [ 1 ] . The model set mixes recent high-end systems, including GPT-6 Astra [ 22 ] , Claude Opus 5.5 [ 2 ] , and GPT-5.4 [ 21 ] , with popular economical or coding-specialized options such as o4-mini, Kimi K2.6, DeepSeek V4 Flash, Gemini 3.5 Flash, and MiMo.

In addition to the 17 main configurations, we run exploratory experiments with DeepSeek V4 Pro, Qwen3.6 Max, and Qwen3-Coder-Next on non-uniform subsets of the benchmark. These runs are not included in the main 120-bug leaderboard, but Appendix F reports paired comparisons against Mini-SWE GPT-5.2-Codex on the exact subset completed by each model.

We set reasoning effort to medium when the model exposes that control. The MiMo endpoint did not expose a reasoning-effort parameter, so those runs use the provider default. Claude Opus 5.5 runs at its API default effort, which is medium, with a 16,000-token output limit and Anthropic prompt caching. For each bug/configuration pair, we average three attempts within the bug, then average equally across all 120 bugs ( Section D.3 ). Section D.1 reports 95% bug-level bootstrap confidence intervals (CIs) for every configuration and paired comparisons between them.


##### Metrics.

We compare generated diagnoses with labeled ground truth using coverage and precision at four granularities: file, function, line, and block. File and function metrics measure whether an agent reaches the right component. Line coverage is the stricter overlap metric, while block coverage is a coarser region-hit metric that asks whether each labeled causal block is reached. We use block coverage as the main localization metric because it is less sensitive to exact line-boundary choices and better captures whether an agent navigates to the causal region. We report line coverage as a stricter sensitivity metric ( Appendix D ). We also report mention coverage : whether the natural-language causal-chain explanation mentions gold functions even when the structured block prediction is wrong. To measure nondeterminism, we compute the within-bug standard deviation of block coverage across the recorded attempts and the number of flaky bugs whose block-coverage spread exceeds 0.2.


##### Metric validity.

Block coverage measures recovery of the annotated causal code, not every plausible intervention or repair point. Most zero-coverage diagnoses reflect incorrect or incomplete causal reasoning: in a score-blinded audit of 20 zero-coverage GPT-5.4 diagnoses, 16 were incorrect or incomplete, and the other four reconstructed the failure mechanism but blamed a different intervention point. Benchmark-wide, most missed gold blocks are genuine misses: in a stratified random sample of 100 incompletely covered attempts from all 17 configurations, two independent AI reviewers, each given the historical fix, agree that 8.8% (95% CI 4.3–14.3%) of the missed blocks were correctly localized; counting them would raise block coverage by 5.0 points. Coverage also matters downstream. In a six-bug within-bug repair pilot, high-coverage diagnoses led the repair agent to edit the gold block in 50.0% of attempts, versus 11.1% without a diagnosis and 0% with low-coverage diagnoses ( Section G.1 ).

#### 4.2 Main Evaluation Results

Table 1 summarizes diagnosis performance across the main model and harness configurations. GPT-6 Astra has the highest aggregate block coverage in our complete sweep: with Mini-SWE, it reaches 83.9% file coverage, 53.9% line coverage, and 67.7% block coverage. Across configurations, however, file coverage remains substantially higher than line and block coverage, and higher-coverage settings often come with broader predictions: Mini-SWE GPT-5.5 has 34.7% block precision and names 3.6 blocks per diagnosis on average. These aggregate results point to a consistent theme: Current SOTA agents can often reach relevant code, but their diagnosis process breaks down when weak incident evidence requires sustained navigation and hypothesis revision. When the report names an exact method, agents often do well: the best current configuration reaches 95.8% block coverage on local-or-adjacent method-named bugs, and 94.8% on no-stack method-named bugs. When the report is opaque, even the best configuration reaches only 65.0% on the 42 no-stack opaque bugs and 40.5% on the seven cross-component opaque bugs. For a fixed baseline, Mini-SWE GPT-5.2-Codex shows the same pattern: its no-stack method-named coverage is 82.8%, but it falls to 44.7% on no-stack opaque bugs and 14.3% on cross-component opaque bugs.

Adding newer models raises absolute coverage but does not remove this weak-evidence gap. GPT-6 Astra improves no-stack opaque block coverage to 65.0%, yet this remains 29.8 percentage points below its 94.8% coverage on no-stack method-named bugs. These cases are common: opaque reports account for 50 of the 120 benchmark bugs, including 42 without a stack trace. The central challenge is navigating from symptoms to causal code without direct code references.

Diagnosis quality varies across repeated attempts on the same bug. GPT-6 Astra has the best aggregate block coverage, but 15 of its 120 bugs are flaky under our definition. Claude Opus 5.5 has 17 flaky bugs, GPT-5.5 has 20, GPT-5.4 has 21, GPT-5.2-Codex has 18, Kimi K2.6 and DeepSeek V4 Flash each have 32, MiMo v2.5 Pro has 22, MiMo v2.5 has 26, and HY3 has 35. The instability is most concerning on bugs that require navigation from weak evidence. For Mini-SWE GPT-5.5, the no-stack opaque cell has 11/42 flaky bugs (26%) and a mean within-bug block-coverage standard deviation of 9.2 points, while the no-stack method-named cell has only 2/16 flaky bugs (13%) and a 3.7-point mean standard deviation. Mini-SWE GPT-5.2 shows the same contrast: 11/42 no-stack opaque bugs are flaky (26%) compared with 1/16 no-stack method-named bugs (6%). This variance matters for diagnosis because it suggests that reports with little direct code evidence create brittle search trajectories rather than only uniformly harder examples.

The full Mini-SWE-Agent model sweep shows that stronger models do not simply raise every category. GPT-5.5 improves aggregate block coverage from 56.4% to 65.1% relative to GPT-5.2-Codex, and it improves difficult weak-evidence cells: no-stack opaque bugs improve by 15.4 percentage points. At the same time, GPT-5.5 emits more predicted blocks per diagnosis than GPT-5.2-Codex, 3.6 versus 2.3, and its block precision falls from 43.1% to 34.7%. GPT-5.5 recovers more causal code on opaque reports, but its broader diagnoses also include more irrelevant code. Agents need to search beyond weak initial clues without losing precision when the report already provides a strong local code reference.

The additional full-suite and subset experiments show the same broad lesson. MiMo v2.5 Pro reaches 58.5% block coverage and 72.6% mention coverage, but uses 2.6M tokens per run on average. MiMo v2.5 is slightly lower at 58.0% block coverage and 69.5% mention coverage while using 2.3M tokens per run. Kimi K2.6 reaches 58.3% block coverage, but uses 2.8M tokens per run on average and has 32 flaky bugs; DeepSeek V4 Flash roughly matches GPT-5.2-Codex block coverage while using 3.4 $\times$ the tokens and lower block precision. Gemini 3.5 Flash is more conservative: it has the highest block precision, 51.1%, but only 47.5% block coverage. In Appendix F , DeepSeek V4 Pro gains 5.0 points while using 2.5 $\times$ the GPT-5.2 tokens. Model scaling can improve exploration, but it is not a substitute for reliable diagnosis control.

Comparing GPT-5.2-Codex across harnesses shows that the harness affects how diagnoses are shaped. Mini-SWE-Agent reaches 56.4% block coverage but 43.1% block precision, while Codex CLI reaches lower block coverage, 46.5%, but the highest block precision, 49.3%. OpenCode is between them at 50.0% block coverage and 47.7% block precision. The blocks/diagnosis column in Table 1 is consistent with this tradeoff: Mini-SWE GPT-5.2-Codex predicts 2.3 blocks per diagnosis on average, compared with 1.6 for Codex CLI and 1.8 for OpenCode. These differences matter, but they are secondary to the shared failure mode: every harness degrades sharply when the report lacks direct causal code references.


#### 4.3 Failure Modes and Design Implications

The results above describe a tunnel-vision problem. Agents often reach relevant files, but their diagnoses are broad, unstable, and especially weak when the report does not name the causal code. We next summarize failure modes and their implications for future harness designs. This analysis also shows why DistDebug-Bench ’s fine-grained evidence breakdown is useful: it provides concrete signals for diagnosing where current agents fail and what future harnesses should improve.

Failure Mode 1: Tool-call nondeterminism drives diagnosis nondeterminism. Subtle differences in command choice can move runs into different evidence scopes, so future harnesses need adaptive tools that augment context automatically when early evidence is incomplete.

Tool calls are a core reason why weak-evidence diagnosis becomes unstable. The models are often good at high-level sensemaking once they are in a relevant region, but the task requires many precise execution decisions: which keywords to search, which directory to enter, which file to open, which symbol to follow, and when to abandon a branch. When the report names the relevant method, different command orders can still converge on the same local region. When the report is opaque, small differences in search terms, directory choices, or the first file opened can send attempts into different subsystems.

For example, in ZooKeeper-3769, node logs are available. The core enabler for a successful diagnosis would be to identify the BufferUnderflowException inside node1.log . We observe that both successful and failed runs read node1.log early on, but successful runs searched for Exception in the log, while failed runs looked at specific line numbers or searched for election-related logs. Those reads revealed other transient errors but missed the BufferUnderflowException . Similar behavior appears in ZooKeeper-2845. The root cause is in ZooKeeperServer.java under the broader /server path, but the issue report strongly emphasizes quorum behavior. Existing agents often narrow early to the /server/quorum subdirectory. Once there, keyword search no longer surfaces the correct class, and the run is steered toward a wrong but coherent diagnosis.

Design Implication 1. To reduce nondeterminism, harnesses should provide tooling layers that infer the model’s intent and automatically augment the context with relevant information. For example, when an agent searches for a keyword, static analysis can return related class definitions, symbol uses, and upstream/downstream contexts. This makes tool execution more precise when two commands are semantically aligned but differ subtly. Future harnesses should not leave context construction entirely to ad hoc shell commands: they need adaptive retrieval and context-augmentation tools that can surface adjacent files, call paths, related symbols, and competing hypotheses when the current search scope is under-supported.

Failure Mode 2: Agents rarely revise initial hypotheses or discover causal code beyond the initial evidence. When the first plausible code region is not the causal one, agents often keep deepening that local explanation instead of reopening the search. In our trace proxy, only 21.0% of parseable runs showed late recovery, and only 11.25% of successful runs did so.

We define late recovery as a run whose final diagnosis files do not appear among the first two inspected source files. Across 124 parseable Mini-SWE-Agent and OpenCode runs with at least two inspected source files, late recovery occurs in only 26 cases (21.0%): 7/21 for Mini-SWE-Agent and 19/103 for OpenCode. Among successful runs, only 9/80 (11.25%) are late recoveries.

Bugs like ZooKeeper-2845 and Ray-8889 illustrate this lock-in. Even when an agent finds code that appears to match the reported symptom (such as the downstream data consumer that raises the exception), it often stops at that obvious location instead of asking what earlier lifecycle state made the symptom possible. Trace inspections show that agents can ask relevant follow-up questions, but whether they explore those questions is highly nondeterministic and shaped by early exploration. This early lock-in reinforces Failure Mode 1: because agents struggle to adapt their scope and reasoning, small tool-execution inaccuracies can become diagnosis failures.

Design Implication 2. Distributed-systems debugging requires each hypothesis path to accumulate its own evidence. Under the current single, ever-growing context, alternatives become harder to compare. This calls for context-management strategies beyond context compaction or sub-agent delegation, such as switching context when pursuing different hypotheses or actively pruning invalidated hypotheses.

Failure Mode 3: Diagnosis is hard because agents lack reliable self-correction signals before finalizing. Distributed-system failures often suffer from reproducibility challenges. Agents often cannot run tests and get quick feedback on whether the diagnosis is correct; instead, they must rely on rigorous reasoning over source code and observed artifacts.

Diagnosis often lacks a cheap pass/fail check for whether a proposed source region is the true root cause. Agents often cannot tell, before finalizing, whether the selected code region accounts for the full causal chain or whether another hypothesis still needs to be explored. Even when a runnable environment is available, agents can give up on testing because they prioritize reproducing the entire incident rather than decomposing it into smaller, unit-test-style checks. Similarly, when agents converge early, they sometimes stop for engineering-practice reasons and lack explicit correctness specifications for deciding whether upstream or downstream code should be blamed.

Our core insight is that bug diagnosis does not inherently lack correctness signals. Rather, signals such as raised exceptions, crash sites, logs, and documentation require consistent evaluation and cross-checking before they become useful.

Design Implication 3. Future harnesses should actively inject correctness signals into the agent’s context, or use an evaluator sub-agent to verify whether the proposed diagnosis fully explains the buggy behavior from start to end, and whether the decision to blame one component is backed by concrete evidence.


### 5 Conclusion and Future Work

We introduced DistDebug-Bench , a benchmark for evaluating LLM agents on code-level root-cause diagnosis of real-world distributed system failures. Our evaluation shows that current agents often reach relevant repository regions but struggle to pinpoint the precise causal locations, especially when issue reports lack direct code references or stack traces. Trace analysis highlights inconsistent tool use and limited revision of initial hypotheses. The evidence breakdown, run-to-run flakiness, and failure-mode analyses together suggest that distributed system debugging requires more than broader search or model scaling. These findings motivate future research and agent harness designs that support adaptive context construction, hypothesis-aware context management, and correctness checks, so that exploration, revision, and validation are explicit parts of agentic diagnosis workflows.

#### A.1 Artifact Layout

Each benchmark instance is stored as a small directory under benchmark/bugs/<system>/<bug-id>/ . The release separates issue-side evidence from gold labels so that an evaluator can instantiate the task without looking at the fixing patch.

benchmark/bugs/<system>/<bug-id>/ report.json # title, description, metadata, links, artifact pointer blocks.json # gold pre-fix root-cause blocks artifact_dir/ # optional logs, screenshots, reproducer files, traces

The report.json file contains the original issue title and description, project metadata, and flags such as whether the report contains logs, stack traces, prior analysis, or attached artifacts. The blocks.json file is the scoring target. Each block uses repository-local coordinates in the pre-fix snapshot:

{ "file": "src/java/main/org/apache/zookeeper/server/ZooKeeperServer.java", "function": "ZooKeeperServer.shutdown", "start_line": 555, "end_line": 558 }

These coordinates are interpreted in the pre-fix checkout. Labels intentionally exclude tests, incidental refactors, defensive hardening, and cleanup unless those edits are necessary to explain the original failure mechanism.

#### A.3 Curation Process

DistDebug-Bench is curated through a staged process. The goal is to retain bugs that are realistic debugging tasks, diagnosable from issue-side evidence, and precise enough to support source-level labels.


##### Candidate discovery.

For each project, we collect historical public issues and apply automatic filters for concrete fixed bugs. The filters require closed or resolved issue status, an associated fixing change, a bug-like issue type or resolution, and an informative report. When project metadata is available, we prioritize high-impact user-facing issues, such as Major, Critical, or Blocker bugs on stable releases. We exclude feature requests, documentation-only issues, test-only issues, and reports whose description is too sparse to support diagnosis.


##### Fix-level filtering.

The fixing change is used only for curation and labeling, not as agent input. We remove broad refactorings, formatting-only changes, dependency updates, and patches dominated by unrelated cleanup. As a practical filter, we exclude fixes with more than 100 changed source lines unless the causal span is clearly separable from auxiliary edits.

##### Manual audit.

Annotators check that an issue is diagnosable from issue-side context alone. Issue reports and attached artifacts are used as the diagnosis context, while fixing commits are used only for human annotation. Later issue-thread comments that reveal the root cause or patch strategy are removed or ignored. This keeps the task focused on diagnosis from incident evidence rather than retrieval of the final answer from post-fix discussion.


##### Root-cause reconciliation.

Each accepted issue is independently inspected by three annotators. The annotators derive candidate pre-fix root-cause blocks from the fixing change and surrounding code context, exclude tests and incidental cleanup, and reconcile disagreements into a final block set. The reconciled labels are the only labels used for benchmark scoring.

The benchmark also records characterization metadata for each accepted issue. These metadata fields are not scoring targets and are not provided as hints to agents. They support the analysis in the paper by letting us break down results by textual code anchors, crash-to-fix distance, issue-side evidence, and root-cause structure.

#### A.6 Threats to Validity


##### Internal validity.

The main internal risks are that the benchmark labels or evaluator may not faithfully measure the diagnosis behavior we intend to study.

Label validity. Distributed-system fixes can include upstream state transitions, downstream guards, invariant checks, tests, and auxiliary cleanup. We mitigate this by deriving labels from the historical fixing change and surrounding code context, having three annotators independently inspect each issue, reconciling disagreements into a final block set, and labeling only the minimal pre-fix code that embodied the failure mechanism. Tests, helper refactors, defensive hardening, and incidental cleanup are excluded unless they are necessary to the causal explanation. On the 51 incidents with retained independent annotation sheets, agreement is high at the file and function levels ( Section A.5 ).

Evaluation sensitivity. A distributed-system failure may be mitigated or repaired at several locations, but the causal chain that produces it is specific. In ZooKeeper-2845, for example, one could add defensive handling later in the synchronization or recovery path. Such a change might reduce the observed inconsistency, but it would not identify the underlying bug: the retained database and shutdown/restart behavior let the state used during synchronization diverge from the transaction log. DistDebug-Bench therefore labels the causal code identified through issue resolution and expert annotation, rather than every location where a symptom could be detected, masked, or repaired; it does not claim that the historical patch is the only valid fix. A diagnosis that blames a different plausible intervention point can still receive low block coverage. The paper therefore reports file, function, line, and block metrics, together with mention coverage, which records whether the causal explanation refers to the labeled functions even when the selected blocks differ. Section G.1 shows that such alternatives explain few zero-coverage diagnoses and that higher-coverage diagnoses guide repair more effectively. Future evaluators could combine multi-reference annotations with semantic and program-analysis-based validation to better capture equivalent causal explanations.

Benchmark leakage. DistDebug-Bench is built from public user-reported failures. This makes the benchmark realistic and reproducible, but it also means that model pretraining exposure cannot be ruled out completely. Public benchmark identifiers and future fix information can contaminate an evaluation if agents retrieve them rather than diagnose from allowed evidence. We mitigate direct answer leakage during benchmark construction by removing issue-thread discussion that reveals the root cause or patch strategy, anonymizing workspace names, and removing commits after the task snapshot. The leakage guard Figure 1 scans visible reasoning and tool inputs/outputs for the original issue identifiers withheld from the agent. This check targets direct retrieval of historical answers, including searches for future fixing commits. Flagged attempts are discarded and rerun, and the team investigates residual identifiers or accessible fix information in the prepared environment. Because detection depends on explicit identifier matches, implicit recall requires separate evaluation. Section G.2 reports guard-hit counts, closed-book probes, and correlations with public-exposure proxies.


##### External validity.

The main external risk is whether conclusions from DistDebug-Bench generalize beyond this benchmark sample.

Selection bias. DistDebug-Bench intentionally focuses on closed, high-impact failures in production distributed systems whose fixes support precise source-level labeling. This selection makes the task realistic and scoreable, but it excludes failures whose fixes are dominated by broad refactorings, configuration changes, test-only changes, or ambiguous cleanup. The benchmark should therefore be interpreted as covering code-level diagnosis for labelable distributed-system bugs rather than all incident-response work.

We mitigate this risk with a principled, staged selection process. For each project, we first collect historical public issues and apply automatic filters for concrete fixed bugs: closed or resolved status, an associated fixing change, high-priority or user-facing failures when priority is available, sufficiently informative reports, and non-test/non-documentation components. We then filter by the fixing change itself, excluding broad refactorings and patches dominated by unrelated cleanup, and using a practical 100 changed-source-line cutoff unless the causal span is clearly separable from auxiliary edits. The ZooKeeper attrition example in Table 2 illustrates the scale of this filtering process. Finally, annotators manually audit the survivors to confirm that the issue-side context is diagnosable without post-report discussion, that the report does not reveal the root cause or patch strategy, and that the fixing change maps to precise pre-fix root-cause blocks. Each accepted issue is then independently annotated by three annotators and reconciled into the final label set. This process does not eliminate selection bias, but it makes the benchmark population the result of consistent filters and explicit audits rather than convenience sampling.


### Appendix B LLM-Assisted Collection Pipeline

Benchmark curation requires human review for two reasons: identifying true bug reports while excluding feature requests, and identifying the source blocks that encode each root cause. We developed an LLM-assisted pipeline for the second bottleneck. The pipeline starts from a bug-fixing commit, fetches the diff automatically, and prompts an LLM to output only the relevant root-cause blocks. Preliminary checks show a non-trivial gap between LLM-produced labels and human labels, but we still see potential in LLM-assisted automation pipelines. ### Appendix C Evaluation Prompts and Output Contract

All evaluated harnesses receive the same diagnosis task: inspect the pre-fix repository and issue-side evidence, identify the pre-fix code blocks that encode the root cause, and emit a structured diagnosis. The exact interaction syntax differs by harness, but the task-level constraints are shared:

- • the agent should diagnose rather than patch the bug;

- • the agent should not modify repository source files;

- • lightweight static analysis is preferred over long-running integration tests or networked services;

- • the final answer must be valid JSON in the required schema; and

- • each completed bug/configuration pair contributes three valid diagnoses.

The required output schema is intentionally small. The evaluator ignores optional narrative fields for scoring and compares the predicted block coordinates against the gold labels at file, function, line, and block granularity.

#### D.1 Aggregation and Statistical Uncertainty

For metric scores $s_{ir}$ on bug $i$ and attempt $r$ , we first compute $\bar{s}_{i}=R_{i}^{-1}\sum_{r=1}^{R_{i}}s_{ir}$ and then report $\hat{\mu}=n^{-1}\sum_{i=1}^{n}\bar{s}_{i}$ . Each included bug has $R_{i}=3$ selected attempts, and bugs have equal weight. Each bootstrap replicate samples $n$ bug IDs with replacement and averages their $\bar{s}_{i}$ values. The 2.5th and 97.5th percentiles of 10,000 replicate means form the reported 95% interval. We use sorted bug IDs, NumPy’s PCG64 generator with seed 2026, and linear interpolation for quantiles. Category intervals use the same procedure within each category. A cell with fewer than two bugs has no CI.

These intervals treat bugs as independent draws from the incidents the benchmark represents. They capture sensitivity to which bugs are sampled, not rerun variability on a fixed bug, which we report separately as within-bug standard deviations and flaky-bug counts. Because bugs from the same system may be correlated, Section D.2 also reports per-system and leave-one-system-out results.


##### Paired differences.

For configurations $A$ and $B$ , we compute one difference per bug, $d_{i}=\bar{s}_{i,A}-\bar{s}_{i,B}$ , and estimate $\hat{\Delta}=n^{-1}\sum_{i}d_{i}$ . Each replicate samples the same $n$ bug IDs for both configurations, equivalently resampling the $d_{i}$ values. We use the same 10,000-replicate percentile procedure, seed, and quantile convention as above. Pairing is by bug ID, not by attempt index; the three selected attempts are averaged within each bug before resampling.

#### D.3 Attempt Selection and Common Evaluation Cohort

For each bug/configuration pair, we sort attempts by numeric run ID and retain the first three with a schema-valid diagnosis.json and completed, matching scores. Attempts missing these artifacts do not occupy a slot; later completed attempts can replace them. Selection does not depend on the score: completed incorrect diagnoses, including schema-valid empty predictions, remain in the evaluation. Additional valid attempts after the first three are unused.

The primary comparison uses all 120 benchmark incidents across 17 configurations: 13 Mini-SWE model configurations, plus two models on each of Codex CLI and OpenCode. The three-attempt protocol gives $120\times 17\times 3=6{,}120$ selected attempts. The same bug cohort and attempt selection apply to accuracy, cost, variability, stratified results, and both kinds of CI.

All primary metrics are recomputed from these selected attempts before aggregation. The released selection manifest records selected run IDs, skipped attempts, extra unused valid attempts, the fixed bug cohort, and source hashes. The portable score snapshot retains the selected per-attempt scores and the common bug IDs, allowing both kinds of CI to be recomputed without access to full trajectories. Exploratory subset and separate trace analyses state their own cohorts.

#### E.6 ZooKeeper-2845 Trace Pattern

ZooKeeper-2845 is an example of early scope lock-in. The report describes retained database state during leader election, a transaction log ahead of a snapshot, and an inconsistent quorum after restart. This language makes quorum and sync code a plausible first target. Several traces therefore begin by searching or reading under src/java/main/org/apache/zookeeper/server/quorum .

The gold block, however, is in:

Runs that stay inside quorum code can build a coherent explanation around leader election or synchronization while missing the lifecycle block that controls database retention. The agent is not failing to find any relevant code; it is stopping at the most obvious symptom-side location before looking for the earlier state transition that made the symptom possible. When the report does not directly name the exact causal code, the initial issue narrative can steer the agent toward a nearby but incomplete diagnosis.


#### E.7 Implication for Future Harnesses

These observations suggest three concrete harness requirements. First, the harness should provide adaptive context construction: when an early scope is under-supported, tooling should surface adjacent files, call paths, dataflow edges, related symbols, and alternative subsystems. Second, the harness should preserve hypotheses as separate state, so evidence collected for one branch does not become the default context for all later reasoning. Third, the harness should add correctness checks that ask whether the proposed source region explains the whole causal chain, rather than merely matching a symptom, stack frame, or local code path.

#### G.1 Evaluator Validation


##### Score-blinded audit.

We audit 20 GPT-5.4 diagnoses selected for zero block coverage, with the scores hidden during qualitative assessment. The assessment distinguishes whether a diagnosis reconstructs the failure mechanism from whether it places responsibility at the annotated code location. For example, one places responsibility for a nil-pointer failure in a specific Op.check implementation, while the accepted localization is in the broader processRequest path. The remaining 16 diagnoses have an incorrect hypothesis or an incomplete causal explanation.

Plausible alternative localizations therefore do not explain most zero-score outputs: 16/20 are incorrect or causally incomplete. Block coverage measures recovery of the annotated causal implementation rather than every plausible intervention or repair point, and the four alternative diagnoses show where this distinction matters. Because the audit samples only zero-scoring outputs, these proportions describe the sample rather than a benchmark-wide false-negative rate.


##### Benchmark-wide false-negative estimate.

We estimate that rate from a stratified random sample of 100 of the 3,293 attempts with incomplete block coverage across all 17 configurations: 69 with zero and 31 with partial coverage, in proportion to the two strata. The sample contains 193 missed gold blocks. Two AI reviewers judge each missed block independently: Claude Opus 5.5 and GPT-6 Astra (run through Claude Code and Codex CLI), both at high reasoning effort, with read-only access to the pre-fix source and no network access. Each receives the issue report, the gold blocks, the historical fix as ground truth, and the diagnosis, without its score or the model that produced it. A missed block is a false negative when the diagnosis names the same code at shifted coordinates, or a different location that is itself the defect: changing it alone would prevent the reported failure, and it is not a caller, a symptom site, or a defensive check. We count a false negative only when both reviewers agree.

The reviewers agree on 85% of missed blocks (Cohen’s $\kappa=0.47$ ). Weighting each stratum by its number of missed blocks, 8.8% of missed gold blocks are false negatives, and counting them would raise block coverage by 5.0 points ( Table 19 ). Of the 17 false-negative blocks, ten name the gold code at different coordinates, mostly because the gold block was annotated against a different revision than the task snapshot; we will correct these labels in the next release. The other seven are alternative locations. Either reviewer alone yields a higher rate, so requiring agreement gives the conservative estimate.

##### Repair results.

On the six mixed cases, replacing a low-coverage diagnosis with a high-coverage one raises gold-file touch by 27.8 percentage points and gold-block touch by 50.0 points ( Table 21 ). #### G.2 Contamination Analyses


##### Direct answer retrieval and the leakage guard.

Our reward-hacking check targets a concrete shortcut: retrieving the historical fix instead of diagnosing the failure from the supplied incident evidence and pre-fix code. Early experiments ran without the leakage guard. Subsequent trace inspection revealed agents searching for and retrieving future fixing commits. Workspace paths also exposed the original issue ID, giving agents a lookup key. We therefore removed commits after the task snapshot and anonymized workspace directory names.

The guard scans visible reasoning, tool inputs, and tool outputs for the original issue ID that should have been hidden from the agent. Matches include the full issue key or its numeric component, such as git log | grep ZooKeeper-2845 and git log | grep 2845 . We apply this check to recorded trajectories, including the early experiments, and discard flagged attempts, rerunning until every bug has three clean attempts. Residual hits also prompt an audit of the prepared workspace to remove exposed identifiers or fix information. ##### Closed-book results and interpretation.

Repository-assisted coverage exceeds every closed-book variant. Providing the issue ID does not improve function coverage in these probes: identifiable reports yield 17.3%, compared with 21.4% for anonymous reports. ID-only prompts yield zero coverage at all four granularities. A separate report-to-ID probe recovers 0/360 exact target identifiers. In contrast, repository-assisted function coverage reaches 45.5% and block coverage reaches 56.9%. The gap supports codebase exploration as an important part of diagnosis: report text and issue identity alone do not recover the same causal-code detail.

Nonzero file/function coverage without repository access can reflect knowledge of project structure or clues in reports, including class and subsystem names that remain after exact gold filenames and function names are removed. For example, references to LocalHealthMonitor , InitProducerId , or QuorumCnxManager.Listener constrain plausible code regions.

Together, the trace audit identifies and removes direct answer-retrieval shortcuts, while the age analysis and closed-book probes test whether public issue exposure readily translates into accurate diagnosis. The results support the importance of exploring the repository to identify causal code. They do not rule out all pretraining exposure or implicit memorization.
