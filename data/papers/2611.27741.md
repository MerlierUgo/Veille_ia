## Can Vision-Language Models Synthesize Executable Game-Playing Programs?

Recent advances in vision-language models (VLMs) have endowed multimodal agents with increasingly strong visual perception and long-horizon reasoning capabilities, making VLM-based autonomous game playing feasible. Existing game benchmarks primarily evaluate whether an agent can select appropriate actions from the current visual state across different scenarios and games. However, most of them adopt a step-by-step interaction paradigm where the current visual observation is sent to the agent before each action. In practical deployment, this paradigm introduces two fundamental limitations: the game loop must wait for model inference, making real-time interaction impractical, and repeated VLM calls incur substantial cost. Therefore, we propose PlayScriptBench, a script-based game benchmark that evaluates whether VLMs can synthesize an executable game-playing program from game states. This setting jointly evaluates visual grounding, understanding of game dynamics, long-horizon strategic reasoning, and executable program synthesis, providing a more comprehensive assessment of game-playing agents. To support more tractable evaluation for current general-purpose VLMs, we further introduce a four-stage pipeline — Explore, Perception, API Construction, and Strategy Composition — that decomposes controller synthesis into game exploration, state perception, interface construction, and strategic control, enabling agents to progressively construct an executable program. Experiments on 16 games spanning 4 genres show that even strong VLMs struggle on our benchmark, revealing a substantial gap between passive visual game understanding and executable closed-loop game control. These results establish script-based controller synthesis as a complementary direction for benchmarking VLM-based game-playing agents.

### 1 Introduction

> Figure 1: Comparison of evaluation protocols. Left: Existing game-agent benchmarks invoke the VLM inside the observation–action loop: every frame, the model receives a screenshot and predicts an action. Right: PlayScriptBench inverts the protocol—the VLM is queried only once during a development phase to synthesize an executable controller, which then runs autonomously.

Recent advances in vision-language models (VLMs) have endowed multimodal agents with increasingly strong visual perception and long-horizon reasoning capabilities, making VLM-based autonomous game playing feasible [ Ouyang et al. 2026 ] . A parallel thread—visual program synthesis (VPS) [ Surís et al. 2023 , Gupta and Kembhavi 2022 , Lu et al. 2023 ] —demonstrates that LLMs can generate executable Python programs from visual inputs, grounding language in composable code modules for visual reasoning. Video games provide a natural testbed for both capabilities: they demand fine-grained visual understanding of dynamic scenes and sustained planning to achieve goals, making them an ideal benchmark for evaluating whether VLMs can act autonomously in visual environments.

Yet the way current game benchmarks are designed constrains how VLMs can participate in games (Figure 1 , left). Whether the target is arcade games [ Zhang et al. 2026 ] , open-world sandboxes [ Ouyang et al. 2026 ] , or puzzle environments [ Ouyang et al. 2026 ] , the per-frame VLM-in-the-loop design is pervasive: at every step, the model receives the current observation, predicts the next action, and executes it, before repeating the cycle from scratch. While practical mitigations—frame skip, observation caching, or asynchronous inference—can reduce per-step cost and latency, the paradigm still ties inference budget to game duration and limits the controller to the model’s instantaneous reasoning horizon. PlayScriptBench inverts this design: instead of querying the VLM at every frame, we ask it to synthesize a standalone executable controller that runs autonomously at native frame rate. This decouples inference cost from play time. We note that this paradigm is complementary to, not a replacement for, per-frame inference: script synthesis compresses visual understanding into persistent code and is most informative for deterministic, bounded-state games, whereas per-frame inference excels at online reactivity in open-world or stochastic environments.

We introduce PlayScriptBench as a complementary benchmark that targets this script-synthesis regime. PlayScriptBench is a script-based game benchmark that evaluates whether VLMs can synthesize an executable game-playing program from game states, focusing on the class of deterministic, bounded-state games where a static controller can in principle play reliably. Visual program synthesis serves as the evaluation means ; game behavioral performance is the evaluation end . The task requires the model to perceive game state from pixels alone—no privileged API access—and produce a persistent, stateful controller under closed-loop execution. Synthesizing such a controller is not a one-shot code generation problem: implicit game parameters must be discovered empirically through interaction. PlayScriptBench therefore structures the task as a four-stage pipeline (Figure 2 )— Explore , Perception , API Construction , and Strategy Composition —that decomposes controller synthesis into perception, interface construction, and strategic reasoning, each producing an independently scorable artifact. We further decouple visual grounding from strategic reasoning by scoring each dimension separately, enabling fine-grained failure diagnosis that a single end-to-end score collapses. A Joint score (Perception $\times$ Strategy under Oracle perception) isolates strategy competence from perception failures, dropping to zero whenever either component fails.

We evaluate frontier VLMs on a diverse set of 16 games spanning 4 genres. Our results reveal a substantial gap between passive visual game understanding and executable closed-loop game control. Even strong VLMs struggle on our benchmark: models that fluently describe a static screenshot frequently fail to produce controllers that act reliably under live gameplay, suggesting that closed-loop debugging remains an open challenge.

Our contributions are as follows.

- 1. A four-stage Explore–Perception–API Construction–Strategy Composition pipeline that enables VLMs to develop fully functional game controllers, with each stage producing a diagnosable artifact.

- 2. PlayScriptBench, a complementary benchmark on 16 deterministic, bounded-state HTML5 games spanning 4 genres, behind a uniform browser-based sandbox that pauses the game during inference so evaluation reflects what the agent decides, not how fast it responds.

- 3. An initial evaluation of 13 frontier VLMs exposing failure modes in perceptual grounding, strategic reasoning, and implicit parameter reasoning, with a Joint score (Perception $\times$ Strategy under Oracle perception) as a diagnostic measure of strategy competence.


### 2 Related Work

VLM and LLM gameplay agents. A growing body of work deploys LLMs and VLMs as gameplay agents. Voyager [ Wang et al. 2023a ] , JARVIS-1 [ Wang et al. 2023b ] , and MineDojo [ Fan et al. 2022 ] use LLM planners in Minecraft but rely on privileged game state; Cradle [ Tan et al. 2024 ] and STEVE-1 [ Lifshitz et al. 2024 ] adopt a strict screenshot-in, action-out interface, demonstrating vision-only play is feasible. GameWorld [ Ouyang et al. 2026 ] , VideoGameBench [ Zhang et al. 2026 ] , Orak [ Park et al. 2026 ] , LMGame-Bench [ Hu et al. 2025 ] , GameDevBench [ Chi et al. 2026 ] , and MCU [ Zheng et al. 2023 ] evaluate VLMs on large game suites under vision-only protocols, but their agents predict actions one step at a time. PlayScriptBench instead requires program synthesis of a complete controller, forcing explicit perceptual grounding via OpenCV-based code, and separates parameter discovery from controller synthesis for finer-grained diagnosis. The two paradigms are complementary: per-frame inference excels at real-time reactivity, while script synthesis tests the ability to compress visual reasoning into persistent code.

Visual program synthesis and code-synthesis evaluators. A parallel lineage uses LLMs to generate executable programs from visual inputs. ViperGPT [ Surís et al. 2023 ] , VisProg [ Gupta and Kembhavi 2022 ] , Chameleon [ Lu et al. 2023 ] , ProgPrompt [ Singh et al. 2022 ] , and CodeVQA [ Subramanian et al. 2023 ] ground language in executable visual modules, but target stateless, single-inference tasks. A related thread evaluates generated code by executing it in interactive environments: Voyager [ Wang et al. 2023a ] synthesizes skill libraries from privileged Minecraft state; Eureka [ Ma et al. ] synthesizes reward functions for physics simulations; Code World Models [ Lehrach et al. 2025 ] learn code-based world models; PlayCoder [ Peng et al. 2026b ] and ProxyWar [ Peng et al. 2026a ] evaluate code by execution outcome in games and GUIs. PlayScriptBench extends both lines to stateful, closed-loop control under a strict vision-only constraint—no DOM, memory, or game-state access—structured as a four-stage pipeline producing independently scorable artifacts, exposing failure modes (drift accumulation, temporal grounding, strategic reasoning) absent from single-shot VPS or privileged-state evaluators.

General agent benchmarks. WebArena [ Zhou et al. 2024 ] , VisualWebArena [ Koh et al. 2024 ] , OSWorld [ Xie et al. 2024 ] , and AgentGym [ Xi et al. 2025 ] evaluate multimodal agents in web or desktop environments, typically granting access to DOM or accessibility trees alongside screenshots, which already encode much of the task-critical information and reduce the perceptual challenge. Text-based game benchmarks such as TextWorld [ Côté et al. 2019 ] and ALFWorld [ Shridhar et al. 2021 ] take the opposite approach, stripping away visual input entirely. PlayScriptBench targets the underserved middle ground: visual environments where agents must extract game state entirely from pixels, without the symbolic abstraction of text games or the structured state access of web agents. GameplayQA [ Wang et al. 2026b ] benchmarks decision-dense video understanding in 3D game environments in a passive QA format, whereas PlayScriptBench requires closed-loop executable scripts.

### 3 Game Agent

PlayScriptBench evaluates VLMs as game agents under a strict protocol. This section formalizes the agent artifacts, the evaluation harness, and the oracle–VLM probe mechanism that enables fine-grained failure attribution.


#### 3.1 Agent Artifacts

Unlike GameWorld [ Ouyang et al. 2026 ] , which studies both computer-use agents (CUA) that emit low-level keyboard/mouse controls and general-agent baselines that predict one action per frame, PlayScriptBench requires the VLM to author four distinct Python artifacts across the pipeline, each consumed by the next stage.

Stage 0 – Explore. Given only the game rules and a representative screenshot, the VLM freely plays the game for a short rollout, observing game mechanics, visual elements, and control responses. An analyst VLM then distills the screenshots and stdout into a structured markdown summary covering game phases, action effects, visual layout, and dynamics. This summary— exploration insights —is consumed by Stage 1 as qualitative context for writing the perception routine.

Stage 1 – Perception. Injected with the exploration insights from Stage 0, the VLM writes a perceive(frame) function that extracts structured game-state attributes from a raw RGB frame. The function receives two inputs beyond the frame itself: (i) exploration insights distilled by Stage 0, which provide qualitative understanding of game mechanics, visual layout, and action effects; and (ii) sample frames from a curated dataset, giving the VLM visual reference for colors, geometry, and anti-aliasing. The function must identify and localize all game-relevant elements—player position, obstacles, collectibles, UI indicators—and return a typed dataclass instance. For games requiring frame-to-frame deltas (e.g., motion-based detection), the signature extends to perceive(frame, prev_frame) . A companion Constants task asks the VLM to fill in a Constants dataclass with concrete values for geometric quantities (positions, sizes) and physical rates (e.g., bridge extension speed), derived either from visual observation or from experiment samples embedded in the prompt.

Stage 2 – API Construction. The VLM writes a GameAPI class that reshapes raw perceptual outputs into strategy-facing interfaces. For example, if Stage 1 detects “block at position (x, y) ”, Stage 2 might expose methods like get_nearest_obstacle() or is_jump_safe() . The class is instantiated on each frame’s state (a SimpleNamespace derived from the perception output) and its methods are compared against an Oracle reference implementation.

Stage 3 – Strategy Composition. The VLM writes a play(env) function that implements the game strategy. The controller is executed end-to-end in the sandbox; the harness captures score and survival time, and each frame is captured as an RGB array and passed to perceive() as input (Figure 3 ). The best controller is then executed across multiple seeds for robustness verification.

This decomposition makes failure attribution concrete: a model that perceives accurately but plays poorly has a strategy defect, while one that perceives poorly cannot produce a viable controller—a distinction that any single end-to-end score collapses.


#### 3.2 Evaluation Harness

Foundation models alone are insufficient for sustained gameplay: the agent needs structured prompts and persistent memory to author coherent controllers. Therefore, we wrap each model in a shared evaluation harness that standardizes these components across all models.


##### 3.2.1 Structured Prompt

To reduce prompt-induced variance across models and games, each stage uses a fixed prompt template that includes Game Rules, the stage-specific specification file (perception_spec.py, api_spec.py, or the combined prepend code), and Output Format. The template structure stays constant across all experiments; only the game-specific content is swapped per configuration, keeping cross-model comparisons controlled.


##### 3.2.2 Prepend Code Injection

Unlike per-step agents that receive raw observations, PlayScriptBench’s synthesized controllers operate on structured state. The harness injects a prepend code block into the execution scope of each play() function, containing the perception specification, the chosen perceive() implementation (Oracle or VLM-authored), an adapter that wraps dict returns in SimpleNamespace for attribute access, and discovered constants. This mechanism decouples perception from strategy: the play() function calls perceive(frame) and operates on the returned state object without knowing whether the perception layer is Oracle-provided or VLM-authored.


#### 3.3 Oracle–VLM Probe Mechanism

Without decoupling, the strategy score inherently conflates visual grounding with strategic reasoning, so a low score cannot distinguish between poor perception and poor strategic planning. A key design choice is the ability to swap the perception layer in Stage 3, enabling two evaluation modes that isolate different failure modes. In the default oracle mode, Stage 3 receives the Oracle’s perceive() and GameAPI , so the play() function operates on ground-truth state, measuring strategic reasoning in isolation. A --use-vlm-probe mode instead plugs in the VLM’s own Stage 1 and Stage 2 artifacts, so errors propagate end-to-end and the full pipeline is tested. A controller must both perceive and act correctly to succeed; the Joint score ( $\mathrm{Obs.}\times\mathrm{Stra.}$ , where $\mathrm{Obs.}=(\mathrm{Per.}+\mathrm{API.})/2$ ) collapses to zero whenever either component fails—a diagnostic measure of strategy competence under Oracle perception.


### 4 PlayScriptBench Benchmark

This section describes the benchmark design, the game suite, the browser-based sandbox environment, and the four-stage evaluation pipeline.


#### 4.1 Benchmark Design

PlayScriptBench evaluates a VLM’s ability to author a closed-loop controller for an unfamiliar HTML5 game, given only the game’s rules and a single representative screenshot. The benchmark enforces a strict protocol: the agent receives only raw RGB frames and a keyboard/mouse action interface, with no access to source code, runtime memory, or any state-querying API.

Three principles guide the design. First, perception must live inside the synthesized controller—unlike benchmarks that grant access to DOM trees, accessibility trees, or game-specific APIs, PlayScriptBench requires the model to implement its own OpenCV-style perception routines. Second, evaluation must be behavioral—controllers are graded by execution score through direct gameplay, not by code quality or textual output. Third, diagnosis must be fine-grained—the four-stage pipeline separates parameter discovery from controller construction, enabling attribution of failure to perception, reasoning, or control.


#### 4.2 Games Environment and Suite

The 16 games currently supported by PlayScriptBench span four genres: runner (continuous scrolling with reflexive obstacle avoidance, e.g., Flappy Bird, Geometry Dash, Chrome Dino), arcade (discrete turns or real-time scoring in a fixed arena, e.g., Pac-Man, Snake, Knife Hit), puzzle (logical reasoning or optimization over a static or semi-static board, e.g., 2048, Minesweeper, Tetris), and platformer (vertical or horizontal navigation across platforms with physics-driven movement, e.g., Doodle Jump, Helix Jump). Games are rendered by a mix of DOM, HTML5 Canvas, and Three.js engines, and accept either keyboard or mouse input, forcing the agent to adapt its perception and control strategy to the underlying representation.

Each game ships with a game configuration that specifies the viewport, action mapping, and any game-specific status flags consumed by the evaluation harness.


#### 4.3 Browser-Based Sandbox Environment

The central design goal of the sandbox is to decouple agent decision quality from inference speed. In real-time games, a slower model faces a harder game state by the time it acts, conflating thinking time with gameplay ability. To eliminate this confound, the sandbox pauses game execution during controller synthesis, so every agent faces identical game dynamics regardless of response latency. Scores then reflect what the agent decides, not how fast it responds.


#### 4.4 Evaluation Pipeline

The benchmark decomposes evaluation into four stages, each producing an artifact that the next stage consumes. All four stages are executed by the same VLM, with no separate models assigned to individual stages. This decomposition isolates whether failure stems from perceptual grounding, API construction, or strategic reasoning—diagnoses a single end-to-end score cannot provide. The pipeline supports two evaluation modes: oracle mode (default) tests strategic reasoning alone by providing Oracle perception, while VLM probe mode tests the full pipeline end-to-end by using the VLM’s own perception artifacts.


##### 4.4.1 Stage 0 – Explore

The analyst VLM distills the rollout screenshots and stdout into a structured markdown summary. The summary is evaluated for coverage (game phases, action effects, visual layout, dynamics) and accuracy against the game specification. The resulting exploration insights artifact is consumed by Stage 1 as qualitative context.


##### 4.4.2 Stage 1 – Perception

The VLM produces a perceive() function and a Constants dataclass. The grader evaluates perception accuracy by running the VLM-authored function on curated frames with known ground truth, measuring per-attribute precision and recall against specification tolerances. The Constants task is scored by comparing filled values against verified reference constants.


##### 4.4.3 Stage 2 – API Construction

The VLM produces a GameAPI class that exposes strategy-facing interfaces over perceptual outputs. The grader instantiates the VLM-authored API on each frame’s oracle perception output, invokes every method, and compares results against the oracle reference implementation. Per-method functional correctness is measured, aggregating into an overall API score.


##### 4.4.4 Stage 3 – Strategy Composition

The VLM produces a play(env) controller. Evaluation proceeds in two phases. Phase 1 (Generation): The controller is executed end-to-end in the sandbox; the harness captures score and survival time, and each frame is passed to perceive() as input. Phase 2 (Multi-Run Verification): The controller is executed $N$ times on a seed set, reporting score and survival time as mean $\pm$ standard deviation along with a discrete execution status (pass, run-time error, timeout). Reporting variance is essential: many HTML5 games are stochastic, and a controller that occasionally scores well by luck is meaningfully different from one that scores reliably.

A key design choice is the ability to swap the perception layer in Stage 3. By default (oracle mode), the controller receives the Oracle’s perceive() and GameAPI , testing strategic reasoning alone. With the --use-vlm-probe flag, the controller receives the VLM’s own Stage 1 and Stage 2 artifacts, testing the full pipeline end-to-end. Comparing scores between these two modes reveals whether failure stems from perceptual grounding or strategic reasoning.

#### 6.1 Explore Stage (Stage 0)

Without Explore, Stage 1 receives only the game rules and perception spec, forcing the model to infer visual properties (color signatures, object positions) solely from the spec’s dataclass definitions. With Explore, the model additionally receives structured observations—e.g., color signatures and spatial layouts of game objects—that provide qualitative grounding for the perception routine.

The Explore benefit is most pronounced on games whose visual elements cannot be inferred from the spec alone, while games with visually self-documenting specs show smaller drops. On GPT-5.6 Luna, removing Explore reduces Obs. from 0.685 to 0.395 ( $-42.3\%$ ), with Per. dropping from 0.793 to 0.463 and API. from 0.576 to 0.327. On Qwen 3.6 Plus, Obs. drops from 0.472 to 0.345 ( $-26.9\%$ ), a more modest decline consistent with this model’s stronger prior for visual property extraction from text. The arrow statistics in Table 2 corroborate this: on GPT-5.6 Luna, 6 out of 16 games degrade by more than 10% without Explore while only 1 improves; on Qwen 3.6 Plus, 8 degrade and 1 improves.


#### 6.2 Perception and API Construction (Stages 1–2)

Two patterns emerge from the perception and API construction stages. First, Stage 2 accuracy drops sharply when Stage 1 is imperfect: on Knife Hit, 74% perception accuracy yields only 3% API accuracy, indicating that perception errors are amplified rather than corrected by the reasoning layer. Second, even the sole perfect game (Match-3 at 100% across both stages) leaves the strategy layer to handle residual execution challenges—the gap between perfect observation and high gameplay score remains non-trivial.

Removing perception entirely (w/o Stage 1) collapses API accuracy to 0.251/0.149 for GPT-5.6 Luna/Qwen 3.6 Plus since the VLM cannot provide perceptual state to the API layer. Removing GameAPI (w/o Stage 2) destroys Stra. (0.255 $\to$ 0.036, $-86\%$ for GPT-5.6 Luna) as the model cannot reason over raw state tuples.

The Probe stage provides measurable benefits when visual parameters are discoverable. For games with clear color signatures and grid geometry (Tetris, Match-3), injected measurements improve perception accuracy. However, for games with dynamic visual elements (Flappy Bird, Knife Hit), the Probe stage contributes less, as the critical parameters change during gameplay.


#### 6.3 Oracle vs. VLM Probe

Replacing the Oracle perception with the VLM’s own Stage 1 and Stage 2 artifacts (w/o Oracle) collapses strategy score to near zero (0.013 for GPT-5.6 Luna, 0.052 for Qwen 3.6 Plus), with the majority of games showing degradation. This confirms that the strategy layer’s performance is tightly coupled to perception quality: even models with strong perception (Stage 1 accuracy 0.793) produce controllers that fail when operating over their own perceptual outputs. The gap between Oracle mode (Stra. 0.255) and VLM probe mode (Stra. 0.013) for GPT-5.6 Luna indicates that perception errors propagate through API construction into catastrophic strategy failures, validating the pipeline’s decomposition of these concerns.

This yields a 2.14 $\times$ speedup (19.7 vs. 42.1 min) alongside a 68.1% higher strategy score (0.600 vs. 0.357). Note that our Stra. is measured under Oracle perception while the in-loop baseline uses its own perception, so this gap reflects amortization under non-matched state access.


### 7 Conclusions and Limitations

PlayScriptBench introduces a complementary script-based evaluation protocol for VLM gameplay agents, shifting from per-frame decision-making to reusable controller synthesis on the class of deterministic, bounded-state games where static controllers can play reliably. Our four-stage pipeline—Explore, Perception, API Construction, and Strategy Composition—decomposes controller synthesis into perception, interface construction, and strategic reasoning, enabling fine-grained diagnosis of failure modes that a single end-to-end score cannot reveal. Our evaluation of frontier VLMs on 16 HTML5 games reveals a substantial gap between passive image understanding and active closed-loop control: perceptual anchoring is fragile, and perception accuracy is necessary but not sufficient, with the bottleneck lying in API construction and strategic reasoning.

PlayScriptBench targets deterministic, bounded-state games, and the synthesized controllers cannot adapt their strategy online. Future work includes introducing online VLM feedback for runtime script refinement and scaling the game suite to cover more genres.

#### A.3 Scoring Methodology

This appendix details the grading criteria for Per. (Stage 1), API. (Stage 2), and their aggregation into the composite metrics reported in the main results.


##### A.3.1 Perception Score

Per. measures how accurately the VLM-authored perceive() function extracts structured game state from raw screenshots. For each game, a curated set of frames with manually verified ground truth is used. The grader runs the VLM’s perceive() on each frame and compares every declared attribute against the oracle, counting individual hits and misses . The per-game score is the ratio of total hits to total expected attributes across all frames:

[Tableau] $$\mathrm{Per}_{g}=\frac{\text{total hits}}{\text{total expected attributes}}.$$

Attribute types and comparison rules. Each attribute is compared according to its declared type:

- • Numeric ( int , float ): A hit is scored when $|v_{\text{probe}}-v_{\text{oracle}}|\leq\tau$ , where $\tau$ is a per-field tolerance declared in the game’s perception specification. For angular fields (e.g., arc angles, ball rotation), circular distance $\min(d,\;2\pi-d)$ is used to handle wrap-around.

- • Boolean : Both sides are coerced to bool and compared by exact equality.

- • Enum / string : Exact equality is required.

- • List by index (e.g., pipes , platforms ): Elements are matched positionally. Each element’s sub-fields are compared via the rules above. If the probe returns fewer elements than the oracle, missing elements count as misses for all their expected sub-fields.

- • Nested list (e.g., board grids in 2048, Minesweeper, Tetris): Cell-wise comparison—each cell $[r][c]$ is compared individually, and the score reflects the fraction of correctly identified cells.

- • List by color (e.g., arcs in Color Switch): Elements are matched by a color key, then non-color sub-fields are compared via tolerance.

If the VLM’s perceive() throws an exception on a frame, all expected attributes for that frame are counted as misses.

Tolerance calibration. Tolerances are set per game and per field by the benchmark authors based on the visual resolution and gameplay sensitivity of each attribute. Representative tolerances are shown in Table 9 . Spatial tolerances (in pixels) reflect the minimum detection error that would causally affect gameplay; tighter tolerances are used for grid-aligned games (e.g., Snake, Minesweeper) where cell-level accuracy is required, while looser tolerances apply to fast-scrolling games (e.g., Geometry Dash) where approximate obstacle positions suffice for control.

##### A.3.2 API Score

Stage 2 score measures functional correctness of the VLM-authored GameAPI class, which wraps perceptual state into strategy-facing methods (e.g., get_empty_cells() , get_closest_obstacle() ). For each method on each frame, the grader invokes both the VLM’s API (fed with the VLM’s own Stage 1 probe output) and the oracle API (fed with ground-truth state), then compares their return values.

Per-method comparison strategies. Different return types require different comparison semantics. The grader dispatches to one of the following strategies per method:

- • Exact equality ( exact ): Python == —used for scalar returns, booleans, and simple structs.

- • Set equality ( set_equal ): Order-independent comparison—used for unordered collections (e.g., palette tuples).

- • Ordered equality ( ordered_equal ): Ordered list comparison.

- • Element-wise ( by_index ): Positional list comparison, used for method returns that are ordered sequences.

- • Tolerance ( tolerance ): Absolute tolerance on numeric returns, analogous to Per.’s numeric comparison.

- • Dict tolerance ( dict_tol / dict_tol_rel ): Per-key comparison for dict returns, supporting both absolute and relative tolerances on individual keys.

The per-game API. is:

[Tableau] $$\mathrm{API}_{g}=\frac{\text{method calls returning correct output}}{\text{total method calls}}.$$

Diagnostic metric. In addition to the primary Stage 2 score (VLM API on VLM probe state), we report a secondary API-on-GT metric: the VLM API evaluated on oracle ground-truth state. This isolates API implementation quality from upstream perception errors, allowing diagnosis of whether Stage 2 failure stems from incorrect API logic or from corrupted input state.


##### A.3.3 Composite Metrics

Obs. Obs. is the arithmetic mean of Per. and API. scores for a given game:

[Tableau] $$\mathrm{Obs}_{g}=\frac{\mathrm{Per}_{g}+\mathrm{API}_{g}}{2}.$$

Strategy Score (normalized). Raw Stage 3 strategy scores (game points) are not directly comparable across games. We apply per-game min-max normalization across all evaluated models:

[Tableau] $$\mathrm{Stra}_{g}=\frac{s_{g}-\min_{m}s_{g,m}}{\max_{m}s_{g,m}-\min_{m}s_{g,m}},$$

where $s_{g,m}$ is the raw mean score of model $m$ on game $g$ over 10 random seeds. When all models achieve the same score ( $\max=\min$ ), the normalized score is $0$ .

Joint Score. The end-to-end Joint score captures the multiplicative dependency between observation and strategy:

[Tableau] $$\mathrm{Joint}=\frac{1}{G}\sum_{g=1}^{G}\mathrm{Obs}_{g}\times\mathrm{Stra}_{g}.$$

A model that perceives perfectly but cannot act, or vice versa, receives a Joint score near zero—enforcing that both components must succeed for a model to score well.

Why Oracle-conditioned Strategy is the primary metric. A naively end-to-end metric—replacing Oracle perception with the VLM’s own Stage 1/2 artifacts in Stage 3—collapses to near zero for most models (Table 2 , “w/o Oracle”: 0.013 for GPT-5.6 Luna, 0.052 for Qwen 3.6 Plus). This is not informative: an error in any single perceived attribute (a mislocalized player, a misclassified obstacle) typically breaks the play() controller outright, so the resulting score conflates any perception imperfection with total strategy failure. With most models clustered near zero, the metric loses discriminative power both across models and across games. We therefore report Oracle-conditioned Strategy as the primary metric (it isolates strategic reasoning once perception is held fixed) and retain the VLM-probe mode as a diagnostic in Table 2 for measuring how perception errors propagate into strategy collapse.


#### A.4 Stage 0 Free-Exploration Mechanism

Stage 0 (Explore) provides the VLM with qualitative familiarity with the game before downstream stages attempt structured perception and control. The paper’s phrase “VLM freely plays the game for a short rollout” is implemented as a code-generation-then-execution pipeline rather than an interactive agent loop, as detailed below.


##### A.4.1 Script Generation

The VLM receives a text-only prompt (no screenshots) consisting of the game’s natural-language rules and the sandbox environment API. It is asked to produce a single Python function play(env) that exercises the game. The available API is:

- • env.reset() — reset the game to its initial state.

- • env.step(action_id) — submit a discrete keyboard event (mapped to the game’s configured key bindings via Playwright).

- • env.click(x, y) — issue a mouse click at pixel coordinates (for mouse-controlled games).

- • env.screenshot(label) — capture a labeled RGB frame for later analysis.

- • env.get_score() — read the current visible game score.

- • env.mark_game_started() — signal that intentional play has begun (disables start-screen detection).

The VLM generates this script in a single forward pass; there is no iterative action-selection loop. If the generated code contains a syntax error, the grader retries up to two times with the error message appended to the prompt.


##### A.4.2 Script Execution and Frame Capture

The generated play(env) function is executed in a headless Chromium browser via Playwright. Each call to env.step() triggers the corresponding keyboard event on the game’s DOM or Canvas element and automatically captures the resulting frame as an RGB numpy array. Labeled screenshots requested via env.screenshot() are saved separately. The script runs under a 90-second wall-clock timeout; execution also terminates on game-over or when the script returns.

After execution, a subset of frames is persisted to disk: the first, last, and evenly spaced intermediate frames (key frames).


##### A.4.3 Analyst Distillation

A second VLM call—the analyst —receives the game rules, the exploration script, stdout output, and up to eight labeled screenshots from the rollout. The analyst is instructed to produce a structured markdown summary covering:

- • Game phases : start overlay, gameplay goal, game-over triggers.

- • Action effects : one-line descriptions of visible changes per action.

- • Visual layout : key objects and approximate spatial relationships (qualitative, no pixel estimates).

- • Dynamics : objects that move, scroll, or change over time.

- • Non-obvious facts : game mechanics that a downstream planner might misinterpret.

The analyst is explicitly instructed not to estimate pixel coordinates, radii, or color ranges—those measurements are the responsibility of Stage 1.


#### A.5 VLM-in-Loop Baseline: GameWorld-Style Continuous Inference

To contextualize PlayScriptBench’s batched pipeline against the dominant agent-loop paradigm, we implement a GameWorld-style continuous observation-action loop as a baseline. This baseline mirrors the architecture used by GameWorld [ Ouyang et al. 2026 ] and similar VLM agent benchmarks: at every timestep, the VLM receives a screenshot of the current game state and outputs a single action.


##### A.5.1 Loop Architecture

The loop follows a strict observe $\to$ infer $\to$ act cycle with no code generation or caching:

- 1. Pause and screenshot : The game is paused, and the current frame is captured as an RGB image.

- 2. VLM inference : The frame is base64-encoded and sent to the VLM along with a prompt containing the game rules, available actions, and a history of the last 5 steps. The model is instructed to reply with a single action name (e.g., "left" ).

- 3. Resume and execute : The game is resumed, the parsed action is mapped to a keyboard event and applied to the game via Playwright.

Unlike PlayScriptBench’s pipeline, no code is generated—the VLM is queried at every step, and its text output is directly interpreted as an action. There is no perceive function, no API abstraction, and no strategy search.


##### A.5.2 Per-Step Prompt

Each VLM call receives the following prompt structure:

- • Role : You are playing a video game. Analyze the screenshot and choose the best action.

- • Game rules : natural-language description of the game (identical to the rules used in Stage 0).

- • Action space : enumerated list of valid actions with their IDs (e.g., 0 (action up) , 1 (action right) ).

- • History : the last 5 steps with their chosen actions and resulting scores, providing short-term context.

- • Instruction : Reply with ONLY the action name (e.g. "right" or "jump"). No explanation.

The system prompt is You are a game player. Output only the action name. No chain-of-thought, no structured output format, and no reasoning instructions are provided.


##### A.5.3 Action Parsing

The VLM’s free-form text response is parsed by matching against known action names (case-insensitive substring match). If no match is found, a fallback dictionary maps common synonyms (e.g., "jump" $\to$ up , "move_left" $\to$ left ). On complete parse failure, the first action in the action space is selected as default.


##### A.5.4 Metrics Collection

Every VLM call is instrumented via the shared MetricsCollector , recording prompt tokens, completion tokens, total tokens, reasoning tokens, and wall-clock latency. The per-step log captures the action taken, score, reward, and whether the game terminated, enabling post-hoc analysis of token consumption and agent behavior.


#### A.6 Pipeline Configuration: Prompt Templates and Feedback Formats

This appendix details the prompt structure and inter-stage feedback mechanisms for each stage of the four-stage pipeline.


##### A.6.1 Stage 0: Free Exploration

Stage 0 runs for a single round. The round proceeds in three phases: the VLM generates a play(env) exploration script, the script is executed under a 90-second wall-clock timeout, and a VLM analyst distills captured screenshots and stdout into structured insights. Syntax errors in the generated script trigger up to 2 retries with the error message appended.

The script-generation prompt carries the system message You are a game exploration agent. Output a Python play(env) function. and includes the game rules, the environment API documentation ( env.reset() , env.step(action) , env.screenshot(label) , env.get_score() , env.click(x,y) , env.mark_game_started() ), and instructions to freely operate the game while taking screenshots before and after each action. The prompt explicitly forbids using env.annotate() , printing pixel coordinates or color values, and attempting to score well.

The analyst prompt receives the game rules, the exploration script (truncated to 2000 characters), stdout (truncated to 1500 characters), and up to 8 labeled screenshots. Under the system message You are a careful game analyst. Output markdown bullet points. , the analyst must produce insights under five headings: Game Phases, Action Effects, Visual Layout, Dynamics, and Non-obvious Facts, without estimating pixel coordinates or quantitative measurements. The final artifact is a consolidated markdown file passed to Stage 1 as qualitative context.


##### A.6.2 Stage 1: Perception

Stage 1 runs for a single round with up to 2 syntax retries. The exam prompt uses the system message You are a computer vision expert. Output a single Python function. and presents the game rules, any exploration insights from Stage 0, the complete perception_spec.py source verbatim (defining the GameState dataclass and perceive() stub), and, when applicable, constants calibration samples as a table of experimental measurements. The task is to complete perceive(frame) (or perceive(frame, prev_frame) for two-frame games) and optionally fill in CONSTANTS = Constants(...) with concrete values. The prompt emphasizes that the transformation must be pure (no env calls, no I/O) and that the dataclasses are pre-defined and must not be re-declared. It is accompanied by 3 diverse sample frames biased toward interesting non-empty states.

The prompt includes a self-verification section in which the probe is executed on up to 5 evenly-spaced frames and a per-field textual summary is produced for each, allowing the VLM to visually compare its detection values against the images.


##### A.6.3 Stage 2: API Construction

Stage 2 runs for a single round with early stopping at 95% API accuracy and up to 2 syntax retries. The prompt uses the system message You are a Python expert. and provides the game rules, the complete perception_spec.py source (so the VLM understands the state shape received by the constructor), the complete api_spec.py source (containing the GameAPI class template and METHOD_SPECS with method signatures, return types, and comparison strategies), and sample frame count for visual context. The VLM must implement only the GameAPI class body, where the constructor receives a SimpleNamespace and the get_* methods must be pure (no env calls, no I/O, no derived quantities or decision logic). When Stage 1 is skipped, a variant prompt is used in which the constructor receives a raw RGB ndarray instead of perceived state, and the VLM must implement perception logic inside the class methods.


##### A.6.4 Stage 3: Strategy Composition

Stage 3 runs for a single round with up to 3 syntax retries and a 60-second wall-clock timeout per play() execution. Verification runs the generated script with 3 screening seeds ( [42, 123, 456] ) and additional robustness seeds.

The prompt uses the system message Write a Python game automation script using the provided GameAPI. and includes the game rules, available actions, environment API documentation, calibration constants as UPPERCASE module-level variables, GameAPI method signatures (docstrings only, not full implementation, to prevent copying stubs), For games requiring real-time measurement of physical constants (e.g., GRAVITY , TAP_IMPULSE , EXTEND_RATE ), a physics probe section instructs the VLM to measure these via environment experiments at the start of play() . The prompt constrains that perceive() and GameAPI are in scope and must not be redefined, a new GameAPI instance must be created on every frame, the function must exit on terminated=True , and time.sleep() is forbidden.

#### A.8 Failure Mode Analysis

We categorize model failures into three recurring patterns across the pipeline, each tied to a distinct cognitive limitation.

(P1) Hallucinated visual grounding (Stage 1). Rather than leveraging the structured perceive() interface, models frequently author hand-coded computer-vision pipelines that guess visual parameters from scratch. A representative example is HSV color thresholding: models hallucinate hue/saturation/value ranges (e.g., lower_yellow = [20, 100, 100] ) that may not match the actual game sprites—producing zero detection accuracy despite the game having high-contrast visual elements. More subtly, models occasionally apply color-space conversions incorrectly (e.g., BGR2HSV on RGB input), producing systematically shifted detections. This failure pattern is widespread: across the evaluated models, few consistently avoid inventing detection heuristics when the prompt provides the opportunity to do so.

(P2) Perception–API cascade (Stage 2). Stage 2 failures are dominated by upstream error propagation rather than API code defects. When Stage 1 perception returns partial or invalid state, the GameAPI constructor receives a None -typed state object, causing AttributeError on every method invocation. On Doodle Jump, GLM-4.6V achieves 0.85 perception accuracy but scores 0.0 on API construction because the perceive() function fails on boundary frames (game-over screens), injecting None into the state stream. Even when perception is structurally correct, CV-derived coordinates contain pixel-level noise (off by 1–2 px per frame), which accumulates across stacked method calls and degrades API accuracy below the threshold needed for downstream strategy. The cascade effect means that a model’s Stage 2 score is bounded above by its Stage 1 accuracy—a ceiling that cannot be broken through without improving perception first.

(P3) Syntactically valid, strategically vacuous (Stage 3). The most common Stage 3 failure is code that parses and executes without error but produces no meaningful gameplay. Among all Stage 3 rounds, a larger class of failures produces syntactically valid controllers with flawed decision logic: Snake controllers use greedy single-step pathfinding without accounting for body growth, and Tetris controllers lack piece-rotation awareness. These scripts run for hundreds of frames, consume full time budgets, yet score zero because the reasoning—not the execution—is defective. This pattern is particularly diagnostic: it separates models that can write runnable code from those that can reason about sequential decision-making under uncertainty.


#### A.9 Implementation Details


##### A.9.1 Game Origins

The 16 benchmark games are sourced from three categories to balance variety with reproducibility:

- • Self-developed (5 games): Color Switch, Knife Hit, Stick Hero, Stack2D, and Match-3. These are original HTML5 Canvas implementations authored by the benchmark authors, with deterministic physics constants and no external dependencies.

- • Adapted from GameWorld (3 games): Chrome Dino, Minesweeper, and Tetris. These were adapted from the GameWorld [ Ouyang et al. 2026 ] benchmark suite with modified environment wrappers for PlayScriptBench’s sandbox interface. Tetris uses the open-source TwitchTetris HTML5 implementation.

- • Open-source / community games (8 games): Space Invaders (MIT, Susam Pal), Doodle Jump, Flappy Bird, Geometry Dash, Helix Jump, Pac-Man, Snake, and 2048. These are sourced from the Offline-HTML-Games-Pack [ CoolDude2349 2026 ] community collection or standalone repositories, wrapped with the standardized environment interface.

All games run as client-side HTML5 Canvas applications in a headless Chromium browser via Playwright ( $\geq$ 1.40.0). No server-side logic or network access is required.

##### A.9.4 Sandbox Timing and Frame Control

The sandbox does not impose a fixed global frame rate. Instead, game progression is controlled by a per-game step_delay_ms parameter—the wall-clock wait time injected between consecutive action steps via page.wait_for_timeout() . This design aligns the sandbox step interval with each game’s native frame time, ensuring that real-time games (e.g., Geometry Dash at 33 ms $\approx$ 30 FPS) advance at approximately their intended speed, while turn-based games (e.g., 2048, Minesweeper) use longer delays (100 ms) to allow animation completion.

Between action steps, the sandbox pauses the game loop by monkey-patching requestAnimationFrame , setTimeout , setInterval , Date.now , and performance.now in the browser context. When paused, all pending animation-frame callbacks are queued and replayed upon resume. This freeze-during-inference mechanism ensures that every agent faces identical game dynamics regardless of response latency—the game clock advances only during active step intervals.

Representative step delays: 30 ms (Color Switch), 33 ms (Flappy Bird, Geometry Dash, Space Invaders), 50 ms (Snake, Chrome Dino, Tetris), 80 ms (Knife Hit), and 100 ms (2048, Minesweeper, Doodle Jump). Match-3 uses a special mode with 0 ms step delay and a 1500 ms post-step delay to allow match animations to complete.
