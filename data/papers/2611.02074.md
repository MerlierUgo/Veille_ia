Coding agents solve repository issues through long sequences of exploration, editing, and validation. These interaction trajectories are increasingly used as post-training data, so how they are collected shapes what the trained model learns. A common approach is to sample multiple trajectories independently for each issue and then select or curate them. However, as more trajectories are sampled independently, later trajectories become increasingly redundant. In fact, earlier trajectories can guide where subsequent collection effort should be spent. A natural way to use this history is to expose it to the coding agent as advice, helping it decide what to do next. But training on such trajectories can make the model rely on advice that is unavailable at test time, creating a train-test mismatch that may reduce downstream performance. Instead, we argue that history should guide where collection effort is spent, while the coding agent decides what to generate by itself. Based on this principle, we introduce SWE-Trail , a trajectory collector that uses earlier trajectories to guide subsequent collection while keeping that history outside the coding agent’s context. During a new rollout, SWE-Trail uses history to identify a state where additional collection effort may be useful. When that state is reached, the coding agent proposes candidate next actions from its ordinary context. SWE-Trail briefly executes candidates from the same checkpoint and uses the results to decide which route continues. We compare collection approaches by training student models on the trajectories they produce and measuring downstream performance. For a 124B student initialized from Ling-3.0-flash-base, SWE-Trail improves mean resolution over independent sampling by 2.33 and 1.60 percentage points on SWE-bench Multilingual and SWE-bench Pro, respectively. Without history, the same collection pipeline produces more resolved trajectories than independent sampling, but improves by only 0.11 points on Multilingual. These results show the value of using history to guide collection without exposing it to the coding agent.


## SWE-Trail: History-Guided Trajectory Collection for Coding Agent Training


### 1 Introduction

Resolving a repository-level issue requires a coding agent to explore the repository, modify code, and validate its changes ( Jimenez et al., 2024 ; Yang et al., 2024 ; Wang et al., 2025a ) . These interactions form trajectories that record not only the final patch but also the agent’s reasoning and actions throughout the repair process. Such trajectories are increasingly used as post-training data, so the collection process directly affects their value for training ( Chen et al., 2026 ; Han, 2026 ) .

A common way to collect coding agent training trajectories is to sample several trajectories per issue and keep those that pass tests or a judge ( Pan et al., 2025 ; Ehrlich et al., 2025 ; Jain et al., 2025 ) . Some work also edits the kept trajectories, masking flawed tool calls or removing redundant steps ( Tao et al., 2026 ; Ma et al., 2026a ; Han et al., 2026 ; Xiao et al., 2026b ) . These methods operate after trajectories are collected, while trajectories for the same issue are still generated independently. However, later independent samples become increasingly redundant as more trajectories are collected. They often revisit repair targets and behaviors already explored earlier. Rather than ignoring this history, subsequent collection can use earlier trajectories to decide where additional collection effort should be spent. For example, disagreements between successful and failed trajectories can reveal decision points where alternative actions are worth comparing. We refer to such evidence as allocation signals and to the earlier trajectories for an issue as its history . Section 2 quantifies the redundancy of independent sampling and tests whether earlier trajectories provide such allocation signals. Since earlier trajectories can provide useful information for a new rollout, a natural way to use this history is to place it in the coding agent’s context as advice ( Chen et al., 2025 ; Wang et al., 2026b ) . This can help the current rollout, but the resulting training trajectories record reasoning and actions generated with access to the advice. However, at test time, the trained model must make decisions without that advice. As a result, these trajectories may provide less useful supervision for training, as we evaluate in Section 4.2 . This leads to our central question: How can history guide where collection effort is spent while the coding agent decides what to generate from its ordinary context?

To answer this question, we introduce SWE-Trail , a trajectory collector that keeps history outside the coding agent’s context. Before collection, SWE-Trail uses history to determine which states should receive more collection effort and what evidence should be considered at those states. During a new rollout, when the agent reaches such a state, it proposes candidate next actions from its ordinary context without access to the history. SWE-Trail then compares candidate actions by briefly executing them from the same checkpoint. It selects the route that is better supported by repository evidence. The coding agent then continues from the selected route to complete the trajectory. A concrete example illustrates this process. On a Rust issue, all prior failed trajectories made an edit and then continued reading without running tests. From this history, SWE-Trail determines that this state should receive additional collection effort when it appears again in a new rollout. When the rollout reaches such a state, the coding agent proposes different next actions from its ordinary context, including further reading and running tests. SWE-Trail briefly executes both choices from the same checkpoint and selects the test-running route based on the resulting evidence. The coding agent then continues from the selected route until the rollout ends.

We evaluate whether SWE-Trail collects trajectories that are more useful for downstream training. The comparison uses the same 300 SWE-rebench V2 issues ( Badertdinov et al., 2026 ) . Each setting collects five trajectories per issue with GLM-5.1 ( GLM-5 Team, 2026 ; Z.ai, 2026 ) . SeedBank provides the independent sampling baseline. H5 uses the five SeedBank trajectories for each issue as history to collect five new trajectories, while H0 runs the same collection pipeline without history. We train the 124B Ling-3.0-flash-base model ( inclusionAI, 2026 ) on the trajectories from each condition, with three independent training runs. Under this controlled setup, H5 improves mean resolution over SeedBank by 2.33 and 1.60 percentage points on SWE-bench Multilingual and SWE-bench Pro, respectively. The H0 control helps isolate the contribution of history. It produces more resolved trajectories than SeedBank, but improves the 124B student’s mean resolution by only 0.11 points on Multilingual. This contrast shows that collection success alone does not explain the downstream gain. A second student model, Qwen3-14B-Base ( Qwen Team, 2025 ) , is also trained on the same H5 trajectories to test whether the gain generalizes across student models. For Qwen3-14B-Base, H5 improves mean resolution over SeedBank by 3.11 and 2.42 percentage points on SWE-bench Multilingual and SWE-bench Pro, respectively. Together, these results support using history to guide trajectory collection without placing that history in the coding agent’s context.


### 2 Motivation

To examine the empirical basis for our motivation, we analyze the independently sampled trajectories in SeedBank. We use attempt to refer to one independent try at solving an issue, and examine both how coverage grows with additional attempts and whether earlier attempts provide allocation signals for subsequent collection.


#### 2.1 Diminishing Coverage Gains from Independent Rollouts

Figure 1 A shows the expected number of issues solved with $k$ attempts per issue, averaging over all $k$ -attempt subsets of the five SeedBank attempts for each issue. For a given $k$ -attempt subset, an issue is counted as solved if at least one of the $k$ attempts succeeds. With one attempt per issue, 58.4 issues are solved in expectation. Increasing $k$ from 1 to 2 adds 13.1 solved issues, while increasing it to 3, 4, and 5 adds only 8.0, 5.1, and 3.4 more issues, respectively. Thus, each additional attempt still expands issue coverage, but by a smaller amount.

B: mean coverage of each issue’s five-attempt patch-target union, grouped by SeedBank outcomes. Both panels average over all $k$ -attempt subsets of the five recorded attempts. The vertical axis in B starts at 65%.

Patch-target coverage shows the same diminishing pattern across different types of history. We use modified files as patch targets and define three history types from each issue’s SeedBank outcomes: stable-solved if all attempts succeed, mixed if both successful and failed attempts occur, and never-solved if all attempts fail. For each history type, Figure 1 B shows the fraction of files modified across an issue’s five attempts that are covered by $k$ attempts. We average this fraction over all $k$ -attempt subsets and then across issues. One attempt already covers 90.0% of these files on stable-solved issues, 73.2% on mixed issues, and 80.1% on never-solved issues. These results show substantial target overlap across all three history types. As more attempts are added, later attempts cover fewer new files. Overlap among successful attempts may simply reflect convergence on the same repair targets. However, even when all independent attempts fail, they still modify many of the same files. This pattern shows that independent sampling does not automatically redirect collection effort after repeated failures. Later attempts may continue spending effort on previously explored repair targets rather than exploring new ones. Together with the issue-level results, these findings show that later independent attempts become increasingly redundant.


#### 2.2 History Provides Allocation Signals

Section 2.1 shows that later independent attempts add less coverage and often revisit repair targets explored earlier. The remaining question is whether history can indicate where additional collection effort may be useful. Mixed issues are informative because successful and failed attempts may choose different next actions from similar states. We therefore examine whether such decision points occur.

For each mixed issue, an auditor compares the most similar successful and failed attempts and locates their first meaningful decision difference. We assess whether the two attempts are similar enough to compare their next actions and whether both actions are reasonable at that point. The audit is conducted independently with GPT-5.6-Sol ( OpenAI, 2026 ) and GLM-5.1. The main analysis includes 43 of the 51 mixed issues, excluding eight whose failed attempt ended in a timeout or collector error. GPT-5.6-Sol identifies such cases in 26 issues and GLM-5.1 in 31, with 20 identified by both models. These results show that mixed histories can reveal decision points where additional collection effort may be useful. The detailed results are reported in Appendix A.3 .

However, this evidence relies on having both successful and failed attempts. To test whether history remains useful without one, we examine never-solved histories and measure the overlap in modified files across failed attempts on the same issue. The mean pairwise Jaccard overlap is 0.841. Among the 198 issues with a defined overlap score, 93 have a score of 1.0. These results show that failed attempts often focus on the same repair targets. This overlap does not explain why the attempts fail, but it shows where effort is repeatedly spent across failed attempts. Thus, even without a success–failure contrast, history can still indicate where additional collection effort may be useful. Together, these findings show that history can provide allocation signals for collection. Appendix A gives the audit procedure and overlap calculations.

### 3 SWE-Trail

Section 2 shows that later independent attempts add less new coverage, while earlier attempts can indicate where additional collection effort may be useful. Motivated by these observations, we introduce SWE-Trail, a trajectory collector that uses history to decide where additional collection effort should be spent in a new rollout. For issue $i$ , let $x_{i}$ contain the issue statement and the repository snapshot at the issue commit. The history $H_{i}$ contains the attempts already collected on that issue. SWE-Trail has access to $H_{i}$ , but the coding agent does not. Reference patches are unavailable during collection. Figure 2 shows the two stages of SWE-Trail. Before collection, SWE-Trail uses the history and read-only repository checks to determine which states should receive additional collection effort and what evidence should be considered at those states. During a rollout, when such a state is reached, the coding agent proposes candidate next actions from its ordinary context without access to the history. SWE-Trail selects candidates for comparison, briefly executes them in parallel from the same checkpoint, and retains the route better supported by repository evidence. The coding agent then continues from the selected route to complete the trajectory.


#### 3.1 Compiling History into Detectors

Earlier attempts can indicate which states should receive additional collection effort, but a new rollout may reach similar situations through a different sequence of actions. The compiler therefore builds a detector $D_{i}$ whose rules recognize such states from the rollout’s actions and observations rather than relying on fixed step numbers. For example, the detector in Figure 2 recognizes repeated reading after an edit without validation. The runtime checks these rules after each new repository observation and samples candidate actions when a state matches.

To build the detector, the compiler first analyzes $(x_{i},H_{i})$ to extract allocation signals from the history. These signals include decisions supported by successful attempts, differences across repair routes, and recurring failures. The history may leave open questions about the issue or repository, so the compiler then runs bounded read-only repository checks to resolve these questions. These checks do not modify source code or access the reference patch. The compiler stores the historical evidence, check results, and remaining questions in a private acquisition record $R_{i}$ . Using $R_{i}$ , the compiler defines the detector rules and a local comparison objective $u_{i}(d)$ for each detector state $d$ . The objective specifies what evidence should be considered when comparing candidate routes at that state. Different histories lead the compiler to focus on different kinds of decisions. For stable-solved histories, repeated success shows which decisions already have strong support. The compiler allocates additional effort only when meaningful uncertainty remains. For mixed histories, it focuses on states where successful and failed repair routes differ. For never-solved histories, it focuses on recurring failure patterns, such as edits followed by further reading without validation. The compiler also sets a sampling-temperature schedule $\lambda_{i}$ for candidate generation when a detector state is reached. Mixed and never-solved histories use higher temperatures to encourage more varied next actions when the history shows unresolved choices or repeated failures.

Before collection begins, the compiler validates each proposed detector state against its supporting evidence and replays its rules on the recorded attempts. States without sufficient support are discarded. The admitted detector states, their comparison objectives, and $\lambda_{i}$ are then fixed for the entire collection round. Appendices B and F.5 provide the compiler details, admission checks, and example records.


#### 3.2 Sampling Comparable Alternatives

The detector determines where additional collection effort is spent, while the actions to consider come from the coding agent itself. When the rollout reaches a state $d$ recognized by $D_{i}$ , SWE-Trail samples several candidate next actions using only the agent’s ordinary context. The history, acquisition record $R_{i}$ , and comparison objective $u_{i}(d)$ are not added to that context. The first sample uses the agent’s ordinary temperature and serves as the default. The remaining samples use $\lambda_{i}$ .

Different samples may propose equivalent actions, so SWE-Trail first groups equivalent proposals together. It keeps the default candidate and shortlists executable alternatives from the remaining proposals. To keep each intervention local and bounded, SWE-Trail chooses at most one alternative from this shortlist using $R_{i}$ and $u_{i}(d)$ . If no suitable alternative is available, the rollout continues with the default action. Otherwise, SWE-Trail restores two isolated workspaces from the same checkpoint, one for the default and one for the chosen alternative. Both candidates start from the same conversation and workspace state and run for the same short horizon, producing two executed suffixes of actions and observations. To avoid expanding collection into a multi-level search tree, each trajectory performs at most one such comparison. Different rollouts on the same issue may still make their comparison at different detector states.


#### 3.3 Selecting a Route by Executed Evidence

Once both suffixes have been executed, SWE-Trail compares their progress using the local comparison objective $u_{i}(d)$ . The two suffixes are presented to SWE-Trail in shuffled order, hiding which one comes from the default candidate. SWE-Trail uses $R_{i}$ only as background for the comparison. It prefers a route only when the two executed suffixes provide clear evidence that one makes better progress under $u_{i}(d)$ . Otherwise, it keeps the default. After selection, the coding agent continues only from the selected workspace until the full rollout ends. For training, SWE-Trail keeps only the selected route, preserves the coding agent’s original reasoning and actions without rewriting, and removes the unselected suffix and private collector events. This ensures that the training record remains a single continuous trajectory generated by the coding agent and that private collection information does not enter the training process. Algorithm 1 in Appendix B summarizes the procedure, and Appendix H.1 provides a full end-to-end case study.

### 4 Experiments


#### 4.1 Setting

We test whether training on SWE-Trail trajectories improves student performance on new issues. Across all comparisons, we use the same collection issues and the same number of coding trajectories for training. The background training data and the training and evaluation protocols remain fixed.

Shared setting. Each training dataset contains five coding trajectories for each of the same 300 SWE-rebench V2 issues ( Badertdinov et al., 2026 ) , giving 1,500 trajectories in total. None of the collection repositories appears in either evaluation benchmark. All coding rollouts use GLM-5.1 ( GLM-5 Team, 2026 ) with the OpenHands scaffold ( Wang et al., 2025a ) . Collection runs in an offline sandbox with repository commit histories removed. Reference patches and published fixes are unavailable during collection. Appendix C details the provenance of the collection issues and verifies that they share no issues or repositories with either evaluation benchmark.

Methods and variants. SeedBank provides the independent-sampling baseline. We apply controlled adaptations of SWE-Gym ( Pan et al., 2025 ) , SWE-TRACE ( Han et al., 2026 ) , and SWE-Lego ( Tao et al., 2026 ) to the same SeedBank trajectories. We also adapt SWE-Exp ( Chen et al., 2025 ) to test a different use of history, where the coding agent reads an experience message compiled from the SeedBank attempts during collection. The message is retained in the training record.

For SWE-Trail, history remains outside the coding agent’s context throughout collection. Its main variant, H5, uses the five SeedBank attempts for each issue as history when collecting five new trajectories. H0 sets $H_{i}=\varnothing$ and runs the same read-only repository checks and compiler without history. Comparing H0 with SeedBank tests the collection pipeline without history, while comparing H5 with H0 isolates what history adds. We also use two H5 variants to test where SWE-Trail makes comparisons and which route it retains. Random detection replaces the history-guided comparison location with a random eligible state while keeping H5’s remaining collection procedure unchanged. Random retention keeps H5’s detector but randomly chooses which executed route to continue. Both variants use the same per-trajectory model-call limits and execution horizon as H5.

#### 4.2 Downstream Training Utility

SWE-Trail improves downstream resolution. Table 1 shows that H5 outperforms all other conditions in the table on both benchmarks. H5 improves mean resolution over SeedBank by 2.33 percentage points on Multilingual and 1.60 points on SWE-Pro. Since the dataset size and training setup are fixed, these differences reflect changes in the collected trajectories. Across three independent training runs, every H5 run exceeds every SeedBank run on both benchmarks. An exact one-sided permutation test over the training runs gives $p=0.05$ on each benchmark. Appendix E reports the individual runs, statistical tests, and results by language. SWE-Exp falls below SeedBank by 1.33 points on Multilingual and 2.78 points on SWE-Pro. This may reflect reliance on advice available during training but absent at evaluation. To examine the role of advice more directly, Appendix H.2 compares two exports of the same trajectories, with the advice either retained or removed. Compared with retaining the advice, removing it improves SWE-Pro but lowers Multilingual. Removing the advice after collection does not remove its influence on how the trajectory was generated. The agent produced its reasoning after reading the advice, so some decisions may remain without the information that originally supported them.

H5 has higher mean resolution than H0. Without history, H0 improves mean resolution over SeedBank by 0.11 points on Multilingual and 0.73 points on SWE-Pro. Adding history in H5 raises mean resolution by a further 2.22 and 0.87 points over H0, respectively. The point estimates are positive on both benchmarks, but task-paired bootstrap gives 95% intervals of $[-0.2,4.6]$ points on Multilingual and $[-0.8,2.5]$ on SWE-Pro. Appendix E.2 gives the full paired analysis. Section 4.4 compares these downstream differences with the corresponding collection outcomes.

Both collection decisions matter. To test these two choices, we randomize each one separately. Random detection replaces H5’s history-guided choice of where to compare with a random eligible point and lowers mean resolution by 1.44 points on Multilingual and 1.28 points on SWE-Pro. Random retention keeps H5’s history-guided comparison location but randomly chooses which executed route continues, lowering mean resolution by 0.89 and 1.19 points, respectively. These decreases support using history to decide where additional collection effort should be spent and execution evidence to decide which route should continue. Both variants remain above SeedBank in mean resolution, while their run ranges overlap H5’s on both benchmarks.

The gains extend to another student. We repeat the comparison with Qwen3-14B-Base using the same SeedBank, H0, and H5 trajectory sets. H5 improves mean resolution over SeedBank by 3.11 percentage points on Multilingual and 2.42 points on SWE-Pro. It also exceeds H0 by 1.67 and 1.60 points, respectively. These results show that the downstream gains from SWE-Trail also appear with another student model. Appendix E.4 gives the full results.


#### 4.3 History Scale and Cost

More history brings smaller gains. Table 2 compares H0, H5, and H10. Using five prior attempts improves mean resolution over H0 by 2.22 points on Multilingual and 0.87 points on SWE-Pro. Increasing the history from five to ten attempts adds only 0.22 and 0.14 points, respectively. H10 also does not improve the collection outcomes over H5, despite increasing tokens spent beyond the ordinary rollout from 307M to 510M, a 66.0% increase, and total collection tokens by 12.9%. More history therefore provides only small additional mean gains at substantially higher collection overhead. The main H5 setting remains close to H0 in cost. Excluding the cost of collecting prior attempts, H5 uses at most 3.7% more tokens than H0. Its ordinary rollouts use 4.4% fewer tokens than H0. The same diminishing gain appears with Qwen3-14B-Base. H5 improves over H0 by 1.67 and 1.60 points, while H10 adds a further 1.00 and 0.36 points on Multilingual and SWE-Pro, respectively. Appendix G.2 gives the complete cost breakdowns.

The increase in comparisons therefore comes mainly from candidate sampling occurring more often. Panel C shows better local progress on one route in 40.7% of H5 rollouts and 28.7% of H0 rollouts. Yet Panel D shows similar alternative-selection rates among completed comparisons, at 37.4% and 39.0%, respectively. Together, Panels C and D show that H5 more often reaches comparisons with clear progress, while the rate of selecting the alternative remains similar.


### 5 Related Work

Three lines of work relate to SWE-Trail. Appendix I gives the extended discussion.

Test-time search and selection. Search methods spend extra compute to solve the current issue. Some sample several independent rollouts and select among them using tests or model judgments ( Ehrlich et al., 2025 ) . Others reuse earlier prefixes or summaries of prior attempts to guide later rollouts on the same issue ( Ding and Zhang, 2026 ; Kim et al., 2026 ) . Tree search explores alternatives within a growing execution tree during the current solve ( Kocsis and Szepesvári, 2006 ; Zhou et al., 2024 ; Antoniades et al., 2025 ) . Instead, SWE-Trail uses prior attempts on the same issue to guide where additional collection effort is spent during trajectory generation. The coding agent proposes actions from its current context, SWE-Trail briefly compares them from the same checkpoint, and the selected route becomes the training trajectory.

Trajectory generation and curation. Methods for constructing training data generate more tasks and trajectories or increase trajectory diversity through adaptive synthesis ( Yang et al., 2025 ; Chen et al., 2026 ) . Others select resolved trajectories or modify completed trajectories through filtering and process-level editing ( Pan et al., 2025 ; Tao et al., 2026 ; Ma et al., 2026a ; Han et al., 2026 ) . Recent work also evolves curation rules using downstream failures ( Wang et al., 2026a ) . Instead, SWE-Trail uses prior attempts on the same issue to guide where additional collection effort is spent during trajectory generation. These comparisons collect new execution evidence rather than only selecting or modifying completed trajectories. Post-hoc selection can still follow, as Section 4.3 shows.

Experience-guided agents. Agents use reflections, distilled insights, workflows, and skills to guide later actions ( Shinn et al., 2023 ; Zhao et al., 2024 ; Wang et al., 2025b ; Li et al., 2026a ) . For coding tasks, this experience can come from earlier repair trajectories, human debugging records, or the ongoing attempt ( Chen et al., 2025 ; Wang et al., 2026b ; Hayashi et al., 2025 ; Guo et al., 2025 ) . These methods use experience to guide the agent’s reasoning or actions. Instead, SWE-Trail uses history to guide where additional collection effort is spent. The coding agent proposes actions from its ordinary context without receiving that history.


### 6 Discussion and Limitations

What the results show. The experiments separate collection success from downstream training value. H0 resolves more trajectories than independent sampling but brings little gain on Multilingual, while adding history in H5 produces larger student gains. Randomizing either where additional collection effort is spent or which executed route continues lowers mean resolution relative to H5. The gains also appear with Qwen3-14B-Base. These results support using history as a collector-side signal for improving the training value of new trajectories, rather than as advice shown to the coding agent.

Limitations and future work. Our experiments use two student models but one collection model and one agent scaffold. Future work could test other collection models and scaffolds. Our current setting also keeps history fixed during each collection round and uses the same collection budget for every issue. Future work could update history across rounds and allocate effort differently across issues. The exploratory replay audit in Appendix G.1 also motivates testing more diverse candidate proposals. Extending SWE-Trail beyond coding would require environments that support state restoration and feedback for comparing alternatives. Web navigation is one possible direction.


### 7 Conclusion

Our results point to a broader lesson: prior attempts are useful not only for what they contain, but also for guiding where new collection effort should be spent. SWE-Trail operationalizes this idea by compiling prior attempts into rules that determine when additional collection effort may be useful during a new rollout. The coding agent proposes actions without seeing the history, while the collector briefly executes candidates from the same checkpoint and uses the resulting evidence to choose which route to continue. With the training setup fixed, SWE-Trail improves the 124B student’s mean resolution over independent sampling by 2.33 percentage points on SWE-bench Multilingual and 1.60 points on SWE-bench Pro. The gains also appear with Qwen3-14B-Base. The H0 comparison shows that collection success alone does not explain the downstream gains. Randomizing either where additional collection effort is spent or which executed route continues lowers mean resolution relative to H5. Together, these results show that prior attempts can improve the training value of new trajectories by guiding collection without being shown to the coding agent as advice.

#### A.2 Decision Differences in Mixed Histories

Mixed histories are informative because they contain both successful and failed attempts on the same issue. The audit asks whether these histories reveal decision points where more than one next action is reasonable given the available evidence. It uses outcomes first to locate a meaningful difference between a successful and a failed attempt. It then removes the outcomes and future feedback and asks whether the two states are comparable and whether both next actions are defensible from the information available at that point. This directly tests the allocation signal studied in Section 2.2 . The issue set, pair construction, model inputs, label spaces, and aggregation rule were fixed before the results were computed. The audit model was GLM-5.1 at temperature zero.

Pair construction. The input contains the 51 mixed issues whose five SeedBank attempts include at least one resolved and one unresolved trajectory. Here, native means generated by the coding agent from its ordinary view, with no collector text. Canonical native events are converted into 1-based action timelines after planning-only events are removed. Each action records its category, repository target, normalized command or edit, the immediately preceding native reasoning, and the resulting observation and error flag. Whitespace is normalized. Problem statements are capped at 7,000 characters, per-action native reasoning at 900, observations at 800, edit summaries at 1,700, and other action summaries at 700.

For every issue, we score every resolved/unresolved pair. When a naturally completed unresolved trajectory exists, collector failures and timeouts are excluded from the candidate pool. Otherwise, the censored unresolved attempts form the pool. This produces 43 primary pairs and eight explicitly censored pairs.

The audit compares a successful and failed attempt that reached similar observed situations. We select the highest-scoring pair for each issue. Let $d_{\mathrm{full}}$ be the SequenceMatcher ratio between the full action-token sequences and $d_{25}$ the ratio between their first 25 actions. An action token is its action category and normalized target. Terminal, environment, and validation actions additionally include the recognized command family. Let $J_{\mathrm{explore}}$ and $J_{\mathrm{patch}}$ be Jaccard overlap of explored and modified repository targets. The score is

[Tableau] $$s=0.45d_{\mathrm{full}}+0.30d_{25}+0.15J_{\mathrm{explore}}+0.10J_{\mathrm{patch}}.$$ (2)

The maximum-scoring pair is selected, with deterministic tie-breaking by fewer coding actions and then run ID.

Stage 1: retrospective localization. The first stage uses the complete trajectories and their outcomes only to locate an early decision difference that may matter for the repair route. The model receives the problem statement, both complete action timelines, their outcomes, the censor flag, and the pair score. It returns a status, one of found , no_meaningful_divergence , and not_comparable , together with a rationale and a confidence. For a found case, it also returns a boundary index for each route, summaries of the shared state and the two route commitments, a divergence type, and an outcome-relevance label. That label is one of direct , plausible , weak , and none . Returned indices are rejected if they fall outside the supplied timelines. The audit uses the following exact system instruction.

The full divergence-type label space is localization, hypothesis, implementation, validation, recovery, finish, resource/infra, and other. Only hypothesis, implementation, and validation occur among the 44 localized cases.

Stage 2: outcome-blind action audit. Only a Stage-1 found case proceeds to Stage 2. For each source route, the model sees the prefix strictly before its localized boundary, including the feedback already available at that point. It also sees the immediate candidate action with its observation removed. It does not receive either trajectory outcome, candidate feedback, future actions, the gold patch, the Stage-1 retrospective rationale, or the solved/failed source identity. The two sources are exposed only as routes A and B, with their source identities hidden.

This stage asks whether the visible states are sufficiently comparable and whether both immediate actions are reasonable using only the information available at those states. The audit uses the following exact system instruction.

The structured response records five labels, a reason, and a confidence. State comparability is equivalent, similar with minor differences, or different. Route distinctness is distinct, equivalent, or unclear. Support for each candidate is supported, partially supported, or unsupported. Information gain for each candidate is high, medium, low, or none. The schema calls the final field prospective branchability. Its labels are two reasonable routes, one reasonable route, equivalent routes, non-comparable, and insufficient evidence. The call is then repeated with A/B order reversed.

Execution, aggregation, and missingness. We aggregate the two route-order judgments before counting supported decision points. Two two_reasonable_routes votes produce the strict label. One such vote produces the possible-two-routes label. Two one-route votes produce a one-route consensus only when they retain the same source-level support pattern. Otherwise, the result is order-sensitive. Other identical votes retain their shared branchability label, and any remaining disagreement is order-sensitive.

Stage 1 returns valid structured results for 47/51 pairs. These comprise 44 localized divergences and three no-meaningful-divergence cases. The remaining four are collector-censored pairs whose audit calls failed after retries. None is imputed as a negative. Both orderings complete for all 44 localized cases, giving 88 valid Stage-2 responses. ### Appendix B Collector Algorithm, Schemas, and Prompts

This appendix gives the implementation details behind Section 3 . The collector uses history only to decide where additional collection effort may be useful and what evidence should distinguish candidate routes. The coding agent receives its ordinary context and generates all candidate actions itself.


#### B.1 End-to-End Collection Algorithm

> Algorithm 1 SWE-Trail collection for one issue. Orange marks collector-private operations; blue marks coding-agent generation from its ordinary visible context.

Algorithm 1 shows the main collection path. For each detector state $d$ , $u_{i}(d)$ specifies what evidence should be considered when comparing the executed routes. Policy calls, including candidate generation and suffix execution, receive only the ordinary issue, conversation, and repository observations. The schedule $\lambda_{i}$ changes sampling temperatures without adding history to the coding-agent prompt. Shortlisting and selection choose among actions already proposed by the coding agent. They do not write new actions or replace the agent’s reasoning. Proposal-only rechecking and runtime failures are described in Appendix B.5 .


#### B.2 Collection Cost Accounting

We separate the size of the exported training corpus from the compute used to collect it. Given an existing set of prior attempts, we use two accounting boundaries:

[Tableau] $\displaystyle C_{\mathrm{overhead}}$ $\displaystyle=C_{\mathrm{compile}}+C_{\mathrm{candidates}}+C_{\mathrm{extra\ suffix}}$ (3) $\displaystyle+C_{\mathrm{selection}}+C_{\mathrm{retry}},$ $\displaystyle C_{\mathrm{bank}}$ $\displaystyle=C_{\mathrm{rollout}}+C_{\mathrm{overhead}}.$

Here $C_{\mathrm{overhead}}$ is the additional compute beyond an ordinary rollout, while $C_{\mathrm{bank}}$ includes both the ordinary rollout and this overhead. We report model tokens and environment actions under these boundaries. Summed trajectory-hours are reported separately from concurrent wall-clock time. Appendix G.2 gives the measured breakdown. Provider-token accounting is complete for H5 and H10. H0 records runtime calls but not offline compilation, and SeedBank has no source-provider usage record. We do not impute unavailable components.


#### B.3 Offline Compiler

The compiler turns information from earlier attempts into fixed rules for deciding where additional collection effort may be useful in a new rollout. It follows the same sequence for each issue. All model-produced fields pass schema and content checks before they can affect collection.

Internally, each evidence item records an identifier, source type, hypothesis or constraint, direct observation, bounded interpretation, uncertainty, history type, and links to supporting or contradicting evidence. The accompanying human-readable representation forms the private acquisition record $R_{i}$ . Neither representation enters a coding-agent request.


#### B.4 Detector Schema and Admission Checks

A detector rule can guide collection only after its rule and supporting evidence pass the checks below. An active detector rule has passed these checks and is fixed for collection. At runtime, the rule is evaluated against the actions and observations seen so far.

Each detector rule contains the following fields.

Executable predicates may use only features available during the current rollout. They cannot contain a reference patch, hidden tests, historical solution actions, repository-specific instructions to the coding agent, or future outcome labels. H5 and H10 rules must cite history evidence and pass history replay. H0 rules must cite source-clean repository evidence. Parse failure, prohibited content, contradictory rationale, duplicate signatures, or insufficient support causes abstention.

H5 compiles 687 candidate detector rules. Of these, 569 match at least one source trajectory during replay, and 397 pass the admission checks for collection. Appendix H.1 gives the concrete post-edit read-without-validation rule used in the running Rust example.


#### B.5 Online Runtime Details

The runtime evaluates the detector after each new repository observation. A trajectory executes at most one comparison. If all sampled candidates are equivalent, no comparison is executed. The collector may sample candidates once more after the default action runs.

### Appendix C Data and Experimental Conditions


#### C.1 Collection Issues and Prior Attempts

The main experiments use 300 repository-level issues from SWE-rebench V2 ( Badertdinov et al., 2026 ) , with one issue per repository. Each collection condition produces five trajectories per issue. SeedBank provides the five independently sampled attempts used as history by H5. H10 adds five more eligible attempts to the same five, giving ten prior attempts per issue.

We define three history types from the outcomes of the five SeedBank attempts before the main collection begins. The stable-solved group contains 37 issues for which all five attempts succeed. The mixed group contains 51 issues with both successful and failed attempts. The never-solved group contains 212 issues for which all five attempts fail. These labels describe the observed SeedBank outcomes and are separate from how the compiler interprets each history. Appendix F.5 reports the compiler classes.

Collection runs in an offline sandbox with no network access and no repository commit history. The coding agent sees the working tree at the issue commit but cannot access later commits. The reference patch, fixing commit, and externally published solutions are also unavailable. The read-only repository checks in Section 3.1 follow the same restrictions. Any information already encoded in the model weights is shared across conditions, since all collection conditions use the same model on the same issue set.


#### C.2 Evaluation Benchmarks and Overlap Audit

We evaluate on SWE-bench Multilingual and SWE-bench Pro. SWE-bench Multilingual, released with SWE-smith ( Yang et al., 2025 ) , contains 300 issues across nine languages: C, C++, Go, Java, JavaScript, TypeScript, PHP, Ruby, and Rust. Appendix E.3 reports results by language. SWE-bench Pro ( Deng et al., 2025 ) contains longer-horizon repository issues whose reference patches typically span multiple files. We use its public split of 731 tasks. Both benchmarks use the evaluation protocol in Appendix D.2 .

We verify that the collection and evaluation sets do not share issues or repositories. Exact instance IDs and canonical lowercase owner/repository names are compared across the sets. The 300 Multilingual tasks span 41 repositories, and the 731 SWE-Pro tasks span 437 repositories. Neither benchmark shares an issue or repository with the collection pool.


#### C.3 Experimental Conditions

The conditions separate three ways of using existing trajectories. The three curation conditions are controlled adaptations rather than full reproductions of the original methods. They modify the same completed SeedBank trajectories without collecting new interactions. SWE-Exp uses prior attempts to create information that is shown to the coding agent during a new rollout. SWE-Trail instead keeps prior attempts private to the collector and uses them to guide where additional collection effort is spent.

Our SWE-Gym adaptation ( Pan et al., 2025 ) conditions each record on its outcome. Successful records receive the outcome annotation while preserving their original messages and actions. Unresolved records remain unchanged. The adaptation does not apply a condition-specific loss mask.

Our SWE-Lego adaptation ( Tao et al., 2026 ) applies deterministic tool-error masking to successful records. It masks only assistant turns whose tool result indicates strict tool misuse, including invalid arguments, missing paths, permission errors, or shell syntax errors. Failed tests and bug reproduction output remain trainable. Unresolved records remain unchanged.

Our SWE-TRACE adaptation ( Han et al., 2026 ) removes noncritical messages from successful records. It retains interactions involving patch-modified files, validation, final repository inspection, and the final answer. Repeated non-mutating observations are deduplicated. Messages are removed rather than loss-masked. Unresolved records remain unchanged.

Our SWE-Exp adaptation ( Chen et al., 2025 ) compiles the same five prior attempts into an experience message. The coding agent receives this message while generating the new trajectory, and the message remains in the exported training record.

The SWE-Trail conditions keep prior attempts outside the coding agent’s context. H0 runs the same collection pipeline without history. H5 uses five prior attempts, while H10 uses ten. Random detection replaces the history-guided comparison location with a random eligible state while leaving the remaining collection procedure unchanged. Random retention keeps H5’s history-guided comparison location but randomly chooses which executed route continues. The randomized controls use the same per-trajectory collection budget and execution horizon as H5.

#### D.3 Metric Definitions

This section defines the metrics used in Section 4 and the appendix tables.

Outcome and collection yield. A trajectory is resolved when its final patch passes the benchmark tests. Resolution is the fraction of evaluated tasks that are resolved. A collection issue is counted as solved when at least one of its five newly collected trajectories resolves. A verified positive is a resolved, process-valid, nonempty selected trajectory that also passes the export checks. The focused Top-5 analysis in Appendix G.3 uses the same exact strict-positive definition for both candidate banks.

Process. Repeated reads count repeated accesses to the same normalized file target. Validation counts executable checks. Post-final-edit validation records whether at least one executable check occurs after the final edit.

Collection mechanism. Candidate sampling counts a rollout in which a detector rule matches the current state and the collector samples next-action candidates. Sampling alone does not imply that a comparison is executed. Equivalent proposals or a failed workspace restoration can prevent execution.

An executed comparison requires both selected candidate suffixes to run from the same checkpoint. Candidate diversity is the fraction of candidate-sampling cases in which the eight proposals contain at least two semantically distinct actions. Alternative selection is the fraction of completed comparisons in which the non-default route is retained.

Semantic progress records whether the selector finds clear evidence that one executed suffix makes better local progress under the comparison objective $u_{i}(d)$ . We report this quantity over all rollouts. Candidate coverage asks whether a useful action appears among the eight sampled proposals at all. Appendix G.1 evaluates this with exact-prefix replay.

Tokens and time. Token counts use provider-reported prompt and completion tokens. Reported reasoning tokens are a subset and are not added a second time. Collection-overhead usage includes compiler, candidate-generation, additional suffix, selector, and retry calls while excluding the ordinary coding rollout. Where tables use the term acquisition-only , it refers to this same boundary. Summed trajectory-hours add elapsed time across individual tasks and are not concurrent suite wall-clock time.

Statistical tests for collection outcomes. The five trajectories collected for one issue are not independent observations, so collection-level bootstrap intervals resample whole issues. Win/loss/tie counts compare the number of resolved trajectories out of five for each issue. Appendix F additionally reports an exact sign-flip test over nonzero issue-level differences. These collection-level analyses describe differences in the collected data. The downstream training endpoint is reported separately in Section 4.2 .

### Appendix G Component Controls, Cost, and Best-of- $N$


#### G.1 Randomized Controls and Selector Replay

The two randomized controls test where comparisons occur and which executed route continues. Both use H5’s five-attempt history, sampling-temperature schedule, training protocol, and evaluation protocol. They also use the same per-trajectory collection budget and execution horizon as H5. This budget allows eight candidate proposals, one shortlist call, one selector call, and at most two two-observation suffix executions. Realized token counts may still differ across trajectories.

Random detection. Random detection replaces H5’s history-guided comparison location with a random eligible state while leaving the remaining collection procedure unchanged. Eligible states are repository-observation boundaries at which the observation has completed, the workspace can be restored, no earlier comparison has been executed, and enough budget remains for both short suffixes. The state is sampled uniformly from these eligible locations without using history or a detector score. If a trajectory contains no eligible state, it completes as an ordinary rollout without a comparison.

Random retention. Random retention keeps H5’s history-guided comparison location and executes the same candidate-generation, shortlisting, and suffix-comparison procedure. Once both suffixes execute successfully, a fair binary draw determines which workspace continues, regardless of the selector’s judgment. If restoration or suffix execution fails, the default route continues.

Separate collection with a stricter selector. We also test whether requiring stronger execution evidence improves the training value of the collected trajectories. This condition runs a separate H5-style collection in which an alternative route is preferred only when its executed suffix provides stronger evidence about the root cause or working hypothesis. The collection resolves 343 of 1,500 trajectories across 97 issues, compared with 345 trajectories across 98 issues for H5. Students trained on these trajectories reach 63.89% on Multilingual and 41.91% on SWE-Pro, 1.78 and 0.91 points below H5. Thus, the stricter criterion leaves collection yield nearly unchanged but produces lower student means on both benchmarks.

Fixed-comparison diagnostic replay. To examine the selector without changing candidate generation or execution, we replay 18 H5 comparisons under the stricter criterion. The visible prefix, workspace, candidates, and both executed suffixes remain fixed, so only the selection judgment changes. These comparisons come from seven issues that the compiler classifies as mixed.

The stricter criterion changes eight decision labels and six retained routes. Some changed decisions become ties and therefore retain the default route, which explains the difference between these counts. Ties increase from 5 of 18 comparisons to 12 of 18. The stricter criterion mainly converts uncertain preferences into abstentions.

Candidate coverage is the most frequent non-exclusive limitation in this sample, appearing in 13 of 18 comparisons. Seven have partial coverage and six have poor coverage. Selection is identified as a limitation in 4 of 18 comparisons, followed by suffix horizon and post-selection drift at 3 of 18 each. A selector cannot recover a useful action that was not proposed, which motivates testing more diverse candidate proposals. These counts describe the 18 replayed comparisons rather than all 968 executed comparisons.

#### I.1 Executable Coding Agents and Trajectory Corpora

SWE-bench established executable repository-level repair, while SWE-agent and OpenHands provided widely used coding-agent scaffolds ( Jimenez et al., 2024 ; Yang et al., 2024 ; Wang et al., 2025a ) . SWE-Gym, R2E-Gym, SWE-smith, and Open-SWE-Traces expand the available tasks, environments, rollouts, and languages for training ( Pan et al., 2025 ; Jain et al., 2025 ; Yang et al., 2025 ; Ahmad et al., 2026 ) . These efforts increase the supply of coding trajectories. Our focus is different: given several prior attempts on the same issue, we ask how that history can guide the collection of additional trajectories.


#### I.2 Inference-Time Search and Selection

A common inference-time strategy samples several complete rollouts and selects or combines them using tests, execution outcomes, or model judgments ( Ehrlich et al., 2025 ) . Other methods reuse earlier computation more directly. They may restore a previous trajectory prefix and continue from an earlier point, or summarize prior attempts and use those summaries to condition later rollouts ( Ding and Zhang, 2026 ; Kim et al., 2026 ) . These methods use additional computation to improve the solution returned for the current issue.

Tree-search methods provide another form of adaptive inference. MCTS and related approaches compare alternatives within a growing online search tree and allocate computation using value estimates, process signals, or terminal outcomes ( Kocsis and Szepesvári, 2006 ; Zhou et al., 2024 ; Antoniades et al., 2025 ) . They can revisit a shared prefix and explore alternatives that independent full rollouts may miss.

SWE-Trail differs in both source and objective. Its guidance comes from independent attempts collected before the new rollout, and the goal is to collect training trajectories rather than to return the best solution from a search tree. It compiles fixed rules before collection and executes at most one comparison during a rollout, without recursive tree expansion or value backup. The H0 control in Section 4.1 evaluates this bounded collection procedure without history, rather than a full tree-search policy.


#### I.3 Trajectory Construction and Post-Hoc Curation

Several methods improve coding-agent training data after trajectories have already been generated. SWE-Gym and related pipelines retain trajectories based on executable outcomes, while other methods mask flawed tool calls, remove redundant interactions, reconstruct better paths, or use process-level signals to identify more useful supervision ( Pan et al., 2025 ; Tao et al., 2026 ; Ma et al., 2026a ; Han et al., 2026 ; Xiao et al., 2026b ) . Data valuation and training-dynamics methods similarly estimate the usefulness of examples that already exist ( Koh and Liang, 2017 ; Ghorbani and Zou, 2019 ; Paul et al., 2021 ; Xie et al., 2023 ) .

These methods are complementary to SWE-Trail. Post-hoc curation decides which parts of completed data should be retained or emphasized. SWE-Trail instead uses prior attempts while a new trajectory is being collected. The comparison can produce new repository evidence that would not exist if the alternative action were never executed. Curation can still be applied afterward. Appendix G.3 evaluates one such combination using verifier-based selection over SeedBank and H5 trajectories.


#### I.4 Training-Time Diversity and Adaptive Curation

Recent work treats the training corpus itself as an object to optimize. TDScaling increases trajectory diversity through blueprint-driven synthesis and adaptive task evolution rather than only sampling more trajectories ( Chen et al., 2026 ) . Han studies filtering of an existing SWE trajectory pool and reports an interaction between data quality, quantity, and model scale ( Han, 2026 ) . CurateEvo represents curation as executable code and updates the curation procedure from downstream failures to construct SFT, RL, and memory data from a fixed raw corpus ( Wang et al., 2026a ) .

SWE-Trail shares the goal of improving the training distribution but acts at a different stage. It changes how new trajectories are collected. Earlier attempts on the same issue guide where additional collection effort is spent, while the coding agent generates the candidate actions without receiving that history.


#### I.5 Experience-Guided Agents

Another line of work converts previous interaction into information that helps an agent act later. Reflexion and ExpeL store feedback or reusable experience across attempts ( Shinn et al., 2023 ; Zhao et al., 2024 ) . Agent Workflow Memory, CODESKILL, Socratic-SWE, and ProPlay derive workflows, skills, or procedural knowledge from previous executions ( Wang et al., 2025b ; Li et al., 2026a ; Xiao et al., 2026a ; Ma et al., 2026b ) . For software repositories, experience may come from earlier repair trajectories, human debugging records, or trajectories produced during the current solve ( Chen et al., 2025 ; Lin et al., 2024 ; Mu et al., 2026 ; Wang et al., 2026b ; Hayashi et al., 2025 ; Xia et al., 2025 ) . Other systems recombine agents or revise failed paths during inference ( Ehrlich et al., 2025 ; Guo et al., 2025 ) .

The common pattern is that distilled experience changes the coding agent’s visible context, workflow, or behavior. SWE-Trail keeps that information outside the coding agent. History guides the collector in deciding where additional collection effort may be useful, while the coding agent proposes its next actions from the ordinary context. This separation is central to our training-data setting because the exported trajectory does not depend on history being available to the student at test time.


#### I.6 Adaptive Acquisition and Harness Optimization

The broader idea of allocating computation using previous observations appears in active learning and experimental design, which choose informative examples or experiments ( Sener and Savarese, 2018 ; Kirsch et al., 2019 ; Foster et al., 2021 ) . Intrinsic-motivation methods similarly direct interaction toward novel or prediction-reducing states ( Bellemare et al., 2016 ; Pathak et al., 2017 ) . For LLM agents, direction-informed gating learns from counterfactual exploration whether a state feature indicates that extra rollouts will help or hurt ( Li et al., 2026b ) , and paired rollouts can estimate the value of asking a clarification question before acting ( Huang et al., 2026 ) . Agent self-improvement and harness-optimization methods adapt prompts, workflows, tools, or control procedures from execution feedback ( Madaan et al., 2023 ; Xi et al., 2024 ; Robeyns et al., 2025 ; Pan et al., 2026 ; Lin et al., 2026 ) .

SWE-Trail applies a narrower form of adaptive allocation within one issue. The history of that issue is compiled before the new collection round, and the resulting rules remain fixed during the rollout. They guide where additional collection effort is spent and how executed alternatives are compared, without changing the coding-agent prompt, tools, or model weights.

Recent results show that simple search can remain a strong baseline ( Gideoni et al., 2026 ) . We compare against independent sampling, a history-free version of the same collection pipeline, randomized controls, and verifier-based selection in Section 4.1 .
