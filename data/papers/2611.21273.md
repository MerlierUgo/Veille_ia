## CAE-Bench: Benchmarking AI Agents for Reusable CAE Solver Development

We developed CAE-Bench, a benchmark to evaluate AI agents on Computer-Aided Engineering (CAE) solver development. A CAE solver is more than a PDE solver; it must be able to generalize across various inputs, such as different boundary conditions, geometries, and material properties. CAE-Bench evaluates the generalizability of AI-developed CAE solvers by providing the same task, such as a heat transfer problem, multiple cases, with each case specifying an input. The AI agent develops a solver for a fixed task using only a few public cases, and the resulting solver is then tested on held-out cases, i.e., cases it has never seen before. We evaluate 12 models across a range of reasoning settings on 80 computational tasks. Our experiments show that even if a solver developed by an AI agent performs well on the public cases, it may even get $0$ score on held-out cases. For tasks such as fluid dynamics problems, even the solver developed by GPT-6 Astra performs poorly on held-out cases. A data format and an SDK for task registration are provided, so the researcher can use the benchmark on their own infrastructure. We hope that CAE-Bench will help the community to develop AI agents that can develop reusable CAE solvers that generalize to various inputs.


### 1 Introduction

For a PDE problem with given geometry and boundary conditions, it is not surprising that AI agents are capable of developing an accurate numerical solver. The AI-developed solvers for a fixed PDE problem can be evaluated through PDEAgent-Bench ( Hang et al., 2026 ) or CFDLLMBench ( Somasekharan et al., 2026 ) . However, for an industrial-level Computer-Aided Engineering (CAE) solver, solving a fixed PDE is not enough. The solver must be able to handle different geometries, boundary conditions, and material properties. The inputs of held-out cases should not be provided during development. Therefore, for a single task , the AI agent is required to develop a CAE solver that can generalize across cases with varying inputs. In this paper, we introduce CAE-Bench , a benchmark to evaluate the ability of AI agents to develop reusable CAE solvers that generalize across inputs.

We consider an extreme example. The task is to develop a solver for the governing equations of a 2-dimensional incompressible flow of a Newtonian fluid. The solver predicts velocity and pressure fields for given inputs. If the AI agent is only required to solve the task for fixed inputs, and the inputs are provided to the agent during development, then the agent can compute and store the answer during development, then return it during evaluation. This does not demonstrate that the agent can develop a reusable solver, since the resulting solver only works for these fixed inputs.

To evaluate the generalizability of AI-developed CAE solvers, we evaluate solvers on the same task with different cases, each case containing inputs and the reference used for scoring. All cases are distinguished into Public cases and Held-out cases . Public cases provide public inputs and example outputs during development. The example outputs have the required format, but their values are random. Held-out cases contain inputs that vary in geometry, material response, initial states, or boundary-condition types. These held-out cases are not provided to the agent during development. In summary, the public cases are used in both development and evaluation, while the held-out cases are only used in evaluation.

Besides input, each case is associated with reference results collected from analytical solutions, existing datasets, and established simulation software. These reference results are used for scoring during the evaluation phase, as discussed in Section 2 .

We also designed a data format to store the requirements of a given task, cases, and the output. Details are discussed in Section A . An SDK with tools for task registration and evaluation is also provided. Therefore, researchers can use the benchmark on their own infrastructure to evaluate the performance of their LLM model or harness.

The RC7 release of CAE-Bench contains 80 computational tasks, which include 13 prescribed-PDE tasks, 43 fluid-mechanics tasks, and 24 fixed-problem tasks adapted from CFDCodeBench ( Somasekharan et al., 2026 ) . Fixed-problem tasks do not have held-out cases and are reported separately. Replication of the complete evaluation is discussed in Appendix B .

Using the RC7 release, we evaluate 12 models across a range of reasoning settings. At medium effort, some AI-developed solvers receive full score on all public cases of a task. However, all AI-developed solvers got $0$ score on at least 1 held-out case of the same task. Also, most 0-score cases reach numerical scoring, which means the solver runs successfully and the output format is correct. However, the output fails the accuracy requirements. These results show that the current best models are not capable of developing an industrial-level reusable CAE solver without human involvement.


##### Related work

Several works have explored the ability of AI agents to develop numerical solvers. CodePDE ( Li et al., 2025 ) uses debugging and iterative refinement to improve AI-developed PDE solvers. PDEAgent-Bench ( Hang et al., 2026 ) evaluates whether AI agents can develop accurate enough PDE solvers using libraries such as DOLFINx, Firedrake, and deal.II. CFDLLMBench ( Somasekharan et al., 2026 ) evaluates AI agents on CFD-related tasks, including code generation and OpenFOAM workflows. PDEBench ( Takamoto et al., 2022 ) evaluates machine learning models by providing simulation datasets covering different initial conditions, boundary conditions, and PDE parameters. The reference solution is also provided to compare the machine learning based methods with traditional methods. These works mainly focus on developing solvers or completing simulations for given problems. For an industrial-level CAE solver, such complete information is impossible to gain during development.


### 2 Tasks and Evaluation Protocol

For a benchmark framework, the most important aspect is the clear definition of tasks and evaluation protocols (scoring). The detailed definition of tasks and cases is discussed in Section 2.1 and the scoring rules are described in Section 2.3 . Besides definitions, we discuss the input data format in Section 2.2 and the evaluation report format in Section 2.3 .


#### 2.1 Tasks, Cases, and Observations

In this paper, the term task defines a physical or mathematical problem. By define, we mean that the task specifies the required inputs, outputs, scoring rules and execution requirements. A single task contains one or more evaluation cases. The term case defines a complete test example for the task. Each case contains specified inputs and reference results. Formally:

[Tableau] $$\text{case}=\text{inputs}+\text{reference result}.$$ (2)

The AI-developed solver must handle all the cases assigned to the task. Table 1 shows the task-case relationship in a released flow task.

[Tableau] Aspect Fixed by the task Supplied by each case Analysis Steady, 2-dimensional, single-phase laminar flow; incompressible Newtonian fluid Fluid domain; positive constant density and viscosity Conditions Supported mechanical boundary conditions, body forcing, and pressure conventions Condition types, boundary assignments, values, and applicable pressure constraint Observations Definitions and units of velocity, pressure, and other supported quantities Requested quantities, locations, and point, average, or integral observations

> Table 1: Cases for the 2-dimensional steady incompressible Newtonian-flow task.

The inputs describe the physical conditions, such as geometry, material properties, and boundary or initial conditions. During evaluation, the submitted solver receives the inputs and produces its own outputs.

Evaluation cases can be distinguished into two groups: Public cases and Held-out cases . Public cases provide inputs and template outputs (which means the data format is identical to the reference results but the numerical values are randomly generated) during development. Held-out cases are not accessible during development but only used for evaluation. A task may contain either or both case groups.

In this paper, we call each requested output produced by an AI-developed solver for a given case an observation . Each observation specifies a physical quantity, its units, and its form. An observation may contain values at multiple locations and times. For example, temperature is a physical quantity, while point values, cell averages, and spatial integrals are different forms of temperature observations. A temperature field can also be observed at a specific time or averaged over a period of time, resulting in different observations.


#### 2.2 Data Formats and SDK

Each task contains instructions, DATA.md , and the shared CONTRACT.md as the agent’s initial prompt. DATA.md explains how to read the inputs and write the outputs. CONTRACT.md defines the common file formats.

In our implementation, an HDF5 file is used to store the sample identifiers, values, and field arrays. For sampling based on a mesh, the sample identifiers refer to node or element tags in a Gmsh .msh file. Each case input includes a problem.json file. problem.json specifies the physical setup, references the data files, and declares the requested outputs.

We also provide an optional SDK to help agents develop without having trouble understanding the data format. The SDK includes tools that test whether files meet format and compatibility requirements without providing evidence that shows numerical accuracy. Detailed discussions of the data format and the SDK are included in Appendix A .

These given prompts and tools guide the agent to develop solvers that follow the task’s physical assumptions and restrictions. Different tasks have different restrictions. For example, some tasks may require the solver to solve prescribed equations while other tasks let the agent decide the equations to solve.

The agent can use analytical expressions, numerical libraries, existing open-source software, or combine them, to develop a CAE solver. Therefore, CAE-Bench does not require Agents to implement every numerical method from scratch.

The submitted AI-developed CAE solver must include a solve.py entry point. CAE-Bench evaluates through the entry point for each case by

python solve.py --input problem.json --output result.h5

The submitted AI-developed solver is fixed after the development phase. The agent cannot revise the solver during the evaluation phase. For each case, CAE-Bench makes a fresh writable copy of the saved solver. The running solver receives the current case input. For that case, the solver must give the requested output. During evaluation, network access is not allowed. The solver must finish the case within the declared time, CPU, memory, and accelerator limits. #### 2.3 Scoring Rules and Evaluation Report

Before giving any score, we first check the execution and output validity of AI-developed solvers. The solver receives $0$ score in one case if it exceeds a time or resource limit, exits with an error, fails to produce output, or produces invalid output. CAE-Bench checks output identifiers, time axes, array shapes, and data types against the requirements. The output values must be finite and data types such as integer and Boolean must follow the exact agreement as in template outputs. Failure of a required type check sets the score to $0$ .

For floating-point observations, we compare the solver’s outputs with the reference values at all requested times and locations, including initial frames and boundaries. To calculate the score, we divide the outputs into groups based on the physical quantity, its components, and time. Each group contains all spatial values of one component at a given time, which are compared with the corresponding reference values.

For example, consider a case that requires 2-dimensional velocity and pressure fields at $10$ different times. Since velocity has $2$ components and pressure has $1$ component, we have $20$ groups for velocity and $10$ groups for pressure, resulting in $30$ groups in total. The number of spatial locations does not affect the number of groups, but only the number of values compared within each group.

We use a weighted normalized root-mean-square error (NRMSE) to evaluate each group. Let $M$ be the number of floating-point groups in a case, and let $i$ index the spatial locations within group $j$ . We use $\widehat{z}_{ji}$ and $z_{ji}$ to denote the solver’s output and reference value, respectively. The NRMSE for group $j$ is defined as

[Tableau] $$e_{j}=\frac{\displaystyle\sqrt{\frac{\sum_{i}w_{ji}(\widehat{z}_{ji}-z_{ji})^{2}}{\sum_{i}w_{ji}}}}{\displaystyle\max\!\left(\sqrt{\frac{\sum_{i}w_{ji}(z_{ji}-b_{j})^{2}}{\sum_{i}w_{ji}}},\ s_{j}\right)}.$$ (3)

The default values of spatial weights $w_{ji}>0$ are equal for all $i$ and $j$ , and the default value for $b_{j}$ is $0$ . The scale floor $s_{j}>0$ prevents division by zero. Spatial weights, scale floors, and scoring transformations are specified in the task descriptions and applied during evaluation. No further alignment or rescaling is allowed.

We denote the RMS of the $M$ group errors as $E$ and define the function $p(E)$ that maps $E$ to a dimensionless score between 0 and 1. Formally,

[Tableau] $$E=\sqrt{\frac{1}{M}\sum_{j=1}^{M}e_{j}^{2}},\qquad p(E)=\begin{cases}1,&E\leq 0.05,\\ (0.10-E)/0.05,&0.05<E<0.10,\\ 0,\>&E\geq 0.10.\end{cases}$$ (4)

Let $\mathcal{T}$ denote a task and $N_{\mathcal{T}}$ be the number of cases in task $\mathcal{T}$ . Index $k$ runs from 1 to $N_{\mathcal{T}}$ and identifies a case. The score of case $k$ is denoted by $p_{k}$ . The case score $p_{k}=0$ if any required check fails. Otherwise, $p_{k}=p(E)$ .

The task score $P_{\mathcal{T}}$ is defined as the mean of all case scores (all assigned cases contribute, whether they are public or held-out cases). Formally,

[Tableau] $$P_{\mathcal{T}}=\frac{1}{N_{\mathcal{T}}}\sum_{k=1}^{N_{\mathcal{T}}}p_{k}.$$ (5)

For tasks with varying physical inputs, we report scores on public cases and held-out cases separately to evaluate how well the solver generalizes to unseen inputs. For fixed-problem tasks (tasks do not contain held-out inputs), the scores only reflect performance on the given inputs. Infrastructure tests are evaluated using exact-match or pass/fail checks, and their results are reported separately from computational tasks.

Researchers can use adapters we provided to run the evaluation tools in their own environments.


### 3 Benchmark Construction

In this section, we discuss how to construct tasks and cases and how to obtain their reference results. Before discussing the details, we summarize the number of tasks and cases in CAE-Bench (RC7) in Section 3.1 . The design of cases for each task is described in Section 3.2 . How the reference results are obtained is discussed in Section 3.3 .


#### 3.1 Benchmark Contents

As shown in Table 2 , CAE-Bench (RC7) contains 2 infrastructure tests and 80 computational tasks. The 80 computational tasks are divided into 3 categories: prescribed-PDE tasks, fluid-mechanics tasks, and fixed-problem tasks.

The prescribed-PDE tasks cover elliptic problems, transport, reaction and diffusion, and coupled systems. The fluid-mechanics tasks cover single-phase flow, energy transport, turbulence, interfaces, thin films, shallow water, rarefied gases, and fluids with memory. Both categories contain tasks with varying physical inputs.

The fixed-problem category uses 24 problems from CFDCodeBench ( Somasekharan et al., 2026 ) . Fixed-problem tasks do not have held-out cases.

The total 630 computational cases comprise 70 public cases and 560 held-out cases. All 24 cases in the fixed-problem category are public cases. The 2 infrastructure are used to check data handling and scoring behavior. In the final report, we exclude these infrastructure tests.


#### 3.2 Case Design and Coverage

For the same task, we create various cases by changing material properties, geometry, boundary conditions, and initial conditions.

For example, the steady heat-conduction task (which is included in RC7) contains 32 cases with different geometries, thermal conductivities, heat sources, and boundary conditions. The boundary conditions include Dirichlet, Neumann, Robin, and mixed conditions. Among these cases, 4 use pure Neumann conditions with an additional mean-temperature constraint.

Figure 2 shows the input variations for another 2 tasks. The periodic advection task contains 24 cases, combining 8 velocities with 3 initial fields. The generalized-Newtonian flow task contains 8 cases with different material models and conditions. The material models include power-law, Cross, Carreau, and Carreau–Yasuda. Another task, transient viscoelastic flow, contains 9 cases with different initial conformation and wall-driving histories, including stopping and reversing wall motion.

For the fixed-problem tasks adapted from CFDCodeBench, we compute reference results using the specified equations and boundary conditions. For example, in the cavity cases, the velocity boundary conditions are prescribed. The momentum and incompressibility equations determine the pressure up to an additive constant.


### 4 Experiments and Findings

In this section, we present the experimental results of CAE-Bench. We first describe the experimental setup in Section 4.1 . We then compare different models and reasoning-effort settings and discuss API costs in Sections 4.2 , 4.3 , and 4.4 , respectively. The generalizability performance is discussed in Section 4.5 .


#### 4.1 Experimental Setup

We test 6 OpenAI models, including GPT-5.6 Luna and GPT-6 Luna (each at none, low, medium, high, xhigh, and max), as well as GPT-5.6 Sol, GPT-6 Sol, GPT-6.1 Sol, and GPT-6 Astra (each at medium). We also test DeepSeek V4.1 Flash (high), Kimi K2.7 Code (thinking), Qwen3.8-Flash (low, medium, and xhigh), GLM-5.3-Flash (low, high, and max), Gemini 3.8 Flash (medium), and Gemini 4 Argon (medium). In total, we evaluate 12 models across 26 cases. Due to the so-called “security issue” under Anthropic dictatorial team ruled by Dario, we cannot access Claude-series model in China. Researchers can implement the experiment and submit into https://github.com/AXeonV/CAE-Bench

The mini-swe-agent 2.4.6 ( Yang et al., 2024 ; Lieret and Jimenez, 2026 ) is used for all experiments. For the Gemini models, development and evaluation use local Harbor runs. For the other models, development and evaluation are conducted in separate Hugging Face Jobs. Agents have 30 to 120 minutes to develop a solver depending on the task. Each agent is given 8 vCPUs and 24 GiB of memory. If an agent fails to submit a solver, he receives a score of 0. More details are discussed in Appendix C .

We use the 80 computational tasks in RC7 to evaluate the models. Complete results are provided in Appendix C .

We calculate the score of each task by averaging its case scores, as defined in Section 2.3 . The final score is the average of the task scores, with equal weight for each task. All scores are reported on a 0-100 scale. We report the results for tasks with varying physical inputs and fixed-problem tasks separately.

### 5 Limitations

CAE-Bench mainly covers prescribed-PDE and fluid-mechanics tasks. The scores only reflect performance on the selected cases and do not guarantee that the developed solvers can handle all possible inputs or other CAE problems.

The reference results are collected from analytical solutions, existing datasets, and simulation software. However, not all reference results have been independently validated for numerical accuracy.

Although held-out cases are not provided during development, their source data may have appeared in model training data. Moreover, public and held-out cases differ in physical inputs and coverage. Therefore, the score differences cannot be attributed solely to withholding the cases.

More details are provided in Appendix C .


### 6 Conclusion

We introduced CAE-Bench, a benchmark for evaluating the ability of AI agents to develop reusable CAE solvers. Unlike existing benchmarks that focus on fixed problems, CAE-Bench evaluates the generalization of AI-developed solvers across unseen physical inputs. Our experiments show that current AI agents are not capable of developing reusable CAE solvers without human involvement. Even when an AI-developed solver performs perfectly on cases used for development, it may fail on unseen cases. We hope CAE-Bench will help researchers develop AI agents capable of building reliable and reusable CAE solvers.

### Appendix A Data Format and Public Tools

Each task contains instruction.md , DATA.md , and the shared CONTRACT.md as the test materials provided to agents.

instruction.md is the overview information in the problem. It also gives the input data range. CONTRACT.md is the general data protocol for data storage and referencing. It serves as a common set of rules suitable for all problems. DATA.md defines the comprehensive rules for certain physical fields and constraints. Any specific rule not covered by CONTRACT.md is declared in DATA.md .

When the problem packages are being assembled, the problem.json will be generated for each case. The solver reads the input from problem.json . This file specifies the physical model, parameters and conditions. The information in fields and outputs describes the input fields and output requirements. Each term of declaration gives the details of HDF5 data such as dataset name, physical quantity, unit, data type, and component labels and shape. It may also specify the location and time axis, or explain whether the data are point values, averages or integrals. Conditions can be given as constants with units or refer to data stored in the input fields in an HDF5 file.

The input from an HDF5 file stores the concrete field array, entity id number and time value in the dataset. If there is a need to use a mesh, problem.json will also provide a Gmsh .msh file in MSH 4.1 ASCII format. The mesh file stores the nodes and edges information which is connected to the entity id number. Otherwise, the locations of this entity id number will be stored in the HDF5 file directly.

The axes of a field are in order: time axes, entity axes and component axes (declared in problem.json ). Every position in the entity axes is aligned to the entity id number. The solver needs to write the output field to a separate HDF5 file and strictly ensure the order.


#### A.1 A Released Heat-Conduction Example

The public samples of the problem heat-conduction-steady-2d are in samples/01 . The problem is designed to solve steady-state heat conduction on a unit square with no heat source. The thermal conductivity is 1 W/(m K). The temperature of 4 boundaries is 4 K. The mesh includes 9 nodes and 8 triangle units. Full information about the problem is available in supplement/heat-conduction-steady-2d-agent.zip .

The sample input/problem.json uses mesh.msh and input.h5 . Here are the condition on the left boundary and the output requirement.

The boundary condition uses left to refer to the left_ids dataset. It stores the element tags of the left boundary. The boundary condition also uses left_coefficients and gives the name to the input.h5 dataset accordingly. The dataset stores 5 temperature polynomial coefficients for each boundary in ascending power order. The polynomial in this case is always 4 K on the left boundary.

The output requirement uses nodes and steady to refer to node_ids and times in the input.h5 dataset. The shapes of the 3 datasets are $(9,)$ , $(1,)$ , and $(1,9,1)$ , respectively. temperature[0,i,0] gives the temperature in the time value 0 of node_ids[i] . This format is demonstrated by output/result.h5 using random temperature values.


#### A.2 Using the Data Tools

The solver uses --input to receive the path of problem.json and --output to receive the path of the HDF5 file it needs to write. The solver can also use SDKs provided by us to read and write. load_problem helps read and check the input. read_field helps read a dataset from the input HDF5 file according to the problem problem.json . write_result helps align and write the calculation output into the arrays. It also helps check the structure of the results under the rules of our DATA.md and CONTRACT.md .

The package also provides a validator to make structural checks. The validator is designed to reduce the burden of reading and writing data under our contract. We do not want the agents to have problems on understanding the dataset input or make errors on the output structure instead of the problem itself. The validator checks formatting, references, and declaration constraints. It does not verify or correct physical results.

Run the following commands in a Python environment to check the released example.

validate-input checks the JSON declaration and mesh and HDF5 reference of problem.json . validate-output checks whether the data type and shape meet the requirements of the entity number id and time value.

python -m caeoj grade performs numerical grading. It grades using input cases and grading criteria grading.json on the solver.

#### C.2 Development and Evaluation Conditions

In our experiments, the agent develops the solver in a public task workspace. It can use a shell to read and write files, run programs, and access the network.

For the Gemini models, development and evaluation use local Harbor runs. For the other models, development and evaluation run in separate Hugging Face Jobs. The jobs use 8 vCPUs and a 24 GiB memory allowance. The evaluator runs each case in a separate process without network access. The solver is required to produce result.h5 per task in between 4 s and 40 min. The time limit depends on each task.

During grading, the solver output result.h5 is compared to reference results. For most tasks, the grader has 60 s to judge per case. For the 3D compressible Navier–Stokes task, the solver has 30 min to produce result.h5 and the grader has 2 min to judge.
