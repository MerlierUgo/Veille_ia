## Free to Look, Free to Reason: Simple LLM Harnesses Outdiagnose Hand-Crafted Root Cause Analysis Agents

Root cause analysis (RCA) of microservice failures has attracted many LLM agents whose investigation is hand-crafted, through standard operating procedures, fixed stages and role agents. Each is evaluated on its own data against few baselines, so it is unknown whether this design beats letting a capable model investigate on its own. We compare three simple harnesses that prescribe none of the model’s calls (one call over an evidence package, a SQL agent and the Codex coding agent) with five published LLM RCA agents and with statistical and causal methods on RCAtlas, 90 validated cases from eight public datasets, across six models and three reasoning efforts. The simple harnesses are the most accurate (PR@1 65–77% on three mid-tier models), ahead of the published agents (16–53%) and the non-LLM methods (6–39%), on every model on which both families were run. The published agents fix from a tenth to all of their model calls in the program, and a case study shows how these prescriptions skip the decisive evidence. A stronger model mainly improves reliability, a multi-turn harness mainly improves aptitude, and more reasoning effort changes accuracy by a few points at most while multiplying the time by up to seven. Among runs more accurate than the best non-LLM method, every Pareto-optimal run in cost or time uses a simple harness.

### 1. Introduction

Failures in the microservices behind web services cascade across components, and operators must find the root cause among hundreds of services, pods and nodes from metrics, traces, logs and events ( Beyer et al., 2016 ; Zhou et al., 2021 ; Dang et al., 2019 ) . Three lines of work improve this task: RCA methods, from statistical and causal ranking ( Lin et al., 2018 ; Wang et al., 2018 ; Ma et al., 2020 ; Li et al., 2022 ; Pham et al., 2024a ) to LLM agents; the LLMs underneath them; and general-purpose agent harnesses. A harness is the program around a model that feeds it data and carries out its actions. The simplest harness only feeds data, in a single call; richer ones let the model query the data, or write and run code as Codex ( OpenAI, 2026 ) does.

Published LLM RCA agents hand-craft the investigation with standard operating procedures, fixed stages, expert or role sub-agents and votes, so the program decides much of what is read and when ( Pei et al., 2025 ; Wang et al., 2024 ; Xu et al., 2025 ; Zhang et al., 2024 ; Muhammad et al., 2026 ) . Each is evaluated against a few baselines on one to three systems, often collected by its own authors, and benchmarks run one reference agent or none ( Fang et al., 2026a ; Cai et al., 2026 ) . Whether hand-crafting still pays off as models and harnesses improve is therefore unknown.

We compare the three lines on the same cases. RCAtlas pools eight public RCA datasets into one format, screens 542 cases for validity and samples 90 across 23 scenarios. On it we run three simple harnesses that prescribe none of the model’s calls (one call over an evidence package, a SQL agent over the raw telemetry, and Codex), five published LLM agents, and statistical and causal methods, with six models, three reasoning efforts and one scorer. We change a method only where it cannot run on our data or has an implementation error.

Harnesses that leave the model free to choose what to look at and how to reason win (Figure 1 ). The simple harnesses reach PR@1 65–77% on three mid-tier models, ahead of the published agents (16–53%), which are mostly ahead of the non-LLM methods (6–39%). The trajectories show why: when the program decides what to read, it can skip the decisive evidence, such as a log line or a service that stops receiving calls. A stronger model mainly improves reliability, a multi-turn harness mainly improves aptitude, and more reasoning effort changes little. Among runs more accurate than the best non-LLM method, every Pareto-optimal run in cost or time uses a simple harness.

Our contributions are:

- • RCAtlas, 90 validated cases from eight public datasets in one format, with a scoring rule for labels at different levels (Section 4 );

- • a field-wide evaluation of simple harnesses, published LLM agents and non-LLM methods on the same cases, across six models and three reasoning efforts (Section 6.1 );

- • analyses of why methods succeed or fail: a case study, the share of model calls each method prescribes, and the separate effects of model capability, reasoning effort and multi-turn investigation on accuracy and reliability (Sections 6.2 – 6.5 );

- • cost- and time-aware recommendations from the Pareto frontier (Section 6.6 ).


### 2. Related Work


##### Root cause analysis methods.

Classical RCA for microservices ranks components from telemetry by statistical deviation (NSigma, BARO ( Pham et al., 2024a ) , $\epsilon$ -Diagnosis ( Shan et al., 2019 ) ), causal discovery and inference (CIRCA ( Li et al., 2022 ) , RCD ( Ikram et al., 2022 ) , DyCause ( Pan et al., 2021 ) , FaultInsight ( Bi et al., 2024 ) ), propagation on dependency graphs (MicroRCA ( Wu et al., 2020 ) , MicroRank ( Yu et al., 2021 ) ), or multi-source fusion (TORAI ( Pham et al., 2026 ) ). LLM-based methods mostly fix the investigation in the program: standard operating procedures the agent must follow (FoA ( Pei et al., 2025 ) ), a controller that never sees data and an executor that writes code (RCA-Agent ( Xu et al., 2025 ) ), observation management with expert sub-agents (RCAgent ( Wang et al., 2024 ) ), voting among role agents (mABC ( Zhang et al., 2024 ) ), one agent per trace span (RCLAgent-V2 ( Zhang et al., 2026 ) ), tree search with self-reflection (LATS-RCA ( Naakka et al., 2027 ) ), or program-side retrieval followed by one LLM reranking call (DecompRCA ( Muhammad et al., 2026 ) ). Failure studies trace recurrent errors to the shared agent architecture rather than the model ( Kim et al., 2026 ) , catalogue reasoning failures across agentic and non-agentic prompting ( Riddell et al., 2026 ) , and contrast successful and failed trajectories ( Lu et al., 2026 ) .


##### General-purpose agent harnesses.

Coding agents have grown into general harnesses such as Codex ( OpenAI, 2026 ) and Claude Code ( Anthropic, 2026 ) : the model decides what to do next and acts by writing and running code, with no task-specific procedure. For RCA, such a harness without any RCA design already outperforms purpose-built agents on OpenRCA and RCAEval ( Huang et al., 2026 ) . OpsHarness ( Huang et al., 2026 ) then adds a self-evolving layer that learns from labelled past incidents of the same system. We take the complementary view: we test simple harnesses without such a layer (Codex, a SQL agent and a single call) against prescribed pipelines and non-LLM methods on the same cases.


##### Benchmarks and evaluation.

Model-wide evaluations rank models on many tasks and sub-capabilities; the Artificial Analysis Intelligence Index ( Artificial Analysis, 2026 ) has recently added an RCA-style task suite, ITBench-AA ( Sebin et al., 2026 ) , built from ITBench ( Jha et al., 2025 ) . RCA-specific datasets include RCAEval ( Pham et al., 2025 ) , OpenRCA ( Xu et al., 2025 ; Fang et al., 2026a ) , LEMMA-RCA ( Zheng et al., 2026 ) , the AIOps challenge data and RCA-100 ( Cai et al., 2026 ; Wen et al., 2026 ) , and a fault-propagation-aware TrainTicket benchmark ( Fang et al., 2026b ) . Each covers one to three systems, and each evaluates a narrow slice of methods: OpenRCA 2.0 runs one reference agent across models, AgenticOpsEval ( Cai et al., 2026 ) releases data and a scoring protocol without method results, and new methods are often evaluated mainly on data collected by their own authors ( Pham et al., 2024a ; Pham et al., 2026 ) . Audits show that simple rules or telemetry-free priors reach high scores on some of them ( Fang et al., 2026b ; Buljić, 2026 ) . RCAtlas pools eight of these sources, screens every case for validity, and evaluates simple harnesses, published LLM agents and non-LLM methods on the same cases with one scorer.


##### Agents on complex tasks.

Evidence from other domains questions elaborate agent pipelines. A fixed localise–repair–validate pipeline competed with software-engineering agents at a fraction of the cost ( Xia et al., 2025 ) ; splitting a task across conversational turns degrades LLMs mainly through lower reliability ( Laban et al., 2026 ) ; and input length alone can hurt even when retrieval is perfect ( Du et al., 2025 ) . More broadly, general methods that scale with computation tend to overtake hand-engineered knowledge ( Sutton, 2019 ) . We test this question directly on RCA.


### 3. Background and Problem


##### Systems and telemetry.

The systems under test are microservice applications on Kubernetes. Their entities are services, the pods and containers that run them, the nodes (hosts) that run the pods, databases and middleware, and the operations a service exposes. Four kinds of telemetry are recorded: metrics , time series per entity such as CPU and memory use, request counts, error rates and latency (timestamp, entity, metric name, value); traces , one span per call between operations (trace and span identifiers, parent span, operation, duration, status), which reveal who calls whom and where errors and delays arise; logs , timestamped lines per pod with a level and a free-text message; and events , Kubernetes records such as restarts, evictions or scheduling failures. Each case also carries an inventory of entities and their relations (calls, deployment, placement).


##### Task.

A case gives an incident’s flagged period, a period known to precede it, the candidate inventory and the telemetry of both periods. The method returns a ranked list of root-cause entities; we score the first five. Labels name one root-cause entity per case (three cases have two), at the level its dataset annotates: service, pod or node (we count databases as services and hosts as nodes).


##### Scoring.

Datasets label at different levels, and an answer may be finer than the label, such as a pod of the faulty service. Before matching, we therefore map each answered entity upward: it is replaced by itself and those of its parents in the inventory (container, pod, service) that lie at the levels the dataset annotates. Duplicates are then dropped, the first five distinct entities form the answer list, and they are compared with the labels by name. For example, when a dataset labels services, an answer naming a pod of cart counts as cart, and a second pod of cart further down the list adds nothing. Methods that rank metric columns, as most non-LLM methods do, are mapped the same way through the entity that owns each column. Each answer can match at most one root cause.

We report two metrics. Let case $i$ of $N$ have the set of root causes $T_{i}$ , with $t_{i}=|T_{i}|$ , and the mapped answer list $a_{i,1},\dots,a_{i,k_{i}}$ ( $k_{i}\leq 5$ ). For a root cause $g\in T_{i}$ , let $r_{i}(g)$ be the position of the first answer that matches $g$ , and $r_{i}(g)=\infty$ if none does (in particular when the case has no answer). Then

[Tableau] (1) $$\mathrm{PR@1}=\frac{1}{N}\sum_{i=1}^{N}\mathbf{1}\bigl[\exists\,g\in T_{i}:r_{i}(g)=1\bigr],$$

[Tableau] (2) $$\mathrm{RR}=\frac{1}{N}\sum_{i=1}^{N}\frac{1}{t_{i}}\sum_{g\in T_{i}}\frac{1}{1+\max\bigl(0,\,r_{i}(g)-t_{i}\bigr)},$$

with $1/\infty=0$ . PR@1 is thus the share of cases whose first answer is a root cause. In RR the first $t_{i}$ positions all score one, so with two root causes A and B both “A, B” and “B, A” score 1. Both means run over all $N$ cases, so a case without an answer scores zero. We do not report PR@ $k$ for larger $k$ , because methods return different numbers of answers: the simple harnesses one to five, chosen by the model; RCA-Agent and mABC always one; DecompRCA about 14; and non-LLM methods a full ranking. To show how hard each case is, we compute its exact random-guess hit rate: the probability that one entity drawn uniformly from the inventory is a hit under the same mapping. Its median over the core set is 3.45%, and Table 1 reports its inverse as the effective number of candidates.


### 4. The RCAtlas Benchmark

RCAtlas pools eight public RCA datasets (ten suites, counting RCAEval RE1–3 separately) into one case format, screens every candidate case for validity, and samples the survivors across systems and fault types (Table 1 ; Appendix C.1 summarises the construction procedure).


##### Sources and format.

The sources span nine systems, from Online Boutique, Sock Shop and TrainTicket to a bank, a telecom system and a cloud platform, with faults injected by chaos tools, by challenge organisers, or in drills on a managed Kubernetes service. Each case is converted to the same tables: an entity inventory with call, deployment and placement relations, and the metrics, traces, logs and Kubernetes events of a window around the fault, all in UTC. The conversion removes traces of the injection tools (for example their pods and log lines) so that no case reveals its answer.


##### Validity screening.

The sources have released 2,359 cases; we screened 542 of them, and 348 pass eight exclusion rules. Among others, a case is excluded if its labels contradict each other, if it contains several faults, if the culprit is missing from the data, if neither a judge model nor an automatic check finds evidence of the fault in the telemetry, if data are incomplete, if the period before the fault is not clean, or if the fault starts late in the flagged window. The most frequent reasons are an unclean before-period (69 cases) and no evidence (56).


##### Sampling.

From the 348 eligible cases we draw the 90-case core set (RCAtlas-Core): a minimum per scenario, then cases that diversify fault class, root-cause level, data kinds and telemetry volume. The core set spans 23 scenarios and ten fault classes; the root cause is a service in 59 cases, a pod in 20 and a node in 11. Cases range from 37k to 5.6M telemetry rows, and the exact random-guess hit rate under our scoring rule ranges from 0.25% to 16.7% (median 3.45%). All experiments in this paper use the core set.


##### Availability.

We provide the core-set case list and our code at ( https://ufile.io/5ww9iyfb ). The file cases/core90_cases.csv gives, for each case, its identifier in the source dataset, the time window, the data kinds and the answer template, so that every case can be rebuilt from its public source; cases/core90_labels.json gives the root-cause labels and their levels (59 services, 20 pods and 11 nodes). The folder methods/ holds the three simple harnesses (the one-shot method, the SQL agent and the Codex run settings) and our reimplementations of FoA (with its SOP files), RCAgent, DecompRCA and SimpleRCA. Shared code in rcatlas/ covers path configuration, an OpenAI-compatible model client, answer parsing and the data tools shared by FoA and RCAgent; prompts/ holds the one-shot prompt templates and background notes, and answer_templates/ the answer templates of the 23 scenarios in the version used in the paper, without hints on the root-cause level. We plan to release the converted core-set data (about 11 GB) and an extended set of about 500 cases built with the same rules.

### 5. Methods Under Test

We evaluate three families (Table 2 ). Every method receives the same information about a case, namely the flagged period, the candidate inventory and the telemetry, and returns a ranked list of root-cause entities, of which the first five are scored.


##### Simple harnesses.

One-shot sends the whole case to the model in a single call: an evidence package with the system inventory, the metric series that moved (as raw samples), per-minute trace statistics, log templates and events; the model answers with up to five candidates and no tools (Appendix C.2 ). The SQL agent is a single ReAct loop over the raw files with DuckDB, modelled on the reference agent of OpenRCA 2.0 ( Fang et al., 2026a ) : tools to list files, read a schema, run SQL and submit, at most 100 calls. Codex runs the Codex CLI ( OpenAI, 2026 ) in the case folder with a task statement and six rules (read only this folder; no network or installs; do not modify the data; do not try to identify the source dataset; always write a final report; one hour at most); the model writes its own shell and Python.


##### Published LLM agents.

We run RCA-Agent ( Xu et al., 2025 ) and mABC ( Zhang et al., 2024 ) from their released code, and reimplement FoA ( Pei et al., 2025 ) , RCAgent ( Wang et al., 2024 ) and DecompRCA ( Muhammad et al., 2026 ) , which have no released code, from their papers; our DecompRCA reproduces the paper’s numbers on RCAEval RE1. The reimplemented agents share one set of data tools over the raw files. We follow one rule for fairness: fix only what prevents a method from running on our data or what is an implementation error, and add no capability. Examples are converting time zones for RCA-Agent, restoring modules missing from mABC’s release, and completing tool descriptions in FoA’s code agent; the appendix summarises the changes. We exclude RCLAgent-V2 ( Zhang et al., 2026 ) (about USD 0.9 and up to an hour per case), LATS-RCA ( Naakka et al., 2027 ) (its released search strips the agents’ tools), EviRCA ( Wang et al., 2026 ) and MicroRCA-Agent ( Tang et al., 2025 ) (each needs a hand-written adapter per system or is built around one benchmark’s data layout), and supervised methods, which need a labelled training split.


##### Non-LLM methods.

NSigma, BARO, CIRCA, RCD and TORAI come from RCAEval ( Pham et al., 2025 ) ; FaultInsight from the authors’ code; SimpleRCA ( Fang et al., 2026b ) is reimplemented from its description. All receive the start of the flagged period; methods with randomness are averaged over three runs. A random ranking gives the floor.


##### Models and settings.

Setting 1 runs every LLM method on three mid-tier models: GPT-6 Luna, DeepSeek V4.1 Flash (1017) and Claude Haiku 5.5. Setting 2 runs the simple harnesses on six models, adding GPT-6.1 Sol, GPT-6 Astra (at xhigh) and MiMo-V2.6-Pro. Below we call the models Luna, Flash, Haiku, Sol, Astra and MiMo. Setting 3 raises the reasoning effort of Luna and Sol to xhigh and max. The simple harnesses on Luna, and the SQL agent and Codex on Sol, are run three times. Tables report the mean over passes; Figures 1 and 5 and Table 8 use the first pass. No generation parameter is sent except the effort in Setting 3; each case has one hour, and a case without an answer scores zero.

### 6. Experiments

We answer five research questions. RQ1 (effectiveness): how do simple harnesses, published LLM agents and non-LLM methods compare on the same cases? RQ2 (mechanism): why do the simple harnesses win, and how much of each method’s investigation is prescribed by its program? RQ3 (capability and effort): how do a stronger model and more reasoning effort change how agents investigate and how accurate they are? RQ4 (aptitude and stability): how much accuracy is reproducible across passes, and how much appears only in some? RQ5 (cost-effectiveness): which model and method combinations are Pareto-optimal in accuracy against cost and time?


#### 6.1. Overall effectiveness (RQ1)

Table 3 shows three layers. Averaged over the three mid-tier models, the simple harnesses reach PR@1 65–77%, the published LLM agents 16–53%, and the non-LLM methods 6–39%, against 5.5% for a random ranking. Codex is best overall, and even the weakest simple harness (one-shot) leads the best published agent (FoA) by 12 points. The lower two layers overlap: NSigma (38.9%) beats DecompRCA and mABC. Every LLM method is less accurate on pod- and node-level root causes than on service-level ones, and the published agents lose the most: from service to pod, Codex drops 9 points, FoA and RCAgent 31–38. NSigma is the only method more accurate on pods than on services (55.0% vs. 33.9%), since resource faults show on the culprit’s own metrics. Appendix C analyses the hardest groups. More kinds of data do not make a case easier. The 17 cases with all four kinds, which come from RCA-100 and ITBench-SRE, are the hardest for the simple harnesses (52–71%), and they form the only column in which a published agent matches the best simple harness: FoA reaches 70.6%, as Codex does. Conversely, the ten cases with metrics only are the easiest for the SQL agent (95.6%). The ordering does not depend on the model (Tables 5 and 5 ). On each of Luna, Haiku and Flash, every simple harness is ahead of every published agent (one-shot’s 5.9-point lead on Luna is not significant), and Codex is best or tied on every model it ran on. Across models, the simple harnesses fall into two tiers at the jump of the AA index from 34.5 to 45.1: 60–71% on Luna and Haiku, 74–87% on Flash, Sol and Astra. Leaving out MiMo (see below), 12 of the 13 cross-tier model pairs differ significantly, but only one of the nine within-tier pairs (Appendix B ). MiMo is the exception: its AA index (46.3) places it in the upper tier, but its accuracy (58–74%) matches the lower one, partly because it finished only 69–86 of the 90 cases.

The difference between the families is who decides what to look at and how to compute on it, which is what the prescribed-call ratio (Section 6.3 ) measures. The SQL agent writes its own queries and Codex writes its own analysis code, so the model chooses both what to read and how to compare it, and none of their calls is prescribed. The published agents fix part of this in the program. FoA can only choose among the steps of its built-in procedures, so when the matched procedure has no log step, it never sees the logs. RCA-Agent’s controller never touches the data and learns about the case only from its executor’s summaries, and mABC starts from an alert its program computes and walks the call chain from there. In the terms of our title, the SQL agent and Codex are free to look and free to reason; one-shot is free to reason over evidence that rules select.

We follow one case through the methods, rca100-main-0104 from RCA-100 (Figure 2 ). The inventory Service selects no pods, so cart’s calls to it are refused. The root cause raises no errors of its own: its request count collapses, while cart’s error rate rises and cart logs “Connection refused (inventory:9090)”. All runs below use Luna.


##### One-shot.

The program decides what the model reads (the evidence-package rules), and the model does the reasoning. The package holds a log template from the cart pod (E27.2) whose refusal line grows from 43 lines before the fault to 609 during it. All three passes cite this item and rank inventory first (Figure 3 ).


##### SQL agent.

The SQL agent starts from the symptom and follows “who cannot reach whom” to the root cause (Figure 4 , left). Its 31 queries reduce to six steps: it reads which tables exist (steps 1–7); counts failing calls by service and finds cart failing (step 12); searches the logs for error keywords and finds 1,291 lines in which cart’s connections to inventory are refused (step 14); queries inventory’s requests per minute and confirms that they fall from about 1,450 to 109 in the first 30 seconds of the fault and then to none; checks inventory’s pod logs and its place in the topology (steps 18–30, including an SQL error at step 17 that it fixes itself); and submits inventory (step 31).


##### Codex.

Codex casts a wide net first and then narrows down, in seven commands. After listing and loading the files, its third command runs comparison code it wrote itself over every entity and metric before and during the fault, together with events, spans and error logs; cart’s error rate (0.017 to 0.325) ranks first, and the refusal line is already in the output. It then pulls the events and the metrics and logs of inventory, cart and frontend side by side (commands 4–6), reads the logs of the two minutes around the onset (command 7), which show inventory serving until 01:59:22 and cart refused from 01:59:23, and writes its report naming inventory.


##### FoA.

The SOP chosen by the program decides what is read. FoA fills in the fault description itself as “microservice incident”, which matches a generic SOP whose fixed steps never read logs; its judge declares the root cause found, cart, in the first round, after four calls of the controller (11 model calls in all). In the original paper the alert carries the fault type (“Network Issue” in its Figure 4), from which the SOP is chosen; we give every method only the anomalous period, because the fault type would reveal the answer. Four of our 12 SOPs, written after the paper’s examples, read logs, but none matched this case (the SOP files are in the released code; Appendix A ).


##### mABC.

The framework walks down the call chain from the alert: the frontend-proxy ingress at 02:03, frontend’s POST, and its four callees. In that minute only cart’s AddItem still receives a call (one, failing); the other three receive none. Inventory, three hops down, is never compared at the interface level; it served 109 calls with no errors at 01:59 and none afterwards. mABC stops at cart. A method that walks the call chain and inspects only the calls a service receives cannot see a service that stops receiving them.


##### Non-LLM methods.

NSigma and BARO score each metric by its largest standardised deviation, keeping the sign, so only metrics that rise score high. Inventory’s request count falls sharply; its z-score is large and negative, and the metric ranks second to last among the 373 columns.


#### 6.3. How much of the investigation is prescribed (RQ2)

To measure what the case study shows across all cases, we compute each method’s prescribed-call ratio : the share of its model calls that its program issues at fixed points rather than the model choosing to make them, over the trajectories of all 90 cases on the three mid-tier models (Table 6 ). From the run records and each method’s code, we sort every model call into one of three kinds:

- • main : the next turn of the model in charge of the task, such as every call of Codex and the SQL agent, the main agent of FoA, and the controllers of RCAgent and RCA-Agent;

- • delegated : a call the main model chooses to hand to another role, such as FoA’s code agent or RCA-Agent’s executor writing code;

- • prescribed : a call the program makes whatever the model decides, such as FoA’s action agent at every step and its judge after every SOP run, RCAgent’s chunked analysis and summary calls, RCA-Agent’s summary after each successful execution, forced final reports, and DecompRCA’s reranking of 15 candidates selected by its program.

For a method run on model $m$ , let $C_{m}$ be the cases with a trajectory, and let case $i$ have $c_{i}$ model calls, of which $f_{i}$ are prescribed. The ratio is averaged over cases and then over the three models $\mathcal{M}$ :

[Tableau] (3) $$\rho=\frac{1}{|\mathcal{M}|}\sum_{m\in\mathcal{M}}\frac{1}{|C_{m}|}\sum_{i\in C_{m}}\frac{f_{i}}{c_{i}}.$$

The three simple harnesses prescribe no call. Every published agent does: at least 0.10 for mABC, 0.29 for RCA-Agent, 0.35 for RCAgent, 0.51 for FoA, and 1.00 for DecompRCA, whose single call is placed by its program. Within the published agents the ratio does not order accuracy (RCA-Agent prescribes fewer calls than FoA yet is less accurate); the clear divide is between harnesses that prescribe nothing and agents that prescribe something.

Three points qualify these numbers. First, the one call of one-shot counts as a main call, because the model receives the whole task, whereas DecompRCA’s single call counts as prescribed, because the model only reranks a list the program has already narrowed. One-shot’s evidence package is still selected by rules (it keeps only metric series that moved), which is why the case study says the program decides what one-shot reads. Second, mABC’s records do not say which role made each call, so its ratio is a lower bound. Third, simply counting calls does not separate the families: the SQL agent makes 27 calls per case, the same order as the multi-step published agents (35–50), while one-shot and DecompRCA both make one.

#### 6.4. Model capability and reasoning effort (RQ3)

Because the simple harnesses leave the investigation to the model, their accuracy rests on the model: it rises with the model’s tier (Section 6.1 ). We now ask how a stronger model and more reasoning effort change the investigation itself. Figure 5 compares three pairs of runs. A stronger model investigates less and finds more (contrast A): from Luna to Sol, both agents make fewer calls and query fewer entities (Codex 16% $\rightarrow$ 12%, SQL agent 21% $\rightarrow$ 12%), yet reach the root cause in more cases and gain 14–18 points of PR@1. Sol turns what it sees into a correct first answer, while a larger budget mostly adds queries that the model then does not use to change its answer. #### 6.5. Aptitude and stability (RQ4)

The comparisons so far use one pass per run, but an LLM’s answers vary between passes. Following Laban et al. (2026) , we run Luna and Sol three times at medium effort and measure aptitude and unreliability. Laban et al. (2026) define them through the 90th and 10th percentiles of a score over many samples; with three passes we use the best and the worst pass. Let $s_{i}^{p}\in\{0,1\}$ be the PR@1 of case $i$ in pass $p\in\{1,2,3\}$ . Then

[Tableau] (4) $$A=\frac{1}{N}\sum_{i=1}^{N}\max_{p}s_{i}^{p},\qquad U=\frac{1}{N}\sum_{i=1}^{N}\Bigl(\max_{p}s_{i}^{p}-\min_{p}s_{i}^{p}\Bigr),$$

so $A$ is the share of cases solved in at least one pass, $U$ the share solved in some passes but not all, and $A-U$ the share solved in all three. Figure 6 shows both. A stronger model mainly buys reliability: from Luna to Sol, A rises by only 2–7 points, but U falls from 32–36 to 7–8. On Luna, a single pass of Codex ranges from 62% to 76%. A multi-turn agent mainly buys aptitude: on Luna, the SQL agent and Codex solve 10–11 points more cases at least once than one-shot, with similar U (30–36). One-shot never solves 26% of the cases in any pass, against 14–16% for the two agents, so it misses cases outright rather than by chance. This is the opposite of the finding of Laban et al. (2026) , where splitting a task over turns mainly costs reliability. Single passes on a weaker model are therefore noisy estimates. On Luna the three passes of Codex give 62%, 69% and 76%, and those of the SQL agent 66% to 71%, so a comparison between methods based on one pass of a weak model can flip. On Sol the passes differ by at most 4.5 points (Codex 86.7–87.8%, SQL agent 81.1–85.6%).

#### 6.6. Cost-effectiveness (RQ5)

In operations, accuracy is not the only concern: an incident needs an answer quickly and at a sustainable cost. Figure 1 plots PR@1 against time and against cost per case. We count a run as usable only if it is more accurate than the best non-LLM method (NSigma, PR@1 38.9%), a threshold fixed before drawing the frontier, and draw the Pareto lines through all usable runs. Seven runs of published agents qualify (FoA, RCAgent and RCA-Agent, 43–63%), yet every run on either line uses a simple harness: each published agent is beaten in accuracy by a simple harness that is no more costly, and by one that is no slower. The DecompRCA runs, the cheapest and fastest of all, fall below the threshold (24–29%). The frontier gives three practical choices. When cost matters most, Luna with Codex reaches 68.9% for under one cent per case. When accuracy per dollar matters, Flash with Codex reaches 85.6% for about five cents. When the answer is needed quickly, Sol with the SQL agent answers in 45 s at 85.6%. The most accurate run, Sol at xhigh with Codex (88.9%), costs about 26 cents and takes 277 s per case, so the last few points of accuracy cost roughly five times as much as the cheapest strong setup.


### 7. Limitations

Our study has five limitations. First, Codex is the only general-purpose coding harness we test; others, such as Claude Code, may behave differently. Second, all models are from 2026, so we cannot say whether the ordering holds for the weaker models for which many prescribed workflows were designed. Third, budget kept us from current frontier models such as Fable, Opus or Argon. Fourth, despite careful conversion and reimplementation, our datasets and methods may still differ from their originals; the appendix summarises the changes. Fifth, the case study follows a single case. The prescribed-call ratio extends its mechanism to all 90 cases, but it measures how much of an investigation is fixed, not that this fixing causes the lower accuracy; an ablation that lifts the prescriptions from one agent would test that directly.


### 8. Conclusion

For microservice root cause analysis, a capable model that is given the data and left to decide what to look at and how to reason outdiagnoses agents whose investigation is hand-crafted, and both mostly outperform statistical and causal methods. A stronger model improves accuracy and reliability; more reasoning effort adds little. Practitioners can start from a simple harness and pick the model and harness on the cost–accuracy frontier. Designers of RCA agents should compare against such harnesses on shared, validated cases, which RCAtlas provides.

Our results do not show that domain knowledge is useless. They show that fixing it into the control flow hurts when a procedure does not fit the case, as in our case study, where the procedure that FoA matched never read the logs. Offering procedures to the model as optional guidance, rather than prescribing them, is a natural next step.

### Appendix A Per-method walkthroughs

We explain why the methods not covered by the case study (Section 6.2 ) succeed or fail; PR@1 is given as Luna / Flash / Haiku.


##### Published LLM agents.

FoA (54.4 / 58.9 / 46.7) runs one of twelve SOPs written before any run after the examples in ( Pei et al., 2025 ) . In FoA the alert names the fault type, which selects the SOP; our setting withholds it, since it would reveal the answer, so FoA describes the incident itself. Luna then matches the generic Microservice Issue SOP (abnormal metrics $\rightarrow$ entry requests $\rightarrow$ traces) in 69 of the 90 cases; Flash, which more often guesses a fault type, does so in 33. Only four SOPs contain a log step (Memory, Network Loss or Partition, Code or Configuration Error, Database or Cache). FoA’s accuracy varies widely by fault group: on Luna 93% on application-code faults but 41% on resource saturation. RCAgent (54.4 / 50.0 / 43.3) prescribes 35% of its calls and, with FoA, comes closest to the simple harnesses on Luna; Luna leaves 7 cases and Flash 19 cases unanswered within its 30 steps. RCA-Agent (32.2 / 63.3 / 34.4): its released executor discards outputs above 16,384 tokens after two tries, which costs Luna, which prints whole tables, 16% of its executor steps (Haiku 3%, yet Haiku scores as low). DecompRCA (24.4 / 32.2 / 28.9): the program’s at most 15 candidates contain the root cause in only 57.8% of the cases, which bounds the model’s rerank. mABC (11.1 / – / 20.0) walks down the call chain from the alert, so a service that receives no requests is never reached. Luna also declares the cause undetermined in 42 of 89 cases, concentrated in sources with few or no traces (LEMMA 5 of 5, RCAEval RE1 8 of 9); Haiku answers 85 of 90.


##### Non-LLM methods.

The gap lies in where the evidence is. On resource saturation (34 cases) NSigma reaches 62%, close to one-shot on Luna (65%); on errors, outages, configuration faults and network breaks (33 cases), whose evidence is in logs, traces and events, NSigma and BARO reach 15% and 6% against 67% for the SQL agent and Codex on Luna. Three causes add to this. Many sources have thousands of series with about 15 pre-fault samples, half of them constant, so normal jumps outrank the root cause. NSigma and BARO score the largest signed deviation, so a drop ranks last (inventory’s request drop in the case study: 372nd of 373). Causal-graph methods cannot learn dependencies from tens of samples: RCD misses the root cause entirely in 71 of 89 cases.

### Appendix C Benchmark and method details


##### Benchmark.

Cases are converted to one format (entity and relation tables, metrics, traces, logs, events; UTC), with traces of the injection tooling removed. Of 542 screened cases, 348 pass the exclusion rules; the most frequent reasons are an unclean pre-fault period (69), no evidence (56), incomplete data (38) and a fault late in the window (37). LEMMA has no traces and hundreds of pods per scenario. RCAEval injects faults into only five services per system, so guessing among the injected services hits 20%; against the full inventory our random-guess rate is far lower (Section 4 ).


#### C.1. Case construction

Cases share entity and relation tables and UTC telemetry; labels and answer material are kept separate. Duplicate metric observations are collapsed, source attributes distinguish otherwise duplicate rows, and injection-tool entities, spans, logs and events are removed. Source fault windows are retained where available; RCA-100 adds 20 minutes before the alert, and sources giving only an injection time use an initial before-period and flag the remainder without exposing the onset. Automatic checks cover label consistency, culprit coverage, fault timing, completeness, shortcuts and observable evidence. Claude Sonnet 5.5 reviews labels, check results, row counts and the twelve most-changed series; ITBench-SRE uses automatic checks only. Exclusions are contradictory labels (8), multiple faults outside the multi-fault scenario (20), a missing culprit or its data (14), no evidence (56), incomplete data (38), failure of the multi-fault pre-filter (5), an unclean before-period or nearby fault (69), and less than a third of the window remaining after the fault (37); rules overlap. Of 542 screened cases, 348 remain. RCAEval supplies three cases per sub-suite (27); other scenarios supply at least three where eligible. Remaining places diversify scenario, fault class, root-cause level, data kinds, volume and clue coverage, with fixed tie-breaking and seed, before method runs.


#### C.2. One-shot evidence package

The prompt includes instructions, the question, recorded and flagged periods, all selected evidence and the scenario’s answer template, with neutral item titles. S1 gives the incident record, inventory, topology, placement and coverage. S2 supplies moved metrics as raw samples: using the before-period median and robust spread (MAD $\times 1.4826$ ), a series needs a change score $\max(\text{median shift},0.6\times\text{largest departure})\geq 4$ spreads, plus a median shift of at least 10% or a departure of at least 20% of the baseline level. Identical series are collapsed; unlabelled duplicate-row series are omitted. At most 120 series are selected in turns across moving entities and rendered on the source time grid, with missing samples marked. S3 gives per-minute entry requests, errors, duration quantiles and caller–callee statistics, including missing downstream spans. S4 groups logs into masked templates: the 30 most-changed entities receive separate items, with up to eight templates and twelve raw lines per entity, prioritising errors, warnings and new templates. S5 groups Kubernetes events by object and reason (at most 60 groups). Constant series are counted only; series beyond the cap, full raw traces and logs, injection traces and answer material are omitted. The case study contains 136 items (about 75k tokens); no one-shot prompt was truncated.


#### C.3. Method settings and hard groups


##### Methods.

LLM methods run without generation parameters (except effort in Setting 3), one hour per case, first five answers scored. Interface fixes: shared raw-data tools for FoA, RCAgent and mABC; complete tool descriptions for FoA’s code agent; UTC+8 times for RCA-Agent; modules missing from mABC’s release, a loop limit, a cut at “Observation” and a format hint; resampling for TORAI; missing functions for FaultInsight. Setting differences: no temperatures; RCAgent’s expert also reads metrics and traces (at most 30 steps); mABC’s alert on the entry service’s requests. The SQL agent differs from the reference agent of ( Fang et al., 2026a ) in temperature, an optional think tool, its answer format, and the topology files that every case folder carries.


##### Hardest groups.

On node-level faults the agents mention the true node in 85–90% of runs but mostly blame a pod or service on it. Three AIOps 2022 cases fail for reasons in the data: no clear metric on the faulty node, a fault that leaves almost no trace, and an unlabelled burst on another node. No one-shot prompt was truncated; cases with all four data kinds have a median of 115k tokens.
