## SPILLWAY: Separating Target Admission from Sanitization to Defend Tool-Using Agents against Prompt Injection

Tool-using agents act on email, files, and payments, so an instruction hidden in a web page or a shared document can make an agent send data or money to an attacker. Many runtime defenses put a language model on the decision that lets an action through, so the decision depends on a model that may read the attacker’s text and adds model calls to every step. Provenance defenses keep the model off the final check but need a model to plan or route each task first. Where an action goes can instead be read from the tools’ typed returns: an email’s sender or a payment’s account arrives in a typed field, while injected instructions arrive as free text. SPILLWAY turns this observation into a deterministic floor with no per-task plan. The check admits a call when each target value that appears in tool output but not in the user’s task was returned by a read-only tool in a typed field or is covered by a fixed delegation rule. A deterministic sanitizer removes instruction-like regions its fixed rules match before the model reads them and retains the removed spans as evidence, and a local judge may restore a refused call, never one whose target lies in the removed text. Across three backbones, and seven task suites on one of them, no standard templated injection redirects an action to an attacker’s target under SPILLWAY, at the highest observed mean utility and composite scores (NRP, ERS) of the defenses we run under that attack. A forged chat template also produces a raw zero, and mean in-scope attack success under a released reinforcement-learning attacker is $.005$ . SPILLWAY reaches this floor with no defense-triggered backbone re-run and almost no added model call. As personal AI agents act on users’ email, files, and payments, SPILLWAY gives them an auditable refusal floor on where their actions go that keeps them useful and holds across backbones.

### 1 Introduction

Tool-using agents now read and act across email, calendars, file stores, chat, and payment services, usually through standardized tool interfaces such as the Model Context Protocol ( Model Context Protocol, 2026 ) . Every tool result the agent reads may carry text written by someone else. An attacker who plants an instruction in a web page, a shared document, or an email can make the agent forward data, pay an account, or invite a stranger, all with the user’s authority. This is indirect prompt injection ( Greshake et al., 2023 ) .

Many runtime defenses add a language model to the loop. In its automated mode, a model writes the privilege policy a checker enforces (Progent ( Shi et al., 2025 ) ), re-runs the trajectory with the user task masked to detect a hijack (MELON ( Zhu et al., 2025 ) ), or validates each call against a plan (DRIFT ( Li et al., 2025 ) ). Others verify each action before it commits ( Lin et al., 2026 ) . The decision that lets an action through then depends on a model that may read the injected text, and adds model work to every step. On AgentDojo, MELON, Progent, and DRIFT still leak on 7 to 11 of 12 backbone-by-suite cells in our runs, and on qwen3:8b they add 2.2 to 13.6 backbone calls per benign episode (Figure 3 ). Provenance defenses keep the model off the final check but move it earlier: CaMeL ( Debenedetti et al., 2026 ) has a planner write the program whose data flow an interpreter checks, and in ROPE ( Ma et al., 2026b ) a router model reads each request and sets which sources and user-given values the task may draw on, before a deterministic origin check enforces it.

We show on AgentDojo and AgentDyn that where an effect goes can be decided from typed tool returns and the user’s task alone. An agent crosses two boundaries. At ingress , untrusted text enters its context, and we decide which parts are instructions. At egress , a call produces an effect, and we decide whether its recipient, account, or file is one the user named or a tool returned as an identity. Tools already type the fields that carry identities: an email’s sender, a channel’s members, and a transaction’s recipient are typed fields, while an injection placed in tool output writes free text such as a body or a description. Section 2 covers the one benchmark vector that fills a channel name. Reading the admitted identities from the typed objects tools return, before they are serialized for the model, separates the targets the user’s tools produced from the targets an attacker wrote, with a set lookup.

We introduce SPILLWAY (Figure 2 ), which makes the two decisions separately and joins them through evidence. Its egress floor admits a side-effecting call when every target value that appears in tool output but not in the user’s task was returned in a typed identity field and is not repeated in free text. Its ingress sanitizer removes forged chat turns and the instruction-like regions its rules match before the model reads them and keeps what it removed as evidence. A local judge re-examines only calls the floor refused, so it can recover work the user delegated, such as a reply to an address found in a document, and it is never asked about a target inside the removed evidence. The judge can therefore improve utility without reopening a removed injection (P2, Sec. 3.4 ), and an injected target the floor refuses leaks only if a delegation rule admits it, or it lies outside the removed spans and the judge approves it (P3).

Contributions.

- 1. Target admission from typed tool returns, with no per-task routing. The target decision is a set lookup over identities read from typed tool returns before serialization. Three rules keep attacker-written values out of admission. Result: zero in-scope attack success on every backbone-by-suite cell, the only defense in the grid to do so, at the highest utility under attack of any defense and with no defense-triggered backbone re-run.

- 2. Sanitization coupled to target admission. The judge, the only model allowed to overturn a refusal, is never asked about a target the sanitizer removed (P1–P3). Result: without the sanitizer the judge admits an attacker’s account. With both, in-scope attack success is zero on every suite and the sanitizer recovers utility the floor alone gives up (Table 3 ).

- 3. A head-to-head comparison with routed-origin enforcement. Result: zero in-scope attack success on all seven delegated-routing suites and both ChatInject suites, at higher utility than routed-origin enforcement on every suite, where it leaks on three and on two. With the agent as its own router, routed-origin leaks and loses more utility (Figure 4 , Table 4 ). Under a released reinforcement-learning attacker (PISmith), mean in-scope attack success is $.005$ (Sec. 5 ).


### 2 Threat Model


##### Agent, attacker, and trust.

The agent receives a task from the user, calls typed tools, reads what they return, and may act or answer. The attacker controls the fields that AgentDojo’s injection mechanism fills in content the agent later reads: free text such as an email body or a web page, and, in the Slack suite, the name of one external channel. The index stores a channel name as one whole value, so an address written inside that name never matches a target, and no injection task in that suite sends an effect to the external channel. The attacker does not control the user’s task, the tool implementations, the tools’ declared return types, or the scorer. A tool provider that itself writes attacker-chosen values into identity fields is outside this threat model. Let $T$ be the user’s text and $U$ the text of tool output, and let $\mathrm{Id}(\cdot)$ return the identity values of a text (emails, URLs, and whole argument values such as a name, an account number, or a channel name), casefolded and whitespace-collapsed. A value $x$ is taint-novel when one of its tokens $\mathrm{tok}(x)$ , the emails and URLs it contains and the whole value if it has at least four characters, appears in tool output but not in the user’s text:

[Tableau] $$\mathrm{taintnovel}(T,U,X)\;=\;\{\,x\in X\;:\;\exists\,t\in\mathrm{tok}(x),\;t\in U,\;t\notin T\,\}.$$ (1)

The executor also collects the identity fields of trusted tool returns into a flat set $I$ (Sec. 3.1 ).


##### What counts as a security event.

An injection can make the agent fetch an injected URL, send an effect to an unauthorized target, send injected content to a legitimate target, commit a booking or transfer to an injected object, or recommend an injected entity in its final answer. Our guarantee concerns the target of an effect: whether it may reach a recipient or account that neither the user named nor a trusted tool returned in an identity field. Objects follow Sec. 3.1 . Injected content sent to a legitimate target, injected text in an answer, and causality laundering through a later call to an admitted target ( Chinaei, 2026 ) are content effects, outside any target check.


### 3 SPILLWAY: An Egress Check and an Ingress Sanitizer

> Algorithm 1 SPILLWAY’s egress floor for a call with identity targets: grant and destruction checks, admission by typed identity and by the user’s named referents, then a two-view judge reached only by a refused target outside the removed spans. Object effects follow Sec. 3.1 .


#### 3.1 The Egress Check: Admission by Typed Identity

The egress check, which we call the floor, decides whether a call’s target lies outside the admitted set. For a proposed side-effecting call, the floor admits the call when every taint-novel value (Eq. 1 ) in the call’s target arguments is in $I$ and none is repeated in free text. Values the user named are never taint-novel. The floor is a set lookup, so its refusals are the same under every backbone.

We build $I$ from the tools’ declared types, never from text. Tool and argument roles come from one fixed lexicon per benchmark: verb prefixes mark read-only, writing, destructive, and granting tools, argument names mark targets and principals, and a short list names the tools that write only to the user’s own calendar or drive. The executor captures the return of each read-only tool as the typed object the tool produced, before it is serialized for the model, and indexes a value only when its declared field type is an identity format (email, URI, UUID, hostname, IP) or its field has a routing role (recipient, sender, participant, channel).

A body, subject, or description never enters $I$ , so an address the attacker writes into free text stays taint-novel. Two rules keep an attacker from adding values to $I$ : only read-only returns are indexed, so an allowed write cannot add a value, and a read whose own arguments are taint-novel adds nothing.

The floor also refuses an email or URL in a free-text field even when it matches a real contact. A reply to the sender of an email the task mentioned is taint-novel, but the sender field is typed, so the address is in $I$ and the reply goes out.

Grants are stricter. A call that grants access to a new workspace or channel member named only in tool output is refused, and no judge reopens it. Event participants and a shared file’s recipient count as targets even when the write lands in the user’s own calendar or drive, and a deletion is refused unless $T$ asks for it. A deletion of an injected object is also an unrequested commit, which the two-view judge may restore (Sec. 3.3 ).


##### Delegation rules.

Some refused targets are ones the user named indirectly. Before the judge, deterministic rules admit a target whose value carries a name the user wrote in $T$ (“send the report to Alice” admits alice.miller@... ), a contact attribute of an entity the user named, or a resource owned by the user’s own account. After the judge, they also admit a download from a URL whose domain the user named, and on repository clone, invite, and ownership-transfer tools a target that lies in no removed span, only when $T$ asks for that grant. The rules read only $T$ , the typed returns, and the removed spans.


##### Effects without an identity target.

A booking, a fetched page, or a recommendation names an object rather than a recipient, and each has its own deterministic first rule. An unrequested commit on an injected object is refused, and only the two-view judge may restore it. An irreversible operation under a superlative criterion (“the largest”, “the cheapest”) is refused when its object is not the winner of that criterion on the typed listing. An injected endorsement is removed from the final answer. What these rules cannot settle, a requested booking of an object the task did not name or a fetch of a URL from tool output, goes to a fail-closed judge that can refuse the call. P1 to P3 concern identity targets.


#### 3.2 Ingress: Remove the Injection Before the Model Reads It

The floor stops the effect, but a model that has read an injection keeps working for the attacker and ignores the user’s task. The sanitizer therefore rewrites what the agent reads next, with rules and no model call. It replaces forged chat-template turns, such as a fabricated <|im_start|> system or user turn, and the text they wrap with a marker. It replaces three kinds of text with an inert placeholder. The first is a region delimited by the benchmark’s injection template ( <INFORMATION> and its “important message” form). The second is tool text that addresses the agent in the second or third person about its task or answer, a forged turn marker, or a dictated tool call. The third is a claim in data that a payee’s account has changed, with the account it puts forward. A removed region ends with its match or, for a clause addressing the agent, at the end of that return, so the data before it stays. Trust stays with the first user message, so a forged user turn never becomes trusted. The instruction rules keep what they remove as the span set $S$ , and a refused target inside $S$ never reaches the judge (Sec. 3.3 ). We build the index $I$ from the raw typed returns, before any rewrite.


#### 3.3 Recovery: A Two-View Judge for Refused Targets

A strict floor also refuses some legitimate calls. When the user asks the agent to send a report to the address given in the meeting notes, that address is taint-novel and is refused like an injected one. A judge re-examines the refused call from two views, and both must agree: the routing view asks whether the target is a recipient the user’s task implies, and the payload view asks whether the user requested this action and this content. The judge sees only calls a deterministic rule has already refused (a target outside $A$ that no delegation rule before it admits, or a commit on an object the task did not name, including a deletion of an injected object). Grant and criterion refusals never reach it.

The judge is also bound by what the sanitizer removed. It is not asked at all when the refused target lies inside removed text, which we call the span veto. Without the sanitizer the judge approved a transfer to the attacker’s account on “pay the bill” (Table 3 ). With it, that account lies in removed text.

The judge is a local model called at temperature 0, and it fails closed: a missing verdict counts as a no. A refused call returns to the agent as a tool message asking it to re-issue the call with values from the user’s request, so the agent can continue the episode.


#### 3.4 What the Construction Guarantees

Write $\mathcal{F}$ for the target-bearing calls SPILLWAY admits without the judge, and $\mathcal{R}_{\bar{S}}$ for refused target-bearing calls whose target lies outside $\mathrm{Id}(S)$ and that are neither grants nor unauthorized destructive calls. Three properties of identity-target calls follow from Alg. 1 and the index rules.

P1 (typed-identity lookup soundness). Under the tokens of Eq. 1 , if the attacker writes only free-text fields (Sec. 2 ), the lookup refuses every call whose target value appears in attacker-written text and not in $T$ , because such a value is either outside $I$ or repeated in free text. Reason: $I$ holds only typed identity fields of read-only returns whose read was not steered by a taint-novel argument, and the lookup refuses a target repeated in free text.

P2 (a bound that holds for any judge). For every judge $J$ and every proposed target-bearing call $c$ : $c\in\mathcal{F}$ implies that $c$ is admitted, and $c$ admitted implies $c\in\mathcal{F}\cup\mathcal{R}_{\bar{S}}$ , with only $\mathcal{F}$ admitted when $J$ always refuses. Reason: the judge sees only refused calls, and only after the span veto. Its size and family therefore affect safety only through $\mathcal{R}_{\bar{S}}$ , which the sanitizer’s evidence narrows. Utility can move either way, since an admitted call changes the rest of the episode.

P3 (remaining admission paths). An attacker-written target that the typed-identity lookup refuses can still be admitted only through a deterministic delegation rule, or through the two-view judge when every taint-novel target of the call lies outside $\mathrm{Id}(S)$ . Reason: by P1 the lookup refuses an attacker’s target. The span veto constrains the judge path, so a target in $\mathrm{Id}(S)$ never reaches $J$ , but it does not by itself veto a delegation rule. A residual leak must therefore satisfy a delegation rule or survive both the span veto and the two-view judgment.


### 4 Experimental Setup

We evaluate SPILLWAY in two settings, both on AgentDojo ( Debenedetti et al., 2024 ) , whose checks serve as the oracle, with hits rescored by executed effect. The breadth setting tests SPILLWAY on three backbones and four stateful suites under the standard attack, plus three single-backbone stress tests and a released RL attacker (PISmith) replayed open-loop. The delegated-routing setting compares the full SPILLWAY with ROPE ( Ma et al., 2026b ) , the closest defense, on the three AgentDyn ( Li et al., 2026b ) suites, many of whose tasks send effects to recipients read from tool output, and the four AgentDojo suites, on gpt-4o-mini. The same floor runs in both settings and across the stress attacks, with only AgentDyn’s tool roles added to the lexicon, so the setup tests whether the floor carries to a new dataset and to stronger attacks. Every AgentDojo grid uses suite v1.2.2 and the full grid of user and injection tasks for every method.


##### Scoring: three attack-success levels.

We report attack success at the in-scope level, which counts an injection that sends an effect to a target the user never named, the event the floor is built to stop. In-scope takes AgentDojo’s raw check and drops two cases no target gate can bound, a target the task $T$ already named (the collision filter, which removes no hit in any cell) and a content-manipulation task that states attacker text but names no recipient or sink. Neither filter reads defense state. SPILLWAY has no hit at either level on any of the twelve AgentDojo cells, while MELON and Progent each leave a raw hit on eleven. The trace, executed, and in-scope levels are all in Appendix A .


##### Executed effect vs. trace hit.

A hit counts only when the environment changed: a defense that blocks a call before execution can leave that call in the transcript, and trace-level scoring would count it. We apply ROPE’s rescoring ( runs/corrections.py ) to every method and every ablation arm. The judge is gemma4:31b in a 4-bit build served locally (Appendix B ).


##### Metrics.

We report three primary quantities and two recognized composites, per backbone–suite cell and as twelve-cell means. Benign utility (BU $\uparrow$ ) is the task success rate on benign traffic (no injection). Under-attack utility (UAU $\uparrow$ ) is the task success rate while under the injection. Attack success rate (ASR $\downarrow$ ) is the fraction of attacked pairs whose injected effect executes, at the in-scope level above. The composites combine robustness $(1-\text{ASR})$ with benign utility: Net Resilient Performance (NRP $\uparrow$ ) $=\text{BU}\times(1-\text{ASR})$ ( Zhang et al., 2025 ) and Effective Robustness Score (ERS $\uparrow$ ) $=$ the harmonic mean of $(1-\text{ASR})$ and BU ( Kavathekar et al., 2025 ) , both higher-is-better.


##### Grid, attacks, and comparators.

The breadth backbones are gpt-4o-mini ( OpenAI, 2024 ) , qwen3-coder:30b, and qwen3:8b ( Yang et al., 2025 ) . The standard attack is AgentDojo’s important_instructions template. Three stress tests follow. Chat-template forging uses ChatInject ( Chang et al., 2026 ) (qwen3:8b, 665 pairs). An attacker-as-sender variant of Workspace has the five injection-carrying emails come from the attacker’s own address, so the attacker writes the typed sender field the floor reads (qwen3:8b, 126 pairs). Optimizer-generated injections come from the AutoDojo release ( Ma et al., 2026a ) , optimized for gpt-4o-mini against Progent and replayed on the three suites it covers (Banking, Slack, and Travel, 389 pairs, with no Workspace split in the release), plus two held-out Banking sets (Sec. 5 ). A released RL attacker, PISmith ( Yin et al., 2026 ) , is then replayed open-loop against every defense on the full grid. We run head-to-head against MELON ( Zhu et al., 2025 ) , Progent ( Shi et al., 2025 ) , DRIFT ( Li et al., 2025 ) , and ROPE ( Ma et al., 2026b ) on the breadth grid and also against ROPE on the delegated-routing grid, from their released code on the same agent, with the changes listed in Appendix B : Progent’s policy is written by the cell’s own backbone, and so is ROPE’s router except where its authors’ router is named. CaMeL ( Debenedetti et al., 2026 ) , which replaces the agent loop with its own planner, is not run. Spotlighting ( Hines et al., 2024 ) and a prompt-injection detector ( Protect AI, 2024 ) serve as reference points. The SPILLWAY code, per-cell results, and seeds are at https://github.com/saintmachines/spillway . SPILLWAY is also released as an SDK on PyPI ( spillway-guard 1.0.0).

##### Cost.

On qwen3:8b benign traffic (Slack / Workspace), SPILLWAY calls its judge $0.43$ and $0.05$ times per episode and changes its backbone calls by less than $0.15$ (Figure 3 plots their sum), while MELON adds $5.29$ and $3.25$ backbone calls, Progent $8.67$ and $5.94$ , and DRIFT $9.91$ and $9.59$ . On the RTX PRO 6000, SPILLWAY’s episodes, timed in a separate session, were within $0.5$ s of the undefended agent’s, against $+4.9$ and $+7.9$ s for MELON, $+1.6$ and $+2.3$ s for Progent, and $+9.9$ and $+10.5$ s for DRIFT. With a 4-bit gemma4:12b judge, the qwen3:8b cells of Table 1 and the ChatInject panel also keep zero attack success, at mean utility $.348$ instead of $.370$ .


##### A comparison with routed-origin enforcement.

Against ROPE with its authors’ Claude Opus 4.8 router (Figure 4 ), SPILLWAY holds in-scope attack success at zero on all seven suites, while ROPE leaks on three (DailyLife $.010$ , Shopping $.044$ , Slack $.048$ ). SPILLWAY’s utility under attack is higher on four suites by $.08$ to $.18$ (Workspace $.848$ vs. $.670$ ), by $.048$ on Slack, by $.022$ on Shopping, and by $.007$ on Banking. With the agent’s own model as its router (gpt-4o-mini), ROPE’s mean utility falls from $.468$ to $.361$ and it still leaks on Shopping ( $.072$ ) and Slack ( $.019$ ). Each suite runs once (seed 42). In a three-seed run of an earlier build, SPILLWAY had no raw hit and its utility varied by at most $.011$ on Slack and Shopping. ### 6 Related Work

Information-flow and capability systems ( Costa et al., 2025 ; Zhong et al., 2025 ; An et al., 2025 ; Wu et al., 2024 ; Li et al., 2026a ) also constrain untrusted data, and Task Shield ( Jia et al., 2025 ) asks whether a call serves the user goal.

The closest sibling is ROPE ( Ma et al., 2026b ) , whose deterministic origin check guards an audited set of sensitive parameters after a router reads each request. SPILLWAY takes a lighter point: a flat typed-identity floor fixed by the tool schemas and a role lexicon, with no per-task router and lighter than the per-step dependency state of APPA ( Kravchenko et al., 2026 ) or AgentArmor ( Wang et al., 2025 ) and the per-argument provenance of PACT ( Fan et al., 2026 ) , and a judge bounded by ingress evidence. CommandSans ( Das et al., 2025 ) learns a token-level sanitizer for tool outputs. Tool-input and tool-output firewalls ( Bhagwatkar et al., 2025 ) run an LLM on every tool input and output and filter content, with no check on where an effect goes. They report zero on the standard attack, but their own adaptive cascade raises their sanitizer’s attack success to $30\%$ (Slack). Agent data injection ( Choi et al., 2026 ) spoofs trusted metadata inside untrusted text, such as a forged author field in a comment body, and succeeds against most defenses it tests except CaMeL’s strict policy. A spoofed value in a typed field is the case of Sec. 7 . SPILLWAY’s floor and sanitizer use no model, and its only model call is a bounded judge, under one call per benign episode on qwen3:8b (Figure 3 ). With its deterministic floor, SPILLWAY holds in-scope attack success at $.000$ under a forged chat template and at $.005$ on average under a frontier reinforcement-learning attacker (PISmith), where content filtering alone does not (Tables 4 , 7 ).


### 7 Limitations

SPILLWAY’s guarantee is scoped to identity targets (Sec. 2 ): an injection that steers an effect to a legitimate identity, such as an existing contact or a payee in a bill the user asked to pay, is left to the sanitizer and the judge, and a target that never appears verbatim in tool output falls outside P1. An attacker who writes a typed field, for example by sending the email, puts its own address in $I$ . Target roles come from a lexicon written once per benchmark, so a new tool set needs its roles declared. Because the floor is a set lookup rather than a classifier, rewording the injection around a target does not change whether the floor admits it. The judge, the delegation rules, and the lexicon are the surface an adaptive attacker ( Zhan et al., 2025 ; Hofer et al., 2026 ) would target, which the four AutoDojo pairs on the P3 path already exercise.


### 8 Conclusion

We presented SPILLWAY, a prompt-injection defense for tool-using agents that separates target admission from sanitization. SPILLWAY reads where an action may go from the tools’ typed returns and the user’s task. The sanitizer removes instruction-like regions before the model reads them, and a local judge restores only refused calls that lie outside the removed text. Targets are decided by structure, and the model is used only where structure cannot decide. Across three backbones and four AgentDojo suites, no standard templated injection reached an attacker’s target, at the highest mean utility and composite scores under that attack of the defenses we run. Under a forged chat template, in-scope attack success was a raw zero. Under a released reinforcement-learning attacker, it averaged $.005$ . Personal agents now act on their own across a user’s mail, calendar, and payments, and prompt injection can turn that autonomy against the user. SPILLWAY sits in front of such an agent as an efficient, auditable egress layer. Because the floor is a set lookup over the tool schemas, not a model call, it runs inline with almost no latency and carries to a new tool set once its roles are declared, so we expect this light layer to slot into many services and agent apps.

##### Agent.

Every method runs on the same agent request: each benchmark’s own default system prompt in the system role, temperature 0, seed 42, at most 8192 output tokens, and the backbone’s reasoning switched off where it has a switch. ### Appendix C Attacker-as-sender variant

The variant breaks P1’s premise: the five injection-carrying Workspace emails come from the attacker’s own address, so the address enters $I$ through the typed sender field. It covers the nine user tasks that read these emails and all 14 injection tasks (126 pairs, qwen3:8b). SPILLWAY, the floor-only arm, Progent, and the prompt-injection detector let no attack through. The undefended agent, MELON, Spotlighting, and DRIFT each execute the attack in one of the 126 pairs. In that pair the floor-only agent tried to email the attacker’s address and was refused, because the injected text repeats the address and the floor refuses a target repeated in free text. With the sanitizer on, the agent never proposed the call. An instruction that names the attacker only by role is not tested here. Utility under attack is $.556$ for SPILLWAY, $.611$ for the floor-only arm, and $.603$ undefended.
