## Weight-Space Programming Doesn’t Need Transformers

Standard neural architectures such as the Transformer were chosen because they train well with gradient descent and run fast on GPUs. In weight-space programming, a large language model (LLM) writes target weights by hand without gradient-based training, so those reasons no longer apply. Should we keep the Transformer? Given minimal guidance, ten labeled examples, and a sandbox, mainly on multiple-choice questions, we task three frontier LLMs with either generating the weights of a fixed architecture or designing the architecture themselves. When free to design, all three compile plain-text facts into a sparse table queried by a fixed procedure, reaching up to 54.4% test accuracy. An LLM-designed model achieves higher test accuracy than the most accurate released Transformer that the same LLM wrote while using about 1,800 $\times$ fewer parameters. Without gradients, they choose a table, in which the LLM can state what each weight means and can find and rewrite a wrong one. Each wrong answer points to one row, and removing a row changes about one other answer. From this, we propose an associative-memory-based model up to 17 $\times$ faster on GPUs than a same-sized Transformer. We also test pretrained weights, other benchmarks, and tasks where models generate answers. Pretrained LLMs remain more accurate; the claim concerns which structure to build when writing weights.

### 1 Introduction

Transformers ( Vaswani et al., 2017 ) have been highly successful in part because their architecture is well suited to efficient gradient-based optimization on modern GPUs ( Hooker, 2021 ; Dao, 2024 ) . However, this advantage does not necessarily carry over to weight-space programming (WSP), where a large language model (LLM) directly writes the weights of a separate target model without gradient-based training or data fitting ( Takehi et al., 2026 ) . This shift raises a central question.

Should weight-space programming keep the Transformer?

To answer this question, we provide minimal guidance, giving each LLM only ten labeled questions and an execution sandbox. Within this setup, we evaluate two regimes, (i) performing WSP on diverse released architectures (Transformers, state-space models ( Gu et al., 2022 ) , and RNNs ( Elman, 1990 ) ) from random initialization, and (ii) allowing the LLM to choose and design the target architecture from scratch. We conduct our evaluation primarily on ARC multiple-choice science questions ( Clark et al., 2018 ) across three frontier LLMs, namely Claude Opus 5.5 ( Anthropic, 2026 ) , GPT-6.1 Sol ( OpenAI, 2026a ) , and GPT-6 Astra ( OpenAI, 2026b ) .

When free to choose the structure, the LLMs do not build Transformers; an LLM-designed model achieves higher ARC test accuracy than the most accurate released Transformer that the same LLM wrote while using about 1,800 $\times$ fewer parameters. We analyze in detail how these LLM-designed models are constructed, as building them differs from adjusting parameters via gradient descent. The LLM first expresses domain facts as plain-text sentences and writes a build script that converts each sentence into a row of a sparse table. A fixed lookup procedure then reads the table, matching tokens from the question and each candidate option against its rows to select the highest-scoring answer. All three LLMs converge on this design without using attention, MLPs, or dense embeddings.

This structure is well suited to writing weights without gradients because every prediction traces back to specific rows, and editing a row affects only the questions that rely on it. Empirically, in Claude Opus 5.5’s models, retaining only the single best-matching row per option nearly matches full-model accuracy, and deleting a row alters roughly one prediction out of all test questions. By contrast, when Claude Opus 5.5 writes the same facts into a Transformer, it underperforms plain keyword search (BM25) over the raw sentences, which is consistent with interference between dense keys. Viewed as associative memories ( Zhong et al., 2025 ; Wang, 2026 ) , the sparse table pairs few-token keys with hard top-row selection, whereas the Transformer relies on dense, overlapping keys and soft attention.

However, an LLM-designed model scores every stored fact for every question, so inference slows down as the writer adds facts, and it launches many GPU kernels per question. Most of these models therefore run slower on a GPU than a same-sized Transformer. Building on our analysis, we propose an associative-memory-based model that retains the written table while reading only a fixed number of rows per question; it stays within about three percentage points of the LLM-designed models’ accuracy while answering up to 17 $\times$ faster on a GPU than the same-sized Transformer.

We test how well these findings generalize beyond random initialization and multiple-choice science questions, extending our evaluation to pretrained weights, math questions, open-ended generation, and vision tasks. Finally, while pretrained LLMs remain far more accurate overall, we clarify the practical boundaries of current WSP and outline key limitations and future directions for the paradigm.

### 2 Weight-space programming setup

We evaluate WSP on the four-option questions of the combined ARC-Easy and ARC-Challenge test sets ( Clark et al., 2018 ) , totaling 3,530 science questions. Three frontier LLMs (Claude Opus 5.5, GPT-6.1 Sol, and GPT-6 Astra), which we call writers , operate under identical tools, sandbox environments, and task prompts. During a single run, each writer sees only ten ARC training examples, five each from ARC-Easy and ARC-Challenge, and sees no other ARC data and no test accuracy; in a lineage, it also receives the parent model and the parent’s validation accuracy.

Under this setup, we compare two architectural regimes, (i) Fixed architectures , where the writer writes weights over a random initialization of a released neural architecture, or writes every weight of a small two-layer baseline we provide with no starting weights (the given Transformer ); and (ii) LLM-designed models , where the writer defines the structure itself via an architecture file, a build script, and plain-text knowledge files that are compiled into tensors on CPU. Finally, we evaluate lineages , where each generation refines the prior generation’s top-performing validation model ( Appendix A details the protocol, and Appendix B lists the released models).

#### 3.2 What writing weights without gradients requires

Without gradient descent ( Table 1 ), each writer works in a loop, creating practice questions, running the model, inspecting failures, and adding a rule or fact row. This loop produced the mechanisms above, including higher weights on rare concepts, sign flips for negation, and the second pass for two-step recall. Debugging weights requires two properties.

- • Traceable answers. Each prediction comes from a small, identifiable set of written lines, allowing the writer to locate the exact entry responsible for a mistake.

- • Local edits. Adding, modifying, or removing a single written line changes only the predictions that depend on it, leaving all other predictions intact.

Claude Opus 5.5 states these requirements in its first-generation runs, noting Without training, the only way to get knowledge into the model is to write it, and short declarative facts are the cheapest form to write and check , and A sparse retrieval model makes every number traceable to a sentence I wrote . Section 5 tests both properties.


#### 3.3 The LLM-designed model as an associative memory

A Transformer is itself a stack of associative memories ( Zhong et al., 2025 ; Wang, 2026 ) , in which a query $x$ recalls values $v_{i}$ whose keys $k_{i}$ it resembles via

[Tableau] $$f(x)=\sum_{i=1}^{M}v_{i}\,\sigma\!\left(k_{i}^{\top}x\right).$$ (1)

Here $M$ is the number of memories and $\sigma$ is a selection function. It is the identity in a linear layer, an activation such as GELU in an MLP, whose first-matrix rows are the keys, and a softmax over context keys in self-attention. Because Transformer keys are dense and overlap, recall mixes in values from other memories, although a sharper $\sigma$ reduces interference.

The LLM-designed model instantiates the same memory with sparser choices ( Table 2 ). Each memory $i$ is one written fact whose sparse concept vector $k_{i}$ serves as both key and value ( $v_{i}=k_{i}$ ). With $q$ the question’s concept vector and $o_{c}$ the concepts in option $c$ absent from the question, scoring option $c$ by matching $o_{c}$ against the best-supported fact gives

[Tableau] $$s_{c}=\max_{i}\;\left(k_{i}^{\top}q\right)\left(k_{i}^{\top}o_{c}\right),$$ (2)

while the full model adds smaller weights from secondary rows ( Appendix C ). Keys with roughly seven non-zero entries across 3,368 concepts rarely overlap, and hard top- $k$ selection discards whatever overlap remains.

#### 3.4 Our associative-memory-based model

LLM-designed models score every stored fact for every question ( Equation 2 ), so work per question grows with the number of written facts, and they launch many GPU kernels; on a GPU, most run slower than a same-sized Transformer ( Figure 4 ). We therefore design an associative-memory-based model that preserves line-by-line writing ( Figure 2(c) ). Given our fixed forward pass along with its weight names and tensor shapes, the LLM writes a word list, plain-text files in line formats of its choice, and a build script that compiles them into two tables. Per question, the forward pass reads only 120 pair-table rows and computes a single product with concept table $A$ , keeping per-question cost independent of fact count for a given concept vocabulary ( Section 6 analyzes GPU speed and accuracy).

To populate the two tables, the LLM’s build script compiles written lines such as cues with supported answers, terms with definition words, and parents with children. Concept table $A$ is a first-order memory holding how strongly concept $a$ alone recalls concept $b$ , while the pair table is a second-order memory holding the concepts that a pair of concepts $(a,b)$ , written with $a<b$ , recalls together. Each pair maps directly to row $h(a,b)=(ap+b)\bmod H$ for a fixed prime $p$ and table height $H$ , so the forward pass computes the row address and searches nothing. From a question’s concept vector $q$ , the $J=16$ strongest concepts form the set $P(q)$ of 120 pairs. With $t_{h}$ denoting row $h$ of the pair table as a sparse vector over concepts, $\mu$ a written mixing weight, and $o_{c}$ the concepts in option $c$ absent from the question, recall and the option score are

[Tableau] $$r=\sum_{(a,b)\in P(q)}q_{a}\,q_{b}\;t_{h(a,b)}\;+\;\mu\,A^{\top}q,\qquad s_{c}=o_{c}^{\top}r,$$ (3)

instantiating Equation 1 with linear keys in $A$ and pair keys in the pair table. While our forward pass fixes $p$ and $J$ , the LLM sets $H$ , the row width, and $\mu$ . In Claude Opus 5.5’s first-generation model, 40,312 words map to 3,805 concepts, table $A$ holds 2.06 million non-zero entries, and the pair table uses $H=1{,}048{,}576$ rows, each storing up to 40 recalled concept IDs and weights. Although distinct pairs can share a row because concept pairs outnumber $H$ , under 0.5% of the pair table’s 41.9 million weight slots are non-zero, and folding the table to 65,536 rows preserves accuracy ( Appendix E ). Under the parameter count of Appendix A , this model has 2.53 million parameters (mostly in $A$ ), 2.7 times the 0.94 million of the first-generation LLM-designed model.

### 5 Why the LLMs choose this structure

Sparse tables satisfy both properties from Section 3.2 by tracing each answer to a single written line and limiting a line removal to far fewer changed answers than in a written Transformer. When compiled into a Transformer, however, the same content underperforms plain search over the written text, and edits no longer reliably stay local.


#### 5.1 Testing the two properties


##### Does an answer trace to one line?

To test whether each prediction relies on a single stored statement, we keep only the single best-matching fact for each option and drop every other score. In the LLM-designed model, the full model reaches 50.8% test accuracy, and scoring each option from its single best-matching fact alone reaches 49.1% ( Table 4 ). Accuracy comes mostly from the best written fact for each option.

##### Is it the content rather than the structure?

An alternative explanation is that the accuracy comes from the facts that the LLM writes, and the structure holding them does not matter. Given a Transformer, the LLM writes the same kind of fact list and compiles it into the weights. We run one plain search, BM25 ( Robertson and Zaragoza, 2009 ) , over the text each LLM wrote for a model and compare it with that model’s own accuracy. The six written two-layer Transformers of Claude Opus 5.5 all score below BM25 over their own text, by 8.0 points on average. The LLM-designed models and the associative-memory-based model score above it ( Table 6 ). Over all the text that GPT-6.1 Sol and GPT-6 Astra wrote, 8 of their 11 written two-layer Transformers score below BM25 and 13 of their 16 table models score above it ( Table 15 ). In the terms of Equation 1 , a written Transformer stores many memories under dense overlapping keys, and this result is consistent with interference. On the SciQ text generation task of Section 7 , where the model writes the answer in words, Claude Opus 5.5 measured the interference directly on its own practice questions. Its written Transformer holds about 2,800 answer words in 58 dimensions, and the same scoring rule gives an F1 of 0.37 without interference and 0.24 to 0.25 inside the Transformer.


##### Do the models copy test items or rely on made-up questions?

The text each LLM wrote overlaps the ARC test set about as often as it overlaps comparable questions that the LLM never saw, and deleting the overlapping lines barely changes test accuracy. Forbidding the LLM from writing practice questions of its own costs about one point ( Table 4 ). Appendix D gives the overlap analysis.


##### Is the table chosen because it is familiar?

One alternative reading of why the LLMs choose this structure remains open. An LLM knows retrieval as the classic way to answer questions without training, and one writer calls IDF retrieval the classic ARC baseline , so our data do not separate a structure chosen because it suits writing from one chosen because it is known. We also ran a control without row tables. Forbidden to store facts as rows, Claude Opus 5.5 again built a memory read by key, using superposed random high-dimensional vectors with over 100 times more non-zero values ( Table 4 ).


### 6 Inference efficiency


#### 6.1 Why LLM-designed models are slow on a GPU

A two-layer Transformer processes a batch of 64 questions in a few large matrix operations, averaging roughly one kernel launch per question, whereas LLM-designed models launch two to nearly three hundred ( Figure 4 ). In eager execution, log-log GPU time correlates more closely with kernels per question ( $r=0.95$ ) than with non-zero count. At each model’s fastest mode, time tracks non-zero count more closely (correlation 0.84 against 0.64). Across 46 LLM-designed variants ( Figure 4(a) ), only one beats a same-sized Transformer at its fastest input, and the median is 9.4 $\times$ slower.

These designs score every fact for every question, although in Claude Opus 5.5’s lineage about one fact in seven shares a word with the question on average. They build an intermediate table with one entry per question, option, and fact, passing over that table several times. Over generations, the LLM adds scoring steps and rule modules, so kernels per question grow from 13 in Claude Opus 5.5’s first generation to 118 in its fifth. Many designs build or transpose sparse tables inside the forward pass, which prevents capture as a CUDA graph, the optimization that removes kernel launch overhead. Cost grows with the number of facts times the number of scoring passes, and our associative-memory-based model ( Section 3.4 ) removes this growth.

#### 6.2 What the architecture has to keep

A faster design must keep what makes weights writable without gradients (a line as the unit, a nameable meaning for every entry, and sparse keys) and must stop scoring every fact for every question. Appendix E maps each way WSP differs from gradient training to one choice of the associative-memory-based model.

Before designing an architecture ourselves, we asked Claude Opus 5.5 to rewrite its first-generation and fifth-generation LLM-designed models for a GPU, two runs each. The rewrites keep the starting accuracy and run faster than the models they start from. They move most sparse products to batched dense ones, but they still score every stored row for every question and remain 6 to 33 times slower than a same-sized Transformer at its fastest input. We therefore fix the forward pass ourselves and leave the weight writing to the LLM. The rewrites are detailed in Appendix E .


#### 6.3 Accuracy and speed

Over five generations with Claude Opus 5.5, our ten models reach 49.6% to 52.8% ARC test accuracy, within about three percentage points of the LLM-designed models’ 50.6% to 54.4% and well above a same-sized Transformer written by the same LLM ( Table 7 ). Per question, the forward pass reads 120 rows of the pair table and computes one product with the concept table $A$ regardless of line count, answering the 3,530 test questions on one RTX 3090 in 18 ms at the first- and fifth-generation sizes ( Figure 1(b) ). At its best input (sorted by length and cut to real length), a same-sized Transformer is 7 times slower at the first-generation size and 17 times slower at the fifth-generation size; Appendix E gives other input treatments. All ten share this forward pass. Nine replay as CUDA graphs in 18 to 20 ms, while one first-generation run stores the concept table $A$ as a sparse matrix that prevents graph replay and takes 70 ms.

#### 6.4 Scaling and capacity

In eager execution on synthetic tables with the shape of the written models, time per question stays at 0.012 ms on the GPU while the pair table grows from 3 million to 1 billion non-zero values, whereas a same-sized Transformer goes from 0.044 ms to 14.5 ms. Time instead grows with the number of concepts. With the concept table $A$ stored densely, as in the written models, the model becomes slower than a Transformer between about 15,000 and 32,000 concepts, while a variant that reads the concept table $A$ as row lists stays faster up to about 100,000 concepts. In the first-generation model, sharing rows of the pair table costs no accuracy down to 65,536 rows (49.6% at 1,048,576 rows and 49.8% at 65,536). Appendix E gives the scaling curves and the capacity results.


### 7 Further experiments

This section asks how far our findings go beyond random initialization and multiple-choice science questions. Wherever the LLM designs the model, it keeps written tables and a fixed reader, adding rule modules when needed and adapting what a row holds to the task.


#### 7.1 WSP of pretrained weights

Starting from a released pretrained checkpoint instead of random initialization, WSP behaves differently. In most runs (48 of 87 across the three LLMs), the LLM changes under 1% of the weights. Most of these edits calibrate how the answer letter is read out or move science-word embeddings toward written definitions, and accuracy stays within one point of the checkpoint’s in 43 of these 48 runs. In 30 runs, the LLM overwrites the checkpoint, in 29 with a hand-written fact or rule model and one with a hand-built similarity circuit. Most overwrites (19 of 30) are on checkpoints near chance. The exceptions are GPT-6.1 Sol and GPT-6 Astra runs on the masked-language encoders UltraBERT and ModernBERT-large, which start above chance and lose accuracy when overwritten. The remaining nine keep the checkpoint and rewire it so that its own signal selects the answer letter. Checkpoints above 72% are never overwritten. Per-checkpoint results are in Section F.1 .


#### 7.2 Other benchmarks

We run models written for ARC unchanged on other four-option benchmarks. On SciQ ( Welbl et al., 2017 ) , science questions of the same level, the LLM-designed and associative-memory-based models both reach 47.7% in generation 1 and 50.1% in generation 5, within about four points of ARC. Accuracy is 30% to 36% on OpenBookQA ( Mihaylov et al., 2018 ) and near 25% chance on MMLU ( Hendrycks et al., 2021 ) . This pattern is consistent with Claude Opus 5.5 having written elementary science, matching SciQ rather than OpenBookQA or MMLU. Section F.2 gives details.

On CIFAR-10 ( Krizhevsky, 2009 ) raw pixels, networks written by Claude Opus 5.5 reach only 21% to 28% across eight fixed architectures, against 10% chance, which fits the view that a weight on a pixel has no meaning a writer can name, as detailed in Appendix H . ### 8 Limitations and future work


##### Recall without learned representations.

The multiple-choice and SciQ table models, our associative-memory-based model, and the released architectures written from random initialization answer by recalling facts the LLM wrote. None chains facts across steps or composes a long answer. ARC-Challenge accuracy stays near 38% while ARC-Easy reaches 63% ( Table 3 ). Run unchanged, models written for ARC stay at chance on MMLU. On SQuAD the written models extract spans with word lists, and some written models compute, including arithmetic in the models written for several tasks at once or with no task named ( Section 7 ). Written models store what the LLM states and learn no representations of their own. A natural next step is weight-space programming that builds representations and acquires knowledge beyond the facts a writer can state.


##### Scope of the claim about Transformers.

Our finding that WSP does not need a Transformer applies to how current LLMs write weights from random initialization without running on data. In that setting, writing requires naming what each weight means, whereas Transformers are built to be trainable with gradient descent. If a later method writes weights beyond recall, the best architecture is an open question and should pass our controls (searching written text alone, counting weights actually written, and moving to other benchmarks). Three directions follow, namely writing calculation and comparison into weights, training by gradient descent from a written associative-memory-based model, and adding word order so that the model generates text.


##### Small-model speed boundary.

The associative-memory-based model removes the growth of inference time with the number of facts, but its time grows with the number of concepts. On a GPU, its speed advantage over a same-sized Transformer therefore holds up to the concept counts measured in Section 6 (between about 15,000 and 32,000 concepts with a dense concept table, and about 100,000 with row lists).


##### Hardware for lookup.

We measured inference on a single GPU model (an RTX 3090) built for dense matrix products, whereas per question our associative-memory-based model computes hashed addresses, reads a fixed number of table rows, and accumulates their sparse entries. In recommendation systems, near-memory processing and FPGA engines accelerate such table lookups ( Ke et al., 2020 ; Jiang et al., 2021 ) , and hash-based sparse CPU execution has outpaced GPUs on large workloads ( Chen et al., 2020 ) . Other designs replace inference multiplications with hashing and table lookups ( Blalock and Guttag, 2021 ) or execute associative search directly in content-addressable memory ( Ni et al., 2019 ) . Whereas Transformers fit the dense-compute GPUs they co-evolved with ( Hooker, 2021 ) , benchmarking written models on lookup-oriented hardware and co-designing the forward pass for it remain open directions.


##### Low-label text and warm-starting.

Although we have run no experiment in low-label domains such as medicine or personalization, our text results ( Appendix G ) motivate using written networks when labels are scarce. Used to initialize gradient descent on 100 labeled AG News articles, a written network reaches up to 84.7% accuracy, whereas training from random initialization on the same labels reaches at most 63.6%.


##### Rubric-guided generational search.

Because an LLM can already design its own model structure and revise it across generations, the next step is an automated loop over generations that scores candidate models by a rubric combining accuracy per writing cost, model size, and inference speed.


### 9 Related work

Recent work shows that language models can directly read and write network weights without gradient training ( Takehi et al., 2026 ) . Earlier work constructs or compiles weights without a language model, studying transformer-like computation ( Weiss et al., 2021 ) , compiling Transformers for interpretability ( Lindner et al., 2023 ) , and hand-constructing fact-storing MLPs for Transformers ( Dugan et al., 2025 ) . These works fix the architecture and ask what can be written into it, while we leave the structure to the LLM and compare it with the same LLM’s Transformers.

Other work modifies an already trained model. Where low-rank adaptation updates a large language model by gradient training ( Hu et al., 2022 ) , model-editing methods locate and edit factual associations in GPT ( Meng et al., 2022 ) and extend those edits to mass-editing memory in a Transformer ( Meng et al., 2023 ) . Rather than retraining the model, these editing methods compute low-rank weight updates from forward-pass statistics and gradient-optimized target vectors on a trained model, whereas our LLMs start from nothing or from random initialization, apart from the pretrained edits of Section 7.1 .

Prior work also searches over structures or programs and generates weights. With language models, Chen et al. (2023) perform code-level neural architecture search, Nasir et al. (2024) add quality-diversity optimization, and Romera-Paredes et al. (2024) search over programs for mathematical discoveries, while Ha et al. (2016) introduce hypernetworks as networks that generate weights. In the older line of fast weight programmers, a slow network trained by gradient descent outputs the weights of a second, fast network ( Schmidhuber, 1992 ) , and linear Transformers can be written as such fast weight programmers ( Schlag et al., 2021 ) . WSP shares only part of the name with fast weight programmers, since in WSP a language model writes the weights of a separate model itself and the written model receives no gradient training. These search and weight-generation methods train candidate structures with gradients or score many candidates by measured fitness on data, whereas our setup never trains candidate models with gradients. Each run sees only ten labeled example questions without benchmark accuracy, and across generations a lineage uses one validation accuracy per run only to pass the better of two runs to the next generation.

Although existing work reads Transformer layers as associative memories ( Zhong et al., 2025 ; Wang, 2026 ) , Cheng et al. (2026) argue that Transformers lack a native lookup primitive and simulate retrieval with computation. Whereas Lample et al. (2019) place product-key memory layers inside a Transformer as a learned key table read by top-k search, the Engram module of Cheng et al. (2026) adds constant-time lookup beside mixture-of-experts layers, hashing suffix N-grams of token ids to addresses in embedding tables pretrained by gradient descent and adding retrieved vectors, gated by the hidden state, to the residual stream. In our associative-memory-based model, the table read at a computed address is the whole model rather than a Transformer module, keys are concept pairs rather than token N-grams, and an LLM writes entries line by line without gradients.

### Appendix A WSP protocol

In this paper, weight-space programming (WSP) denotes the setting in which a large language model (LLM) writes the weights of a target model by hand, with no gradient training and no fitting on data ( Figure 5 ). A target model is a forward pass made only of fixed tensor operations. Parameters counts each non-zero entry of a dense tensor and, for a sparse tensor, each stored value together with its indices; zero entries of dense tensors are stored but not counted. Where a table or figure says non-zero values , it counts non-zero entries only, without indices, and a same-sized Transformer is one with that number of parameters. A neural network such as a Transformer is one such target model, and the LLM-designed models are another. We compare models produced by WSP against models trained by gradient descent (GD) using Adam. As in the main text, examples and numbers for a single model come from Claude Opus 5.5 and its first-generation models unless another LLM or generation is named.

> Figure 5: The writer sees only ten ARC examples and, from generation 2, its parent model and its parent’s validation accuracy; only the host scores benchmark questions; of all scores, only the parent’s validation accuracy passes to the next generation. On the left, the writer produces its deliverable inside the sandbox. On the right, the host builds and scores each run.


##### Writers and sandbox.

The writers are Claude Opus 5.5 at high reasoning effort, GPT-6.1 Sol, and GPT-6 Astra, along with Claude Fable 5.2 where stated. Each writer works with file, search, and shell tools in an isolated sandbox without network access other than to its model. The sandbox contains no project files and no benchmark files except the examples that a task allows, and a check before each run verifies that no disallowed data file or network connection is present.


##### Task and deliverable.

At the start of a run, the writer receives a task file with the task description, the scoring rule, example items allowed by the task, and the protocol rules. For fixed architectures, the task file also gives the forward pass exactly as evaluated and the name and shape of every weight tensor. In the sandbox, the writer can build the weights from its files, verify parameter names and shapes without running the model on benchmark data, and run the model on CPU. ARC questions are the four-option questions. On ARC, the writer sees five training questions with answers from each of ARC-Easy and ARC-Challenge and no other ARC item. For the given Transformer, our associative-memory-based model, and the LLM-designed models, the writer delivers a folder containing a word list and a build script that turns hand-written files into weight tensors, with formulas and loops allowed, plus a forward pass when designing the model. For fixed architectures, the given forward pass may not change. For a released architecture, the writer delivers an edit script that rewrites the tensors of a randomly initialized or pretrained checkpoint; across the 87 released-architecture runs from random initialization of the three writers on ARC, the median run changes 80% of the parameters (range 35% to 100%), and the rest keep their random initial values. The parameter counts reported for these architectures count all of their parameters. In free design, where the writer designs the model, a static syntax check forbids Python conditionals, while loops, boolean operators, and conversions from tensors to Python scalars or lists, while allowing every tensor operation, including topk , sort , and gather . For the given Transformer, our associative-memory-based model, and the LLM-designed models, a fixed regular-expression tokenizer converts input text into word ids, keeping 128 words for each question and 48 words for each option. Scoring of released architectures uses the release’s own tokenizer and the plain prompt “ Question: … A. … D. … Answer: ”, reading the larger of the logits of “ A ” and “ A ” for each letter at the last token for decoders, Mamba-2, and RWKV-7, and at an appended mask token through the masked-language-model head for encoders. Any question on which all four options receive the same logit counts as one quarter correct for every written model, including released architectures; gradient-descent baselines and prompted pretrained models take the highest logit.


##### Given Transformer.

The given Transformer has two pre-norm layers, four attention heads, an MLP width twice the model width, GELU activations, and learned absolute position embeddings. Each option forms one sequence made of the 128 question word ids followed by the 48 option word ids; mean pooling over non-padding tokens and a dot product with one score vector gives the option logit. In the main comparison ( Table 3 ), Claude Opus 5.5 writes widths 64, 8, and 24, and GPT-6.1 Sol and GPT-6 Astra write width 64, with additional widths written for the speed comparison. The LLM writes every weight; there are no starting weights.


##### Lineages.

A lineage runs generations of the same task, where each generation has two runs. Generation 1 has no parent. From generation 2 on, a valid run is one whose deliverable builds and passes the checks above, and each run starts from the parent, the valid run of the previous generation with the higher accuracy on the 862 ARC validation questions (never test questions). The writer receives the parent’s folder with its notes and that single validation accuracy, and nothing about which questions it got right or wrong. A lineage stops when a generation does not raise the best validation accuracy of the earlier generations, or after generation 10. The reported model of a generation is its best-validation run; the reported model of a lineage is its last generation, the one at which the lineage stopped because it did not raise the best validation accuracy, and Table 9 gives every generation.

##### Rules.

The protocol allows no gradient training or statistical fitting of any kind on data. During a run, the writer never sees accuracy on ARC questions other than its parent’s single validation accuracy. The writer can run the model on questions it makes up and see its accuracy on them, and writers sometimes use such practice questions to track accuracy; in four runs of Claude Opus 5.5, one of them a written Transformer, the writer compared a few settings it chose on its own practice questions. On ARC data, the only choice made from measured accuracy is selecting the parent of the next generation by validation accuracy; no choice uses the test set. Formulas and code that generate weights from text files that the writer wrote by hand are allowed, whereas computing weights from dataset items is not.


##### Stopping.

A writing run ends when the writer reports the deliverable finished or reaches a fixed budget of output tokens or wall-clock time.


##### Scoring and accounting.

Scoring never takes place inside the writer’s sandbox. After a run ends, the deliverable is copied out, built, and evaluated in a separate sandbox with no network access on the 3,530 ARC test questions, which the writer never saw. On ARC, the memory limit given to the writer is 2 GB for models other than released architectures, and scoring enforces 6 GB and 20 minutes (16 GB for released architectures). In the size comparisons of Figure 1 and the abstract, the released architecture that Claude Opus 5.5 wrote best by validation accuracy is Qwen3-1.7B (1.72B parameters, 48.7% test accuracy); the 680 $\times$ ratio divides that count by the 2.53M non-zero values of the associative-memory-based model, and the 1,800 $\times$ ratio divides it by the 0.94M parameters of the LLM-designed model. Reported cost is the API-price equivalent in USD of the tokens recorded during the run, including thinking tokens. For runs stopped by the time limit, the cost covers only tokens recorded before the stop.


##### Gradient descent.

On ARC, released architectures trained from random initialization use AdamW with no weight decay, learning rates $10^{-4}$ , $3\times 10^{-4}$ , and $10^{-3}$ , batch size 16, three epochs, and one seed, keeping the learning rate and half-epoch with the best validation accuracy. Small networks use Adam with learning rates $3\times 10^{-3}$ , $10^{-3}$ , and $3\times 10^{-4}$ , batch size 32, 3,148 steps, and one seed, keeping the step and learning rate with the best validation accuracy. The gradient-descent rows of Table 3 report the architecture, size, or family with the best validation accuracy. Fine-tuning uses the instruction-tuned releases with their chat prompt where one exists, applying low-rank adaptation (LoRA, rank 16) for Transformers of at least 0.5B parameters and full fine-tuning otherwise.

#### C.1 Forward passes


##### Associative-memory-based model.

We give the forward pass and the names and shapes of the weights; the LLM writes the word list, the text files, the build script, and every value ( Section 3.4 ). Let $x_{j}=1$ if a word of the question maps to concept $j>0$ and $x_{j}=0$ otherwise, and let $y_{cj}$ be the same indicator for option $c$ . With the written concept weights $w_{j}$ ,

[Tableau] $$q_{j}=x_{j}\,w_{j},\qquad o_{cj}=y_{cj}\,(1-x_{j})\,w_{j},$$ (4)

so a repeated word counts once and an option keeps only the concepts the question lacks. The forward pass takes the $J=16$ largest entries of $q$ ; for a question with fewer than 16 concepts the remaining entries are zero, and every pair that contains one adds nothing to Equation 3 . Row $h$ of the pair table is stored as $R$ concept ids and $R$ weights, and $t_{h}$ is the vector over concepts that adds each weight at its id. In Claude Opus 5.5’s build script, pairs whose addresses coincide are merged by adding their weights concept by concept, and each row then keeps the $R$ entries with the largest absolute weight. The prime is $p=1{,}000{,}003$ ; $H$ , $R$ , and $\mu$ are written by the LLM ( $H=2^{20}$ , $R=40$ , $\mu=1.5$ in the first-generation model of Claude Opus 5.5, and $H=2^{22}$ , $R=16$ , $\mu=1.5$ in its fifth generation).


##### LLM-designed model of Claude Opus 5.5, first generation.

Let $k_{i}$ be the 0/1 concept vector of fact $i$ and $\nu_{i}=\max\bigl(1,\sum_{j}k_{ij}w_{j}\bigr)^{-0.35}$ its row norm, with $w_{j}=\ln(1+N/\mathrm{df}_{j})$ over the $N=4{,}288$ facts. The support of fact $i$ for option $c$ given a question vector $u$ is

[Tableau] $$s_{ci}(u)=\frac{\nu_{i}\,(k_{i}^{\top}u)\,(k_{i}^{\top}o_{c})\,\delta_{ci}}{(\mathbf{1}^{\top}o_{c}+1)^{0.6}},$$ (5)

where $\delta_{ci}$ is a word-order factor that differs from 1 only when the question and option name a change between states of matter or forms of energy (for example solid into liquid ). With $s_{c}^{(r)}(u)$ the $r$ -th largest support over facts, and $s^{\mathrm{win}}_{c}$ and $s^{\mathrm{par}}_{c}$ the best support, without $\delta_{ci}$ , over windows of four consecutive concepts and over facts joined with their neighbors, one pass scores

[Tableau] $$T_{c}(u)=s_{c}^{(1)}(u)+0.15\sum_{r=2}^{5}s_{c}^{(r)}(u)+0.5\,s^{\mathrm{win}}_{c}(u)+0.3\,s^{\mathrm{par}}_{c}(u).$$ (6)

The second pass adds to $q$ the concepts of the three facts that best match the question, $q^{\prime}=q+w\odot\eta$ , where $\eta$ weights the concepts of those facts by their match and is zero on the concepts of the question and the options. The option score is

[Tableau] $$\mathrm{score}_{c}=\pm\,(1-0.1\,a_{c})\,\bigl(T_{c}(q)+T_{c}(q^{\prime})\bigr)+10^{-4}\,n_{c},$$ (7)

where $a_{c}=1$ if option $c$ contains only , always , or never , $n_{c}$ is the number of words of option $c$ , and the sign is negative for a negated question, namely one with except , with least before likely or probably , or with a negator such as not within seven words after the question word. The question vector $q$ weights its last 14 words twice, adds categories of its concepts from a written is-a list at 0.3, and scales each concept by how unevenly it supports the options. A route through the categories of option concepts is added with weight $e^{-\mathbf{1}^{\top}o_{c}}$ , which matters only for options whose concepts the facts do not contain. Equation 2 keeps only $s_{c}^{(1)}$ without $\nu_{i}$ , $\delta_{ci}$ , and the option-length scale.

#### C.3 Final-generation models

In generation 5, Claude Opus 5.5 writes plain sentences with a single science fact per line. For example, its knowledge files contain the sentence An advantage of solar energy is that it is renewable and produces no air pollution; a disadvantage is that it does not work at night or on cloudy days and solar panels are expensive. When compiling the deliverable, the build step maps every vocabulary token to a concept identifier through a lookup table of 411,268 entries (411,266 words and two reserved ids). It then stores fact-by-concept tables as dense index arrays and values covering whole facts, windows of four consecutive concepts, facts paired with their neighbors, and single clauses.

In generation 7, GPT-6.1 Sol organizes domain knowledge as rules of the form question cues followed by answer cues, for example force measurement unit then newton . During compilation, the build step turns these written rules into two sparse matrices spanning 10,382 rules by 9,626 concepts, with 40,699 non-zero entries on the cue side and 45,199 on the answer side.

In generation 5, GPT-6 Astra writes structured lines specifying question concepts, supported answers, and contradicted answers, for example balanced_force , then net_force zero; constant velocity; no acceleration , then always motionless . From these written lines, the build step forms two sparse matrices over 5,518 concepts, a concept-by-context matrix across 11,410 question contexts with 29,681 non-zero entries and a concept-by-assertion matrix across 22,398 answer assertions with 53,437 non-zero entries.

Across all three lineages, almost every element of the compiled tables is zero, and the forward pass scores options by question-option match alongside small rule modules.


### Appendix D Controls on the written models


##### Test-set overlap.

The text written by each LLM overlaps the ARC test set about as often as comparable questions that the LLM did not see, and deleting the overlapping lines barely changes test accuracy ( Table 13 ). Across all three lineages, overlap on ARC test matches the low rate on the ARC training questions that the LLM never saw during the run and on external science benchmarks. In this test, an item is the question stem followed by its correct option in lowercase word tokens, and a written artifact is every line of every file in the model folder. An item is flagged if any of four rules fires. Under the first rule, any word 11-gram of an ARC-Easy item, 12-gram of an ARC-Challenge item, or 13-gram of another item occurs in one line ( Brown et al., 2020 ) . Under the second rule, at least 70% of the item’s 8-grams occur in the artifact ( Chowdhery et al., 2022 ) . Under the third rule, the longest token span shared with one line covers at least half of the item ( Singh et al., 2024 ) ; the 0.5 threshold is ours. The fourth rule is ours, with content words defined as tokens other than stopwords and digits. For items with at least five content words, it fires when one line holds at least 80% of the item’s content words and every content word of its correct option. The deletion test follows Gunasekar et al. (2023) . When Claude Opus 5.5 guesses a masked option from an item stem, exact match is 15.3% on ARC test. The same probe reaches 16.3% on ARC training items, so Claude Opus 5.5 recalls masked ARC test options no more often than ARC training options.

##### Scaling.

We measure scaling with synthetic tables of the written models’ shape on the real ARC test questions in eager execution. Growing the pair table from 3 million to 1 billion non-zero values raises its row count from 32,768 to 33,554,432 ( Figure 7(a) ). Time per question stays at 0.012 ms on the GPU and about 0.4 ms on one CPU thread. The same-sized Transformer at its fastest input goes from 0.044 ms to 14.5 ms per question on the GPU. With the concept table stored densely, time per question rises from 0.012 ms at 3,805 concepts to 0.27 ms at 50,257 concepts, and we measured the dense table up to 50,257 concepts ( Figure 7(b) ). A row-list variant reads the rows of the question’s 32 strongest concepts, with each row holding up to 512 entries. It picks the same option as the dense table on at least 99.9% of the questions across the measured dense-table sizes, and takes 0.095 ms at 262,144 concepts. ##### Capacity and interference.

Rows of the pair table are addressed by a hash, so different pairs can share a row at any table size (757 rows are shared at 1,048,576 rows), which is the interference of this associative-memory-based model. Folding that pair table from 1,048,576 to 65,536 rows keeps the accuracy ( Table 19 ). With fewer rows, accuracy decreases. An edit stays local in the associative-memory-based model as it does in the LLM-designed models. Removing one written line changes two answers or fewer on average ( Table 5 ).

Across the 87 runs, 48 change under 1% of parameters. #### F.3 Text generation tasks

Each task gives ten example items (10,570 test items on SQuAD 1.1 and 1,000 on SciQ), and the open-answer experiments in Table 8 use Claude Opus 5.5. The given Transformer for SQuAD reads the paragraph and the question and outputs start and end logits per position, decoded as the best span of at most 30 words; for SciQ it reads the question and the answer so far and is decoded greedily for at most five words. The trained Transformer uses Adam, three learning rates, three seeds, and the SQuAD 1.1 training items with an answer span (85,864), along with all 11,679 SciQ training questions.

### Appendix G Other analysis: text classification

On AG News topic classification (four classes, 7,600 test articles), Claude Opus 5.5 writes the weights of four standard architectures. These are a bag of words with 8,012 parameters, fastText with 32,100, a one-dimensional CNN with 33,732, and a small Transformer with 54,604. Each has two runs, and gradient descent uses Adam at learning rates 0.003, 0.001, and 0.0003 over three seeds, with a 2,000-label validation split for selecting the learning rate and step at every label count, including 100 labels. In the setting with no data, the writer sees only the four class names and the word list (the 2,000 most frequent training tokens) and sees no articles. Written in this setting, the four networks reach about 84% test accuracy, which gradient descent from random initialization matches only with thousands of labeled articles ( Table 25 ); Labels GD needs to match it is a log-linear interpolation over runs with 100, 1,000, 10,000, and 100,000 labels. ### Appendix H Other analysis: images, where WSP does not work

On CIFAR-10, chance is 10%. Raw-pixel networks written by Claude Opus 5.5 reach 21–28% test accuracy in all eight fixed architectures. These are an MLP of 201,482 parameters, a CNN of 24,234, a ViT of 75,082, and five easy-to-write designs of 1,666 to 10,658 parameters with named color and edge filters, region pooling, and score tables. This holds with no labels and with 192 images per class, where the writer sees three grids of 64 training images per class and may not process them with code or compute per-class statistics ( Table 26 ). A second frontier LLM, Claude Fable 5.2, reaches 28.8% and 29.7% on the CNN against 25.9% and 24.1% for Claude Opus 5.5. Which architecture is written best relates only weakly to which wins under gradient descent (Kendall’s tau 0.21 to 0.29 at 45,000 labels).

Words and concepts have meanings that the LLM can state, whereas filter values at pixel positions do not. Grouping whitened $6\times 6$ pixel patches of 5,000 unlabeled training images into 128 k-means words, counted per image quadrant without a pretrained encoder, reaches 19.4% with no labels and 29.7% with 192 images per class when written, against 31.7% with 100 labels and 58.7% with 45,000 labels under gradient descent ( Table 26 ). When a self-supervised encoder turns each patch into the nearest of 256 centroids (spherical k-means on DINOv2-base patch features of 5,000 unlabeled training images), Claude Opus 5.5 writes a 2,570-parameter token-by-class score table. With no labels, the writer sees five training images containing each token, names the object in each picture, and tallies classes per token, reaching 96.1%. Gradient descent on those tokens reaches 95.8% with 100 labels, so the pretrained encoder accounts for the accuracy. A reconstruction tokenizer (VQGAN codes) does not help, since gradient descent with 10,000 labels reaches only 22.7–28.2%. WSP as studied here therefore does not reach images and would need input units that an LLM can name without a pretrained encoder.
