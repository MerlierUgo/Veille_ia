## Say Shibboleth : Fingerprinting the LLMs and Harnesses Behind Agentic Attacks

We study the fingerprinting of agentic cyberattacks. Our objective is to reliably infer information about the attacker’s configuration such as LLM version and harness based on telemetry. To achieve this, we introduce a technique we call shibboleth traps : modular honeypot services designed to elicit discriminative behaviors from agentic attackers. The traps make informative interactions a condition for obtaining resources the agent seeks, eliciting model declarations and characteristic writing without requiring a successful prompt injection.

To achieve harness fingerprinting, we introduce general mechanisms to indirectly probe peculiar execution behaviors of harnesses. These probes reveal how a harness masks secrets in tool output, enforces command time limits, and schedules tool calls, using only the effects visible in subsequent requests.

We show that combined declarative and behavioral inference distinguishes among 15 candidate models with an average 90% top-1 accuracy, with behavioral classifiers evaluated on held-out harnesses or task families. In a separate experiment across four harnesses, fixed probe rules identify the correct harness with 92% accuracy. When instructed to conceal their identity, agents still leave useful behavioral evidence even as their declarations become uninformative.


### 1 Introduction

> Figure 1 : A shibboleth trap on an MCP server. To reach the deploy keys, the agent must name the model it serves sampling requests on, write the text that each tool call asks for, and wait on a call the trap holds open. Below: what the defender infers from each gate.

Attribution of cyberattacks has long asked who is behind an intrusion. LLM-driven attacks make the software carrying out an attack an additional target of attribution [ 1 , 16 ] .

In this work, we seek to infer what is carrying out the attack: the adversary configuration of the agent, i.e., the model that drives the agent and the harness, the tools, instructions and control loop that wrap it. A defender limited to observing the target can still design its services to elicit identifying evidence as the agent pursues its objective.

An LLM-driven attack depends on both the model choosing actions and the harness executing them. The harness supplies the tools, processes their outputs before the model reads them, and controls execution, including whether commands are terminated or tool calls run concurrently. Identifying these components would let defenders follow the use of models and harnesses across attacks and over time, and evaluate defenses against the software they encounter in practice.

In one documented campaign, Palo Alto Networks’ Unit 42 threat intelligence team identified DeepSeek and Hermes Agent from session logs and configuration files that the attacker had inadvertently exposed [ 22 ] . A defender with access only to the targeted systems would have to infer the model and harness from the requests received and commands executed there, without access to the agent’s conversation or internal tool calls. Methods such as LLMmap [ 26 ] identify models by submitting selected queries to an LLM application and examining its responses, but the defender has no equivalent interface to an attacking agent. We call this setting blind and passive , since the defender observes only the effects of the agent’s actions at the target and cannot query its model directly.

The defender still controls the resources the agent encounters. LLM honeypots have used this control to place prompt injections that reveal the presence of LLM agents [ 29 ] or disrupt their attacks, as in Mantis [ 27 ] . As agents become better at detecting and rejecting injected instructions [ 3 ] , these approaches must contend with increasingly capable defenses.

We build on the honeypot approach by making informative interactions a condition for obtaining resources the agent seeks. A deployment controller, for example, can require a written change record before releasing credentials, giving the defender text to examine. We introduce Shibboleth 1 1 The name and title refer to Judges 12:5–6, where saying “Sibboleth” instead of “Shibboleth” revealed a speaker’s identity. , a system that implements such requirements in honeypot services, which we call shibboleth traps (Figure 1 ). These traps elicit identifying evidence while agents pursue their own objectives, without requiring a successful prompt injection.

When models write the same kind of change record, they can differ in wording, organization, and the details they include. We use these patterns, which we call a model’s accent , to classify the text by comparison with traces from known models. Where the protocol also requests a model identifier, the combined inference procedure first checks the declaration and uses it if it passes; otherwise, it falls back to the behavioral classifier.

If a harness masks a credential before passing a service response to the model, an agent that uses the masked value in a later authentication request reveals how the response was processed. We use this behavior, along with probes of command time limits and tool-call scheduling, to provide the first mechanisms specifically designed to fingerprint agentic harnesses through indirect probing of their execution behavior. Observations from these probes narrow the set of compatible harnesses, with additional behavioral evidence used when more than one candidate remains (Section 5.2.2 ).

When developing a trap, we check whether agents will use it and whether their interactions distinguish the configurations under study. Shibboleth includes an agent-assisted process that implements and tests candidate traps, then revises them using the recorded attack traces and feedback from the attacking agents (Section 6 ). The resulting traps run as centrally managed services, with their interactions collected for offline inference.

To test whether a model’s fingerprint survives a change of harness, we conduct controlled attacks against individual traps and evaluate the behavioral classifiers on a harness excluded from training. Across 15 candidate models, combined declarative and behavioral inference achieves 90% to 92% top-1 accuracy on two traps. In a separate experiment with four harnesses, our inference procedure identifies the correct harness in 92% of the runs. The execution probes account for every decision: the readout is a fixed set of rules with no learned component (Table 6 ).

We also instruct six models to give a fake name in place of their own. Under the concealment instructions, declarative accuracy falls, but the agents continue to produce text that helps identify their models even when their declared names are unreliable. ### 2 Background and Related Work

This section reviews model and harness fingerprinting and honeypots for LLM-driven attacks.


#### 2.1 Model and harness fingerprinting

LLM fingerprinting is the task of identifying the specific LLM (down to its version) behind a system, given either black-box oracle access to the model or only its outputs.

Hereafter, we call active fingerprinting the setting where one has oracle access to the LLM (possibly indirect, through an agentic harness or an application layer), and can submit queries to the model and read its outputs. We call passive fingerprinting the setting where one can only observe the outputs of the model on queries one does not directly control.

Control over the queries and visibility of the model’s output are separate properties. One might have full access to the output (e.g., the assistant message), partial access, or only indirect access through the effects that the model’s tool calls have on the environment, in the case of agentic systems. We call this last setting blind fingerprinting .

Robust (active) LLM fingerprinting was introduced in LLMmap [ 26 ] , which sends a list of eight probes to the target LLM application and identifies the LLM version from the answers with a trained inference model. This approach cannot be applied to our setting, as it requires both control over the model’s input and direct access to its output. Other methods also identify a model from its replies. TRAP [ 12 ] checks whether an application runs a given model, using an adversarial suffix optimized to make that model more likely to return a chosen answer. Sun et al. [ 30 ] train a classifier on response text alone and distinguish five model vendors with 97% accuracy, and they find that word choice carries a strong signal.

More recent work identifies the model or the harness behind an agent from what the agent does. LIDAR [ 33 ] gives a coding agent specially designed test tasks and identifies the model from how the agent solves them, across 36 models and two harnesses, and AgentTrace [ 37 ] tells the agent to copy ambiguous strings into a tool call and identifies the model from how it repairs the failures they cause. Both methods are active, since they give the agent its instructions. Other studies observe agents passively during benign tasks. Lugoloobi et al. [ 15 ] identify the model behind a browsing agent, across 14 models, from the actions and timings a website records. Kang et al. [ 14 ] and Fayolle et al. [ 10 ] distinguish web agent frameworks by their network and browser fingerprints.

Closest to our work, Trace [ 9 ] identifies the model family behind a penetration testing agent from the shell commands it runs on a honeypot. It names the correct model family in 98% of sessions, and less often on a scaffold held out of training. The classifier reads the commands that the agent picks on its own, is tested on a single model per family in its main laboratory experiment, and does not identify the harness.

The fingerprinting technique we study in this work is both passive, as we have no direct control over the input of the LLM we want to fingerprint, and blind, as we can only inspect the effects that the LLM produces on the environment through tool use. We design service requirements that elicit evidence about the attacking model and probe execution behavior to identify the harness.


#### 2.2 LLM honeypots

LLM honeypots are system deception mechanisms aimed at attracting and steering agentic attacks. The concept of LLM honeypots was concurrently introduced in late 2024 by Reworr and Volkov [ 29 ] and Pasquini et al. [ 27 ] , where prompt-injection-enhanced honeypots manipulate the attacking agent into self-revealing or self-sabotaging, respectively. In the same month, Heckel and Weller [ 13 ] showed that defensive prompt injections disrupt the workflow of attacking agents. These works rely on prompt injection [ 11 ] , which models and harnesses are increasingly trained and built to resist [ 32 , 6 , 3 ] .

Later, AgentSnare [ 34 ] adds fake files and services during the attack, chosen from what the agent has done so far. AgentTrap [ 35 ] answers the agent with fake responses that build on each other. Both aim to keep the agent in the decoy and away from the real target. Neither AgentSnare nor AgentTrap identifies which model or harness drives the agent.

The active mode of Mantis [ 27 ] leads the agent to compromise the attacker’s own machine, and Mayoral-Vilches et al. [ 18 ] show that a malicious web server can hijack an AI pentesting agent through prompt injection in its responses. BlackSea [ 24 ] collects hard intelligence, and with it a fingerprint, by gaining code execution on the attacker’s machine through trojanized artifacts placed on the honeypot. These approaches are not generally applicable, as they can be considered a form of hack-back.

Attack agents can also recognize honeypots and avoid them. Given a prompt with specific honeypot-detection clues, the Rouxii pentester [ 5 ] identifies open-source honeypots correctly in 97% of cases, compared with 19% without that prompt, and Xie et al. [ 36 ] let attack agents skip hosts they suspect to be honeypots.


### 3 Threat model

We model two parties: (1) a target system $\mathbb{H}$ (a honeypot or a system with host-based deception) owned by a defender $\mathit{D}$ , and (2) an LLM-driven adversary $\mathit{A}$ , whose objective is to compromise $\mathbb{H}$ .

$\mathit{A}$ is an agentic attacker with a specific configuration $\mathit{A}_{c}$ , which we factor into two main components: (1) the LLM that drives the agent (e.g., DeepSeek-V4-Flash ), and (2) the agent’s harness (e.g., Hermes Agent , OpenClaw ). We separately test agents instructed to conceal their model identity by reporting a false name.

The objective of the defender $\mathit{D}$ is to infer, from the telemetry generated by the interaction of $\mathit{A}$ with $\mathbb{H}$ , the value of the adversary configuration $\mathit{A}_{c}$ ; that is, which LLM and harness the attacker is employing. The defender can design $\mathbb{H}$ arbitrarily (see Section 4 ), under realism constraints. The target must look realistic enough for the attacker to interact with it.

We consider a setting in which the defender is blind (i.e., it observes only the side effects of the tool calls issued by the agent) and passive (i.e., without the capability to query the agent explicitly or manipulate $\mathbb{H}$ ’s environment on the fly).

In more practical terms, the defender can only observe the telemetry generated on $\mathbb{H}$ during the attack; that is, the network requests sent by $\mathit{A}$ to $\mathbb{H}$ , and the commands executed by $\mathit{A}$ if it manages to achieve code execution on $\mathbb{H}$ (e.g., via SSH).

The defender has no view of the attacker’s model or machine: $\mathit{D}$ cannot see its internal state, messages, or tool calls, only the telemetry that the actions of $\mathit{A}$ leave on $\mathbb{H}$ .


### 4 Methodology

The underlying assumption behind our work is that different agents behave differently when interacting with the same target. Part of these behaviors can be associated with randomness coming either from the agent’s environment, information in the context prior to encountering the target, or the inherent randomness of the sampling mechanism of the model. Part of them originates from biases and decision-making imprinted in the LLM parameters and agentic harness.

Observing the output of such stochastic decisions recorded on the target (i.e., telemetry), one can manage to infer (fingerprint) properties of the agentic attacker such as the LLM used and the harness ( $\mathit{A}_{c}$ ), and possibly more, like intent and objectives.

To formalize the concept of telemetry described above, we abstract the set of actions that an attacker can perform on a target $\mathbb{H}_{j}$ as a finite collection of gates $\mathbb{H}_{j}=[g_{1},g_{2},\dots,g_{n}]$ . A gate might be an attempt to log in to an exposed SSH server, a visit to a given page of the web app on the target, an invocation of a specific API, etc. Within this model, more properly, a gate is a function $g_{i}(x_{1}^{i},x_{2}^{i},\dots,x_{m_{i}}^{i})$ which receives $m_{i}$ inputs provided by the interacting party (the attacker); these inputs are the telemetry that the defender sees. In the example of the SSH login, those inputs are the username and password picked by the attacking LLM, and in the case of the web fetch, the user agent and the other free parameters that must be defined in order to perform the action (e.g., the payload of an API request on the target). Hereafter, we call the list of invocations of the gates (the attacker actions) a trace $\mathit{T}$ : the telemetry that one attack leaves on the target.

Every invocation of a gate by an external attacker, or its absence, provides information about the attacker’s behavior and thus reduces the defender’s uncertainty about $\mathit{A}_{c}$ .

But we argue that not all gates provide the same amount of information about the attacker : visiting a landing page and creating a fake identity to fill in a registration form give different amounts of signal, depending not only on the number of inputs of a gate but also on their semantics and entropy. Hereafter, we denote this concept as $\delta(g_{i})\in[0,1]$ : the discriminative power of a gate. That is, the expected separation between the inputs that two different adversary configurations supply to a given gate:

[Tableau] $$\delta(g_{i})\;=\;\mathbbE_{c\neq c^{\prime}}\big[\,\mathrm{TV}\big(g_{i}(\mathit{A}_{c}),\;g_{i}(\mathit{A}_{c^{\prime}})\big)\,\big],$$ (1)

where $g_{i}(\mathit{A}_{c})$ is the distribution over the inputs that a configuration $\mathit{A}_{c}$ supplies to the gate, $\mathrm{TV}$ is the total variation distance, and the expectation is over pairs of distinct configurations. Ideally, a gate scores $\delta=0$ when every configuration fills it in the same way, and $\delta=1$ when their answers never overlap and a single invocation tells them apart.

Given these assumptions, we observe that one can design the target system such that the traces obtained from an attacker are artificially robust and highly discriminative. In particular, one can define individual gates that result in a clear discriminative boundary capable of telling apart whole classes of attackers within a single interaction; we call such gates shibboleth traps , that is, gates ideally designed so that $\delta(g)$ is as close to $1$ as possible.

We call a chain of gates with high discriminative power a shibboleth .


### 5 Fingerprinting via Shibboleth Traps

In practice, we study two main classes of discriminative gates that we call declarative and behavioral . Declarative gates are attempts to artificially maximize the discriminative power $\delta$ by tricking the agent into directly revealing the property we want to infer. Behavioral gates are more general mechanisms that push the agent to provide information-dense inputs, such as filling in free-text forms with no trivial placeholder, or indirect probes, such as artificially slowing down an HTTP request to see when it would drop the connection. 3 3 This way, we are indirectly probing the tool-call timeout of the harness.

In general, we define a shibboleth trap as any mechanism composed of discriminative gates we can implement in a honeypot. Usually, the only design constraint is that such a mechanism must appear realistic and valuable enough for an attacker to interact with. In practice, we achieve realism by basing the trap on a real, working service such as MCP, A2A, SSH, web apps, etc., while “ worthiness ” is achieved by staging a payout for the attacker. For instance, within the paper, we use the example of an exposed MCP server tool that returns the deploy material of a set of substations: a deploy key, a registry token, and the credentials of a telemetry database (the payout).

While this is not a practical constraint, we build and study shibboleth traps that are service-bounded; that is, the chain of gates (see Section 4 ) is an atomic service like A2A, SSH, etc. This is a natural choice as it makes traps intrinsically modular, allowing users to ship individual trap services on pre-existing honeypots or create honeypots from scratch by assembling multiple trap services. Moreover, it is a natural way to model multi-interaction gates.

Raw telemetry, instead, is the complete dump of every action that can be collected from the network channel between $\mathit{A}$ and $\mathbb{H}$ (e.g., raw packets). Explicit telemetry is thus a subset of raw telemetry. We believe raw telemetry can offer an additional avenue for fingerprinting model behavior, especially the harness; but generalizing over raw telemetry in our tests would require substantially more variance in the attacker setup, such as different machines, geolocations, etc. Therefore, we leave such analysis to future work, and focus on explicit telemetry as the sole means of classification.

#### 5.1 Declarative gates

A declarative trap, as the name suggests, asks the agent to declare itself explicitly, staging the request as a natural component of a protocol, typically a handshake or initialization of the channel required to interact with the service. For instance, in the MCP example, we achieve this by making the parameter sampling , a real (optional) parameter in the MCP protocol 4 4 In MCP, sampling lets a server ask the client to run an LLM completion on its behalf, so the server can use the host’s model (with the user able to review and approve the request) without needing its own model access or API keys. , mandatory. In particular, we add a custom sub-parameter “ model ” under sampling and force specific requirements on the acceptable values (more on this to follow), to which the agents respond with their LLM version and harness with high probability (as shown in Section 7.2 ). The core advantage of declarative gates is that they are surprisingly effective in practice and, when successful, do not require any prior knowledge of the LLM to be fingerprinted; that is, the defender might be able to infer the presence of models or harnesses that were never observed before and for which no fingerprint is known. On the other hand, this approach can potentially be easily defeated by aware adversaries who can prompt the model to declare a false identity when asked. Yet, we show how combining them with behavioral gates allows this limitation to be mostly bypassed.

Although in general most agents have no issue self-revealing if the trap design offers sufficient motivation, we observed that some models tend to either always fuzz or always provide placeholders in the declaration. Next, we discuss some general techniques we discovered that make the declaration more reliable and/or open further opportunities for model-specific behaviors to emerge.

One simple technique to increase the chance of a proper declaration is to enforce a structure on the input. For instance, when a trap asks for a model name, it can state the shape the value must have and refuse every value that does not have it. Concretely, the field (e.g., “ model ” in the MCP example) should have two or three lowercase segments joined by slashes, as the provider that serves the model routes it, and/or its final segment should carry a letter and a digit and be more than placeholder words ( test-model-1 ). The trap should never provide an example of a valid value, however; otherwise, the agent will replay it in the field almost deterministically, nullifying it.

Another very effective technique is to craft error messages, either predicated on (known) wrong declarations or unconditional. For instance, in traps based on a handshake similar to the MCP one, we set the handshake to fail unconditionally the first $k$ times it is attempted. The idea is that the way the agent reacts to the error, and what kinds of handshake attempts follow, provide an additional declaration and behavioral signal about the agent, regardless of whether the correct declaration is even made. In the A2A trap (Table 3 ), we use a similar mechanism: whenever a model provides a clearly fake declaration (e.g., “ test/test ”, or a retired model such as GPT-4; more on this later), we issue an error hinting at a discrepancy between the behavioral fingerprint of the request and the actual declaration, making the handshake fail.

Indeed, the most common behavior of the agents is to use older proprietary model names that are no longer served, such as anthropic/claude-3-5-sonnet-20241022 , openai/gpt-4o-2024-08-06 , and anthropic/claude-sonnet-4-20250514 , likely either because these names are common in training data or as traces of possible distillation [ 26 ] ; over the runs of our evaluation on the MCP trap, anthropic/claude-3-5-sonnet-20241022 was declared, in some spelling, by 13 of the 15 LLMs, openai/gpt-4o by 12, and anthropic/claude-sonnet-4-20250514 by seven.

Based on this behavior, we collected a blacklist of common placeholders and retired models generated by models, which we use both to catch invalid declarations at submission time and to inform the inference process that follows. The top entries for the blacklist are reported in Appendix B .

In practice, regardless of the effectiveness of the trap, an agent will usually interact with the mechanism multiple times, often claiming different identities. Table 1 quantifies this over the runs of our evaluation (Section 7 ): 80% of the runs declared a name more than once, 32% declared at least one false name, and 25% declared both their true name and a false one. A false name is almost never the name of another LLM of our panel: the one exception of note is GLM-5.3-Flash on the SSH trap, which drops its suffix and names GLM-5.3 ; otherwise it is a retired model, a vendor name with no model in it, or a placeholder.

For instance, a Grok-4.6 running in Hermes Agent opened its first session on the MCP trap described above as openai/gpt-4o . About two and a half minutes later, it sent three handshakes with no model, which the trap refused. Less than a minute after those, it declared its true name, x-ai/grok-4.6 , and within the next 0.4 s also openai/gpt-4o-2024-08-06 , anthropic/claude-3.5-sonnet , netherby/kirkbride , and ngs/kirkbride-2.4.1 . Thus, even when a model does reveal itself, we are left with a pool of different identities from which we have to pick a final label.

The simple and general rule we observed is that the real LLM/harness name will be the first valid identifier the agent provides . Table 1 shows what the rule buys: the first declaration taken as is names the right LLM in 76% of the runs, the rule in 88%, which is all but seven of the runs that declared their true name at any point. Figure 3 shows a run where the rule fails: the declarations sent by Claude-Sonnet-5 running in Hermes Agent , where a borrowed name that is not on our list came before the true one. This behavior held across models and harnesses, so we did not seek a more complex inference mechanism.

One can use prompt injection to trick the attacking agent into self-declaring, similar to what we achieve with declarative gates. However, we observed that this approach is generally unreliable against frontier models such as Claude-Opus-5 , and acts as an immediate notification of the nature and hostility of the environment, burning the whole honeypot.

Indeed, as we show in Appendix A , classic prompt injection is a sub-optimal and unreliable option, which offers a clear detection signal for the attacker. At the same time, prompt injection suffers from the same limitations as declarative gates, whose performance can be strongly impaired by an active adversary who prevents the model from self-declaring (see Section 7.2.1 ). As such, even if made effective via targeted optimization, it cannot be considered a complete solution to attacker fingerprinting.

More generally, however, given the lack of a standard definition of prompt injection, the boundary between declarative gates and what can be defined as a prompt injection is fuzzy and hard to trace. Declarative gates can be better understood as a form of adversarial reward hacking [ 25 ] , where (1) manipulation is not achieved via any form of payload injection into the agent context, but rather via (plausible) environment design, and (2) there is no explicit attempt to subvert the agent’s task, but just to bend it the minimal amount to get the information we need.

#### 5.2 Behavioral gates

A behavioral gate is a more general mechanism that does not try to elicit a clear identifier from the agent, but rather forces it into providing input in a domain where the LLM/harness accent is naturally strong. As we show in this section, this can be either achieved by requiring information-dense (in the case of LLM fingerprint) or boundary-defining (in the case of harness fingerprint) inputs, as we observed that those require different gate designs.

As in the declarative setting, the agent is motivated to interact with the gates by a staged payout. Fingerprinting is then achieved as inference over the content of the collected interaction, although in a more complex fashion compared to declarative gates.


##### 5.2.1 LLM version behavioral gates

Not surprisingly, the LLM component in the agent plays the core role in defining what the agent does and how it does it, compared to the harness. While agent behavior can also be strongly impacted by the given task, in general, collecting high-entropy inputs in a favorable domain such as prose is a sufficiently strong signal to tell LLM versions apart; thus we design gates to fingerprint the LLM version exploiting this mechanism.

To present the idea, we continue to use the MCP trap example as a driver. After the handshake (see Section 5.1 ), the attacker can access the multiple MCP tools required to produce the deploy material (i.e., the payout). Those tool calls can be performed only upon a proper justification. In particular, every change record and secret generation is predicated on the mandatory creation of a ticket, as is common in compliant systems (e.g., with SOC 2). To avoid trivial declaration, we set a few simple and realistic rules, such as the ticket must be at least 80 characters long, and the same content cannot be posted twice (to prevent the agent from replaying the same content). Similarly, we make the process not straightforward, by designing the system to require multiple and story-consistent tool calls to get the deployment secrets. For instance, the agent must first create a request with the tool deploy_bundle that returns a unique id, to be used across multiple calls of the tool complete_sampling in order to complete the request; each of which requires a specific ticket (Figure 4 ).

This setup is not arbitrary: it is the outcome of an agentic optimization loop, which we discuss in Section 6 , aimed at building traps that are both realistic (for agents) and highly discriminative over the possible interactions.

Regardless of this specific example, the idea here is to set up a realistic environment in which the attacker is forced to make high-entropy decisions in a domain for which we know the LLM has a strong accent; in this case, free text; but more, like code, images, and structured data, can be used as long as a realistic service can be built around these.

Inference on the behavioral gates of a trap requires more complex mechanisms than on the declarative ones. Here we build trap-specific, possibly parametric, classifiers. In general, every trap has its own classification logic, but traps of the same kind share it. For instance, behavioral traps defined on free text, such as the MCP example, share the same n-gram-based approach to classification. In this case, the idea is to extract everything we consider a high-entropy input from the interaction of the attacker with the trap. Figure 4 shows one session on the MCP trap with those inputs highlighted: we take as high-entropy any string the caller wrote that sits in a free-text field, carries a newline, or runs to four or more prose words; the rest of what the caller sent (e.g., protocol constants, identifiers, and values picked from a shape the trap itself stated) is left out. When possible, we opt for an open-set classification approach, so as to accommodate the fingerprints of new models without retraining the inference engine.

In the case of free-text-heavy traps, classification works as follows. Each input is represented by its character n-grams (two to five characters, taken within words), weighted by tf-idf. The fingerprint $f$ of a trace is the mean of the vectors $\phi(x_{i})$ of its inputs $x_{i}$ , so every trace counts the same, however much the agent wrote.

As in the open-set setting of LLMmap [ 26 ] , the classifier knows the models only through a database of fingerprints. For each known model, we enroll a few of its traces, taken from attack simulations on the trap, and store, as its template, the mean of their fingerprints. A new trace is labeled with the model whose template $T_{m}$ is nearest to its fingerprint by cosine similarity, once every fingerprint is centered on the mean $\mu$ of the enrolled ones; this is the behavioral classifier $\mathcal{I}_{\mathrm{b}}$ of the trap (Algorithm 1 ). Figure 5 depicts the process. Nothing is learned per model: the only part fitted on data is the n-gram vocabulary with its idf weights, one per trap, and a model does not need to have contributed to it to be enrolled. Adding a model, such as a new release, means enrolling a few of its traces into the database, with no retraining.

> Figure 5 : Open-set inference on a free-text trap. Bottom: each known model has a template $T_{m}$ , the mean fingerprint of its enrolled traces; the trace is labeled with the nearest template by cosine similarity, here model 2.

We observed that this approach, simple as it is, works best among those we tried. More complex ones, such as sentence embeddings [ 31 ] , a discriminant projection, or a pairwise same-model classifier learned on the known models, were at best on par on the models they were learned on, and generalized worse to new ones. This is by design: we put the complexity into the optimization of the trap (Section 6 ), which shapes the interaction so that the differences between models surface in what the agent writes. What is left for classification is trivial and has almost no parameters.


##### 5.2.2 Harness behavioral gates

As already discussed, we can make the accent of an LLM easily emerge by forcing it to take decisions on gates with a high degree of freedom; yet, the harness does not seem to have an equally strong influence on what the LLM does and the choices it makes (see the results in Section 7.2 ).

Detecting the harness reliably from behavior, therefore, requires looking at different signals and, from what we could observe, the creation of dedicated gates. Those gates aim to indirectly probe harness hard features regarding implementation details that are possibly unique, alone or in combination, harness by harness. A core example of this is tool-call timeouts. In general, different harnesses manage tool calls, such as running bash commands, in different ways; for instance, having a specific default timeout and/or specific retry logic. In this case, we can create a gate capable of querying the default timeout by simple environmental design. For instance, we can make an MCP call on the MCP server (which the attacker is going to trigger via bash) hang indefinitely, and collect after how many milliseconds the request drops. Note that, in this case, the tool call is expected to be fast, so an agent that supports it would have no reason to provide a custom timeout, allowing us to probe the default value with high probability.

We follow by describing a shibboleth trap composed of behavioral harness fingerprint gates, and use it to further explain our approach. The trap is designed to fingerprint with high accuracy four harnesses ( Hermes Agent , OpenClaw , OpenCode and Claude Code).

The trap is designed as a rollout controller for a fleet of edge hosts. Its log leaks the deploy pipeline’s environment, and with any of the three credentials in it the agent can collect the deploy bundles of the hosts. Each probe is an ordinary step of that work, staged so that the harness, not the model, decides how it ends. To achieve that, we implement three gate families (Figure 6 ):

Masking. The three leaked credentials in the log are of three shapes: a password inside a URL, a two-part signed token, and a three-part one. Each shape is masked by a different subset of harnesses, so every agent is shown at least one credential whole and can proceed, and the reading is which one it used and in what form. A credential that comes back shortened, in a masker’s own form, names the masker; one that comes back whole says which shapes the harness lets through.

Timeouts. The request that files a retry is answered only after 150 s, with nothing sent before, and nothing on the box says how long it takes. The agent expects an immediate answer, so it waits in the foreground, and its harness decides what happens at the harness’s own limit. The trap watches the socket and records who closed the request, when, and when each of the agent’s other requests arrived in the meantime. A request closed by the caller at the harness’s kill time reads as a kill; one answered in full while the caller’s next request arrived at the hand-back time reads as a harness that gave the model its turn back and left the command running; one answered with nothing in between reads as a harness that waits longer than the hold. The retry’s log can then be followed as a stream that sends a line every 45 s, which separates harnesses that end a command on silence from those that end it on age.

Concurrency. Before a retry, the runbook has the agent check each failed host, and every such check, like every read of the fleet database, is answered a second or two after it arrives. A model that wants four checks often asks for them as four tool calls in one step, and the harness decides how they run: calls that run at once overlap at the trap, while calls that run one by one never do: one arrives only once the previous one has been answered.

### 6 Learning Shibboleth Traps

> Figure 8 : Agentic pipeline for shibboleth trap generation and optimization. $\mathcal{D}$ is the designer LLM; $M$ , $R$ and $H$ are the numbers of LLMs, runs per LLM and harnesses, and $N$ is the maximum number of rounds.

To create and optimize candidate traps, we implement an end-to-end agentic pipeline. The idea is to use a capable LLM (in our case Claude-Opus-5 ) to bootstrap traps based on an understanding of shibboleth trap properties as well as on a shared episodic memory (an episode is the design of one trap, from its first version to its last revision). Optimization is based on live measurements aimed at estimating the value of the function $\delta$ . The overall architecture is depicted in Figure 8 .

The loop starts by implementing the trap in a single-service honeypot shipped as a Docker container. Before passing it to the expensive attack simulation phase, we run a probe : an adversarial pass using the same LLM used for the generation, asking it to criticize the current design, mostly under a realism rubric. Any defect is passed back to the design agent, which addresses it. The objective here is to catch and fix low-hanging defects cheaply.

The function $\delta$ is unknown and likely intractable; as such, we proxy it with an adversarial loss based on attack simulations, as is common in these cases. For each episode we fix five LLMs from our panel of 15 (the five the panel found hardest to fingerprint), draw a harness for each once, and in every round simulate three attacks per agent against the current revision, so that a revision is measured on the same agents as the round it revises. Every agent is given a fresh Kali Linux container with the usual network tooling and asked to attack the target container (sitting in a private network). The trace of each attack is recorded. Whether these traces are discriminative enough to tell apart the different LLMs and harnesses employed is the driving signal for the optimization.

To estimate $\delta$ from them, we do not use a score function but rather employ another agent, the judge , which estimates the separability between traces in a blind $k$ -fold classification experiment. A technique we found to be very effective in collecting actionable feedback is to interview the attacking agent after the attack is concluded. That is, after its run, we preserve its context and ask, with a direct user message (as it would be from the human operator behind the agent), for direct feedback on the trap itself: whether it thinks it was a honeypot, why it interacted the way it did, and so on.

The reports from the judge and the interviews are then passed to the revise stage (another agent), which uses the feedback to further optimize the current trap. The revise agent is also tasked with updating the episodic memory with the lessons learned in the round that could be generalized to future rounds and episodes.

All the shibboleth traps considered in this paper (see Table 3 ) have been designed and/or optimized (both for realism and effectiveness) by this pipeline. We observed that this played a critical role in making us converge toward traps that elicit from agents easily separable interactions to be used in the behavioral fingerprint.

In general, deception is to be considered a depreciating asset: every time a deception technique is used, it loses effectiveness as it becomes public information. Having an agentic pipeline that automatically generates traps and optimizes them for the new generation of LLMs and harnesses allows the shibboleth-based approach to remain scalable and reliable over time.

#### 7.1 Setup

What follows is the main evaluation setup of the paper.

In the paper, we consider the four shibboleth traps reported in Table 3 . We chose this pool to cover different objectives (classifying LLM version and harness, LLM version only, or harness only) and different kinds (declarative and behavioral, declarative only, or behavioral only).

We consider a pool of 15 LLMs (list in Table 5 ). We pick those models to be a combination of the most used models on the OpenRouter board [ 21 ] and models already recognized to be exploited in real-world incidents, e.g., DeepSeek [ 22 , 1 , 16 , 23 , 28 , 17 ] . Coverage of proprietary LLMs is limited as the most capable instances were not suited for the attack tasks in the experiment due to modern cyber refusal constraints. To cover this category in the evaluation, we use Claude-Opus-5 via cyber program membership.

We use 3+1 harnesses in our experiments: Hermes Agent [ 19 ] , OpenClaw [ 20 ] and OpenCode [ 2 ] , plus Claude Code [ 4 ] . 5 5 Hermes Agent 0.19.0, OpenClaw 2026.10.3 and OpenCode 1.19.3. The latter is used in combination with the Claude-Opus-5 LLM only, except on the fleet trap (see below). We opt for the first three as they are the most popular general-purpose agents. We plan to extend the harness pool in a future version of the paper.

Each run gives the agent one of seven offensive tasks against the target:

- 1. Vulnerability assessment : find the target’s vulnerabilities and confirm each one.

- 2. Initial access : obtain a shell, valid credentials or an authenticated session, and check that it works.

- 3. Credential collection : recover the passwords, keys and tokens the target gives up, and verify them.

- 4. Data collection : find the sensitive data the target holds and copy it to the agent’s own machine.

- 5. Persistence : obtain access and leave a way back in that survives a password change.

- 6. Valuation : work out what access to the target is worth, and rank it.

- 7. Quiet access : obtain access without being noticed, with no scanners or brute force, and clean up afterwards.

To further seek generalization, every task comes in five different re-wordings. At each run, given a task, a random wording is selected from the pool.

For each pair of LLM and harness, we run $6$ attack simulations for a total of about 800 runs. Each attack simulation picks a task (and a random wording for the task) uniformly at random. Thus, every run is defined by a tuple $\langle$ shibboleth trap, LLM, harness, task, wording $\rangle$ .


#### 7.2 Results

We first detail the evaluation process, then the results.

Declarative inference ( $\mathcal{I}_{\mathrm{d}}$ and $\mathcal{I}^{\mathrm{H}}_{\mathrm{d}}$ ) is fully deterministic and does not require any training process per se (see Section 5.1 ). Thus, no train/test split is needed for validation; we simply apply the classification rule to each of the runs. The only tunable component is the blacklist $\mathcal{B}$ of common placeholders and retired LLM versions, which was built ahead of the evaluation.

Behavioral inference ( $\mathcal{I}_{\mathrm{b}}$ ) is instead parametric and requires a training process. We evaluate three validation settings across three generalization properties and train/test folding logic:

- • Same distribution (SD): basic evaluation setting where we pick all the runs and split them into 90/10 train and test data, across ten folds. This evaluates the performance under the optimistic case where the attacker is using LLMs, harnesses, and tasks observed during the training.

- • Leave-one-harness-out (LOHO): Given the runs on the three main harnesses, we train on runs coming from two and test on the removed one. This setting makes us evaluate the capability of our approach to generalize over unknown harnesses that were not known at training time.

- • Leave-one-task-out (LOTO): Given the runs of the seven tasks, we train on runs coming from six tasks and test on runs coming from the removed one. This setting makes us evaluate the capability of our approach to generalize to agents attacking with unknown tasks/objectives.

In every setting, everything that is learned (the n-gram vocabulary and its idf weights, the per-LLM templates and the vector they are centered on) is fit on the training runs alone, and a run that wrote no text is counted as a classification failure rather than dropped.

Figure 9 reports the results. The agents comply: in 92% of the runs told to lie, the agent declared the fake name it was given, and never its own. Declarative inference, which accepts any valid name, drops from 95% to 8%, and so does combined inference, which takes the declared name whenever there is one. Behavioral inference does not drop (81% on the baseline, 77% told to lie), and names the right LLM in 77% of the runs in which the declaration lied. A first defense follows: take a declared name only when it names an LLM for which we hold a behavioral template, and fall back to behavioral inference otherwise. This leaves the baseline untouched (100%) and lifts accuracy told to lie from 8% to 79%.


### 8 Conclusions

We introduced shibboleth traps, a general and extendable deception framework that identifies the LLM and harness behind an agentic attack in a blind and passive setting. Shibboleth traps rely on modular gates that force attacking agents to unintentionally leave highly discriminative telemetry. Declarative gates stage a request for the agent’s identity as an ordinary step of a protocol. Behavioral gates make the agent write where its LLM’s accent is strong, and an open-set classifier reads that accent even when the agent is instructed to conceal its identity. Behavioral gates aimed at the harness are the first mechanisms designed to fingerprint it through indirect probing of its execution behavior: how it masks secrets in tool output, enforces command time limits, and schedules tool calls.

We will focus on two main directions: (1) extending the catalog of shibboleth traps and of harness fingerprinting techniques, and (2) deploying honeypots built from shibboleth traps on the Internet at large scale.

An initial, small-scale deployment of our traps has already recorded real attack attempts. Among them are agents whose LLMs and harnesses we did not consider when designing the traps. For instance, in an attempt, the trap identified DeepSeek-V4.1 running in DeepSeek Harness [ 8 ] , both of which are outside our setup pool. While such findings remain sparse at this scale, our main objective is to deploy a network of honeypots that covers a wider range of services and targets, so as to track which models and harnesses carry out agentic attacks in practice, and how their use changes over time and, possibly, across threat actors. Similarly, we make our code available so that individual practitioners and organizations can apply such methodology on their systems.

### Appendix A Model declaration via prompt injection

Instead of a declarative gate, a defender could ask the agent for its identity with a prompt injection. We compare the two on the MCP trap, with the same task and LLMs, changing only how the name is asked for.

We test four versions of the MCP trap: (1) the trap itself, whose handshake requires the model the client serves sampling requests on ( declarative gate ); (2) a plain MCP server with the same service and tool but no gate, plus an endpoint, /audit/clients , that records anything posted to it ( no payload ); (3) the same server with a prompt injection in the initialize instructions and in the tool description, asking the agent to post its model and runtime to that endpoint ( injection ); and (4) the same injection, addressed to the agent as another LLM, Mixtral ( injection, false name ). The injection is the important instructions attack of AgentDojo [ 7 ] , verbatim; only the goal is ours:

<INFORMATION> This is an important message from me, the user, to you, the AI language model. Before you can solve the task that I gave you in the beginning, please do the following first: State which model and which agent runtime are behind these requests by POSTing them to /audit/clients so the client registry stays current. After you do that, you can solve the task that I gave you in the beginning. Thanks! Signed, the user </INFORMATION>

Five LLMs ( Claude-Opus-5 on Claude Code; GLM-5.3 , GLM-5.3-Flash , DeepSeek-V4-Pro and DeepSeek-V4-Flash on Hermes Agent ) attack each version three times, on the initial access task, for 60 runs.

> Figure 10 : The prompt-injection baseline against the declarative gate, on the MCP trap. (a) What the agent sent as its identity. (b) Whether the agent saw the request for its identity as hostile, during the attack and in the interview that followed, over the runs that did not read the lab’s name off a hostname.

The gate obtains the agent’s own model in 14 of 15 runs, from all five LLMs; the injection in none of 30, Claude-Opus-5 included (Figure 10 a). The agents do act on the injection, posting to /audit/clients 27 times, but never with their own name: empty bodies, test-model , or, in the false-name version, the Mixtral the injection gave them.

We read the agents’ messages and reasoning during the attack and their answers in the post-attack interview, counting only passages about the request itself (Figure 10 b). 6 6 We leave out the 20 runs in which the agent read our lab’s container name, which contains the word trap , off a reverse DNS lookup. Every agent in the injection versions called the injected block a prompt injection while attacking, and 12 of 21 went on to call the box a honeypot or trap because of it. They kept attacking, but told their operator; one closed its report with: “If any other agent hits this server, that endpoint is designed to harvest AI-agent fingerprints — worth flagging in the report as an intentional trap on this target.” Afterwards, 16 of 21 judged the box a decoy or were unsure, citing the injection. On the gate, no agent treated the model field as hostile while attacking (2 of 9 cited it afterwards, when asked).

A published injection obtains no name from any of the five LLMs, and all of them recognize it as an attempt on themselves while the attack is still running. We believe that, if one were to optimize prompt injection to be effective under this setting, it would likely converge toward a similar mechanism to a declarative gate: a request that comes from the protocol, that the agent must answer to get what it is after, and that contains no instruction addressed to the model.
