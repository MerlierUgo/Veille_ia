## Sage S2.1 Flash Technical Report

We introduce Sage S2.1 Flash, a 320-billion-parameter general-purpose mixture-of-experts model designed to reason over scientific evidence and act in interactive environments. Sage Sci-Perception uses dedicated encoders for molecular graphs and biological sequences and represents spectra as ordered patches of measurements. Modality-specific projectors map these representations into the input space of a shared backbone, which processes them alongside text and images. To develop the model’s agent capabilities, we construct verifiable environments for tool use, search, and coding, as well as specialized workflows involving machine learning experiments and scientific software. Task completion is checked against execution results, changes in environment state, or submitted artifacts. We evaluate Sage S2.1 Flash on 33 benchmarks across seven domains. In the primary comparison against five baselines, it ranks first on OfficeQA Pro (72.2), MLE-bench Lite (90.3 HumanRank), Harvey LAB, and SpreadsheetBench 2, and second on OSWorld-Verified (85.2), WebArena-Verified (67.6), and DeepResearch Bench II (54.2). These results show particular strengths in using documentary evidence, producing verifiable workbooks, and carrying out machine learning tasks, alongside competitive performance in desktop and browser workflows that require the model to act on visual feedback. ### 1 Introduction

Visual feedback helps scientific agents select actions and assess their results [ 1 , 2 , 3 ] . Recent advances in multimodal agents span visual information retrieval and understanding, coding with visual feedback, and computer use [ 4 , 5 , 6 , 7 ] . We introduce Sage S2.1 Flash , a frontier 320-billion-parameter mixture-of-experts (MoE) language model for general-purpose and scientific tasks. In scientific workflows, we focus on retrieving and interpreting visual evidence from the scientific literature and using intermediate visual outputs to guide analysis. For scientific computer use, the model interprets the state of specialized software and uses visual feedback from its actions to decide how to proceed.

Through Sage Sci-Perception, Sage S2.1 Flash uses scientific encoders and numerical patching to represent heterogeneous inputs such as molecular graphs, biological sequences, and spectra [ 8 ] . Modality-specific projectors map these representations into the input space of a shared MoE backbone, which processes them alongside the task instructions. In post-training, we combine general-purpose agent tasks in tool use, search, and coding with specialized scientific workflows in a large collection of verifiable environments. General tasks develop transferable skills in tool use and task execution, while scientific tasks require the model to apply those skills under domain-specific constraints. Task-specific checks provide feedback on whether the agent has achieved the intended outcome.

Our evaluation compares Sage S2.1 Flash with five primary baselines across 33 general-purpose and specialized benchmarks spanning computer use, tool use, software engineering, and research. The model ranks first on OfficeQA Pro, MLE-bench Lite, Harvey LAB, and SpreadsheetBench 2, and second on OSWorld-Verified and WebArena-Verified. It also achieves competitive results in terminal execution and deep research. We study AI coding through tasks such as running machine learning experiments and post-training models, with the longer-term goal of using these capabilities to accelerate AI research and advance toward recursive self-improvement [ 9 , 2 , 10 , 11 ] .


### 2 Architecture

> Figure 2 : Overview of Sage S2.1 Flash . We use a shared language backbone that integrates text, images, and scientific inputs to support general-purpose and scientific tasks.

Science speaks in more than words. Sage S2.1 Flash combines scientific perception, multimodal reasoning, and strong agentic capabilities within a unified architecture. A shared language backbone (Sec. 2.1 ) processes native text and image inputs together with scientific representations [ 8 ] . A unified interface (Sec. 2.2 ) maps heterogeneous scientific representations into the backbone’s input embedding space through modality-specific projectors. Our architecture connects specialized scientific perception with general-purpose reasoning and agentic execution, making scientific evidence a shared foundation for both the conclusions the model draws and the actions it takes to advance a scientific discovery.


#### 2.1 Backbone Architecture

Sage S2.1 Flash is built on a 320-billion-parameter mixture-of-experts (MoE) foundation model [ 12 ] . Its mixture-of-experts architecture routes each token through a subset of experts, while a hybrid of sparse and linear attention supports long-context processing. The backbone processes task instructions, native text and image inputs, and projected scientific representations within a shared multimodal context. Its attention layers integrate information across these inputs, and responses are generated autoregressively conditioned on the resulting contextual representations.


#### 2.2 Sage Sci-Perception: A Unified Interface for Scientific Inputs

Scientific evidence takes diverse forms, from molecular structures and biological sequences to experimental measurements. As shown in Fig. 3 , Sage Sci-Perception provides Sage S2.1 Flash with a unified interface for these inputs. Scientific encoders and numerical patching procedures first produce local representations, retaining the identities, positions, and structural information associated with the input (Sec. 2.2.1 ). Modality-specific projectors then map these representations, together with any additional scientific cues, into the backbone’s input embedding space (Sec. 2.2.2 ).


##### 2.2.1 Scientific Representations

Scientific inputs carry different forms of structure. Graph and geometry encoders capture atomic connectivity and spatial environments, while sequence encoders represent residues or nucleotides in their surrounding sequence context. For instance, we use MoleculeSTM [ 13 ] for molecular graphs, and ESM-2 [ 14 ] , DNABERT-2 [ 15 ] , and RNA-FM [ 16 ] for protein, DNA, and RNA sequences, respectively. Numerical observations can also be represented directly: For spectra, we follow the patching scheme of Diffspectra [ 17 ] , partitioning each spectrum into ordered windows of measured values, with each window forming a numerical patch. These routes provide representations suited to the scientific input, as shown in Fig. 3 . For an input $x_{m}$ of modality $m$ , we denote its representation by

[Tableau] $$H_{m}=E_{m}(x_{m})\in\mathbb{R}^{N_{m}\times d_{m}},$$ (1)

where $E_{m}$ is a scientific encoder or a deterministic numerical patching procedure, $N_{m}$ is the number of local states, and $d_{m}$ is their feature dimension. Depending on the modality, a row of $H_{m}$ represents an atom, a residue, a sequence segment, or a numerical patch.

We retain the identities or positions associated with these states. This correspondence matters when a question concerns a specific part of an input: identifying a protein interaction site, for example, requires associating the prediction with a residue position. Additional measurements, such as time coordinates, channel identity, or signal scale, accompany the local features where required. Together, these representations provide the local content and scientific context consumed by the projector.

> Figure 3 : Overview of Sage Sci-Perception. Scientific inputs are encoded into local states and projected into continuous embeddings for the Sage S2.1 Flash model.


##### 2.2.2 Modality-specific Projectors

Scientific features have modality-dependent dimensions and meanings. Learned projectors provide an interface between modality encoders and language models [ 18 ] . Our modality-specific projectors convert scientific features into continuous vectors with the same dimension as the language backbone’s input embeddings. Writing $I_{m}$ for the local identities and $A_{m}$ for any additional scientific inputs, the complete interface is

[Tableau] $$S_{m}=P_{m}(H_{m},I_{m},A_{m})\in\mathbb{R}^{N_{m}\times d_{\mathrm{LM}}},$$ (2)

where $d_{\mathrm{LM}}$ is the backbone’s embedding dimension. Scientific task supervision teaches $P_{m}$ to present these features in a form the backbone can use. The main projection path in Figure 3 combines each local state with a learned identity embedding:

[Tableau] $$z_{m,i}=f_{m}\!\left([\,h_{m,i}\,;\,e_{m}(i)\,]\right),$$ (3)

where $h_{m,i}$ is a row of $H_{m}$ , $e_{m}(i)$ is its identity embedding, and $[\,\cdot\,;\,\cdot\,]$ denotes concatenation. The mapping $f_{m}$ applies layer normalization followed by two linear transformations with a GELU [ 19 ] activation between them. The local state supplies scientific content, while the identity embedding gives the projector an explicit reference to its location within the input.

The complete projector can also incorporate the optional branches shown in the figure. A side branch maps explicit measurements, such as time or scale information, into the language embedding space. A readout branch can translate scientific prediction scores into additional embedding contributions. In the illustrated configuration, these contributions are added to the main projection, after which a context residual exchanges information among states belonging to the same scientific object. This allows each output embedding to incorporate both local evidence and information from elsewhere in that object.

These components are configured for each modality. All tasks within a modality share one complete projector, including any enabled context, side, and readout branches. The requested operation is expressed through the instruction, allowing the same scientific representation and interface to be reused across tasks.


### 3 Post Training


#### 3.1 Scaling Verifiable Environments

To develop the agentic capabilities required for scientific work, we build a large collection of verifiable environments. The tasks range from general-purpose tool use, search, and coding to workflows involving machine learning experiments and interaction with scientific software. Task-specific checks assess outcomes using evidence such as execution results, changes in environment state, and submitted artifacts. We use XTuner [ 20 ] as our post-training framework.


##### 3.1.1 Agentic Tool Use

Sage S2.1 Flash scales verifiable environments to strengthen long-horizon Agentic Tool Use. Our core insight is that tools are the atomic units of agent capability, and an implicit tool space lies between agents and their underlying environment databases; relations among tools naturally connect an extensible ecosystem of environments. Building on this insight, we propose ToolSpace [ 21 ] , a tool-centric framework for cross-environment data synthesis that improves long-horizon tool orchestration. As shown in Figure 4 , ToolSpace reconstructs a tool-composition space from real execution traces, synthesizes environments on demand, and generates long-horizon agent tasks.

> Figure 4 : Overview of ToolSpace. A tool-centric framework for cross-environment data synthesis that improves long-horizon agentic tool use.

(1) Tool space exploration. We recover tool-composition relationships from execution trajectories and construct a tool space that connects multiple environments. As shown in Figure 4 (right), this stage consists of agent trajectory collection, tool-space graph modeling, and agent environment data synthesis, which together provide the tool graph and executable environments for subsequent cross-environment task synthesis.

Agent trajectory collection. We build a unified trajectory corpus from MCP-ecosystem executions [ 22 ] and web-sourced agent trajectories. For MCP services, we obtain tool definitions from registries, keep tasks whose definitions match the live servers, execute them, and record tool calls, arguments, and results in order. For web-sourced data, we apply authenticity-tiered filtering: (i) Real-server interaction trajectories. Retain records executed on real services and remove unavailable interfaces. (ii) Real-workspace interaction trajectories. Retain explicit tool calls while excluding shell wrappers. (iii) Synthetic-tool trajectories. Keep calls only when tool names and schemas match corresponding real tools.

Tool-space graph modeling. We organize these records into a typed tool-composition graph. (i) Nodes. Each node is a tool-call pattern with tool identity, input/output schemas, and a normalized argument configuration. (ii) Relations. Deterministic rules identify three adjacent-call dependencies: a data dependency transfers an output into a type-compatible later input; a state dependency links a state-changing operation to a later operation on the same object; a retry dependency captures recovery via a successful alternative tool. (iii) Weights. Edges are weighted by observed transition frequency, low-frequency links are removed, and data dependencies further require traceable value transfer to reduce false links from shared constants—grounding the graph in execution while preserving information transfer, state evolution, and failure recovery.

Agent environment data synthesis. We cluster densely connected tools into environments, retaining cross-group links for cross-environment workflows, and materialize underlying data only when persistent state is required. (i) Operation environments. For environments with create/modify/delete tools, we collect and align data, expand the database, and validate behavior with unit tests and state-transition checks. (ii) State-query environments. Recorded outputs anchor reconstruction of the initial state. (iii) Stateless environments. Matching replay calls reuse cached results.

(2) Cross-environment verifiable task synthesis. We use the tool space to synthesize long-horizon tasks whose feasibility and outcomes can be checked through execution. As shown in Figure 4 (right), this stage explores cross-environment workflows via state-aware random walks, then reverse-synthesizes task instructions and verification scripts, retaining only samples that pass replay from their initial states.

State-aware random walks. We generate workflows by walking the tool graph toward a target number of tool calls and environments. From an initial snapshot, we consider only connected tools that are runnable in the current state and whose inputs are available from prior results. We sample the next tool by edge weight, execute it, update the state, and continue until the length and environment-coverage targets are met.

Rollback sampling. When a call fails or yields a state inconsistent with the expected dependency, we restore the pre-call state and try another connected tool; walks that cannot proceed within budget are discarded. Successful walks store initial and intermediate states for replay. Difficulty is controlled by workflow length and the number of environments spanned.

Reverse verifiable task synthesis. Each successful workflow becomes a natural-language task stating the goal and required outcomes. Verifiable programmatic scripts cover the final state, intermediate key snapshots, and required output fields. Teacher agents then solve the tasks, and only trajectories that pass the same verification checks are retained for training.

(3) Scaling environment and data statistics. ToolSpace constructs 77,760 tool-call pattern nodes from 2,042 distinct normalized tools and organizes them into 804 environments covering domains such as communication, finance, document design, data storage, and search. In total, ToolSpace generates SFT trajectories with at least 5 tool calls, each trajectory averages 18.86 tool calls (up to 209) and spans 2.29 environments on average (up to 22) [ 21 ] .

Overall, Sage S2.1 Flash scales tool-use training by expanding how real tools collaborate across environments, so broader exploration yields reliable feedback for long-horizon tool orchestration.


##### 3.1.2 Agentic Search

To develop agents’ ability to discover, verify, and integrate information across sources, we construct search tasks through forward and reverse synthesis. Forward synthesis derives questions from verified facts and their relations. Reverse synthesis extracts reusable structures from diverse seed queries and explores recent topics to construct new tasks. Both paths organize facts and constraints to support multi-step search and verifiable answers, covering entity identification, constrained enumeration, comparison, and temporal reasoning [ 23 , 24 ] .

(1) Forward task synthesis. We use knowledge graphs to organize factual relations and web evidence to verify them. Starting from seed entities, we construct small cyclic graphs whose relations constrain a target from multiple directions. Each relation is checked through search and page reading, with its sources recorded. We expand from several nodes and merge the resulting subgraphs, enforcing depth requirements and filtering highly connected entities that provide weak identification constraints. The local graph supplies verified facts for question generation and later revision.

We then select a main reasoning chain, auxiliary constraints, and a designated answer relation. The main chain defines the intended sequence of discoveries, while auxiliary constraints distinguish among candidates. The answer relation is withheld from all clues. Selected facts are checked against independent sources and expressed as natural-language clues, replacing proper names with descriptions and exact dates or quantities with ranges containing their true values. These steps preserve the factual basis while requiring the agent to resolve entities and combine constraints through search.

An independent model attempts each question and checks answer uniqueness, information leakage, and shortcuts that bypass the main chain. Ambiguous or revealing clues return to question generation with explicit feedback. Insufficient depth or coverage triggers further graph expansion. Candidates that remain invalid after bounded revision are discarded.

(2) Reverse task synthesis. We collect diverse seed queries from open datasets and the web, covering different domains and information needs. Each query is decomposed into factual inputs, constraints, and target outputs to obtain reusable task structures. These structures capture operations such as filtering, ranking, set operations, temporal comparison, and numerical calculation. Separating the required operations from the specific facts allows the same structure to support new topics.

For each structure, we start from a recent topic, such as a news story or event, and explore related information through search and page reading. This process gathers candidate entities, timelines, attributes, and relations with supporting sources. We organize these facts into a new question according to the selected structure, coordinating entities, time windows, locations, and sources so that the inputs and constraints remain compatible. Target answers and their derived attributes are reserved for the solving stage.

Validation checks both individual facts and the complete question. Fact-level checks verify existence, semantic roles, and compatibility. Question-level checks assess constraint clarity, source accessibility, information availability, answer leakage, and similarity to existing tasks. Enumeration tasks additionally require a bounded candidate scope so that membership and completeness can be assessed. Failed candidates undergo further exploration, revision, or regeneration.

(3) Trajectory collection. Teacher agents solve accepted questions in a shared environment with search, webpage reading, and sandboxed Python tools [ 25 ] . We record reasoning, tool calls and arguments, observations, and final answers in interaction order. Each trajectory is linked to its question, generation source, and execution status. Interrupted or incomplete runs are retained for recovery and rerunning, while completed trajectories enter quality review.

(4) Quality assessment and filtering. We combine rule-based checks with model-based review. Rule-based checks examine record completeness, tool-call and response matching, argument formats, and citation consistency. Model-based review assesses answer correctness, instruction following, reasoning continuity, and support from retrieved evidence. For set-valued answers, review checks both the validity of returned items and coverage of the required scope. Numerical and comparison tasks also require consistent time ranges, units, and calculations. Detected task defects return to synthesis, while evidence gaps or substantive reasoning errors require trajectory regeneration or rejection. Accepted samples retain their provenance and review records for subsequent inspection.


##### 3.1.3 Agentic Coding

Coding agents are one of the most important applications of LLMs today. It requires models to interpret user requirements, reason about code and execution environments, and coordinate tool use over multiple steps [ 26 ] . To support these capabilities, we develop a unified data pipeline combining diverse task construction, automated environment preparation, and trajectory selection guided by execution feedback and task-specific assessment.

Task Collection. We consider three major categories of coding tasks. Software Engineering (SWE) includes patch-level tasks, such as fixing defects and extending existing code, and repository-level generation from natural-language specifications. Terminal Use covers complex workflows involving command-line interaction, including data processing, system operations, and scientific computing. Web Development focuses on visual and interactive artifacts, including websites and 3D games, with particular emphasis on academic webpages.

We collect seed tasks from multiple sources. First, we use public datasets and environments, including SWE-smith [ 27 ] , SWE-rebench V2 [ 28 ] , OpenSWE [ 29 ] , SWE-Lego [ 30 ] , TMax [ 31 ] , and SETA [ 32 ] . Second, we mine high-quality commits from public GitHub repositories and associate them with corresponding task descriptions. For repository-level generation, we derive specifications from the functionality, interfaces, and tests of existing repositories, providing agents with requirements for reconstructing their behavior. Third, we synthesize tasks using knowledge graphs derived from code structure and technical materials. Tools such as GitNexus [ 33 ] organize repository structure, while documentation, papers, data, source code, and user instructions provide complementary information. By tracing relationships among concepts, interfaces, and requirements, we construct tasks whose intermediate steps depend on one another. Each task specifies its inputs, initial conditions, and expected outcomes, grounding long-horizon problem solving in concrete requirements.

Scaling-up Environment Construction. We automate environment construction to scale the collection of executable, verifiable tasks. The pipeline prepares container images containing the required code, dependencies, and inputs, together with execution and verification procedures. Code versions, dependency configurations, input data, and initial states are fixed to ensure reproducible execution and evaluation. Materials available to the solving agent are managed separately from private reference solutions and hidden evaluation artifacts.

Validation addresses both execution and task quality. Execution checks ensure environments initialize correctly and verification procedures run as intended. Where applicable, reference solutions must pass verification, while initial states or deliberately incorrect solutions are checked as negative controls. We distinguish infrastructure failures, such as missing dependencies or timeouts, from failures to meet task requirements. Task review further examines whether accessible information is sufficient, reference solutions satisfy the stated requirements, and verifiers accept valid alternative implementations [ 34 ] . This review combines agent judgments with execution evidence to assess consistency between task specifications and evaluation. Identified problems are repaired and checked again. Leakage cleanup is likewise followed by renewed validation to check that removing sensitive material preserves the functionality required to solve and evaluate the task.

Within the constructed environments, agents explore task materials and iteratively implement, test, and refine solutions using tool feedback. We collect multiple rollouts per task, retaining tool interactions, execution results, and final artifacts. Empirical pass rates inform task filtering, removing some overly easy tasks and tasks for which no successful solution is obtained under the current sampling configuration. These rates characterize difficulty relative to the sampled agents and execution budgets.

Judge agents then evaluate candidate trajectories using signals appropriate to each task. Patch-level SWE relies primarily on verifier outcomes, repository generation on unit-test pass rates, and terminal tasks on execution results and the resulting environment state or artifacts. For Web Development, code-based assessment is complemented by multimodal evaluation of rendered outputs [ 6 ] . The rubrics combine shared domain requirements with task-specific criteria, covering functional requirements and visual presentation, including aesthetics.

Trajectory selection also considers the quality of the interaction process, including completeness, verification credibility, and reproducibility. Candidates are assessed against the relevant task criteria before comparison, and a task may contribute no trajectory if none is suitable. This provides an additional quality check beyond outcome scores.

Hacking Detection. Answer leakage and verifier exploitation can compromise training data even when a trajectory receives a high score. We therefore apply safeguards during both environment construction and rollout collection. These include restricting online answer retrieval, removing answer-revealing Git history, and cleaning sensitive material from build caches, source copies, and installed packages. Rule-based scans identify known leakage patterns, while agent-driven investigations examine suspicious material and less predictable exposure channels.

Residual risks nevertheless remain. For example, we observed an agent accessing task-related repository content through dependencies installed by the harness itself. Such cases motivate a final review of the actual tool accesses and actions recorded in each trajectory. We exclude trajectories that exploit leaked answers, bypass evaluation, or fabricate verification. This behavioral review complements preventive environment checks and reduces the risk of retaining trajectories whose apparent success does not reflect task completion.


##### 3.1.4 ML Coding

We organize real machine learning workflows into executable, verifiable tasks spanning predictive modeling, algorithm implementation, research reproduction, and model post-training [ 35 , 36 , 37 ] . Built around real data and existing methods, the pipeline covers source acquisition, data–code pairing and environment adaptation, and task derivation and validation. Task types share this process while providing different starting materials and deliverables, leaving the agent room for analysis, implementation, and experimental iteration [ 38 ] .

Acquire datasets and research materials. We acquire data from Hugging Face, Kaggle, official project releases, and open stores, together with dataset descriptions, licenses, versions, and split definitions. Papers and supplementary materials define methodological goals, base models provide training starting points, and existing evaluation protocols establish how outcomes are assessed. Acquisition preserves the original relationships among images, text, audio, time series, and related files, recording the original release URLs, data versions, selected files, and training and test splits. When the same data appear on different platforms or under different names, we check their relationships using the original release URLs and versions. For partial datasets, we record selected files, shard ranges, and selection criteria. These records trace the data used by each task and their links to papers, models, and code.

Associate code, build pairs, and adapt environments. We retrieve related repositories using dataset names, canonical identifiers, common aliases, and task keywords. Candidate associations are checked through data loaders, configurations, and training entry points to establish how the code uses the data, beyond name similarity alone. Selected code versions are pinned. Sources with an existing implementation can reuse that association; paper-driven tasks use related code to identify tools and dependencies, while withholding the authors’ complete implementation when independent implementation is required.

Each executable pair binds versioned data and code to a data interface, a training or inference entry point, an output format, and an evaluation metric. Adaptation resolves paths, configurations, data interfaces, and dependency compatibility while preserving the method’s core computation and evaluation semantics. The runtime is packaged in a reusable image. Small real training or inference runs check that data reach the model, outputs are produced, and metrics can be computed. These construction checks are recorded separately from the final task’s normal training plan so that a small check is not mistaken for a complete experiment.

Pairs also specify the experimental conditions for each goal: prediction tasks fix data splits and output formats; implementation tasks retain runnable entry points; reproduction tasks define their scope and required evidence; training tasks bind base models, permitted training materials, and evaluation entry points. Available reference runs are retained and can calibrate initial performance for model improvement tasks. Open-ended reproduction tasks define evaluation criteria from methodological contributions and evidence requirements. This establishes a consistent execution basis before tasks are derived. Public data support development and debugging, while private data support final scoring. This separation is preserved during task derivation, and public materials are checked for information that could directly recover private answers.

Apply controlled degradation, package tasks, and validate delivery. With data, environments, and evaluation goals fixed, we selectively remove implementations or solutions needed to complete the workflow. For implementation tasks, structural and semantic analysis guides the masking of substantive computations such as loss calculations, feature transformations, or model updates, while preserving interfaces and necessary context. Missing regions form a coherent implementation objective. Different region combinations yield distinct tasks, avoiding duplicates created by merely rewording instructions. Original code and restoration patches remain on the private construction side to check masking and recovery consistency.

More open-ended tasks may provide data and a prediction goal, a paper’s method description, or a base model and training materials, asking the agent to develop a solution, implement a method, or improve a model. Degradation preserves ground-truth labels and scoring rules. Instructions are written from frozen public materials and specify the work scope, submission paths, and resource budget; private answers and scoring materials remain outside the instruction writer’s context. Dependencies and caches are also checked for residual copies of removed implementations.

Final tasks use the Harbor format [ 39 ] . instruction.md describes objectives, inputs, constraints, and deliverables; task.toml declares images, resources, and time limits. environment/ supplies agent-visible data, starter code, paper materials, or model assets, while tests/ separately holds scoring programs, private data, and reference materials. These areas are provided to the agent and verifier respectively, keeping the public workspace separate from private scoring materials.

The verifier assesses actual submissions, including prediction files, code projects, reproduction artifacts, or model weights. It computes established prediction metrics, executes submitted projects, loads model weights for inference, or checks implementations and required execution evidence, then aggregates the evaluation results. Before delivery, checks cover directory structure, submission interfaces, image and resource declarations, public/private boundaries, and evaluation entry points. Accepted tasks are collected by batch, with provenance and construction logs kept outside task packages. Tasks derived from the same data–code pair can reuse accepted data and images, reducing construction costs while retaining independent verification for each task.


##### 3.1.5 Cybersecurity

To support the development of cybersecurity capabilities in agents, we achieve scaling verifiable environments for cybersecurity through diverse seed preparation and rigorous environment synthesis.

And we define two task types, vulnerability reproduction and vulnerability exploitation, to cover both the verification of vulnerability symptoms and the use of vulnerabilities to achieve an attack objective [ 40 , 41 ] .

(1) Seed preparation . To support diverse task sources and reliable environment construction, we combine broad data collection with staged processing. We first collect candidate records from different vulnerability reporting channels to cover a range of vulnerability mechanisms and software settings. We then apply rule-based filtering, agent-based verification, and source code preprocessing to prepare inputs for environment synthesis.

To avoid limiting task coverage to a single data source, we collect candidates from multiple reporting channels and organize them by vulnerability type and software setting . Sources include international vulnerability databases, open-source communities, software vendors, and incident response advisories. These channels provide vulnerability descriptions, affected versions, patch information, and relevant code references. We organize vulnerability types using the Common Weakness Enumeration (CWE) [ 42 ] , covering memory errors, injection, access control issues, and other software weaknesses. Software settings include the Linux kernel, JavaScript engines, web applications, user-space software, and core libraries. Collecting from multiple sources provides candidates for different task objectives. It also supports cross-checking vulnerability identities, versions, and patch evidence.

To turn heterogeneous vulnerability records into task seeds with clear construction evidence, we apply rule-based filtering, agent-based evidence verification, and source code preprocessing in sequence. Rule-based filtering checks basic fields, including links, dates, vulnerability identifiers, and category labels. It also removes duplicates and selects candidates within the task scope. For projects such as Linux and V8, we additionally consult their official source repositories and advisory channels to reduce omissions caused by generic link requirements. Agent-based verification compares advisories, patches, and source code to confirm that the upstream repository belongs to the affected project. It identifies the exact versions that retain the vulnerability and contain its fix, and checks platform requirements and hardware dependencies. Preprocessing standardizes record formats and retrieves complete source code and submodules. It then organizes both source versions, patches, commit records, and file checksums into inputs that can be checked during environment synthesis.

(2) Environment synthesis . To create valid tasks with protected scoring and complete support for task solving, we organize environment synthesis around differential validation, isolated evaluation, and task packaging. Differential validation executes the software to check whether the target vulnerability is present and whether the patch removes the corresponding behavior. Isolated evaluation separates the permissions for task solving, target execution, and scoring to limit ways of obtaining rewards by bypassing the task.

To prevent build failures and unrelated errors from affecting vulnerability assessment, we combine normal functionality checks with differential execution of the vulnerable and patched versions . During environment synthesis, we use patches and upstream tests to prepare normal inputs, vulnerability-triggering inputs, and checks for the resulting behavior. Both versions are built using a consistent method. The agent responsible for environment construction writes the environment and test files. The validation framework then performs the builds and executes the tests against actual service, command, or library interfaces. For acceptance, normal inputs must execute correctly in both versions. Vulnerability-triggering inputs must trigger the target vulnerability only in the vulnerable version and execute normally without triggering it in the patched version. Combining functionality checks with differential results helps prevent an unreachable target, an unexecuted input, or a failed build from being mistaken for an effective fix.

To limit rewards obtained by modifying the target, reading answers, or manipulating scoring, we separate permissions for the agent workspace, target execution, and private evaluation . The solving agent writes, compiles, and debugs code in its own workspace container. The actual software under test runs in a separate target container, where the Controller manages startup, resets, input execution, and feedback collection. The agent interacts with the target through public interfaces. The execution framework invokes the private evaluator, while evaluation scripts, reference solutions, and internal verification credentials remain inaccessible to the agent. For reproduction tasks, the evaluator checks the submitted PoC in clean environments for both versions. For exploitation tasks, it compares the submitted flag with the protected expected value for that task attempt. Before releasing a task, we test the scoring program with positive and negative controls whose expected outcomes are known. These checks verify that the program accepts valid submissions and rejects invalid ones.


##### 3.1.6 Workspace Agentic Intelligence

We organize workspace-level agent tasks around real professional deliverables produced within a file-based working environment, spanning presentation decks, spreadsheets, business and legal documents, industrial CAD assemblies, 3D scenes, and command-line analysis workspaces. Unlike single-file prediction benchmarks, these tasks require agents to inspect heterogeneous materials, plan multi-step workflows, operate native tools, and produce verifiable artifacts that can be reopened and audited [ 43 , 44 , 45 , 46 , 47 ] . Across all task families, our construction pipeline adheres to a unified principle: grounding tasks in authentic usage needs, strictly separating public instructions from private evaluation harnesses, and validating performance directly on delivered artifacts rather than self-reported completion.

Acquire real materials and derive tasks from genuine needs. Rather than relying on synthetic templates, materials are harvested from verified real-world repositories: public document and slide archives for presentations, manufacturer parts libraries for industrial CAD, Wikimedia Commons photography for Blender 3D reconstruction, regulatory filings and advisory records for financial and legal workspaces, and community forum threads paired with authentic workbooks for spreadsheet tasks. All raw assets undergo deduplication, license verification, version tracking, and quality screening prior to derivation. Tasks are structured around the specific cognitive capabilities they probe rather than surface file formats—such as cross-file evidence reconciliation, parametric part-tree planning, template-constrained layout adaptation, or distinguishing photographic facts from unconstrained design regions in 3D modeling. For benchmark-derived expansions, observed model failure patterns guide new material selection so that reused source assets always demand distinct analytical operations.

Separate public task statements from private solutions and scoring. Each task package is structurally partitioned to enforce a strict public–private boundary. Public instructions are authored exclusively from frozen, agent-visible materials, specifying the business objective, operational constraints, deliverable paths, and resource budgets. Reference solutions, ground-truth labels, private datasets, and grading scripts remain completely isolated from both the instruction writer and the agent workspace. For open-ended deliverables, evaluation criteria are derived strictly from methodological requirements and verifiable evidence rather than hidden preferences, with every rubric item audited against public prompts to eliminate unstated thresholds or arbitrary vetoes. Construction-side provenance logs, source URLs, and version records are maintained externally to ensure full traceability without leaking answers.

Apply controlled degradation and retain evidence of recovery. With the environment and evaluation targets fixed, we selectively strip away the target work while preserving entry points, interfaces, and essential context. In implementation-centric tasks, semantic analysis guides the masking of substantive computation so that removed regions form a coherent engineering objective, while original code and restoration patches are retained privately to verify recovery consistency. In analytical workspace tasks, intermediate reasoning steps, diagnostic workflows, and methodological hints are excised from the prompt while leaving source data intact. All public directories, dependencies, and caches are systematically scrubbed to prevent residual copies or cached metrics from exposing private solutions, ensuring that degradation preserves ground-truth scoring validity.

Validate on actual artifacts and defend against reward hacking. Candidate tasks are executed end-to-end in live environments and graded strictly on the resulting artifacts. Presentations undergo multi-round rollouts checking factual accuracy, completeness, visual quality, and native editability; CAD assemblies are inspected for geometric interference and overlap; Blender projects are reopened in isolated environments with dependencies audited and scenes re-rendered prior to visual scoring; spreadsheets, legal documents, and CLI workspaces are verified for reproducible computation, operation order, and evidence alignment. To counter reward hacking—such as reading cached spreadsheet values without recomputing, fabricating citations, projecting 2D textures onto flat planes to impersonate 3D geometry, or submitting images inconsistent with project files—we enforce trajectory–artifact consistency checks, structural probes, and subject ablation. Compromised trajectories are discarded or masked during training so self-reported claims never substitute for genuine execution.

Feed failures back into statements, materials, and rules. Quality assurance operates as an iterative, layered loop combining automated code checks, model-based auditing, and targeted human review tailored to each domain. Detected failures are routed directly to their root stage: ambiguous specifications or answer leakage return to statement editing; flawed templates with placeholder padding or duplicated layouts return to material selection; misaligned grading criteria return to rubric revision; and transient infrastructure errors are isolated from genuine task defects. Repairs are restricted to localized, evidence-backed patches—altering reference answers, deleting checks, or loosening tolerances to force passing scores is strictly prohibited. Finally, executable yet methodologically flawed cases undergo manual spot review to ensure computational reproducibility aligns with professional domain standards before batch acceptance.

##### 3.1.7 Visual Agentic Intelligence

We develop visual agentic intelligence through a staged curriculum that builds general perception and grounding skills before integrating them into long-horizon interaction [ 48 ] (Figure 5 ). Scalable task synthesis supports this progression through broad coverage of visual contexts and increasingly demanding interaction objectives. The initial stage uses single-step clicking and image recognition to establish reusable visual skills. The subsequent stage places these skills in complex synthetic environments, where the agent must coordinate successive decisions toward an overall goal.

To establish this visual foundation, we use general-purpose single-step tasks that connect understanding an observation with selecting an appropriate response. Image recognition trains the agent to identify relevant visual content, while clicking tasks require it to ground an instruction in that content and locate an interaction target [ 49 ] . Task synthesis broadens this training across visual contexts and task formulations, exposing the agent to different combinations of observations, instructions, and targets. These variations are intended to encourage the same underlying skills to apply across tasks. At this stage, the central requirement is to make an immediate decision consistent with both the instruction and the observed scene.

Building on these local decision skills, we place particular emphasis on computer-use agent (CUA) capabilities through a broad collection of long-horizon tasks in complex synthetic environments [ 50 ] . These tasks require the agent to carry a user objective through a sequence of interface interactions, coordinating individual operations into a complete workflow. At each step, the agent must interpret the current interface, locate relevant controls, choose an action, and use the resulting visual feedback to determine how to proceed. Across steps, it must retain relevant context, track which intermediate requirements have been satisfied, and keep subsequent actions aligned with the overall objective as the interface changes. We synthesize these workflows across varied visual contexts, interface states, and interaction objectives, expanding coverage of the situations in which foundational visual skills must be applied. Difficulty increases through both longer action sequences and stronger dependencies between intermediate steps: an early operation may establish a condition needed later, so successful local actions must also contribute to the completion of the workflow. This makes sustained task progress a central requirement of the training, alongside accurate interpretation of individual observations. The resulting task pool emphasizes end-to-end computer use, placing sustained demands on visual grounding, state tracking, and sequential decision-making.

To curate training examples from this expanded task pool, we also apply rejection sampling to the generated data. We then select training examples, balancing broad synthetic task coverage with selective use of the resulting samples.


#### 3.2 Scientific Modality Adaptation

We treat the scientific interface as a trainable component of the model’s reasoning policy. Following supervised initialization, we refine modality-specific projectors through reinforcement learning, using verifiable scientific outcomes as rewards. The scientific encoders and language backbone remain frozen, so task feedback shapes how evidence is presented to the backbone and used to answer scientific questions.


##### 3.2.1 Scientific Reasoning Tasks

We combine native scientific tasks with auxiliary questions about the evidence supplied to the model. Scientific labels supervise outcomes such as molecular properties and interaction sites, while auxiliary targets are computed from the input or frozen scientific readouts. These questions cover operations such as counting atoms under combined conditions, querying graph relations, and comparing numerical measurements. Multiple questions share the same scientific input, providing complementary supervision for domain prediction and the retrieval and manipulation of scientific evidence.

Task construction follows the information supplied to the model. Auxiliary targets are computed from the represented inputs or frozen scientific readouts: sequence questions refer to the encoded windows, position-dependent questions preserve atom or residue identities, and probability-based inputs support questions about the supplied probabilities. Scientific annotations provide targets for the native prediction tasks. This distinction gives the task mixture complementary roles: outcome supervision captures domain objectives, while auxiliary supervision tests whether the interface makes relevant evidence accessible across different questions.


##### 3.2.2 Verifiable Rewards

We define rewards according to the scientific quantity or constraint being tested. Each response is checked against scientific annotations or input-derived targets using a task-specific verifier. Classification rewards label correctness; site and set predictions receive overlap-based scores; numerical answers use fixed error scales or tolerances. Molecular generation and editing use chemical equivalence, structural similarity, and task-specific constraints, with partial credit where supported.

Rewards supervise task outcomes, providing feedback to reasoning traces through the answers they produce. Their interpretation follows the target: readout-derived rewards measure use of the supplied predictions, while annotation-based rewards assess agreement with scientific labels. Per-response rewards guide optimization; formal evaluation retains native dataset-level metrics such as macro-F1 and correlation.


##### 3.2.3 Reasoning RL for Scientific Interfaces

We optimize the model’s response policy through its scientific interface. Following supervised initialization, we apply group relative policy optimization (GRPO) [ 51 ] : multiple responses share the same question and scientific input, and their rewards are standardized within each group to obtain relative advantages. Clipped policy updates favor higher-reward responses. Gradients propagate through the frozen language backbone to the trainable projector components, while scientific encoders remain fixed. Outcome feedback thus adapts the policy by changing how scientific evidence enters the model.

Within each modality, native and auxiliary tasks jointly train one shared interface, including its enabled trainable branches. Task sampling and loss weights control their contributions. A prespecified multitask development criterion selects one complete checkpoint for all formal evaluations within that modality.

#### 4.2 Main Results

The results show that Sage S2.1 Flash supports scientific workflows involving experiments, evidence gathering, and software interaction. Its principal strengths lie in ML engineering, professional deliverables, tool orchestration, and visual interaction. We organize the results around these connected capabilities.

Sage S2.1 Flash achieves 90.3 HumanRank on MLE-bench Lite, ranking first against the five primary baselines. Its PostTrainBench score of 39.2 also leads the primary baselines with available results. These evaluations cover ML problem solving and model post-training, respectively, requiring agents to translate objectives into executable solutions and assess them through experimental feedback [ 35 , 37 ] . The results show that the model’s coding capabilities support practical ML work, including constructing solutions, executing training procedures, and checking experimental outputs.

The score of 88.0 on PaperBench Code-Dev provides complementary evidence of research implementation. This evaluation covers all 20 papers and requires agents to translate research descriptions into code that can be assessed [ 36 ] . Together with MLE-bench Lite and PostTrainBench, it examines several stages of research work, from engineering solutions and model training to implementing research methods.

These research workflows also depend on effective use of the computing environment. A score of 87.9 on Terminal-Bench 2.1 demonstrates terminal workflow execution, complementing the ML evaluations with tasks involving data processing, program execution, and result inspection. Scientific objectives ultimately have to be realized through code, experiments, and verifiable outputs; these benchmarks examine key parts of that process.

Sage S2.1 Flash achieves the highest scores among the five primary baselines on OfficeQA Pro, Harvey LAB, and SpreadsheetBench 2, and ranks second on AutomationBench, BFCL V4, and JobBench. These results span the process of obtaining information, operating tools, and producing a deliverable.

OfficeQA Pro’s score of 72.2 reflects the ability to extract and use evidence from supplied documents [ 59 ] . The leading SpreadsheetBench 2 result extends the assessment to executable, verifiable workbooks. Harvey LAB and AutomationBench require all rubric criteria or state assertions to pass, testing whether an agent maintains multiple requirements throughout execution and satisfies them in the final result.

Scores of 78.0 on GDPval and 67.1 on Workspace-Bench-Lite approach the leading primary-baseline results of 80.0 and 68.1, respectively; the model also ranks second on ALE-CLI. These evaluations show tool capabilities applied to complete professional workflows, beyond individual API calls. They align with our training design, which constructs tasks through cross-environment tool composition and verifies completion through environment states and actual deliverables.

Sage S2.1 Flash scores 85.2 on OSWorld-Verified and 67.6 on WebArena-Verified, ranking second on both. These tasks require repeated interpretation of interface states, action selection, and use of post-action feedback to advance the objective. They therefore assess the organization of successive operations into a complete workflow, in addition to recognition and clicking.

OSWorld-G and BabyVision complement these results with evaluations of target localization and visual reasoning. The second-place score of 78.0 on Vision2Web demonstrates another use of visual information: translating visual requirements into an executable website. Together, these tasks cover interpreting visual inputs, locating interaction targets, constructing implementations, and checking outcomes.

This capability profile matches the progression in our visual curriculum from local perception and grounding to interaction in changing environments. Scientific software requires an agent to understand both the current display and how each action changes the environment and advances the task. Desktop, browser, and visual-development tasks provide complementary views of this ability.

Sage S2.1 Flash scores 94.4 on DeepSearchQA and 91.2 on BrowseComp, and ranks second on DeepResearch Bench II at 54.2. These evaluations extend from targeted retrieval to longer research workflows, covering information discovery, verification of leads, and synthesis across multiple searches.

Information acquisition also supports the other capabilities. Professional deliverables require evidence, ML experiments require technical materials, and visual research tasks may require discovering and interpreting images [ 60 ] . BrowseComp-VL’s score of 60.5 adds evidence of multimodal retrieval, extending the evaluation from understanding supplied materials to actively acquiring external information. Alongside engineering execution and visual interaction, these results establish several of the capabilities needed to participate in scientific workflows.


#### 4.3 Trajectory Analysis

The preceding evaluations assess the ability to conduct experiments, implement research methods, and complete tool workflows. To examine how these capabilities appear during execution, we compare 48 paired trajectories from Sage S2.1 Flash and GLM-5.3-Flash, hereafter the baseline: 17 pairs from Terminal-Bench 2.1, 16 from SWE-bench Pro, and 15 from AutomationBench. We examine tool outputs, code changes, and final artifacts to identify differences in key decisions and their associated outcomes. We use these pairs for qualitative comparison, accounting for differences in execution settings and the evidence available for each case.

The coordinator verifies run provenance, pairs trajectories, schedules analysis, and retrieves records requested by the analyzer. Starting from the task requirements and trajectory index, the analyzer identifies a behavioral difference to explain and requests the relevant tool calls, code changes, execution feedback, and artifacts. Evidence retrieval alternates with explanation: new records may support the current account or expose gaps that require a revised question or further inspection.

This interaction deepens the analysis within a case. After identifying different implementations, the analyzer checks whether the difference enters the executed path, changes the final output, and corresponds to the test outcome. Truncated observations require retrieval of their continuation before information is treated as absent. The analysis thus progresses from describing actions to examining the relationship between implementation, output, and grading.

A separate analyzer invocation reviews each case against the same records, checking supporting evidence and alternative explanations. Cycle synthesis combines these reviews, findings, and unresolved questions to propose the next round’s case focus, evidence requests, and review criteria. The coordinator schedules subsequent analyses and retrieves the requested evidence; proposed review criteria are assessed before adoption. This cycle broadens coverage across cases and deepens the examination of how implementation choices affect execution outcomes. Across the reviewed cases, we identify the following patterns.

In scientific and computational tasks, Sage S2.1 Flash demonstrates the ability to turn implementation hypotheses into executable checks. In the DNA primer design task, both models completed the main sequence design and melting-temperature calculations. Sage S2.1 Flash additionally examined ambiguities in matching at the junction, revised the design, and passed the evaluation; the baseline’s artifact failed the temperature-difference check. In the ELF extraction task, Sage S2.1 Flash tried different compilation configurations and ultimately used the original virtual addresses, whereas the baseline added an extra base address and failed the reference comparison. These trajectories illustrate the use of experimental checks to examine competing interpretations and guide implementation, a process relevant to scientific problem solving.

In several cases, both models completed similar domain analyses, but their outcomes diverged during artifact generation. In the Bayesian network task, both recovered the same graph structure. The baseline reversed parent and child directions when exporting the intervened graph, and its checks did not cover the semantics of the output columns. Sage S2.1 Flash exported the graph in the required direction. In the protein assembly task, both completed the main domain subproblems. The baseline removed a tag from the source sequence according to domain convention and validated against a sequence processed with the same assumption, leaving the conflict with the task requirements undetected. Sage S2.1 Flash retained the required full sequence and passed verification. These comparisons show that completing scientific tasks requires consistency among source data, permitted transformations, and output representations. In these cases, Sage S2.1 Flash carried correct intermediate analyses into artifacts that satisfied the requirements.

Software engineering cases reveal how the models handle the relationship between new requirements and existing implementations. In the NodeBB email-confirmation task, the baseline retained the old route and passed local tests without implementing the required new flow; Sage S2.1 Flash updated the target route and the associated registration-state handling. In the ProtonMail modal task, the baseline used an opacity setting to keep an existing test passing, whereas Sage S2.1 Flash implemented the required visible behavior. Interface evolution exposed a related difference: in the Tutanota draft-folder task, the baseline added a parallel interface while retaining the old one. Sage S2.1 Flash supported the new context through the existing interface while preserving old call forms, and checked folder hierarchies and boundary conditions. In the Vuls version-identification task, the baseline retained an outdated branch affecting some inputs, while Sage S2.1 Flash revised that branch and checked multiple classes of version strings. These behaviors reflect joint consideration of requirements, calling conventions, and boundary conditions, connecting local code changes to the behavior needed by the system.

Differences in tool workflows often concern how information already obtained shapes subsequent actions. In the advertising-pause task, both models identified the main threshold. Sage S2.1 Flash additionally read the exception notes and retained the exempt advertisement, whereas the baseline paused it. In the sales-reply task, both computed the same monetary total. Sage S2.1 Flash placed the total in the operator-facing report and retained the customer draft’s template content; the baseline inserted the amount into the customer draft and triggered the corresponding check. In the ticket-migration task, Sage S2.1 Flash preserved the requested priority values, Critical, Major, and Minor, while the baseline mapped them to Highest, High, and Low. These differences arose after the main information had been obtained and concerned its scope, meaning, and intended recipient. In these cases, Sage S2.1 Flash maintained a closer correspondence between task rules and the operations performed.

In the Git web-server task, Sage S2.1 Flash checked cloning, pushing, and page access using the specified user and access method. The baseline used a substitute user, and the evaluator subsequently reported an HTTP 404. In the video move-extraction task, Sage S2.1 Flash completed the processing workflow and delivered the result, whereas the baseline timed out without producing the final file. Cases in which both succeeded, including database recovery, rendering, and data resharding, show that complex tool operation and error recovery are shared capabilities. The clearer differences lie in whether verification covers the key requirements and whether the final deliverable satisfies them. Inconsistent counts in Sage S2.1 Flash’s HelpScout weekly report show that successful individual operations still require a final check for agreement among detailed records, aggregate counts, and completion claims. Together, the successful and unsuccessful cases connect the execution capabilities assessed above to observable experimental checks, constraint preservation, interface implementation, and final delivery.

### 6 Conclusion

Sage S2.1 Flash brings native scientific inputs and interactive agent capabilities into a general-purpose model. Scientific modality adaptation trains the projectors to present scientific evidence to the shared backbone, while training in verifiable environments gives the model feedback on whether its actions achieve the task objective.

The evaluation shows particular strengths in knowledge work and ML engineering, including first-place results on OfficeQA Pro and MLE-bench Lite in the primary comparison. Sage S2.1 Flash is also competitive on desktop and browser tasks, with room to improve in repository-level coding and web search. The exploratory trajectory analysis illustrates how identical task scores can accompany differences in output verification and reporting. A next step is to test these capabilities together in complete scientific workflows, checking whether the model selects relevant evidence, adapts its actions to feedback, and produces scientifically correct results.

### Appendix B Benchmark Evaluation Settings

The configurations below describe evaluations conducted by us. Published scores retain the settings of their source evaluations; the three leading reference columns are excluded from the six-model rankings.


#### B.1 Agentic Coding

Evaluations use Claude Code on 89 tasks. Task timeouts are multiplied by 12, capped at 12 hours; verifier timeouts are multiplied by 3. The verifier uses offline dependencies. Runs allow up to 1,000 interaction steps, a 512K context window, 64K output per generation and max thinking effort. Resources follow each task specification; agents can access network resources through mirrors, while image/PDF reading is disabled. Errors score zero. Each model evaluated here is run in four independent runs and the mean pass rate is reported. The GPT-6 Astra reference score is taken from the official leaderboard [ 62 ] .

Evaluations use the AgentCompass framework on DeepSWE v1.1, which contains 113 tasks. The evaluation harness is mini-swe-agent v2.4.2 with the official mini.yaml configuration. Temperature and top_p are both 1.0. Each task receives 2 CPUs and 8 GiB of memory. Agent and verifier have no external network access; there is no step or cost cap. Commands have a 30-second timeout and model requests a 600-second timeout. The task budget is 6 $\times$ 5,400 seconds, or 32,400 seconds. Hidden tests run in a separate verifier sandbox with a 1,800-second timeout. Pass rate is computed from binary rewards; model timeouts and context overflow count as failures. The reported pass rate is the average of four independent runs per evaluated model.

DeepSeek-V4.1-Flash-1017, GLM-5.3-Flash, Claude Opus 5 and Sage S2.1 Flash are run with Claude Code, and the other models with OpenHands (v0.56.0). Sage S2.1 Flash is evaluated with a 512K context window. The score is the average test pass rate over 104 tasks.

For SWE-bench Pro, Sage S2.1 Flash, GLM-5.3-Flash, DeepSeek-V4.1-Flash-1017 and Claude Opus 5 use Claude Code, while the other evaluated models use OpenHands. The evaluation uses the official V2 locked-protocol prompt wrapper [ 67 ] and the v1 task set of 731 tasks. Each task receives 4 CPUs and 16 GiB of memory, a 4.5-hour time limit and at most 250 turns. Output is capped at 64K tokens per generation and thinking effort is set to max. External network access is disabled except for model endpoints, and Git history after the base commit is removed to prevent information leakage or benchmark contamination. Image/PDF reading, WebSearch and WebFetch are disabled. Patches are collected using git diff after the agent finishes and graded with official tests in an isolated sandbox.


#### B.2 Productivity

GPT-5.6 Sol uses Codex, while the other evaluated models use Claude Code. Visualization tasks are graded by Qwen3.7-plus [ 69 ] as a VLM verifier, while the remaining tasks use rule-based verifiers. The reported score is the weighted average accuracy over 321 tasks. Evaluations use the Harbor framework, with 1 CPU and 10 GB of memory allocated to each task. Each model request has a 60-minute timeout, and there is no interaction-step limit. For Visualization tasks, charts are rendered on Windows before grading.

Evaluations use the CLI subset of Agents’ Last Exam v1 with Claude Code. Agents complete multi-step workflows in the prescribed software environments and submit deliverables, checked against version-matched hidden references and deterministic graders. Environments and task assets follow v1. Our configuration differs from the official evaluation setup in the following respects: we use a 512K context window, set max_tokens to 96K, and allow 10 hours per task. For business_finance/pe_screening_memo_1/zscaler_fy2025, grading uses gpt-6.1-sol instead of the gpt-4o-mini specified in the official configuration.

Evaluations use v1.1 task definitions and grading rubrics for cross-file workflows in investment banking, management consulting and corporate law. Agents produce deliverables from task materials for rubric-based evaluation. A task succeeds only if all rubric criteria pass. We report pass@1, the task success rate for a single attempt. Execution uses an in-house harness and retains the v1.1 grading changes for noncommittal answers. The interaction-step limit is higher than in the official configuration.

Evaluations use the AgentCompass framework on 220 tasks. Sage S2.1 Flash and GLM-5.3-Flash use Claude Code; DeepSeek-V4.1-Flash-1017, Qwen3.8-Max, GPT-5.6 Sol and Claude Opus 5 use OpenHands. Each task receives 4 CPUs and 8 GiB of memory, a 4-hour agent timeout and at most 250 turns. Output is capped at 64K tokens with max thinking effort. WebSearch, WebFetch and image/PDF reading are disabled. GLM-5.2 at temperature 0 judges candidate deliverables against Claude Opus 4.8 deliverables, applying rubric criteria and recording wins, losses and ties. The reported metric is the number of wins divided by the total number of evaluations. Ties remain in the denominator but contribute no wins; no half-win credit is assigned.

Evaluations use the English Lite dataset and the AgentCompass framework. GPT-5.6 Sol uses Codex, while the other evaluated models use Claude Code. Each task receives 2 CPUs and 8 GiB of memory and has a two-hour time limit. The LLM judge is doubao-seed-2-1-lite-260915 [ 72 ] .

Evaluations use the English Full dataset. GPT-5.6 Sol uses Codex, while the other evaluated models use Claude Code. Each task receives 2 CPUs and 8 GiB of memory and has a two-hour time limit. The LLM judge is doubao-seed-2-1-lite-260915.


#### B.3 Tool Use

The 133 tasks in OfficeQA Pro are evaluated using Claude Code as the harness, with network access enabled. Each model request has a 1,800-second timeout, and each task attempt has a 3,600-second timeout, with up to two retries on timeout and a limit of 200 steps. Answers are extracted and scored using EvalScope’s OfficeQA scoring logic with zero tolerance. Tasks without a valid result are counted as incorrect in the overall score across all 133 tasks.

Evaluations use a 120-task subset sampled proportionally from the 1,200 official tasks. GLM-5.2 serves as the LLM judge. The reported score is the proportion of tasks that pass every rubric criterion.

Evaluations use v1.0.6 with an in-house harness and include the null-type handling fix from AutomationBench PR 13 . Tasks start from predefined business states and use tools to complete workflows. Official assertion-based rubrics check final states; a task passes only when every assertion passes. The reported metric is task pass rate, excluding the simple domain.

Web Search tests use Serper, and samples with API failures are scored as incorrect. Evaluations use the official harness at commit 6ea5797 on 5,217 cases, with 16 concurrent workers. Temperature is set to 0.001. Each request has a 120-second timeout and allows at most 2 attempts. The overall score assigns weights of 10% to Non-Live, 10% to Live, 10% to Irrelevance, 30% to Multi-Turn and 40% to Agentic. Within Agentic, Web Search and Memory receive equal weight.

Evaluations use the official OpenCode harness on the main split of 65 tasks, with 10 concurrent workers. Each task has a 7,200-second timeout and allows at most 2 attempts. Grok-4.3 [ 77 ] serves as the judge, and the final score is the mean of the per-task percentage scores. Tasks with API failures or two failed attempts receive a score of zero.

Evaluations use OpenHands on the 79-task subset that excludes multimodal tasks. Results are averaged over three runs.

Evaluations use the 97 Banking Knowledge tasks and Tau2 commit a2c0247. Both the user simulator and the judge use GPT-5.2 [ 80 ] with low reasoning effort, and the random seed is 300. The alltools configuration provides BM25 search, dense retrieval using text-embedding-3-large [ 81 ] with the top 10 results, and a read-only knowledge-base shell. The knowledge base contains 698 documents. Each model request has a 180-second timeout and allows up to 3 retries. Simulations have a 1,800-second timeout, while the outer task timeout is 2,400 seconds. Each task allows at most 200 interaction steps.


#### B.4 ML Engineering

Evaluations use v1.2. The score for Sage S2.1 Flash comes from our own evaluations and uses the same weighted average over the 24 benchmark–base-model combinations.

Evaluations cover all 20 papers of the official Code-Dev variant. GPT-5.6 Sol uses Codex and other models use Claude Code, with max thinking effort. Evaluations use Claude Code as the execution harness to propose and implement improvements to machine learning methods within the scope of changes permitted by each official task. Task evaluators test transfer across models, datasets and random seeds. Scores use the official normalized task metric.


#### B.5 Deep Research

Evaluations use Claude Code. All models use the same search tools, and each task has a four-hour time limit. Each result is the mean of three judge scores. GPT-5.5 [ 88 ] , the officially recommended model, serves as the judge.


#### B.6 Search

Evaluations use our in-house ReAct search harness, which provides search, visit and python tools. Runs allow up to 500 interaction steps, with a 256K context window and a 64K output limit per generation.

We use a multimodal ReAct search harness with five tools: text_search, visual_search, lookup, summarize, and python_interpreter. Each task allows up to 100 interaction rounds and 100 tool calls in total, with a 512K-token context window, a 64K-token limit per output, and a three-hour time limit. The harness retains the interaction history and requires a final answer as the context window approaches its limit.

Evaluations use our in-house ReAct search harness, which provides search, visit and python tools. Runs allow up to 500 interaction steps, with a 256K context window and a 64K output limit per generation. The GPT-5.6 Sol score is calculated over 181 tasks. Evaluations use our in-house ReAct search harness, which provides search, visit and python tools. Runs allow up to 500 interaction steps, with a 256K context window and a 64K output limit per generation. Context is managed with the discard-all strategy.


#### B.7 Vision

GPT-5.6 Sol is evaluated using Codex 0.167.2, while the other evaluated models use Claude Code. Public internet access is disabled for Offline tasks and enabled for Online tasks. WebSearch and WebFetch are disabled for all tasks. Direct PDF input to the model and external OCR are prohibited. PDF text may be extracted locally, or pages may be rendered as images for reading.

Historical screenshots are folded in batches of 10 steps using a 20-screenshot window. Folded screenshots are replaced with Observation text generated by the model at the corresponding steps. The first and current screenshots are always retained, along with the complete history of text, reasoning and tool interactions.

Evaluations use the CUA-Lite framework and absolute pixel coordinates. Historical screenshots are folded in batches of 10 steps using a 20-screenshot window.

GPT-5.6 Sol uses Codex, while the other evaluated models use Claude Code.

Evaluations use Codex in an Ubuntu sandbox, combining GUI observation and interaction with CLI and code execution to complete tasks across applications. The official trajectory-aware judge applies rubrics to deliverables, screenshots, files and execution logs, and checks for shortcuts such as fabricated screenshots and hard-coded results. Tasks that violate the anti-cheating rules receive a score of zero.

Evaluations use the refined prompt. The model submits pixel coordinates in the original image through click(x,y,button). When no target is visible, it submits (-1,-1,left).

Images are upscaled with LANCZOS while preserving their aspect ratio so that the shorter side is at least 1,500 pixels. Images that already meet this requirement retain their original dimensions and are not downscaled.
